# Race detector

## Обнаружение гонок данных

Гонка данных (data race) — одна из важных ошибок в конкурентном программировании.

Проще говоря, гонка данных возникает, когда:

1. как минимум две горутины обращаются к одному и тому же адресу памяти;
2. эти обращения происходят без необходимой синхронизации;
3. хотя бы одно из обращений — запись.

Например, если две горутины одновременно изменяют одну и ту же переменную, может возникнуть гонка данных.

Чтобы запустить тесты Go с race detector,
используется:

```bash
go test -race ./...
```

Здесь:

* `-race` — включает race detector;
* `./...` — рекурсивно проверяет пакеты внутри текущего модуля.

Обычную программу тоже можно запустить с race detector:

```bash
go run -race main.go
```

Race detector добавляет в код программы дополнительную инструментацию. Ему нужно отслеживать обращения к памяти.

Поэтому программа, работающая с `-race`:

* может работать медленнее обычного;
* может расходовать больше памяти.

Значит, результат производительности, полученный с race detector, нельзя использовать как измерение производительности в production.

> **Внимание**
>
> Race detector отслеживает только те пути кода, которые реально выполнялись во время работы программы. Например, если гонка
> данных находится в редко выполняемой ветке, а тесты эту ветку не выполняют, детектор её не увидит.
>
> Поэтому то, что `-race` не выдал предупреждения, не значит, что гонки данных нет ни при одном возможном выполнении.
> Старайтесь реально выполнять важные пути конкурентного кода в тестах.

Если race detector находит гонку данных, в отчёте обычно показываются конфликтующие обращения к памяти.

Также приводятся трассировки стека (stack trace) горутин, выполнивших эти обращения.

Эта информация помогает определить, откуда исходит проблема.

Просто спрятать предупреждение о гонке — неправильное решение.

Главный вопрос должен быть таким:

> Какая горутина владеет этим общим состоянием и как другие горутины должны безопасно к нему обращаться?

В зависимости от проблемы можно использовать разные средства синхронизации:

* `sync.Mutex`;
* `sync.RWMutex`;
* каналы;
* атомарные операции;
* архитектуру, где состоянием управляет только одна горутина.

Какое средство нужно, зависит от назначения кода.

## Примеры

### 1. Гонка данных на общей переменной

Этот пример намеренно пишет неправильный конкурентный код.

Две горутины пишут в одну и ту же переменную `value`.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	value := 0

	go func() {
		value = 1
	}()

	go func() {
		value = 2
	}()

	time.Sleep(100 * time.Millisecond)
	fmt.Println(value)
}
```

Сначала пишется:

```go
value := 0
```

Нулевое значение типа `int` — `0`, но здесь значение ещё и явно задано как `0`.

Затем первая горутина:

```go
go func() {
	value = 1
}()
```

записывает в `value` значение `1`.

А вторая горутина:

```go
go func() {
	value = 2
}()
```

записывает в ту же переменную `2`.

Обе горутины пишут в один и тот же адрес памяти.

Между ними нет:

* мьютекса;
* канала;
* атомарной операции;
* другой синхронизации.

Поэтому это гонка данных.

При запуске программы через:

```bash
go run -race main.go
```

race detector может обнаружить конфликтующие записи в память.

Следующая строка:

```go
time.Sleep(100 * time.Millisecond)
```

содержит важную тонкость.

`Sleep()` даёт горутинам время на выполнение. Но он их не синхронизирует.

То есть:

```go
time.Sleep(...)
```

не исправляет гонку данных.

Он используется только для того, чтобы в этом маленьком примере `main()` не завершилась слишком быстро.

В production-коде для ожидания завершения горутин обычно нужен явный механизм синхронизации.

Например, в зависимости от ситуации можно использовать `sync.WaitGroup`, канал или другое решение.

### 2. Запись в разные элементы slice

В этом примере две горутины тоже работают с одним slice.

Но они пишут в разные элементы slice.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	values := make([]int, 2)

	go func() {
		values[0] = 10
	}()

	go func() {
		values[1] = 20
	}()

	time.Sleep(100 * time.Millisecond)
	fmt.Println("Записи завершены")
}
```

Сначала через:

```go
values := make([]int, 2)
```

создаётся slice длиной `2`.

Его индексы:

```text
0
1
```

Первая горутина:

```go
values[0] = 10
```

пишет в элемент `0`.

А вторая горутина:

```go
values[1] = 20
```

пишет в элемент `1`.

Эти два элемента slice обозначают отдельные места в памяти.

Поэтому эти две записи не считаются конфликтующими обращениями.

Кроме того, пока горутины работают, `main()` не читает значения:

```go
values[0]
```

или:

```go
values[1]
```

Она только выводит другой текст:

```go
fmt.Println("Записи завершены")
```

Поэтому:

```bash
go run -race main.go
```

не должен сообщать о гонке данных для записи в эти два элемента.

Но и здесь:

```go
time.Sleep(100 * time.Millisecond)
```

— не механизм синхронизации, надёжно подтверждающий, что горутины завершились.

В этом маленьком примере он используется только для того, чтобы дать горутинам возможность выполниться.

В реальном коде, если нужно точно знать, когда горутины завершились, вместо `Sleep()` нужно использовать правильное средство синхронизации.
