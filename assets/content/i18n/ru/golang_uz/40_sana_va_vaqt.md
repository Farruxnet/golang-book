# Работа с датой и временем в Go

В Go для работы с датами, временем и временными интервалами используется пакет `time` из стандартной библиотеки.

В backend-программах работа со временем встречается очень часто. Например:

* сохранить, когда была создана запись в базе данных;
* проверить, истёк ли срок действия токена;
* поставить тайм-аут на HTTP-операцию или операцию с базой данных;
* показать пользователю время в его часовом поясе;
* вычислить, сколько времени прошло между двумя событиями;
* выполнить какую-то работу через определённое время.

При работе со временем важно различать три основных понятия:

* `time.Time` — точная точка на временной шкале;
* `time.Duration` — временной интервал, показывающий, сколько что-то длилось;
* `time.Location` — определяет, по правилам какого часового пояса показывать точку во времени.

Например, одна встреча может быть в `14:00` в Ташкенте. Та же встреча в Лондоне отображается в другой местный час.

Это не значит, что встреч две. Точка на временной шкале одна. Отличается только `Location`, используемый для её отображения.

## Получение текущего времени

Для получения текущего времени используется `time.Now()`.

Эта функция получает текущее время от операционной системы и возвращает значение `time.Time`:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	now := time.Now()

	fmt.Println("Местное время:", now)
	fmt.Println("Время UTC:", now.UTC())
}
```

Результат зависит от того, когда и в какой среде запущена программа. Например:

```text
Местное время: 2026-03-15 14:30:20.123456789 +0500 +05 m=+0.000031201
Время UTC: 2026-03-15 09:30:20.123456789 +0000 UTC
```

Здесь `now` хранит время в местном часовом поясе сервера.

А `now.UTC()` возвращает ту же самую точку во времени в виде UTC.

Важно, что `time.Now()` не всегда возвращает UTC. Он использует местный `Location` системы.

Например, если сервер настроен на UTC:

```go
time.Now()
```

результат сам по себе тоже может быть в UTC.

Если сервер работает в часовом поясе Ташкента, результат может выйти со смещением около `+05:00`.

Поэтому угадывать в коде, в каком часовом поясе работает сервер, — плохой подход. Если нужен UTC, лучше написать это явно:

```go
now := time.Now().UTC()
```

Стандартное текстовое представление `time.Time` выше состоит из нескольких частей:

| Часть                | Значение                                                             |
| -------------------- | -------------------------------------------------------------------- |
| `2026-03-15`         | год, месяц и день                                                    |
| `14:30:20.123456789` | час, минута, секунда и дробная часть секунды                         |
| `+0500`              | сдвиг относительно UTC, то есть offset                               |
| `+05`                | имя часового пояса; в зависимости от системы может быть другим       |
| `m=+...`             | показание monotonic clock, которое может быть внутри `time.Time`     |

Последняя часть `m=+...` на первый взгляд может показаться странной. Она не является частью обычной даты или часового пояса.

### Что такое монотонное время?

При измерении времени полезно разделять два понятия:

* wall clock (настенные часы);
* monotonic clock (монотонные часы).

**Wall clock** — обычные дата и время, которые видит пользователь.

Например:

```text
2026-03-15 14:30:20
```

Это время связано с часами операционной системы.

А системное время может меняться. Например:

* администратор может изменить часы вручную;
* NTP может скорректировать время;
* системные часы могут сдвинуться вперёд или назад.

Если вычислять длительность между двумя событиями только по wall clock, такие изменения могут повлиять на результат.

**Monotonic clock** же предназначен для измерения временных интервалов.

Его главная задача:

> отвечать не на вопрос «который час?», а на вопрос «сколько времени прошло?».

Значение `time.Time`, возвращённое `time.Now()`, может хранить и монотонное показание.

Например:

```go
start := time.Now()

// Выполняется какая-то работа.

elapsed := time.Since(start)
```

Если у `start` есть монотонные данные, `time.Since` меньше зависит от корректировок wall clock операционной системы.

Операции вроде `Sub`, `Before`, `After` тоже могут их использовать, если монотонные данные есть у обоих операндов.

Здесь есть тонкость.

Понимать значение `m=+...` как:

> «Время, прошедшее с запуска программы»

неправильно.

Это внутреннее монотонное показание, используемое runtime. Это не постоянный идентификатор, и его не нужно сохранять в базу данных или отправлять в другой сервис.

При форматировании и сериализации монотонная часть обычно отбрасывается.

Например:

```go
now.Format(time.RFC3339)
```

не записывает `m=+...` в результат.

Точно так же при преобразовании `time.Time` в JSON монотонное показание не передаётся в другую систему.

## Получение частей даты и времени

Из значения `time.Time` можно отдельно получить год, месяц, день, час и другие части.

Для этого у `time.Time` есть методы:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	moment := time.Date(2024, time.February, 29, 16, 45, 30, 0, time.UTC)

	fmt.Println("Год:", moment.Year())
	fmt.Println("Месяц:", moment.Month())
	fmt.Println("День:", moment.Day())
	fmt.Println("День недели:", moment.Weekday())
	fmt.Println("Час:", moment.Hour())
	fmt.Println("Минута:", moment.Minute())
	fmt.Println("Секунда:", moment.Second())
}
```

Результат:

```text
Год: 2024
Месяц: February
День: 29
День недели: Thursday
Час: 16
Минута: 45
Секунда: 30
```

В этом примере `time.Now()` не используется.

Время задано заранее точно:

```go
time.Date(2024, time.February, 29, 16, 45, 30, 0, time.UTC)
```

Поэтому результат каждый раз одинаковый.

Назначение методов:

```go
moment.Year()
```

возвращает год.

```go
moment.Month()
```

возвращает месяц в виде типа `time.Month`.

```go
moment.Day()
```

даёт номер дня в месяце.

```go
moment.Weekday()
```

возвращает день недели.

```go
moment.Hour()
moment.Minute()
moment.Second()
```

дают соответствующие части времени.

`Month()` возвращает не обычный `int`, а тип `time.Month`.

При выводе через `fmt.Println` он может выглядеть как английское название:

```text
February
```

Точно так же `Weekday()` даёт английское значение:

```text
Thursday
```

Если пользователю нужно показать русские названия:

```text
Февраль
Четверг
```

это нужно отдельно локализовать на уровне приложения.

Пакет `time` не переводит автоматически названия месяцев и дней недели на другие языки.

## Форматирование времени

Значение `time.Time` может понадобиться отправить пользователю или другой системе в виде строки.

Для этого используется метод `Format`.

Система форматирования времени в Go отличается от многих других языков программирования.

Например, в других языках может встречаться такой вид:

```text
YYYY-MM-DD
```

В Go такие символы формата не используются.

Вместо них используется специальное **reference time**, то есть эталонное время:

```text
Mon Jan 2 15:04:05 MST 2006
```

При написании layout в Go нужный формат выражается частями этого эталонного времени.

Для запоминания используют и такую последовательность:

```text
01/02 03:04:05PM '06 -0700
```

Эти числа выбраны не случайно.

Они используются соответственно как:

```text
01 → месяц
02 → день
03 → час в 12-часовом формате
04 → минута
05 → секунда
06 → последние две цифры года
-0700 → смещение часового пояса
```

Пример:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	moment := time.Date(2024, time.August, 9, 16, 7, 5, 123_000_000, time.UTC)

	fmt.Println("Дата:", moment.Format("02-01-2006"))
	fmt.Println("Время:", moment.Format("15:04:05"))
	fmt.Println("API:", moment.Format(time.RFC3339Nano))
}
```

Результат:

```text
Дата: 09-08-2024
Время: 16:07:05
API: 2024-08-09T16:07:05.123Z
```

Первый формат:

```go
moment.Format("02-01-2006")
```

означает такой порядок:

```text
день-месяц-год
```

Поэтому получается:

```text
09-08-2024
```

Второй формат:

```go
moment.Format("15:04:05")
```

даёт 24-часовой вид:

```text
час:минута:секунда
```

Результат:

```text
16:07:05
```

При передаче времени между API и сервисами обычно лучше использовать стандартные форматы.

Например:

```go
time.RFC3339
```

или, если нужно сохранить точность до наносекунд:

```go
time.RFC3339Nano
```

Этот подход безопаснее, чем произвольно придумывать новый формат даты в каждом проекте.

### Основные части layout

Часто используемые части layout в Go:

| Часть layout   | Значение результата                          |
| -------------- | -------------------------------------------- |
| `2006`         | год из четырёх цифр                          |
| `06`           | год из двух цифр                             |
| `01`           | месяц из двух цифр                           |
| `1`            | месяц без ведущего нуля                      |
| `Jan`          | короткое название месяца                     |
| `January`      | полное название месяца                       |
| `02`           | день из двух цифр                            |
| `2`            | день без ведущего нуля                       |
| `Mon`          | короткий день недели                         |
| `Monday`       | полный день недели                           |
| `15`           | час в 24-часовом формате                     |
| `03`           | час в 12-часовом формате                     |
| `PM` или `pm`  | обозначение периода в 12-часовом формате     |
| `04`           | минута                                       |
| `05`           | секунда                                      |
| `.000`         | миллисекунды, всегда три цифры               |
| `.000000`      | микросекунды, всегда шесть цифр              |
| `.000000000`   | наносекунды, всегда девять цифр              |
| `MST`          | имя зоны                                     |
| `-0700`        | смещение вида `+0500`                        |
| `-07:00`       | смещение вида `+05:00`                       |
| `Z07:00`       | `Z` для UTC, числовое смещение в других зонах |

Запоминать эту таблицу не обязательно. Но узнавать основные части вроде `2006-01-02` и `15:04:05` очень полезно.

Особенно при переходе в Go из других языков очень часто встречается такая ошибка:

```go
// Неправильно: "YYYY" — не символ layout в Go.
fmt.Println(moment.Format("YYYY-MM-DD"))
```

Этот код компилируется.

Проблема в том, что Go не распознаёт `YYYY`, `MM` или `DD` как специальные символы формата.

Он воспринимает их как обычный текст.

Поэтому такая ошибка может не обнаружиться на этапе компиляции.

Например, для года нужно использовать:

```text
2006
```

для месяца:

```text
01
```

для дня:

```text
02
```

```go
moment.Format("2006-01-02")
```

Здесь важно понимать модель reference time в layout Go. Иначе код может казаться рабочим, но выдавать неправильную строку.

## Преобразование строки во время

Иногда время приходит не как `time.Time`, а как строка.

Например, HTTP-запрос может прислать значение:

```text
2024-08-09
```

Чтобы преобразовать такую строку в `time.Time`, используется `time.Parse`:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	input := "2024-08-09"
	moment, err := time.Parse("2006-01-02", input)
	if err != nil {
		fmt.Println("Неверная дата:", err)
		return
	}

	fmt.Println(moment.Format(time.RFC3339))
}
```

Результат:

```text
2024-08-09T00:00:00Z
```

`time.Parse` принимает две важные части информации:

```go
time.Parse(layout, value)
```

Первая — layout, показывающий, в каком формате строка.

Вторая — значение, которое нужно распарсить.

В этом примере:

```go
"2006-01-02"
```

соответствует такой строке:

```text
2024-08-09
```

Часть со временем в строке не указана.

Поэтому используется:

```text
00:00:00
```

В layout нет и часового пояса.

В таком случае `time.Parse` создаёт значение в UTC.

Поэтому результат:

```text
2024-08-09T00:00:00Z
```

Строка должна соответствовать layout.

Например:

```text
2024-02-30
```

— дата, которой нет в календаре.

30 февраля не существует.

Поэтому `time.Parse` возвращает ошибку.

Это особенно важно при работе с внешними данными.

Писать так опасно:

```go
moment, _ := time.Parse("2006-01-02", input)
```

Здесь ошибка полностью игнорируется.

Если input неверный, дальнейшая бизнес-логика может работать с неправильным временем.

Поэтому при парсинге времени, пришедшего снаружи, нужно проверять `err`.

### Парсинг местного времени в определённой зоне

Представим такое значение:

```text
2024-08-09 14:30
```

В этой строке есть дата и время.

Но нет часового пояса.

Поэтому возникает важный вопрос:

> `14:30` — это местное время какого региона?

Если это время Ташкента, приложение должно это знать.

В такой ситуации используется `time.ParseInLocation`:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	location, err := time.LoadLocation("Asia/Tashkent")
	if err != nil {
		fmt.Println("Часовой пояс не загружен:", err)
		return
	}

	input := "2024-08-09 14:30"
	moment, err := time.ParseInLocation("2006-01-02 15:04", input, location)
	if err != nil {
		fmt.Println("Неверное время:", err)
		return
	}

	fmt.Println("Ташкент:", moment.Format(time.RFC3339))
	fmt.Println("UTC:", moment.UTC().Format(time.RFC3339))
}
```

Результат:

```text
Ташкент: 2024-08-09T14:30:00+05:00
UTC: 2024-08-09T09:30:00Z
```

Рассмотрим процесс по шагам.

Сначала загружается location Ташкента:

```go
location, err := time.LoadLocation("Asia/Tashkent")
```

`Asia/Tashkent` — имя из базы часовых поясов IANA.

Затем вызывается:

```go
time.ParseInLocation("2006-01-02 15:04", input, location)
```

В `input` часовой пояс не указан.

Поэтому Go интерпретирует это время по правилам:

```text
Asia/Tashkent
```

Результат:

```text
2024-08-09T14:30:00+05:00
```

Затем вызывается:

```go
moment.UTC()
```

Результат:

```text
2024-08-09T09:30:00Z
```

Здесь точка во времени не изменилась.

Только то же самое время показано в другом часовом поясе.

То есть:

```text
14:30 +05:00
```

и:

```text
09:30 UTC
```

— одна и та же точка во времени.

`time.LoadLocation` нужны данные часовых поясов IANA.

Эти данные могут браться из базы zoneinfo операционной системы.

В обычных дистрибутивах Linux она обычно есть.

Но если используется очень минимальный образ контейнера, базы zoneinfo может не быть вовсе.

В таком случае:

```go
time.LoadLocation("Asia/Tashkent")
```

может вернуть ошибку.

Проблему можно решить несколькими способами.

Например, установить данные zoneinfo в образ контейнера.

Или добавить базу часовых поясов в Go-программу:

```go
import _ "time/tzdata"
```

Этот способ добавляет данные часовых поясов внутрь исполняемого файла.

Преимущество — программа меньше зависит от внешних файлов zoneinfo.

Недостаток — исполняемый файл становится больше.

Поэтому выбор варианта зависит от требований к развёртыванию.

> **Внимание**
>
> `time.FixedZone("UZT", 5*60*60)` создаёт зону с постоянным смещением `+05:00`.
>
> Но `FixedZone` не знает исторических правил часовых поясов или изменений вроде перехода на летнее время.
>
> Если правила времени региона менялись в истории или могут измениться в будущем, лучше использовать `time.LoadLocation` и IANA-имя вроде `Asia/Tashkent`.

## Создание времени через `time.Date`

Чтобы создать `time.Time` из определённых года, месяца, дня и часа, используется `time.Date`.

Пример:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	moment := time.Date(
		2024,
		time.August,
		9,
		14,
		30,
		0,
		0,
		time.UTC,
	)

	fmt.Println(moment.Format(time.RFC3339))
}
```

Результат:

```text
2024-08-09T14:30:00Z
```

Аргументы `time.Date` упрощённо можно представить так:

```text
год
месяц
день
час
минута
секунда
наносекунда
location
```

В этом примере:

```go
2024
```

— год.

```go
time.August
```

— август.

```go
9
```

— 9-е число месяца.

```go
14, 30, 0
```

— `14:30:00`.

Наносекунда:

```go
0
```

А location задан как:

```go
time.UTC
```

Месяц можно записать и так:

```go
time.Date(2024, 8, 9, ...)
```

Это компилируется.

Причина в том, что `time.Month` — именованный тип на основе целого числа.

Но запись:

```go
time.August
```

гораздо понятнее.

Человеку, читающему код, не нужно вспоминать, что означает `8`.

### `time.Date` нормализует значения

Здесь есть важная тонкость.

`time.Date` не всегда отвергает значения вне диапазона как ошибку.

Он может их нормализовать.

Например, если задать 32 января, результат перейдёт в следующий месяц.

То есть:

```text
32 января 2024 года
```

неверное календарное значение может без ошибки превратиться в дату в феврале.

Поэтому использовать `time.Date` как валидатор для вопроса:

> «Существует ли на самом деле дата, введённая пользователем?»

нехорошо.

Если пользователь или внешний API присылает текст, например:

```text
2024-02-30
```

лучше проверять его строгим layout через:

```go
time.Parse("2006-01-02", input)
```

`Parse` возвращает ошибку для неверной календарной даты.

## `Duration`: временной интервал

`time.Time` обозначает точку на временной шкале.

А `time.Duration` обозначает, сколько что-то длилось.

Например:

```text
90 минут
2 секунды
500 миллисекунд
```

это не точки во времени, а длительности.

В Go `time.Duration` — именованный тип на основе `int64`.

Внутреннее значение выражается в наносекундах.

Но в коде не нужно писать число наносекунд вручную.

Есть стандартные константы:

```go
time.Nanosecond
time.Microsecond
time.Millisecond
time.Second
time.Minute
time.Hour
```

Например:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	start := time.Date(2024, time.January, 1, 12, 0, 0, 0, time.UTC)
	duration := 90 * time.Minute
	end := start.Add(duration)

	fmt.Println("Начало:", start.Format(time.RFC3339))
	fmt.Println("Конец:", end.Format(time.RFC3339))
	fmt.Println("Длительность:", end.Sub(start))
}
```

Результат:

```text
Начало: 2024-01-01T12:00:00Z
Конец: 2024-01-01T13:30:00Z
Длительность: 1h30m0s
```

В этом примере:

```go
duration := 90 * time.Minute
```

создаёт `Duration` на 90 минут.

Затем:

```go
end := start.Add(duration)
```

прибавляет 90 минут ко времени начала.

В результате получается:

```text
12:00 + 90 минут = 13:30
```

Затем:

```go
end.Sub(start)
```

возвращает длительность между двумя моментами.

Результат:

```text
1h30m0s
```

### Почему нет `time.Day`?

В стандартной библиотеке Go есть:

```go
time.Hour
```

Но нет:

```go
time.Day
```

Причина в том, что календарный день не всегда означает ровно `24*time.Hour`.

В регионах, где применяется летнее время (DST), некоторые календарные дни в реальном времени могут длиться:

```text
23 часа
```

или:

```text
25 часов
```

Поэтому:

> «Ровно 24 часа»

и:

> «Следующий календарный день»

— два разных понятия.

Эту разницу мы увидим в разделе про `Add` и `AddDate` ниже.

### `ParseDuration`

В конфигурации временной интервал может прийти текстом.

Например:

```text
1.5s
```

или:

```text
1h30m
```

Такие значения можно прочитать через `time.ParseDuration`:

```go
timeout, err := time.ParseDuration("1.5s")
if err != nil {
	return err
}
```

Здесь:

```text
1.5s
```

равно такой длительности:

```text
1500ms
```

`ParseDuration` возвращает ошибку для неверного формата или неизвестной единицы.

Например, при работе с внешней конфигурацией важно проверять ошибку.

`time.Duration` внутри основан на `int64`.

Поэтому его диапазон не бесконечен.

При вычислении очень больших значений нужно учитывать и возможность переполнения `int64`.

В обычных тайм-аутах и конфигурации сервисов это встречается редко, но в коде, выполняющем арифметику с очень большими длительностями, эта тонкость может быть важна.

## Разница между `Add` и `AddDate`

В Go есть как минимум два важных способа прибавить что-то ко времени:

* `Add`;
* `AddDate`.

Их смысл не одинаков.

### `Add`

`Add` прибавляет точную `Duration`:

```go
later := moment.Add(2 * time.Hour)
earlier := moment.Add(-30 * time.Minute)
```

В первой строке:

```go
2 * time.Hour
```

прибавляются ровно два часа.

Во второй строке, поскольку используется отрицательная длительность:

```go
-30 * time.Minute
```

вычитается 30 минут.

Значит, `Add` работает на временной шкале с точной длительностью.

### `AddDate`

`AddDate` же работает с календарными единицами:

```go
nextMonth := moment.AddDate(0, 1, 0)
twoMonthsAgo := moment.AddDate(0, -2, 0)
nextWeek := moment.AddDate(0, 0, 7)
```

Аргументы `AddDate` имеют вид:

```go
AddDate(years, months, days)
```

Поэтому:

```go
moment.AddDate(0, 1, 0)
```

прибавляет один календарный месяц.

```go
moment.AddDate(0, -2, 0)
```

переходит на два календарных месяца назад.

```go
moment.AddDate(0, 0, 7)
```

прибавляет семь календарных дней.

### `24*time.Hour` и один календарный день

Следующие два фрагмента кода не всегда означают одно и то же:

```go
moment.Add(24 * time.Hour)
```

и:

```go
moment.AddDate(0, 0, 1)
```

Первый вариант говорит:

> Прибавь ровно 24 реальных часа.

Второй вариант говорит:

> Перейди на следующий календарный день.

В зоне, где используется DST, следующий календарный день по местному времени может наступить через 23 или 25 реальных часов.

Поэтому метод выбирают в зависимости от требования.

Если требование:

> «Ровно через 24 часа»

подходит:

```go
Add(24 * time.Hour)
```

Если требование:

> «Завтра в тот же местный час»

больше подходит:

```go
AddDate(0, 0, 1)
```

### Тонкий случай при прибавлении месяцев

Календарные месяцы имеют разную длину.

Например:

* некоторые месяцы — 31 день;
* некоторые — 30 дней;
* февраль — 28 или 29 дней.

Поэтому при переходе на месяц вперёд с 31-го числа в новом месяце 31-го числа может не быть.

`AddDate` вычисляет такие случаи по правилам нормализации `time.Date`.

Поэтому если бизнес-требование:

> «Ровно последний день следующего месяца»

просто:

```go
AddDate(0, 1, 0)
```

не всегда даст нужный бизнес-результат.

Для такой задачи нужно написать отдельное календарное правило для «последнего дня месяца».

## Работа с часовыми поясами

Недостаточно считать `time.Time` простой структурой, хранящей только год, месяц и час.

Он может отображать точку во времени с определённым `Location`.

`Location` определяет, в какой местный час пользователь видит это время.

Чтобы показать одну точку во времени в другом часовом поясе, используется метод `In`:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	tashkent, err := time.LoadLocation("Asia/Tashkent")
	if err != nil {
		fmt.Println("Зона не загружена:", err)
		return
	}

	moment := time.Date(2024, time.January, 15, 9, 0, 0, 0, time.UTC)

	fmt.Println("UTC:", moment.Format(time.RFC3339))
	fmt.Println("Ташкент:", moment.In(tashkent).Format(time.RFC3339))
}
```

Результат:

```text
UTC: 2024-01-15T09:00:00Z
Ташкент: 2024-01-15T14:00:00+05:00
```

Начальное значение:

```text
2024-01-15T09:00:00Z
```

в UTC.

Затем вызывается:

```go
moment.In(tashkent)
```

Поскольку Ташкент на `+05:00` впереди UTC, отображение будет:

```text
2024-01-15T14:00:00+05:00
```

Здесь:

```text
09:00 UTC
```

и:

```text
14:00 +05:00
```

— не две разные точки во времени.

Они показывают одну и ту же точку в двух разных часовых поясах.

Поэтому `In` используется не для того, чтобы:

> превратить само время в другое время

Он используется для того, чтобы:

> показать ту же точку во времени по правилам другого `Location`

В backend-системах распространён такой подход:

1. хранить точки во времени в UTC;
2. между сервисами передавать UTC или стандартный формат с явным смещением;
3. при выводе пользователю переводить в его `Location`.

Этот подход уменьшает многие ошибки, связанные с часовыми поясами.

Но принудительно считать все данные «точкой во времени» тоже неправильно.

Например, дата рождения часто является календарной датой. Она не обязана быть точным моментом в UTC.

Эту разницу нужно учитывать при проектировании API и модели базы данных.

### Offset и `Location` — не одно и то же

Следующее значение:

```text
+05:00
```

обозначает только текущий сдвиг относительно UTC.

Оно не обозначает полные исторические правила региона.

Например:

```text
Asia/Tashkent
```

— имя часового пояса IANA, опирающееся на правила в базе zoneinfo.

Если нужен такой location, используется:

```go
time.LoadLocation("Asia/Tashkent")
```

Поэтому:

```text
+05:00
```

и:

```text
Asia/Tashkent
```

— не одно и то же понятие.

## Сравнение времени

Для сравнения двух значений `time.Time` как точек во времени есть специальные методы:

* `Before`;
* `After`;
* `Equal`.

Пример:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	utc := time.Date(2024, time.January, 1, 9, 0, 0, 0, time.UTC)
	fixed := time.FixedZone("UTC+5", 5*60*60)
	local := time.Date(2024, time.January, 1, 14, 0, 0, 0, fixed)

	fmt.Println("Одна точка во времени:", utc.Equal(local))
	fmt.Println("UTC раньше:", utc.Before(local))
}
```

Результат:

```text
Одна точка во времени: true
UTC раньше: false
```

Здесь первое время:

```text
2024-01-01 09:00 UTC
```

Второе время:

```text
2024-01-01 14:00 UTC+5
```

`UTC+5` на пять часов впереди UTC.

Поэтому:

```text
14:00 - 5 часов = 09:00 UTC
```

Значит, два значения выражают одну и ту же точку во времени.

Поэтому:

```go
utc.Equal(local)
```

возвращает `true`.

А `utc.Before(local)` — `false`.

Потому что `utc` не раньше второго значения. Они равны.

### Почему не стоит использовать `==`?

`time.Time` в Go — сравнимый (comparable) тип.

Значит, синтаксически можно написать:

```go
a == b
```

Но такое сравнение может учитывать не только точку на временной шкале, но и другие части внутреннего представления `time.Time`.

Например:

* `Location`;
* монотонные данные.

Поэтому для вопроса:

> «Являются ли эти два значения ровно одной и той же точкой во времени?»

лучше использовать:

```go
a.Equal(b)
```

Если:

```go
time.Time
```

используется как ключ `map`, эта тонкость особенно важна.

Например, можно использовать:

```go
map[time.Time]string
```

Но одна и та же точка во времени может прийти с разным внутренним представлением.

Поэтому перед использованием в качестве ключа map нужно чётко определить правило нормализации времени.

## Unix timestamp

Unix timestamp — способ выразить точку во времени одним числом.

Начальной точкой считается Unix epoch:

```text
1970-01-01T00:00:00Z
```

Unix timestamp показывает, сколько секунд или более мелких единиц времени прошло с этого момента.

Пример:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	moment := time.Date(2024, time.January, 1, 0, 0, 0, 0, time.UTC)
	seconds := moment.Unix()
	restored := time.Unix(seconds, 0).UTC()

	fmt.Println("Timestamp:", seconds)
	fmt.Println("Восстановлено:", restored.Format(time.RFC3339))
}
```

Результат:

```text
Timestamp: 1704067200
Восстановлено: 2024-01-01T00:00:00Z
```

Сначала:

```go
moment.Unix()
```

преобразует точку во времени в Unix-секунды.

Результат:

```text
1704067200
```

Затем:

```go
time.Unix(seconds, 0)
```

создаёт из этого timestamp новый `time.Time`.

А `.UTC()` даёт результат в виде UTC.

### Единицу timestamp нужно указывать явно

Одна из самых распространённых ошибок при работе с Unix timestamp — путаница единиц.

Например:

```text
1704067200
```

может быть в секундах.

А другой API может присылать timestamp в миллисекундах:

```text
1704067200000
```

Если принять значение в миллисекундах за секунды или наоборот, получится совершенно неправильная дата.

В Go есть методы, явно выражающие единицу:

```go
moment.Unix()
moment.UnixMilli()
moment.UnixMicro()
moment.UnixNano()
```

Их имена показывают, в какой единице значение.

В контракте API единицу тоже нужно указывать явно.

Например, полезно указать:

```text
created_at_unix_seconds
```

или в документации:

```text
Unix timestamp in milliseconds
```

### Unix timestamp не хранит часовой пояс

В Unix timestamp:

```text
1704067200
```

нет информации вроде:

```text
Asia/Tashkent
```

или:

```text
Europe/London
```

Он обозначает только точку во времени.

Какой `Location` использовать при показе пользователю, выбирается позже.

## JSON и форматы API

Стандартный пакет Go `encoding/json` обычно сериализует значение `time.Time` как текст в формате RFC 3339.

Например:

```json
{
  "created_at": "2024-08-09T09:30:00Z"
}
```

Преимущество такого вида в том, что смысл часового пояса понятен.

Здесь:

```text
Z
```

означает UTC.

Значение в другой зоне может выглядеть, например, так:

```text
2024-08-09T14:30:00+05:00
```

При передаче времени между сервисами важно использовать формат, в котором смысл часового пояса или смещения понятен.

### Календарная дата и точка во времени — не одно и то же

Иногда API нужно хранить только дату.

Например:

```text
2024-08-09
```

Layout Go для этого:

```text
2006-01-02
```

Здесь автоматически придавать значению смысл точки во времени не всегда правильно.

Например, день рождения:

```text
2000-05-10
```

часто — просто календарная дата.

Если преобразовать его в:

```text
2000-05-10T00:00:00Z
```

а потом перевести в другой часовой пояс, в некоторых зонах дата может сдвинуться на:

```text
2000-05-09
```

или другой календарный день.

Это нарушает бизнес-смысл.

Поэтому не смешивайте в модели данных такие понятия:

* точная точка во времени;
* только календарная дата;
* местное календарное время.

Эта семантика важна и при выборе столбца базы данных.

Например, в базе данных:

* точка во времени;
* только дата;
* встреча, привязанная к местному времени пользователя

— это не один и тот же тип данных.

Как драйвер базы данных и тип столбца работают с часовыми поясами, тоже нужно проверять отдельно.

## `Sleep`, timer и ticker

Пакет `time` нужен не только для форматирования дат.

Он даёт и средства для управления работой горутин по времени.

### `time.Sleep`

`time.Sleep` приостанавливает текущую горутину как минимум на заданную длительность:

```go
time.Sleep(500 * time.Millisecond)
```

Здесь горутина приостанавливается примерно на полсекунды.

Важный момент:

```go
time.Sleep(500 * time.Millisecond)
```

не означает «ровно через 500 миллисекунд CPU снова отдадут этой горутине».

Из-за планировщика и операционной системы горутина может продолжить работу немного позже.

То есть `Sleep` обозначает минимальную длительность ожидания.

Если задать нулевую или отрицательную длительность:

```go
time.Sleep(0)
```

или:

```go
time.Sleep(-1 * time.Second)
```

`Sleep` сразу возвращается.

### Timer

Если нужен одиночный сигнал через определённое время, используется `time.NewTimer`:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	timer := time.NewTimer(20 * time.Millisecond)
	defer timer.Stop()

	<-timer.C
	fmt.Println("Таймер сработал")
}
```

Результат:

```text
Таймер сработал
```

Здесь:

```go
timer := time.NewTimer(20 * time.Millisecond)
```

создаёт таймер на 20 миллисекунд.

Внутри таймера есть канал:

```go
timer.C
```

Затем:

```go
<-timer.C
```

ждёт сигнала из этого канала.

Когда срок таймера истекает, горутина продолжает работу и выводится:

```text
Таймер сработал
```

### `Stop`

В следующей строке:

```go
defer timer.Stop()
```

таймер останавливается, когда он больше не нужен.

Если таймер уже сработал, `Stop` может не иметь практического эффекта.

Но если ещё активный таймер или тикер больше не нужен, остановить его важно, чтобы не расходовать ресурсы зря.

### Ticker

Если нужен периодический сигнал, используется `time.NewTicker`.

Например, тикер удобен для выполнения какой-то работы каждую секунду.

Но о тикере есть важная тонкость.

Если потребитель работает медленно, предположение, что тикер:

> собирает каждый пропущенный тик в неограниченную очередь

неверно.

Поэтому код не должен слепо полагаться на требование:

> «Для каждого интервала обязательно обрабатывается ровно одно событие»

Если учёт каждого временного интервала по отдельности важен для бизнеса, может потребоваться другой дизайн.

### Не синхронизируйте через `Sleep`

Такой подход плох:

```go
go doWork()

time.Sleep(time.Second)

// предполагаем, что doWork завершилась
```

Здесь программа предполагает:

> «Одной секунды, наверное, хватит»

Но `doWork` может завершиться и быстрее, и медленнее.

Чтобы дождаться завершения горутины, нужно использовать:

* `sync.WaitGroup`;
* канал;
* другое явное средство синхронизации.

А для backend-операций, где нужны тайм-аут и отмена, часто подходит:

```go
context.WithTimeout
```

## Измерение прошедшего времени

Чтобы измерить, сколько длилась операция, можно использовать `time.Now()` и `time.Since()`:

```go
start := time.Now()

// Измеряемая работа.

elapsed := time.Since(start)
fmt.Println(elapsed)
```

Процесс очень простой:

1. перед началом работы берётся время;
2. выполняется операция;
3. через `time.Since(start)` вычисляется, сколько времени прошло.

Например:

```go
start := time.Now()

doWork()

fmt.Println("Длительность:", time.Since(start))
```

Если в значении `start` есть данные monotonic clock, `time.Since` может их использовать.

Это уменьшает влияние изменений wall clock на измерение длительности.

Но для анализа производительности одного такого измерения недостаточно.

Например, если один раз получилось:

```text
12ms
```

это не значит, что функция всегда работает 12 миллисекунд.

На результат могут влиять:

* планировщик;
* сборщик мусора;
* нагрузка на CPU;
* кеш;
* операционная система;
* другие процессы.

Для повторяемого и более стабильного измерения производительности лучше использовать бенчмарки Go.

## Тестирование кода, зависящего от времени

При тестировании бизнес-логики, зависящей от времени, прямой вызов `time.Now()` внутри функции может создать проблемы.

Например:

```go
func expired(deadline time.Time) bool {
	return !time.Now().Before(deadline)
}
```

Результат этой функции зависит от того, когда запущен тест.

Чтобы тест был стабильнее, текущее время можно передавать снаружи:

```go
package main

import (
	"fmt"
	"time"
)

func expired(now, deadline time.Time) bool {
	return !now.Before(deadline)
}

func main() {
	now := time.Date(2024, time.January, 1, 12, 0, 0, 0, time.UTC)
	deadline := now.Add(30 * time.Minute)

	fmt.Println(expired(now, deadline))
	fmt.Println(expired(deadline, deadline))
}
```

Результат:

```text
false
true
```

Для первого вызова:

```go
expired(now, deadline)
```

`now` на 30 минут раньше deadline.

Поэтому:

```go
now.Before(deadline)
```

— `true`.

А функция возвращает:

```go
!now.Before(deadline)
```

Результат:

```text
false
```

то есть срок ещё не истёк.

Во втором вызове:

```go
expired(deadline, deadline)
```

`now` и `deadline` равны.

`Before` возвращает `true`, только если первое время раньше второго.

Если они равны:

```go
deadline.Before(deadline)
```

— `false`.

Поэтому:

```go
!false
```

— `true`.

Результат будет:

```text
true
```

Значит, бизнес-правило в этом коде такое:

> Даже если `now` равно deadline, срок считается истёкшим.

Это очень важный граничный случай.

В реальных проектах нужно осознанно выбирать между:

```text
now > deadline
```

или:

```text
now >= deadline
```

Это не просто техническая деталь. Это бизнес-решение.

Поэтому такие граничные случаи нужно закреплять тестами.

### Передача функции часов

В более крупном сервисе источник времени можно передавать как функцию:

```go
type Clock func() time.Time
```

В production-коде передаётся:

```go
time.Now
```

А в тесте можно передать функцию, всегда возвращающую заранее заданное время.

Например:

```go
fixedNow := func() time.Time {
	return time.Date(2024, time.January, 1, 12, 0, 0, 0, time.UTC)
}
```

Польза в том, что тест не зависит от реального времени.

Результат каждый раз одинаковый.

В тестах, работающих с таймерами, использование настоящего `time.Sleep` тоже часто плохой подход.

Например:

```go
time.Sleep(2 * time.Second)
```

замедляет тест.

Кроме того, тесты, зависящие от тайминга, могут быть нестабильными в сильно нагруженной CI-среде.

По возможности лучше использовать такие подходы, как:

* сигналы;
* каналы;
* часы, переданные как зависимость;
* управляемая абстракция таймера.

## Частые ошибки

При работе со временем часто встречаются такие ошибки.

* Думать, что `time.Now()` всегда возвращает UTC.

  `time.Now()` использует местный `Location` системы.

  Если UTC точно нужен, пишите:

  ```go
  time.Now().UTC()
  ```

* Использовать `YYYY-MM-DD` в layout.

  Go не использует символы формата `YYYY`, `MM`, `DD`, принятые во многих других языках.

  Правильный layout Go:

  ```text
  2006-01-02
  ```

* Не проверять ошибку `time.Parse`.

  Внешний input может быть в неверном формате или выражать несуществующую дату.

  Поэтому после:

  ```go
  moment, err := time.Parse(...)
  ```

  проверяйте `err`.

* Парсить строку без зоны в неправильной зоне.

  Если время без зоны нужно интерпретировать как UTC, можно использовать:

  ```go
  time.Parse
  ```

  Если оно относится к определённому местному часовому поясу, может понадобиться:

  ```go
  time.ParseInLocation
  ```

* Считать offset и `Location` одним и тем же.

  ```text
  +05:00
  ```

  обозначает только сдвиг относительно UTC.

  ```text
  Asia/Tashkent
  ```

  опирается на правила региона в базе zoneinfo.

* Считать, что календарный день всегда длится 24 часа.

  Для «ровно 24 часа»:

  ```go
  Add(24 * time.Hour)
  ```

  а для «следующего календарного дня»:

  ```go
  AddDate(0, 0, 1)
  ```

  может понадобиться.

* Сравнивать точки во времени через отформатированные строки.

  Например:

  ```go
  a.Format(...) == b.Format(...)
  ```

  — плохой подход для проверки равенства времени.

  Используйте методы `Before`, `After` и `Equal`.

* Сравнивать `time.Time` через `==` для равенства времени.

  `==` может учитывать и другие части внутреннего представления.

  Для равенства точек во времени используйте:

  ```go
  a.Equal(b)
  ```

* Не указывать единицу Unix timestamp.

  Явно пишите в контракте API, в чём timestamp:

  ```text
  seconds
  ```

  или:

  ```text
  milliseconds
  ```

* Синхронизировать горутины через `time.Sleep`.

  `Sleep` не гарантирует:

  > «За это время горутина обязательно завершится»

  Используйте `WaitGroup`, канал или другое средство синхронизации.

* Слишком полагаться на `Sleep` в тестах.

  Такие тесты становятся медленными и зависимыми от тайминга.

* Думать, что монотонное значение внутри `time.Time` сохраняется при сериализации.

  Данные monotonic clock используются для вычисления длительностей внутри процесса.

  Они не сохраняются в JSON, обычном форматировании или при передаче между сервисами.

## На что обращают внимание на собеседовании?

В вопросах о дате и времени в Go часто недостаточно знать только `time.Now()`.

Важно понимать следующие различия:

* Layout Go работает на основе специального reference time:

  ```text
  Mon Jan 2 15:04:05 MST 2006
  ```

  Например, стандартный layout даты:

  ```text
  2006-01-02
  ```

* `time.Time` и `time.Duration` выражают разные понятия.

  `time.Time`:

  > точная точка на временной шкале.

  `time.Duration`:

  > длительность между двумя моментами.

* Нужно знать разницу между `time.Parse` и `time.ParseInLocation`.

  Если `time.Parse` парсит значение без зоны, время создаётся в UTC.

  А `time.ParseInLocation` интерпретирует значение без зоны на основе заданного `Location`.

* `Add` и `AddDate` имеют разный смысл.

  `Add` работает с точной длительностью.

  `AddDate` работает с календарными годами, месяцами и днями.

* Одна и та же точка во времени в разных часовых поясах может отображаться с разным часом.

  Например:

  ```text
  09:00 UTC
  ```

  и:

  ```text
  14:00 +05:00
  ```

  могут быть одной и той же точкой во времени.

* Для проверки равенства точек во времени нужно использовать:

  ```go
  Equal
  ```

* `time.Now()` может хранить и данные monotonic clock.

  Эти данные полезны в вычислениях длительности вроде `Sub` и `Since`.

  Но через форматирование и сериализацию они не передаются в другую систему.

* В backend-сервисах часто удобно хранить точки во времени в UTC и передавать между сервисами UTC или формат с явным смещением.

  При показе пользователю можно переводить в его `Location`.

  Но значения, которые являются только календарной датой, например день рождения, не нужно принудительно превращать в точку во времени UTC.
