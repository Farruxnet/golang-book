# Работа с каналами в Go

Канал (channel) — средство передачи значений определённого типа между горутинами. Он используется не только для отправки данных, но и для синхронизации работы горутин друг с другом.

Проще говоря, одна горутина отправляет значение в канал, а другая горутина принимает это значение.

Например, пусть несколько горутин получают данные из разных внешних API. Каждая горутина может записывать свой результат в общий `map`. Но если несколько горутин одновременно пишут в один `map`, нужна отдельная синхронизация.

Вместо этого каждая горутина может отправить свой результат через канал одной собирающей горутине. Тогда уменьшается необходимость нескольким горутинам одновременно писать в общие данные.

Здесь есть важная тонкость. Через канал можно отправлять и значения со свойствами ссылок: указатели, slice, map и другие. Канал синхронизирует отправку и получение такого значения.

Но канал не защищает автоматически данные внутри отправленного объекта.

Например, через канал отправили указатель на объект. Если потом и отправляющая, и принимающая горутина одновременно изменяют этот объект, может возникнуть `data race`.

Значит:

* канал синхронизирует передачу значения;
* но не защищает автоматически последующее конкурентное изменение отправленного объекта.

## Создание канала

Тип канала записывается ключевым словом `chan` и типом элементов, передаваемых через канал:

```go
var ch chan int
```

Здесь тип переменной `ch` — `chan int`.

Это значит, что через канал отправляются и принимаются значения `int`.

Но код выше ещё не создаёт рабочий канал. Значение `ch` будет `nil`.

Канал, используемый на практике, обычно создаётся через `make`:

```go
ch := make(chan int)
```

Этот код создаёт небуферизованный канал для значений `int`.

`chan int` принимает только значения `int`. Например, следующий код приводит к ошибке компиляции:

```go
ch := make(chan int)

// ch <- "привет" // compile error
```

Причина в том, что значение `"привет"` имеет тип `string`, а канал ожидает значения `int`.

Значит, каналы типобезопасны. Отправляются только значения указанного типа.

Для создания канала не нужно импортировать никакой отдельный пакет. `make` — встроенная функция языка Go.

## Отправка и получение

При работе с каналами используется оператор `<-`.

Отправка значения:

```go
ch <- value
```

Здесь значение `value` отправляется в канал `ch`.

Получение значения:

```go
value := <-ch
```

Здесь значение берётся из канала `ch` и записывается в переменную `value`.

Символ `<-` показывает, в какую сторону течёт значение.

В следующем коде:

```go
ch <- value
```

значение идёт от `value` к каналу.

А в следующем коде:

```go
value := <-ch
```

значение приходит из канала к `value`.

Операции отправки и получения могут быть блокирующими.

Особенно в небуферизованном канале send и receive ждут друг друга.

Например, горутина дошла до следующей строки:

```go
ch <- 10
```

Если в этот момент ни одна горутина не готова взять значение из `ch`, отправляющая горутина ждёт на этой строке.

Точно так же, когда выполняется строка:

```go
value := <-ch
```

и ещё никто не отправил значение, принимающая горутина ждёт.

В небуферизованном канале значение передаётся, когда send и receive встречаются в одной точке. После этого обе горутины могут продолжить работу.

Поэтому канал не только передаёт данные. Он также создаёт синхронизацию между горутинами.

## Первый пример

В следующем примере отдельная горутина вычисляет квадрат числа и отправляет результат через канал в горутину `main`:

```go
package main

import "fmt"

func square(number int, results chan<- int) {
	results <- number * number
}

func main() {
	results := make(chan int)

	go square(6, results)
	value := <-results

	fmt.Println("Результат:", value)
}
```

Результат:

```text
Результат: 36
```

Посмотрим по шагам, как работает код.

Сначала внутри `main` создаётся канал:

```go
results := make(chan int)
```

Это небуферизованный канал `int`.

Затем функция `square` запускается в новой горутине:

```go
go square(6, results)
```

Второй параметр функции `square` записан так:

```go
results chan<- int
```

`chan<- int` — тип канала, разрешающий только отправку значений.

То есть функция `square` может отправить значение в канал `results`:

```go
results <- number * number
```

Но получать значения через этот параметр нельзя.

Польза направленного канала в том, что по сигнатуре сразу видно, как функция должна работать с каналом.

После вычисления `6 * 6` значение `36` отправляется в канал.

В это время горутина `main` ждёт на следующей строке:

```go
value := <-results
```

`main` не продолжит работу, пока в канал не придёт значение.

Когда горутина `square` доходит до отправки, send и receive встречаются:

```text
горутина square:

results <- 36
       |
       | значение передаётся
       v
горутина main:

value := <-results
```

В результате значение `value` становится `36`.

Затем:

```go
fmt.Println("Результат:", value)
```

выводит:

```text
Результат: 36
```

В этом примере отдельный `WaitGroup` не нужен.

Причина в том, что `main` и так ждёт, чтобы получить результат из канала. Получение результата гарантирует, что горутина `square` вычислила результат и дошла до его отправки в канал.

Значит, здесь нужную синхронизацию обеспечивает сам канал.

## Сбор нескольких результатов

Теперь рассмотрим пример, где одновременно работают несколько горутин.

Следующая программа вычисляет квадраты трёх чисел. Каждое вычисление выполняется в отдельной горутине.

Результаты отправляются в один канал:

```go
package main

import (
	"fmt"
	"sync"
)

type result struct {
	number int
	square int
}

func calculate(number int, results chan<- result, wg *sync.WaitGroup) {
	defer wg.Done()

	results <- result{
		number: number,
		square: number * number,
	}
}

func main() {
	numbers := []int{2, 3, 4}
	results := make(chan result)

	var wg sync.WaitGroup

	for _, number := range numbers {
		wg.Add(1)
		go calculate(number, results, &wg)
	}

	go func() {
		wg.Wait()
		close(results)
	}()

	values := make(map[int]int, len(numbers))

	for item := range results {
		values[item.number] = item.square
	}

	for _, number := range numbers {
		fmt.Printf("Квадрат %d: %d\n", number, values[number])
	}
}
```

Результат:

```text
Квадрат 2: 4
Квадрат 3: 9
Квадрат 4: 16
```

Сначала создана структура `result`, представляющая результат:

```go
type result struct {
	number int
	square int
}
```

В каждом результате хранятся два значения:

* какое число вычислялось;
* чему равен его квадрат.

Например:

```go
result{
	number: 3,
	square: 9,
}
```

Функция `calculate` принимает одно число:

```go
func calculate(number int, results chan<- result, wg *sync.WaitGroup)
```

`results chan<- result` означает, что эта функция только отправляет значения `result` в канал.

А `wg *sync.WaitGroup` используется, чтобы сообщить `main`, что работа завершена.

В начале функции написано:

```go
defer wg.Done()
```

Это гарантирует вызов `wg.Done()` при завершении функции `calculate`.

Затем результат вычисляется и отправляется в канал:

```go
results <- result{
	number: number,
	square: number * number,
}
```

Внутри `main` есть три числа:

```go
numbers := []int{2, 3, 4}
```

Цикл запускает горутину для каждого:

```go
for _, number := range numbers {
	wg.Add(1)
	go calculate(number, results, &wg)
}
```

Перед запуском каждой горутины вызывается:

```go
wg.Add(1)
```

Значит, `WaitGroup` ждёт завершения трёх работ.

Здесь возникает важный вопрос: кто и когда закроет канал `results`?

Канал нужно закрыть после завершения всех воркеров.

Поэтому создана отдельная горутина:

```go
go func() {
	wg.Wait()
	close(results)
}()
```

Эта горутина:

1. ждёт завершения всех горутин `calculate`;
2. затем закрывает канал `results`.

А основная горутина `main` в это время принимает результаты:

```go
for item := range results {
	values[item.number] = item.square
}
```

`range` продолжает работать, пока канал не закрыт и пока из него не взяты все значения.

Например, результаты могут прийти в канал в таком порядке:

```text
4 -> 16
2 -> 4
3 -> 9
```

или:

```text
3 -> 9
4 -> 16
2 -> 4
```

Нет гарантии, какая из горутин завершится первой.

Поэтому результаты собираются в `map`:

```go
values[item.number] = item.square
```

Затем при выводе используется порядок slice `numbers`:

```go
for _, number := range numbers {
	fmt.Printf("Квадрат %d: %d\n", number, values[number])
}
```

Поэтому, хотя результаты приходили в канал в разном порядке, на экране они всегда выводятся в таком порядке:

```text
Квадрат 2: 4
Квадрат 3: 9
Квадрат 4: 16
```

В этом примере есть и очень важная ситуация взаимоблокировки.

Если бы было написано так:

```go
wg.Wait()

for item := range results {
	// ...
}
```

могла бы возникнуть проблема.

Разберём причину по шагам.

`results` — небуферизованный канал:

```go
results := make(chan result)
```

Каждый воркер пытается отправить значение на строке:

```go
results <- result{...}
```

Но в небуферизованном канале для работы send нужен одновременно и получатель.

Если `main` сначала выполнит:

```go
wg.Wait()
```

она ещё не начнёт принимать результаты.

Тогда ситуация будет такой:

```text
горутины-воркеры:
    results <- ...
    ждут получателя

main:
    wg.Wait()
    ждёт завершения воркеров
```

Поскольку воркеры не могут отправить значения, они не доходят до `Done()`.

А `main` ждёт, пока воркеры вызовут `Done()`.

В результате они ждут друг друга.

Поэтому `wg.Wait()` и `close(results)` выполняются в отдельной горутине.

Одновременно с этим `main` принимает значения через `range`.

## Закрытие канала

Канал можно закрыть так:

```go
close(ch)
```

Смысл `close(ch)`:

> Через этот канал больше не будет отправлено новых значений.

Закрытие канала не удаляет его из памяти.

Кроме того, `close` — не команда принимающим горутинам «остановиться».

Он лишь сообщает, что больше отправок в канал не будет.

Канал обычно закрывает сторона, которая производит значения.

Например:

```text
producer -> channel -> consumer
```

В этом случае производитель знает, что больше не будет отправлять значения. Поэтому ответственность за закрытие канала обычно лежит на производителе.

Если производителей несколько:

```text
producer 1 \
producer 2  -> channel -> consumer
producer 3 /
```

отдельная координирующая горутина может дождаться завершения всех и затем закрыть канал.

В предыдущем примере:

```go
go func() {
	wg.Wait()
	close(results)
}()
```

выполнял именно эту задачу.

Потребитель обычно не должен закрывать канал.

Причина в том, что потребитель не всегда знает, будут ли другие производители ещё отправлять значения.

Если потребитель закроет канал раньше времени, а производитель потом выполнит:

```go
ch <- value
```

программа вызовет panic.

При работе с закрытым каналом есть несколько важных правил.

### Значения, оставшиеся в буфере, будут получены

Если закрыть буферизованный канал, значения в нём не пропадают.

Например:

```go
ch := make(chan int, 2)

ch <- 10
ch <- 20
close(ch)
```

Хотя канал закрыт:

```go
fmt.Println(<-ch)
fmt.Println(<-ch)
```

сначала даёт значения:

```text
10
20
```

### Когда значения закончились, возвращается нулевое значение

Если канал закрыт и в нём не осталось значений, получение не блокируется.

Оно сразу возвращает нулевое значение (`zero value`) типа элементов.

Например, для `chan int` нулевое значение:

```text
0
```

Для `chan string`:

```text
""
```

Для `chan bool`:

```text
false
```

### Отправка в закрытый канал вызывает panic

Следующий код неправильный:

```go
ch := make(chan int)
close(ch)

ch <- 10
```

`ch` уже закрыт. Повторная отправка значения в него вызывает panic во время выполнения.

### Повторное закрытие канала вызывает panic

Следующий код тоже неправильный:

```go
ch := make(chan int)

close(ch)
close(ch)
```

Канал можно закрыть только один раз.

Второй `close(ch)` вызывает panic.

### Закрытие `nil`-канала вызывает panic

Например:

```go
var ch chan int

close(ch)
```

Здесь `ch == nil`.

Попытка закрыть `nil`-канал вызывает panic.

### Как узнать, что канал закрыт?

Проблема в том, что закрытый канал при получении возвращает нулевое значение.

Например:

```go
value := <-ch
```

Представим, что получилось `value == 0`.

Это может означать одно из двух:

1. через канал действительно отправили `0`;
2. канал закрыт, и значения закончились.

Чтобы различить эти два случая, используется получение с двумя значениями:

```go
value, ok := <-ch
```

Например:

```go
value, ok := <-ch
if !ok {
	// Канал закрыт, и в нём больше нет значений.
}
```

Здесь `ok` сообщает состояние канала.

Если:

```text
ok == true
```

то `value` — настоящее значение из канала.

Если:

```text
ok == false
```

то канал закрыт и брать из него больше нечего.

В этом случае `value` — нулевое значение типа элементов.

Например, результат:

```go
value, ok := <-ch
```

может быть:

```text
value = 0
ok = false
```

Поэтому проверять только:

```go
if value == 0 {
	// канал закрыт
}
```

неправильно.

Потому что `0` тоже мог быть отправлен как настоящие данные.

## Получение через `range`

Для последовательного получения значений из канала очень удобен `range`:

```go
for value := range ch {
	fmt.Println(value)
}
```

Этот цикл принимает значения, пришедшие через канал, по одному.

Например, если:

```go
ch <- 10
ch <- 20
ch <- 30
close(ch)
```

то `range` получает значения:

```text
10
20
30
```

Когда канал закрыт и все значения в нём закончились, цикл завершается автоматически.

На деле это похоже на более удобную форму цикла, написанного с `value, ok := <-ch`.

Логически это близко к:

```go
for {
	value, ok := <-ch
	if !ok {
		break
	}

	fmt.Println(value)
}
```

Здесь есть важная тонкость.

Если канал, используемый в `range`, не закрыт, цикл может продолжать ждать следующее значение.

Например:

```go
for value := range ch {
	fmt.Println(value)
}
```

все значения отправлены в канал, но `close(ch)` не вызван.

Цикл не получает сигнала «больше значений не будет». Поэтому он застревает в ожидании на следующем получении.

Но из этого не следует правило «каждый канал обязательно нужно закрывать».

Канал нужно закрывать только тогда, когда получатель должен узнать, что поток закончился.

Например, если канал — постоянный поток событий, используемый всё время работы программы, закрывать его в какой-то конкретный момент может быть не нужно.

## `nil`-канал

Нулевое значение типа канала — `nil`.

Например:

```go
var ch chan int
```

Здесь:

```go
ch == nil
```

`nil`-канал — это не рабочий, но пустой канал.

Эти две ситуации нельзя путать.

Следующий канал — настоящий канал:

```go
ch := make(chan int)
```

Даже если сейчас в нём нет значения, если появится другая горутина и выполнит send или receive, операция может продолжиться.

А в `nil`-канале, созданном через:

```go
var ch chan int
```

send и receive блокируются навсегда.

Например:

```go
var ch chan int

ch <- 10
```

Эта отправка никогда не завершится успешно.

Потому что у `nil`-канала на другой стороне нет самой реальной структуры канала, где мог бы сработать receive.

Точно так же:

```go
var ch chan int

value := <-ch
```

получение тоже блокируется навсегда.

Неправильный пример:

```go
// Неправильный пример: никогда не продолжится.
// var ch chan int
// ch <- 10
```

Это поведение иногда используется намеренно.

Например, внутри `select` можно присвоить переменной канала `nil`, чтобы временно отключить определённый case.

Причина в том, что send или receive на `nil`-канале никогда не становится готовым.

Этот приём подробно рассматривается в теме о `select`.

## Каналы и синхронизация памяти

Одна из важных задач канала — синхронизация видимости памяти.

Проще говоря, если одна горутина записала какие-то данные до send, а другая горутина выполнила соответствующий receive, то после завершения receive она может увидеть предыдущие записи.

Например:

```go
data := 0
ch := make(chan struct{})

go func() {
	data = 42
	ch <- struct{}{}
}()

<-ch
fmt.Println(data)
```

Здесь воркер сначала выполняет:

```go
data = 42
```

Затем отправляет сигнал через:

```go
ch <- struct{}{}
```

А `main` принимает сигнал через:

```go
<-ch
```

Благодаря синхронизации через канал после завершения receive записи воркера, сделанные до send, становятся видны на принимающей стороне.

Здесь через канал отправлено не само `42`. Отправлен только сигнал.

Тем не менее send и receive создают нужную точку синхронизации между горутинами.

Но из этого не следует, что потом две горутины могут одновременно изменять один объект.

Например:

```go
items := []int{1, 2, 3}
ch := make(chan []int)

go func() {
	ch <- items
}()
```

Через канал отправлен slice.

Но slice не копирует глубоко весь свой базовый массив. Отправитель и получатель могут ссылаться на один и тот же базовый массив.

Если потом обе горутины одновременно сделают запись вроде:

```go
items[0] = ...
```

может возникнуть `data race`.

Поэтому как практическое правило полезен следующий подход:

> После отправки значения через канал передайте владение им получателю.

То есть после отправки отправитель не должен снова изменять эти изменяемые данные.

Если данные должны использоваться совместно несколькими горутинами, конкурентное изменение нужно защитить `mutex` или другим подходящим средством синхронизации.

## Ситуация, ведущая к взаимоблокировке

В следующей программе создан небуферизованный канал:

```go
package main

func main() {
	ch := make(chan int)
	ch <- 10
}
```

Код компилируется.

Но во время выполнения программа не может продолжиться.

Runtime обычно выводит сообщение вроде:

```text
fatal error: all goroutines are asleep - deadlock!
```

Разберём причину по шагам.

Сначала создаётся канал:

```go
ch := make(chan int)
```

Это небуферизованный канал.

Затем выполняется:

```go
ch <- 10
```

Для send в небуферизованный канал на другой стороне нужен receive.

Например:

```go
value := <-ch
```

Но в программе нет другой горутины.

Сама `main` заблокирована на строке отправки.

Ситуация такая:

```text
горутина main:
    ch <- 10
    |
    +-- ждёт получателя

другие готовые горутины:
    нет
```

Поскольку в программе не осталось другой горутины, способной продолжить работу, Go runtime обнаруживает взаимоблокировку.

Но не стоит думать, что это сообщение обязательно появится при любой взаимоблокировке.

Например, в реальном сервере некоторые горутины могут ждать:

* сетевой сокет;
* таймер;
* внешний ввод-вывод;
* другое событие runtime.

Даже если программа логически где-то застряла, runtime может не считать, что все горутины полностью уснули.

Поэтому логическая взаимоблокировка не всегда сразу приводит к сообщению:

```text
fatal error: all goroutines are asleep - deadlock!
```

## Частые ошибки

### Канал закрывает не та сторона

Кто закрывает канал, должно быть ясно заранее.

Обычно канал закрывает сторона, отправляющая значения.

Если получатель сам закроет канал, другой отправитель может ещё работать.

Например:

```text
sender 1 ----\
sender 2 -----> channel ---> receiver
sender 3 ----/
```

Представим, что получатель закрыл канал.

В это время `sender 3` мог ещё не успеть выполнить:

```go
ch <- value
```

Если отправитель отправит значение после закрытия канала, произойдёт panic.

Поэтому ответственность за закрытие лучше оставлять на стороне:

* единственного отправителя;
* или координатора, который знает, что все отправители завершились.

### Принудительное закрытие каждого канала

Новички иногда думают, что после каждого `make(chan T)` где-то обязательно должен быть `close`.

Это неправильно.

Канал не нужно закрывать, чтобы освободить память.

Сборщик мусора может собрать неиспользуемый канал и относящуюся к нему память.

Главная задача `close` другая:

> Сообщить получателю, что новых значений больше не будет.

Например, `close` может понадобиться, чтобы сообщить `for range` об окончании потока.

Но если канал использовался только для однократной отправки сигнала и после этого к нему никто не обращается, закрывать его отдельно не всегда нужно.

### Бесконечное получение из закрытого канала

Обычное получение из закрытого канала не блокируется.

Например:

```go
ch := make(chan int)
close(ch)

fmt.Println(<-ch)
fmt.Println(<-ch)
fmt.Println(<-ch)
```

Эти получения продолжают возвращать нулевое значение `chan int`:

```text
0
0
0
```

Поэтому, если нужно знать, что поток закончился, используется:

```go
value, ok := <-ch
```

Или можно использовать:

```go
for value := range ch {
	// ...
}
```

`range` автоматически завершается, когда канал закрыт и все значения закончились.

### Думать, что канал полностью устраняет гонки данных

Использование канала не делает программу автоматически свободной от `data race`.

Например:

```go
type User struct {
	Name string
}
```

Через канал отправлен указатель:

```go
users := make(chan *User)
```

Сам указатель может безопасно передаться от одной горутины к другой.

Но если потом отправитель и получатель одновременно выполнят:

```go
user.Name = ...
```

они изменяют один и тот же объект `User`.

Канал не защищает автоматически эти последующие записи.

То же самое важно для slice и map.

Например, при отправке slice может копироваться заголовок slice, но его базовый массив остаётся общим.

А map работает через ссылку на свою внутреннюю структуру данных.

Поэтому при работе с каналами полезно думать о владении (ownership):

```text
отправитель -- отправляет значение --> получатель
отправитель -- больше его не изменяет
получатель -- становится владельцем значения
```

Если передать владение нельзя и данные остаются общими, конкурентное изменение нужно синхронизировать отдельно.

## На что обращают внимание на собеседовании?

В вопросах о каналах на собеседовании знания одного синтаксиса недостаточно. Важно понимать и их поведение при блокировке и синхронизации.

Обратите внимание на следующее:

* в небуферизованном канале send и receive могут ждать друг друга;
* помимо передачи значений, канал создаёт синхронизацию между горутинами;
* `ch <- value` отправляет значение;
* `<-ch` принимает значение;
* `chan<- T` — тип канала, разрешающий только отправку;
* отправка в закрытый канал вызывает panic;
* получение из закрытого канала сначала отдаёт оставшиеся значения;
* когда значения закончились, получение возвращает нулевое значение типа элементов;
* `value, ok := <-ch` позволяет отличить настоящее значение от закрытия канала;
* `ok == false` означает, что канал закрыт и в нём не осталось значений;
* канал обычно закрывает отправитель или координатор, который знает, что все отправители завершились;
* и send, и receive на `nil`-канале блокируются навсегда;
* `nil`-канал и созданный через `make`, но пока пустой канал — не одно и то же;
* отправка указателя, slice или map через канал не защищает внутренние данные автоматически;
* если отправленный изменяемый объект потом параллельно изменяется несколькими горутинами, может возникнуть `data race`;
* при работе с каналами должно быть заранее ясно, кто отправляет, кто принимает, кто закрывает и когда получатель останавливается.

Следующая важная часть каналов — разница между небуферизованными и буферизованными каналами. Кроме того, канал можно ограничить только отправкой или только получением. Эти свойства напрямую влияют на то, как работают трафик и синхронизация между горутинами.
