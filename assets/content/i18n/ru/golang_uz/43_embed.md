# Встраивание файлов в программу Go: `embed`

Пакет `embed` позволяет на этапе компиляции поместить файлы и каталоги внутрь исполняемого файла программы Go, то есть внутрь binary.

В обычном случае нужные программе HTML-шаблоны, SQL-миграции, конфигурация или статические файлы хранятся на диске отдельно. Во время работы программа читает эти файлы с диска.

При использовании `embed` эти файлы добавляются в binary во время сборки.

В результате не нужно переносить отдельные файлы вместе с программой.

Например, CLI-программе нужен текст справки. Его можно записать прямо в код Go в виде длинного `string`, но это неудобно:

* текст становится сложнее редактировать;
* код разрастается больше, чем нужно;
* текст и логика программы смешиваются в одном месте.

Вместо этого текст справки можно хранить в файле `help.txt`. Затем через `//go:embed` этот файл встраивается в binary.

При таком способе файл по-прежнему удобно редактировать отдельно. А пользователю достаточно отдать один binary.

Go добавил пакет `embed` в стандартную библиотеку в версии Go 1.16. Поэтому для запуска кода из этой статьи нужен Go 1.16 или новее.

## Как работает `go:embed`?

`//go:embed` — это не обычный комментарий. Это специальная директива для компилятора Go.

Например:

```go
//go:embed hello.txt
var hello string
```

Здесь компилятор работает так:

1. видит директиву `//go:embed hello.txt`.
2. во время сборки читает файл `hello.txt`.
3. добавляет содержимое файла в binary.
4. задаёт переменной `hello` содержимое этого файла в качестве начального значения.

Этот процесс происходит при `go build`, `go run` и в других случаях, когда пакет компилируется.

Директива может задать значение только переменной уровня пакета одного из следующих типов:

* `string` — для одного текстового файла;
* `[]byte` — для одного текстового или бинарного файла;
* `embed.FS` — для одного или нескольких файлов и каталогов.

Здесь есть важное различие.

Встроенные файлы не читаются с диска во время выполнения. Они заранее помещены внутрь binary.

Например, если изменить файл `hello.txt` после сборки программы, текст внутри старого binary не изменится.

Чтобы новое содержимое файла попало в binary, программу нужно пересобрать.

**Внимание**

Директиву нужно писать именно в виде `//go:embed`.

Такая запись неправильна:

```go
// go:embed hello.txt
```

Перед `go:embed` не должно быть пробела.

Директива относится к одному объявлению переменной уровня пакета. Её нельзя применить к локальной переменной внутри `func main()` или другой функции.

## Встраивание одного текстового файла как `string`

Начнём с самого простого случая.

Пусть в одном каталоге лежат два файла:

```text
.
├── hello.txt
└── main.go
```

Содержимое файла `hello.txt`:

```text
Привет, мир!
```

Теперь встроим этот файл как `string` в `main.go`:

```go
package main

import (
	_ "embed"
	"fmt"
)

//go:embed hello.txt
var hello string

func main() {
	fmt.Print(hello)
}
```

Запускаем программу в каталоге с файлами:

```bash
go run .
```

Результат:

```text
Привет, мир!
```

В этом коде `hello` объявлена на уровне пакета:

```go
var hello string
```

Директива перед ней:

```go
//go:embed hello.txt
```

сообщает компилятору, что содержимое `hello.txt` нужно поместить в `hello`.

Поэтому во время выполнения код вроде следующего не выполняется:

```go
os.ReadFile("hello.txt")
```

Чтение файла уже выполнено во время сборки.

### Зачем импортируется `_ "embed"`?

Код не использует тип `embed.FS` напрямую.

Несмотря на это, в файле Go, где используется директива `//go:embed`, пакет `embed` обязательно должен быть импортирован.

Поэтому используется пустой (blank) импорт:

```go
_ "embed"
```

Пустой импорт позволяет импортировать пакет, не используя его имя в коде.

Если используется `embed.FS`, пустой импорт не нужен:

```go
import "embed"
```

импортируется обычным способом.

### Зачем используется `fmt.Print()`?

В коде используется:

```go
fmt.Print(hello)
```

Причина в том, что в конце файла `hello.txt` может быть символ новой строки.

Если использовать:

```go
fmt.Println(hello)
```

`Println()` сам тоже добавит перевод строки.

В результате строка перенесётся дважды и может появиться лишняя пустая строка.

`embed` не изменяет байты файла. Файл попадает в `string` ровно таким, какой он есть.

## Встраивание бинарного файла как `[]byte`

Не каждый файл — это текст.

Например:

* изображение PNG или JPEG;
* сертификат;
* PDF;
* аудио;
* другие бинарные форматы

хранятся как последовательность байтов.

Такой файл удобно встраивать в тип `[]byte`:

```go
package main

import (
	_ "embed"
	"fmt"
)

//go:embed logo.png
var logo []byte

func main() {
	fmt.Printf("Размер изображения: %d байт\n", len(logo))
}
```

В одном каталоге с этой программой должен лежать `logo.png`.

Например, если размер файла `4821` байт, результат будет таким:

```text
Размер изображения: 4821 байт
```

Переменная `logo` не хранит путь к файлу.

То есть внутри неё нет имени:

```text
logo.png
```

Она хранит сами байты файла `logo.png`.

Поэтому эти байты потом можно:

* записать в HTTP-ответ;
* использовать для вычисления хеша;
* передать парсеру;
* использовать для определения формата;
* передать другой функции.

Например, `len(logo)` возвращает число байтов в файле.

### `[]byte` изменяем

`string` неизменяем (immutable), то есть отдельный байт внутри него нельзя изменить напрямую.

А `[]byte` — это slice, поэтому его элементы можно менять:

```go
logo[0] = 0
```

Но это изменение затрагивает только slice `logo` внутри текущего процесса.

Оно:

* не изменяет файл `logo.png` на диске;
* не перезаписывает сам binary;
* не изменяет встроенные данные навсегда для следующего запуска.

При перезапуске программы встроенные данные снова берутся из исходного состояния внутри binary.

> **Информация**
>
> Для `string` и `[]byte` шаблон в директиве `//go:embed` должен соответствовать ровно одному файлу.
>
> Если нужно несколько файлов или каталог, используется `embed.FS`.

## `embed.FS` для нескольких файлов

Несколько файлов нельзя поместить в один `string` или `[]byte`.

В таком случае используется `embed.FS`.

`embed.FS` — виртуальная файловая система, предназначенная только для чтения.

К файлам внутри неё можно обращаться по путям, похожим на пути файлов на диске.

Возьмём такую структуру:

```text
.
├── main.go
└── texts
    ├── file1.txt
    ├── file2.txt
    └── notes
        └── file3.txt
```

Пусть содержимое файлов будет таким:

```text
texts/file1.txt -> Первый файл
texts/file2.txt -> Второй файл
texts/notes/file3.txt -> Третий файл
```

Теперь встроим весь каталог `texts`:

```go
package main

import (
	"embed"
	"fmt"
	"io/fs"
	"log"
)

//go:embed texts
var textFiles embed.FS

func main() {
	err := fs.WalkDir(textFiles, "texts", func(path string, entry fs.DirEntry, walkErr error) error {
		if walkErr != nil {
			return walkErr
		}
		if entry.IsDir() {
			return nil
		}

		data, err := textFiles.ReadFile(path)
		if err != nil {
			return err
		}
		fmt.Printf("%s: %s\n", path, data)
		return nil
	})
	if err != nil {
		log.Fatal(err)
	}
}
```

Результат:

```text
texts/file1.txt: Первый файл
texts/file2.txt: Второй файл
texts/notes/file3.txt: Третий файл
```

В этом примере:

```go
//go:embed texts
var textFiles embed.FS
```

добавляет весь каталог `texts` во встроенную файловую систему.

Учитываются и обычные файлы внутри каталога, и вложенные каталоги.

### Что делает `fs.WalkDir()`?

Следующая строка:

```go
fs.WalkDir(textFiles, "texts", ...)
```

обходит дерево в файловой системе `textFiles`, начиная с каталога `texts`.

`WalkDir()` вызывает callback-функцию для каждого файла и каталога:

```go
func(path string, entry fs.DirEntry, walkErr error) error
```

Назначение параметров:

* `path` — путь текущего файла или каталога;
* `entry` — информация о текущем объекте;
* `walkErr` — ошибка, возникшая при обходе.

Сначала через:

```go
if walkErr != nil {
	return walkErr
}
```

проверяется ошибка, переданная `WalkDir()`.

Это важно. Если к некоторым файлам нет доступа или возникла другая проблема, игнорирование ошибки скроет проблему.

Затем через:

```go
if entry.IsDir() {
	return nil
}
```

каталоги не читаются.

Цель здесь — вывести только содержимое файлов.

Если текущий элемент — файл:

```go
data, err := textFiles.ReadFile(path)
```

читается его содержимое.

`ReadFile()` возвращает `[]byte`.

Затем:

```go
fmt.Printf("%s: %s\n", path, data)
```

выводит путь к файлу и его содержимое.

### В каком порядке обходятся файлы?

`fs.WalkDir()` обходит имена внутри каталога в отсортированном порядке.

Поэтому результат обычно выводится в порядке имён.

### `embed.FS` и `io/fs`

`embed.FS` реализует интерфейс `io/fs.FS`.

Это очень полезное свойство.

Потому что многие пакеты стандартной библиотеки умеют работать с `io/fs.FS`.

Например:

* `fs.WalkDir`;
* `fs.ReadFile`;
* `fs.ReadDir`;
* `html/template`;
* `text/template`;
* `net/http`.

Значит, для работы со встроенными файлами не нужно изучать отдельный специальный API. Во многих случаях хватает функций обычной экосистемы `io/fs`.

## Правила записи шаблонов

Значение, записанное после директивы `//go:embed`, называется шаблоном (pattern).

Например:

```go
//go:embed templates/*.html
```

здесь:

```text
templates/*.html
```

— шаблон.

Очень важно понимать, от чего отсчитывается шаблон.

Он вычисляется не относительно корня модуля, а относительно каталога пакета, к которому относится файл Go с директивой.

Например:

```text
project/
├── go.mod
└── cmd
    └── app
        ├── main.go
        └── templates
            └── index.html
```

Если в `main.go` написано:

```go
//go:embed templates/*.html
```

шаблон работает относительно каталога `cmd/app`.

Даже в Windows при записи шаблона в качестве разделителя пути используется `/`.

Например:

```go
//go:embed templates/*.html static/css/*.css
var content embed.FS
```

Здесь в одной директиве два шаблона:

```text
templates/*.html
static/css/*.css
```

Файлы, найденные по обоим шаблонам, помещаются в `content`.

То же самое можно записать и двумя директивами:

```go
//go:embed templates/*.html
//go:embed static/css/*.css
var content embed.FS
```

Оба варианта означают одно и то же.

### Важные правила шаблонов

Хотя шаблоны `go:embed` похожи на обычные пути файловой системы, у них есть ограничения.

#### Нельзя выйти за пределы пакета

Не разрешаются:

```text
/static
../static
C:/static
```

Причина в том, что встроенные файлы не должны выходить за пределы текущего пакета.

В частности, переход в родительский каталог через:

```text
../
```

не разрешён.

#### `.` не используется как шаблон

Для текущего каталога нельзя написать:

```go
//go:embed .
```

Вместо этого используется шаблон, соответствующий нужным файлам.

Например:

```go
//go:embed *
```

Но `*` не во всех случаях означает получение полного рекурсивного содержимого каталога. Правила встраивания каталогов работают отдельно.

#### Каждый шаблон должен соответствовать хотя бы одному объекту

Например, если написано:

```go
//go:embed templates/*.html
```

во время сборки должен существовать хотя бы один файл `.html`.

Если ничего не найдено, сборка остановится с ошибкой.

Это хорошее свойство. Так не создаётся binary, работающий в ситуации, когда нужный ресурс случайно пропал.

#### Некоторые каталоги и файлы не встраиваются

Обращение через шаблон к следующему ограничено:

* символические ссылки;
* `.git`;
* `vendor`;
* каталоги других модулей, внутри которых есть свой `go.mod`.

Эти ограничения помогают сохранять контекст сборки понятным и контролируемым.

#### Если в имени файла есть пробел

Шаблон можно записать в двойных кавычках:

```go
//go:embed "docs/user guide.txt"
var guide string
```

Здесь кавычки не являются частью шаблона. Они используются, чтобы правильно выразить наличие пробела.

### Разница между именем каталога и `*`

Здесь есть тонкое различие, в котором часто путаются новички.

Следующая директива:

```go
//go:embed assets
var assets embed.FS
```

рекурсивно встраивает каталог `assets`.

Но файлы и каталоги, имена которых начинаются с `.` или `_`, обычно пропускаются.

Например:

```text
assets/
├── main.css
├── .hidden
└── _internal
```

при обычной записи:

```go
//go:embed assets
```

`.hidden` и `_internal` могут не попасть внутрь.

Если такие файлы тоже нужны, используется префикс `all:`:

```go
//go:embed all:assets
var assets embed.FS
```

`all:` означает, что учитываются и скрытые объекты, и объекты, начинающиеся с подчёркивания.

Теперь посмотрим на разницу с:

```go
//go:embed assets/*
```

`assets/*` как шаблон соответствует объектам первого уровня внутри `assets`.

Поэтому он может совпасть и со скрытым файлом первого уровня.

Но при рекурсивном заходе во вложенный каталог скрытые файлы этого каталога снова подчиняются особым правилам.

Поэтому если нужен весь каталог, запись:

```go
//go:embed assets
```

обычно понятнее.

Если скрытые файлы тоже нужны полностью, понятнее использовать:

```go
//go:embed all:assets
```

## Практический пример с HTML-шаблоном

В backend-программах очень удобно встраивать HTML-шаблоны в binary.

Иначе при развёртывании нужно переносить вместе:

* binary;
* каталог `templates`;
* все нужные файлы `.html`.

При использовании `embed` шаблоны находятся внутри binary.

Пусть есть такая структура:

```text
.
├── main.go
└── templates
    └── welcome.html
```

Шаблон:

```html
<h1>Привет, {{.Name}}!</h1>
```

Теперь программа Go:

```go
package main

import (
	"embed"
	"html/template"
	"log"
	"os"
)

//go:embed templates/*.html
var templateFiles embed.FS

type PageData struct {
	Name string
}

func main() {
	tmpl, err := template.ParseFS(templateFiles, "templates/*.html")
	if err != nil {
		log.Fatal(err)
	}

	err = tmpl.ExecuteTemplate(os.Stdout, "welcome.html", PageData{Name: "Aziza"})
	if err != nil {
		log.Fatal(err)
	}
}
```

Результат:

```text
<h1>Привет, Aziza!</h1>
```

Здесь сначала через:

```go
//go:embed templates/*.html
var templateFiles embed.FS
```

все шаблоны `.html` были помещены во встроенную файловую систему.

Затем был вызван:

```go
tmpl, err := template.ParseFS(templateFiles, "templates/*.html")
```

`template.ParseFS()` читает шаблоны не с диска, а из встроенной файловой системы внутри `templateFiles`.

Это одно из главных отличий от `template.ParseFiles()`.

### Как работает `ExecuteTemplate()`?

Следующий код:

```go
tmpl.ExecuteTemplate(
	os.Stdout,
	"welcome.html",
	PageData{Name: "Aziza"},
)
```

выполняет шаблон `welcome.html`.

В шаблоне есть:

```html
{{.Name}}
```

А `PageData` передан со значением:

```go
PageData{Name: "Aziza"}
```

Поэтому вместо:

```html
{{.Name}}
```

записывается:

```text
Aziza
```

Результат:

```html
<h1>Привет, Aziza!</h1>
```

`html/template` также выполняет экранирование с учётом HTML-контекста. Это безопаснее для создания веб-страниц, чем обычный `text/template`.

### Зачем проверяются ошибки?

Если синтаксис шаблона неверен:

```go
template.ParseFS(...)
```

возвращает ошибку.

Например, если в шаблоне есть незакрытое выражение, программа не сможет его разобрать.

Поэтому нужна проверка:

```go
if err != nil {
	log.Fatal(err)
}
```

`ExecuteTemplate()` тоже может вернуть ошибку.

Например, может возникнуть:

* неверное имя шаблона;
* ошибка при записи;
* другая проблема при выполнении.

В реальном HTTP-сервере вместо:

```go
os.Stdout
```

обычно передаётся `http.ResponseWriter`.

Например:

```go
func handler(w http.ResponseWriter, r *http.Request) {
	err := tmpl.ExecuteTemplate(w, "welcome.html", PageData{
		Name: "Aziza",
	})
	if err != nil {
		http.Error(w, "template error", http.StatusInternalServerError)
	}
}
```

Здесь сгенерированный HTML записывается прямо в HTTP-ответ.

### Раздача статических файлов по HTTP

При работе со статическими файлами бывает удобно убрать верхний префикс каталога во встроенной файловой системе.

Например:

```go
staticFS, err := fs.Sub(templateFiles, "static")
if err != nil {
	return err
}

handler := http.FileServer(http.FS(staticFS))
```

Этот фрагмент — не отдельная полная программа.

Здесь:

```go
fs.Sub(templateFiles, "static")
```

возвращает файловую систему, в которой каталог `static` внутри `templateFiles` показан как новый корень.

Например, если исходный встроенный путь:

```text
static/css/main.css
```

в файловой системе после `fs.Sub()` он выглядит как:

```text
css/main.css
```

Затем:

```go
http.FS(staticFS)
```

оборачивает интерфейс `io/fs.FS` в адаптер, понятный `net/http`.

Затем:

```go
http.FileServer(...)
```

может раздавать эти файлы по HTTP.

В практическом коде вместо `templateFiles` нужно использовать `embed.FS`, в который действительно встроен каталог `static`.

Например:

```go
//go:embed static
var staticFiles embed.FS
```

а затем написать:

```go
staticFS, err := fs.Sub(staticFiles, "static")
```

— так понятнее.

## `embed.FS` только для чтения

`embed.FS` — файловая система только для чтения (read-only).

У неё есть такие методы:

```go
Open
ReadFile
ReadDir
```

Но нет методов для таких операций:

```text
WriteFile
Create
Remove
Rename
```

Причина в том, что встроенные данные помещаются в содержимое binary во время сборки.

Во время выполнения их нельзя навсегда изменить, как в обычной файловой системе.

Например, начальную конфигурацию можно встроить в binary:

```text
default-config.yaml
```

При первом запуске программа может использовать эту конфигурацию как значения по умолчанию.

Но если пользователь потом изменит конфигурацию, записать её обратно в `embed.FS` нельзя.

Такие изменяемые данные нужно хранить:

* на диске;
* в базе данных;
* в объектном хранилище;
* в другой внешней системе хранения.

Точно так же `embed` очень удобен для SQL-миграций.

Файлы миграций обычно поставляются вместе с версией приложения и не меняются во время выполнения.

Но загруженные пользователями файлы, вроде:

```text
uploads/
```

нельзя добавить в `embed.FS`.

Потому что `embed.FS` — не хранилище файлов времени выполнения.

## Частые ошибки

### Не импортировать пакет `embed`

В файле, где используется `//go:embed`, пакет `embed` обязательно должен быть импортирован.

Следующий код неправилен:

```go
// Неправильно: в этом файле не импортирован "embed".
//go:embed message.txt
var message string
```

При сборке будет получена примерно такая ошибка:

```text
go:embed requires import "embed"
```

Если встроенное значение — `string` или `[]byte`, можно использовать:

```go
import _ "embed"
```

Например:

```go
import (
	_ "embed"
	"fmt"
)
```

Если используется `embed.FS`, имя пакета нужно в коде:

```go
import "embed"

//go:embed files
var files embed.FS
```

Поэтому в этом случае используется обычный импорт, а не пустой.

### Отделение директивы от переменной

`//go:embed` относится к одному конкретному объявлению переменной.

Следующий код неправилен:

```go
// Неправильный пример.
//go:embed message.txt
const defaultName = "Go"

var message string
```

Здесь после директивы оказалось объявление:

```go
const defaultName = "Go"
```

А `go:embed` должен был относиться к переменной `message`.

Поэтому писать директиву прямо над переменной — самый понятный способ:

```go
//go:embed message.txt
var message string
```

Пустая строка или некоторые комментарии грамматически могут быть допустимы, но они запутывают код.

В практическом коде хорошая привычка — писать директиву и переменную рядом.

### Ожидание обновления внешнего файла во время выполнения

Это одно из самых важных понятий при работе с `embed`.

Предположим, программа встроила такой шаблон:

```text
templates/welcome.html
```

Затем был собран binary:

```bash
go build -o app
```

После этого файл на диске:

```text
templates/welcome.html
```

был изменён.

Старый binary:

```text
app
```

этого изменения не увидит.

Причина в том, что шаблон не читается с диска во время выполнения. Он уже внутри binary.

Чтобы использовать новый шаблон, нужно снова выполнить:

```bash
go build -o app
```

В production это может быть полезно.

Потому что развёрнутый binary и его ресурсы остаются согласованными.

Но если шаблон нужно менять во время работы программы, `embed` может не подойти.

В таком случае нужно:

* читать файл с диска;
* использовать внешнее хранилище;
* или после изменения заново собирать и развёртывать программу.

### Игнорирование ошибок

Даже если встроенный файл существовал во время сборки, в коде времени выполнения можно указать неверный путь.

Например, если встроен файл:

```text
texts/file1.txt
```

то:

```go
data, err := textFiles.ReadFile("texts/file1.txt")
```

правильно.

Но:

```go
data, err := textFiles.ReadFile("file1.txt")
```

может быть неправильно.

Причина в том, что внутри `embed.FS` путь хранится ровно по встроенной структуре.

Поэтому ошибки, возвращаемые:

* `ReadFile`;
* `ReadDir`;
* `ParseFS`;
* `fs.Sub`;
* `Open`

нужно проверять.

Например:

```go
data, err := textFiles.ReadFile("texts/file1.txt")
if err != nil {
	return err
}
```

Игнорирование ошибки затрудняет поиск проблемы с неверным путём или неверным шаблоном.

## Размер, память и безопасность

Встроенные файлы увеличивают размер binary.

Например, если binary изначально весит:

```text
8 MB
```

и к нему добавляется:

```text
20 MB
```

статических ресурсов, итоговый binary тоже заметно вырастет.

Для нескольких небольших:

* HTML-шаблонов;
* SQL-миграций;
* текстов справки CLI;
* небольших CSS;
* небольших JavaScript;
* конфигурации по умолчанию

это обычно не проблема.

Но для сотен мегабайт:

* видео;
* больших архивов;
* больших наборов данных;
* часто обновляемого контента

`embed` может быть плохим выбором.

Большой binary:

* может дольше собираться;
* передаёт больше данных по сети;
* увеличивает размер образа контейнера;
* занимает больше места в хранилище артефактов.

Такой контент часто лучше хранить во внешнем хранилище.

### Встроенный файл не является секретным

Это очень важное правило безопасности.

`embed` помещает данные внутрь binary, но не шифрует их.

Поэтому встраивать в binary следующее небезопасно:

* API-ключ;
* пароль;
* приватный ключ;
* токен доступа;
* учётные данные базы данных.

Пользователь, имеющий доступ к binary, может извлечь данные изнутри разными инструментами.

Поэтому для секретных значений нужно использовать:

* переменные окружения;
* менеджер секретов;
* секреты оркестратора;
* специальное хранилище учётных данных.

`embed` — инструмент упаковки. Это не инструмент защиты секретов.

### Воспроизводимость результата сборки

`embed` помогает хранить программу и её статические ресурсы как один артефакт.

Например:

```text
app binary
+ templates
+ migrations
+ static files
```

не развёртываются по отдельности.

Всё это находится внутри одного binary.

Это упрощает процесс развёртывания и уменьшает рассогласования вроде «binary новый, шаблон старый».

Если встроенный файл изменится, система сборки Go учтёт это изменение.

Соответствующий пакет будет пересобран, и будет создан новый binary.

Поэтому встроенный ресурс тоже рассматривается как часть исходных зависимостей.

## Важные моменты для собеседования

* `//go:embed` задаёт начальное значение только переменной уровня пакета типа `string`, `[]byte` или `embed.FS`.
* `string` и `[]byte` работают с одним шаблоном, соответствующим одному файлу.
* `embed.FS` может работать с несколькими файлами, каталогами и шаблонами.
* Шаблон вычисляется не относительно корня модуля, а относительно каталога пакета, к которому относится файл Go с директивой.
* `embed.FS` реализует интерфейс `io/fs.FS`.
* Поэтому его можно использовать со стандартными API вроде `fs.WalkDir`, `template.ParseFS`, `http.FS`.
* `embed.FS` предназначен только для чтения.
* Встроенные файлы не берутся с диска во время выполнения.
* Если исходный файл на диске изменится, копия внутри старого binary не изменится.
* Чтобы встроенный ресурс обновился, программу нужно пересобрать.
* `embed` увеличивает размер binary.
* `embed` не защищает секретные данные.
* Для небольших статических ресурсов `embed` очень удобен.
* Для большого контента, меняющегося во время выполнения, больше подходит внешнее хранилище.
