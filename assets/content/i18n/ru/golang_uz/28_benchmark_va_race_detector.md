# Бенчмарки

Бенчмарк (benchmark) помогает измерить, сколько времени занимает определённая операция в программе и сколько памяти она выделяет. Для этого измеряемый код выполняется много раз подряд.

## Написание бенчмарка

Бенчмарки Go обычно пишутся в файле `_test.go`. Имя функции-бенчмарка начинается с `Benchmark`, и она принимает `*testing.B`:

```go
package text

import (
	"strings"
	"testing"
)

var result string

func BenchmarkJoin(b *testing.B) {
	parts := []string{"go", "lang", "uz"}
	b.ReportAllocs()

	for i := 0; i < b.N; i++ {
		result = strings.Join(parts, "-")
	}
}
```

Этот бенчмарк измеряет производительность операции `strings.Join()`.

Важная строка:

```go
for i := 0; i < b.N; i++ {
```

Здесь `b.N` — не обычное заранее заданное число. Его значением управляет сам запускатель бенчмарков.

Сначала `b.N` может быть небольшим. Затем Go снова и снова запускает бенчмарк и увеличивает `b.N`. Цель — чтобы измерение длилось достаточно долго, а результат был относительно стабильным.

Поэтому внутри бенчмарка обычно используется такая форма:

```go
for i := 0; i < b.N; i++ {
	// измеряемая операция
}
```

Результат бенчмарка записывается в переменную уровня пакета `result`:

```go
var result string
```

и:

```go
result = strings.Join(parts, "-")
```

Причина — показать компилятору, что результат бенчмарка используется. Если вычисленное значение нигде не используется, компилятор в некоторых случаях может выбросить ненужное вычисление при оптимизации.

Бенчмарк можно запустить так:

```bash
go test -bench=.
```

Эта команда запускает бенчмарки текущего пакета.

Чтобы видеть и информацию о выделениях памяти,
используется:

```bash
go test -bench=. -benchmem
```

В результате бенчмарка могут встречаться такие показатели:

* `ns/op` — сколько наносекунд в среднем заняла одна операция;
* `B/op` — сколько байт памяти в среднем выделено на одну операцию;
* `allocs/op` — сколько выделений (allocation) в среднем произошло за одну операцию.

Например, результат может выглядеть так:

```text
BenchmarkJoin-8    12000000    95.0 ns/op    16 B/op    1 allocs/op
```

Точные числа здесь меняются в зависимости от компьютера, версии Go и среды.

`b.ReportAllocs()` просит добавить информацию о выделениях в результат бенчмарка:

```go
b.ReportAllocs()
```

Ту же информацию можно вывести и из командной строки через `-benchmem`.

В бенчмарке может быть и одноразовый код подготовки. Например, если нужно создать большой slice или заранее подготовить тестовые данные, это время может не относиться к основной измеряемой операции.

В таком случае подготовку можно выполнить до цикла, а затем вызвать:

```go
b.ResetTimer()
```

`ResetTimer()` сбрасывает время и статистику бенчмарка, накопленные до него. После этого начинается основное измерение.

## Правильная интерпретация результатов

Увидеть результат бенчмарка легко. А правильно его интерпретировать требует отдельного внимания.

Бенчмарк даёт результат только для именно проверенных:

* кода;
* входных данных;
* компьютера;
* версии Go;
* операционной системы;
* состояния CPU;
* других процессов.

Поэтому неправильно делать из результата микробенчмарка вывод:

> Это решение и на реальном сервере будет работать ровно так же быстро.

Микробенчмарк обычно измеряет очень маленькую операцию в изоляции. А в реальной программе есть и другие затраты:

* сетевой ввод-вывод;
* база данных;
* диск;
* блокировки;
* планировщик;
* сборщик мусора;
* другие горутины;
* разбор запросов;
* сериализация.

Поэтому микробенчмарк может быть полезен для сравнения двух реализаций, но сам по себе не доказывает общую задержку (latency), которую видит пользователь.

В микробенчмарках часто встречаются следующие ошибки.

### Компилятор может выбросить вычисление

Если результат нигде не используется, компилятор может счесть некоторые вычисления ненужными.

Например, если значение только вычисляется и потом не используется, есть вероятность, что бенчмарк измеряет не реальную работу.

Поэтому во многих бенчмарках важный результат записывают в переменную уровня пакета или другое наблюдаемое извне место.

### Подготовка может быть дороже основной операции

Представьте, что вы хотите измерить один поиск в map. Но если на каждой итерации создавать огромный map, большая часть результата будет измерять время создания map.

Такой бенчмарк показывает в основном стоимость подготовки, а не ту операцию, которую вы имели в виду.

Поэтому может понадобиться выполнить подготовку отдельно или временно остановить таймер.

### Слишком простые данные могут не отражать реальную ситуацию

Например, бенчмарк, работающий со slice из 3 элементов, может не полностью отражать поведение slice из миллиона элементов в production.

Точно так же постоянно одна и та же строка или данные, которые всегда лежат в кеше, могут отличаться от реальной нагрузки.

### Состояние компьютера влияет на результат

Фоновые процессы, изменение частоты CPU, тепловой троттлинг и состояние планировщика могут менять результат бенчмарка.

Поэтому опираться на одно измерение — плохая идея.

При сравнении бенчмарков полезно запускать их несколько раз:

```bash
go test -bench=. -count=5
```

Важно получать результаты «до» и «после» по возможности в одинаковой среде.

Сначала нужно измерить проблему. Затем нужно оптимизировать узкое место, которое действительно важно для производительности.

Выигрыш нескольких наносекунд только в микробенчмарке не всегда даёт заметную пользу для реальной программы.

## Примеры

### 1. Измерение суммы целых чисел

Этот пример показывает написание бенчмарка в обычном файле `_test.go`.

Бенчмарк многократно выполняет операцию суммирования чисел от `1` до `100`.

```go
package benchmark

import "testing"

var sumResult int

func BenchmarkSum(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sum := 0

		for number := 1; number <= 100; number++ {
			sum += number
		}

		sumResult = sum
	}
}
```

Сначала пишется:

```go
sum := 0
```

Причина, по которой сумма начинается с `0`, проста:

```text
0 + x = x
```

Прибавление `0` не меняет результат.

Следующий цикл:

```go
for number := 1; number <= 100; number++ {
	sum += number
}
```

пошагово увеличивает значение `number`:

```text
1
2
3
...
99
100
```

Поскольку здесь использовано `<= 100`, `100` тоже входит в сумму.

После завершения вычисления выполняется:

```go
sumResult = sum
```

`sumResult` объявлена как глобальная переменная:

```go
var sumResult int
```

Это записывает результат бенчмарка в наблюдаемое извне место. В результате снижается вероятность того, что компилятор выбросит всё вычисление как неиспользуемый код.

Главное правило в этом примере — основная операция внутри бенчмарка выполняется `b.N` раз.

### 2. Стоимость объединения строк через `+`

В этом примере измеряется объединение нескольких строк оператором `+`.

```go
package benchmark

import "testing"

var textResult string

func BenchmarkStringPlus(b *testing.B) {
	b.ReportAllocs()

	for i := 0; i < b.N; i++ {
		textResult = "Go" + " " + "programming" + " " + "language"
	}
}
```

Здесь:

```go
b.ReportAllocs()
```

добавляет в результат бенчмарка информацию о выделениях.

Команда `go test -bench=. -benchmem` показывает, сколько выделений в среднем приходится на одну операцию.

Но в этом примере есть тонкость.

Все объединяемые части — константные строки:

```go
"Go"
" "
"programming"
" "
"language"
```

Компилятор может заранее объединить такое выражение на этапе компиляции.

То есть, хотя в исходном коде написано:

```go
"Go" + " " + "programming" + " " + "language"
```

во время выполнения не обязательно каждый раз выполняется отдельная конкатенация строк.

Поэтому результат этого бенчмарка не даёт общего вывода:

> В целом оператор `+` всегда делает столько выделений при объединении строк.

Он измеряет поведение только именно этой формы кода.

### 3. Резервирование ёмкости для `strings.Builder`

В этом примере строка строится с помощью `strings.Builder`.

Ёмкость, которая понадобится builder, заранее задаётся через `Grow()`.

```go
package benchmark

import (
	"strings"
	"testing"
)

var builderResult string

func BenchmarkBuilder(b *testing.B) {
	b.ReportAllocs()

	for i := 0; i < b.N; i++ {
		var builder strings.Builder

		builder.Grow(18)
		builder.WriteString("Go")
		builder.WriteString(" language basics")

		builderResult = builder.String()
	}
}
```

Сначала создаётся пустой builder:

```go
var builder strings.Builder
```

Затем вызывается:

```go
builder.Grow(18)
```

Итоговая строка:

```text
Go language basics
```

Её длина — `18` байт. (Здесь намеренно используется ASCII-текст: каждая кириллическая буква в UTF-8 занимает 2 байта, и расчёт длины был бы другим.)

Поэтому builder заранее сообщается, что ему нужно как минимум `18` байт ёмкости.

Затем записываются две части:

```go
builder.WriteString("Go")
builder.WriteString(" language basics")
```

Если зарезервированной ёмкости достаточно, builder может не понадобиться дополнительное выделение для увеличения буфера.

Итоговая строка получается через:

```go
builderResult = builder.String()
```

Этот пример показывает главную цель `Grow()`: если нужный размер оценён заранее, можно сократить лишние выделения при росте буфера.

### 4. Исключение времени подготовки через `ResetTimer()`

В этом примере перед бенчмарком подготавливается slice.

Создание и заполнение slice — не основная измеряемая операция. Поэтому это время исключается из измерения.

```go
package benchmark

import "testing"

var lastValue int

func BenchmarkLastValue(b *testing.B) {
	numbers := make([]int, 1000)

	for i := range numbers {
		numbers[i] = i
	}

	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		lastValue = numbers[len(numbers)-1]
	}
}
```

Сначала через:

```go
numbers := make([]int, 1000)
```

создаётся slice длиной `1000`.

Его допустимые индексы:

```text
0
1
2
...
998
999
```

Затем slice заполняется значениями индексов:

```go
for i := range numbers {
	numbers[i] = i
}
```

После этого вызывается:

```go
b.ResetTimer()
```

Подготовка до этой точки не включается во время бенчмарка.

В основной операции бенчмарка используется:

```go
numbers[len(numbers)-1]
```

Значение `len(numbers)`:

```text
1000
```

Поэтому получается:

```text
len(numbers) - 1
1000 - 1
999
```

Значит, берётся последний элемент.

Главное правило в этом примере — отделять стоимость подготовки от бенчмарка с помощью `ResetTimer()`.

### 5. Временная остановка на время подготовки

В этом примере таймер останавливается вручную, а затем снова запускается.

```go
package benchmark

import "testing"

var lookupResult bool

func BenchmarkLookup(b *testing.B) {
	b.StopTimer()

	values := map[string]int{
		"go":  1,
		"api": 2,
	}

	b.StartTimer()

	for i := 0; i < b.N; i++ {
		_, lookupResult = values["go"]
	}
}
```

Сначала:

```go
b.StopTimer()
```

временно останавливает таймер.

Затем создаётся map:

```go
values := map[string]int{
	"go":  1,
	"api": 2,
}
```

В этом примере создание map — не измеряемая операция.

Поэтому, когда map готов, таймер бенчмарка снова запускается через:

```go
b.StartTimer()
```

А внутри цикла:

```go
_, lookupResult = values["go"]
```

выполняет поиск в map.

Поиск в map может вернуть два значения:

```go
value, ok := values["go"]
```

В этом примере само значение не нужно. Поэтому первый результат отброшен через `_`.

`lookupResult` хранит, найден ли ключ.

В этом map `"go"` есть, поэтому значение будет `true`.

Этот пример показывает разделение подготовки и основной операции бенчмарка с помощью таймера.

### 6. Указание объёма входных данных через `SetBytes()`

В некоторых бенчмарках важно не только, сколько времени заняла одна операция, но и сколько данных было обработано.

В таких случаях используется `SetBytes()`.

```go
package benchmark

import (
	"strings"
	"testing"
)

var containsResult bool

func BenchmarkContains(b *testing.B) {
	text := strings.Repeat("a", 1024)

	b.SetBytes(int64(len(text)))

	for i := 0; i < b.N; i++ {
		containsResult = strings.Contains(text, "z")
	}
}
```

Сначала через:

```go
text := strings.Repeat("a", 1024)
```

создаётся строка из `1024` символов `a`.

Поскольку это символы ASCII, каждый занимает один байт.

Значит, размер строки:

```text
1024 байта
```

`1024` байта равны:

```text
1 KiB
```

Затем:

```go
b.SetBytes(int64(len(text)))
```

сообщает запускателю бенчмарков, сколько примерно байтов обрабатывается в каждой операции.

Основная операция:

```go
strings.Contains(text, "z")
```

В тексте нет `z`.

Поэтому поиск не находит подходящего символа и для этого ввода продолжает искать по всей строке.

`SetBytes()` позволяет вычислить в результате бенчмарка показатель пропускной способности (throughput), например `MB/s`.

Это особенно полезно для кода, который занимается разбором, кодированием, хешированием или работает с большими буферами.

### 7. Вывод собственного показателя

Бенчмарки Go не ограничены стандартными показателями `ns/op` или выделениями.

Через `ReportMetric()` можно вывести и нужный вам показатель.

```go
package benchmark

import "testing"

var productResult int

func BenchmarkProduct(b *testing.B) {
	numbers := []int{2, 3, 4, 5}

	b.ReportMetric(float64(len(numbers)), "elements/op")

	for i := 0; i < b.N; i++ {
		product := 1

		for _, number := range numbers {
			product *= number
		}

		productResult = product
	}
}
```

Здесь slice:

```go
numbers := []int{2, 3, 4, 5}
```

состоит из четырёх элементов.

Поэтому результат:

```go
len(numbers)
```

равен:

```text
4
```

Затем:

```go
b.ReportMetric(float64(len(numbers)), "elements/op")
```

добавляет в результат бенчмарка показатель в смысле:

```text
4 elements/op
```

А произведение начинается с:

```go
product := 1
```

Причина:

```text
1 × x = x
```

`1` — нейтральное значение для умножения.

Шаги вычисления:

```text
1 × 2 = 2
2 × 3 = 6
6 × 4 = 24
24 × 5 = 120
```

Итоговый результат:

```text
120
```

Этот пример показывает, что в бенчмарк можно добавить свой показатель, полезный для предметной области.

### 8. Многократный повтор бенчмарка

Результат одного бенчмарка может случайно оказаться быстрее или медленнее обычного.

Поэтому при сравнении производительности полезно запускать бенчмарк несколько раз.

```go
package benchmark

import "testing"

var compareResult int

func BenchmarkCalculation(b *testing.B) {
	a, multiplier, extra := 25, 4, 10

	for i := 0; i < b.N; i++ {
		compareResult = (a * multiplier) + extra
	}
}
```

В этом примере выполняется вычисление:

```go
(25 * 4) + 10
```

По шагам:

```text
25 × 4 = 100
100 + 10 = 110
```

Но главная мысль этого примера — не само вычисление. Главная цель — показать многократный повтор бенчмарка.

Настоящий бенчмарк из `_test.go` можно выполнить пять раз так:

```bash
go test -bench=. -count=5
```

Здесь:

```text
-count=5
```

повторяет запуск бенчмарка пять раз.

Почему это полезно?

Потому что отдельный результат может получиться под влиянием временных факторов:

* другой процесс может использовать CPU;
* планировщик мог распределить работу иначе;
* частота CPU могла измениться;
* состояние кеша может отличаться.

Несколько измерений помогают увидеть разброс результата.

Но сравниваемые бенчмарки должны выполняться по возможности в одинаковой среде.

Обнаружение гонок данных (data race) в конкурентном коде отдельно рассматривается в уроке о Race detector.
