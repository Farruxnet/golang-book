# Ожидание горутин с `sync.WaitGroup`

`sync.WaitGroup` — средство синхронизации, которое используется, чтобы дождаться, пока группа горутин завершит работу.

Его задача проста: он считает, сколько работ ещё не завершено. Когда это число падает до нуля, все зарегистрированные работы считаются завершёнными, и ожидающая горутина продолжает работу.

В предыдущих темах мы видели важную ситуацию: когда функция `main()` завершается, завершается и программа. Go не ждёт автоматически завершения других горутин.

Например, если запустить горутину, а затем `main()` сразу вернётся, вспомогательная горутина может не успеть закончить работу.

Иногда, чтобы этого избежать, используют `time.Sleep`:

```go
time.Sleep(time.Second)
```

Но это ненадёжное решение.

Если работа продлится дольше секунды, программа всё равно может завершиться раньше. Если работа закончится за 10 миллисекунд, программа будет впустую ждать оставшееся время.

`WaitGroup` же не угадывает время. Он отслеживает, что работа действительно завершилась.

## Как работает `WaitGroup`?

В классическом способе работы с `WaitGroup` в основном используются три метода:

* `Add(n)` — добавляет `n` к счётчику незавершённых работ;
* `Done()` — уменьшает счётчик на единицу;
* `Wait()` — заставляет текущую горутину ждать, пока счётчик не станет нулём.

Обычный рабочий процесс такой:

1. Сначала выполняемая работа добавляется в счётчик.
2. Затем запускается горутина.
3. Закончив работу, горутина вызывает `Done()`.
4. Ожидающий код через `Wait()` ждёт завершения всех работ.
5. Когда счётчик падает до нуля, `Wait()` возвращается.

Например, если должны работать три горутины, счётчик логически меняется так:

```text
Начало:
counter = 0

Add(3):
counter = 3

горутина 1 Done():
counter = 2

горутина 2 Done():
counter = 1

горутина 3 Done():
counter = 0

Wait() продолжает
```

Нулевое значение `WaitGroup` готово к использованию.

Поэтому отдельный конструктор вызывать не нужно:

```go
var wg sync.WaitGroup
```

После этой записи можно сразу использовать методы `wg.Add()`, `wg.Done()` и `wg.Wait()`.

## `WaitGroup.Go()` в Go 1.25 и новее

Начиная с Go 1.25, у `WaitGroup` есть и метод `Go()`. Он увеличивает счётчик, запускает новую горутину и автоматически уменьшает счётчик, когда функция завершается.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup

	for i := 1; i <= 5; i++ {
		id := i
		wg.Go(func() {
			fmt.Println("Привет!", id)
		})
	}

	wg.Wait()
	fmt.Println("Все горутины завершились")
}
```

При таком способе не нужно отдельно писать `wg.Add(1)`, `go` и `wg.Done()`. Не вызывайте `Done()` повторно внутри функции, переданной в `Go()`, иначе счётчик уменьшится лишний раз. Эта функция не должна вызывать panic.

Знать методы `Add()` и `Done()` всё равно важно. Они встречаются в коде для Go 1.24 и более старых версий, а также в случаях, когда работа уже запущена в другом месте. В следующих примерах рассмотрим и классический способ.

## Первый пример

Следующая программа запускает пять горутин. А `main()` ждёт, пока все они завершатся.

```go
package main

import (
	"fmt"
	"sync"
)

func greet(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("Привет!", id)
}

func main() {
	var wg sync.WaitGroup

	for i := 1; i <= 5; i++ {
		wg.Add(1)
		go greet(i, &wg)
	}

	wg.Wait()
	fmt.Println("Все горутины завершились")
}
```

Один из возможных вариантов вывода:

```text
Привет! 5
Привет! 1
Привет! 2
Привет! 3
Привет! 4
Все горутины завершились
```

Теперь разберём код по шагам.

Сначала создаётся `WaitGroup`:

```go
var wg sync.WaitGroup
```

Счётчик изначально `0`.

На каждой итерации цикла вызывается:

```go
wg.Add(1)
```

Это сообщает, что есть новая незавершённая работа.

После первой итерации:

```text
counter = 1
```

После второй итерации:

```text
counter = 2
```

А после пятой итерации:

```text
counter = 5
```

После этого запускается горутина:

```go
go greet(i, &wg)
```

Обратите внимание, что здесь используется `&wg`. В функцию передаётся не копия `WaitGroup`, а указатель на него.

Поэтому все горутины работают с одним и тем же `WaitGroup`.

Внутри `greet()` написано:

```go
defer wg.Done()
```

`Done()` уменьшает счётчик на единицу.

Например:

```text
5 -> 4 -> 3 -> 2 -> 1 -> 0
```

Из-за `defer` `Done()` выполняется перед завершением функции.

А строка внутри `main()`:

```go
wg.Wait()
```

ждёт, пока счётчик не упадёт до нуля.

Только после того как все пять горутин вызовут `Done()`, выполняется строка:

```go
fmt.Println("Все горутины завершились")
```

Порядок строк приветствия не гарантирован.

Например, они могут вывестись и так:

```text
Привет! 3
Привет! 2
Привет! 5
Привет! 1
Привет! 4
Все горутины завершились
```

Причина в том, что горутины планирует планировщик Go. Какая горутина первой получит время CPU, заранее не гарантируется.

Но одно гарантировано: строка `"Все горутины завершились"` выводится после завершения всех вызовов `greet()`.

## Почему `Done()` обычно пишут с `defer`?

`Done()` на деле уменьшает счётчик на единицу.

Следующие две операции по смыслу одинаковы:

```go
wg.Done()
```

и:

```go
wg.Add(-1)
```

Но в практическом коде использовать `Done()` гораздо понятнее.

Его можно просто вызвать и в конце функции:

```go
func work(wg *sync.WaitGroup) {
	doSomething()
	wg.Done()
}
```

Этот код работает.

Проблема начинается, когда функция может вернуться из нескольких мест.

Например:

```go
func work(value int, wg *sync.WaitGroup) {
	if value < 0 {
		return
	}

	wg.Done()
}
```

Здесь при `value < 0` функция не доходит до `wg.Done()`.

В результате счётчик `WaitGroup` не уменьшается.

Поэтому обычно пишут так:

```go
func work(wg *sync.WaitGroup) {
	defer wg.Done()

	// По какому бы пути return ни вышла функция,
	// Done будет вызван перед её возвратом.
}
```

`defer` откладывает вызов до завершения функции.

Поэтому, откуда бы функция ни вышла обычным `return`, `Done()` выполнится.

Это особенно полезно в функциях с несколькими `return`.

Но здесь есть тонкость.

Если функция вообще не возвращается, например навсегда блокируется, отложенный `Done()` тоже не выполнится.

Пример:

```go
func work(wg *sync.WaitGroup) {
	defer wg.Done()

	select {}
}
```

`select {}` блокируется навсегда. Функция не завершается. Значит, и `Done()` не вызывается.

Ещё одна ситуация — `panic`.

Если внутри функции происходит `panic`, во время раскрутки стека выполняются отложенные функции. Значит, `wg.Done()` может быть вызван.

Но если `panic` не восстановлен (recover), программа после этого всё равно остановится.

## Вызывайте `Add` до запуска горутины

Одно из самых важных правил при работе с `WaitGroup`:

> Положительный вызов `Add` нужно выполнить до запуска горутины.

Следующая запись неправильна:

```go
// Неправильный пример:
// go func() {
//     wg.Add(1)
//     defer wg.Done()
//     work()
// }()
// wg.Wait()
```

На первый взгляд этот код может показаться логичным.

Горутина запускается, добавляет себя в счётчик, выполняет работу и вызывает `Done()`.

Но когда выполняются горутины, решает планировщик.

Может случиться такая последовательность:

```text
1. main создаёт новую горутину.
2. Новая горутина ещё не получила CPU.
3. main вызывает wg.Wait().
4. Счётчик WaitGroup всё ещё 0.
5. Wait() сразу возвращается.
6. main продолжает работу или программа завершается.
7. Новая горутина может выполнить Add(1) позже.
```

Значит, `Wait()` может вернуться до того, как новая работа будет добавлена в счётчик.

Правильная запись:

```go
wg.Add(1)

go func() {
	defer wg.Done()
	work()
}()
```

Здесь сначала выполняется:

```go
wg.Add(1)
```

Только после этого создаётся горутина.

Теперь, в каком бы порядке ни работал планировщик, `Wait()` увидит, что есть как минимум одна незавершённая работа.

Например:

```text
counter = 0

wg.Add(1)
counter = 1

горутина запускается

wg.Wait()
если counter всё ещё 1, Wait ждёт

горутина Done()
counter = 0

Wait возвращается
```

Положительный вызов `Add`, сделанный, когда счётчик на нуле, должен выполниться до соответствующего `Wait()`.

## Что будет, если счётчик не сходится?

Работа `WaitGroup` зависит от правильного управления счётчиком.

Каждая зарегистрированная работа в итоге должна быть снята со счётчика.

Например, если используются две горутины, счётчик можно сразу увеличить до `2`:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	wg.Add(2)

	for i := 1; i <= 2; i++ {
		go func(id int) {
			defer wg.Done()
			fmt.Println("Работа завершена:", id)
		}(i)
	}

	wg.Wait()
	fmt.Println("Вся работа завершена")
}
```

Возможный вывод:

```text
Работа завершена: 2
Работа завершена: 1
Вся работа завершена
```

Здесь:

```go
wg.Add(2)
```

сообщает, что есть две незавершённые работы.

Начальное состояние:

```text
counter = 0
```

После `Add(2)`:

```text
counter = 2
```

Когда завершается первая горутина:

```text
counter = 1
```

Когда завершается вторая горутина:

```text
counter = 0
```

После этого `Wait()` возвращается.

Порядок первых двух строк может меняться. Но:

```text
Вся работа завершена
```

всегда выводится после рабочих горутин.

Если счётчик и вызовы `Done()` не соответствуют друг другу, возникают две основные ошибки.

### Если `Done()` вызван недостаточно

Пример:

```go
wg.Add(2)
wg.Done()
wg.Wait()
```

Счётчик меняется так:

```text
0 -> 2 -> 1
```

Но никогда не падает до `0`.

Поэтому:

```go
wg.Wait()
```

продолжает ждать.

Если в программе нет другой горутины, способной продолжить работу, runtime может обнаружить взаимоблокировку (deadlock).

Намеренно неправильный пример:

```go
// Счётчик не падает до нуля:
// wg.Add(2)
// wg.Done()
// wg.Wait() // Ждёт вечно, потому что не хватает ещё одного Done.
```

### Если `Done()` вызван лишний раз

Теперь посмотрим на другую ошибку:

```go
wg.Add(1)
wg.Done()
wg.Done()
```

Счётчик:

```text
0 -> 1 -> 0 -> -1
```

Счётчик `WaitGroup` не может быть отрицательным.

Поэтому runtime вызывает panic:

```text
panic: sync: negative WaitGroup counter
```

Намеренно неправильный пример:

```go
// Счётчик становится отрицательным:
// wg.Add(1)
// wg.Done()
// wg.Done() // panic: sync: negative WaitGroup counter
```

Важно, что `n` в `Add(n)` не обязательно должно быть числом горутин.

Оно выражает количество логически незавершённых работ.

Но в обычном коде, если одна горутина выполняет одну логическую работу, следующая пара понятна и безопаснее:

```go
wg.Add(1)

go func() {
	defer wg.Done()
	// работа
}()
```

При таком способе легче увидеть, что `Add` и `Done` соответствуют друг другу.

## Практический пример: параллельный подсчёт размеров файлов

Теперь рассмотрим пример, где `WaitGroup` используется вместе со сбором результатов.

Следующая программа распределяет задачу, связанную с несколькими файлами, по отдельным горутинам.

Чтобы пример не зависел от реальной файловой системы, имена и размеры файлов заданы заранее.

```go
package main

import (
	"fmt"
	"sync"
)

type file struct {
	name string
	size int64
}

func main() {
	files := []file{
		{name: "users.json", size: 1200},
		{name: "orders.json", size: 3400},
		{name: "report.csv", size: 800},
	}

	sizes := make([]int64, len(files))
	var wg sync.WaitGroup

	for i, item := range files {
		wg.Add(1)
		go func(index int, current file) {
			defer wg.Done()
			sizes[index] = current.size
		}(i, item)
	}

	wg.Wait()

	var total int64
	for i, item := range files {
		fmt.Printf("%s: %d байт\n", item.name, sizes[i])
		total += sizes[i]
	}
	fmt.Println("Итого:", total, "байт")
}
```

Результат:

```text
users.json: 1200 байт
orders.json: 3400 байт
report.csv: 800 байт
Итого: 5400 байт
```

В этом примере есть несколько важных моментов.

Сначала для хранения результатов создаётся slice:

```go
sizes := make([]int64, len(files))
```

В `files` три элемента. Значит, в `sizes` тоже будет три элемента:

```text
[0 0 0]
```

Затем для каждого файла создаётся горутина:

```go
for i, item := range files {
	wg.Add(1)

	go func(index int, current file) {
		defer wg.Done()
		sizes[index] = current.size
	}(i, item)
}
```

Каждая горутина пишет в свой индекс slice `sizes`.

Например:

```text
goroutine 1 -> sizes[0]
goroutine 2 -> sizes[1]
goroutine 3 -> sizes[2]
```

Поэтому две горутины не пишут в один и тот же элемент.

Кроме того, длина slice задана заранее.

Здесь:

```go
append(sizes, ...)
```

не используется.

Это важно, потому что если несколько горутин конкурентно делают `append` в один и тот же slice, может возникнуть гонка данных на заголовке slice или его базовом массиве.

Индекс и значение передаются анонимной функции как аргументы:

```go
}(i, item)
```

а параметры принимаются так:

```go
func(index int, current file)
```

Это делает явным, с каким индексом и каким файлом работает каждая горутина.

Затем вызывается:

```go
wg.Wait()
```

`main` читает результаты только после завершения всех горутин:

```go
for i, item := range files {
	fmt.Printf("%s: %d байт\n", item.name, sizes[i])
	total += sizes[i]
}
```

Поэтому запись рабочих горутин и чтение `main` не происходят одновременно.

Результаты выводятся не в порядке завершения горутин.

Они выводятся в порядке slice `files`:

```text
users.json
orders.json
report.csv
```

Поэтому итоговый вывод детерминирован.

В реальной программе вместо взятия `current.size` из готового значения горутина могла бы, например, вызывать `os.Stat`.

В таком реальном коде появляются дополнительные вопросы:

* сохранение ошибки, возникшей при проверке файла;
* ограничение количества одновременно открываемых файлов;
* остановка операции через отмену;
* применение тайм-аута.

`WaitGroup` сам не решает ни одну из этих задач.

## Чего не делает `WaitGroup`?

Задача `WaitGroup` узкая и точная:

> Он только ждёт завершения зарегистрированных работ.

Он не делает следующего:

* не возвращает результаты из горутин;
* не собирает ошибки автоматически;
* не передаёт ошибки другой горутине;
* не отменяет горутины;
* не даёт тайм-аута;
* не ограничивает количество одновременно работающих горутин;
* не защищает общий `map`, slice или другую память от конкурентной записи.

Например, если две горутины пишут в один `map`:

```go
var wg sync.WaitGroup
m := map[string]int{}

wg.Add(2)

go func() {
	defer wg.Done()
	m["a"] = 1
}()

go func() {
	defer wg.Done()
	m["b"] = 2
}()

wg.Wait()
```

то, хотя здесь есть `WaitGroup`, конкурентная запись в `map` не становится безопасной.

`WaitGroup` лишь ждёт завершения двух горутин.

Для защиты общих данных нужно другое средство. Например:

* `sync.Mutex`;
* канал;
* модель владения данными одной горутиной.

Для передачи результата или ошибки часто используют канал.

Для отмены и тайм-аута обычно используется:

```go
context.Context
```

А чтобы ограничить количество одновременно работающих горутин, применяют подход вроде worker pool или семафора.

> **Внимание**
>
> Использование `WaitGroup` не защищает код от гонок данных автоматически. Он только гарантирует, что зарегистрированные работы завершатся до возврата `Wait()`. Если несколько горутин конкурентно пишут в одну и ту же память, нужна отдельная синхронизация.

## Видимость памяти и синхронизация

`WaitGroup` — не только средство «ожидания». Он также даёт соответствующие гарантии синхронизации памяти.

Упрощённо говоря:

> Данные, которые горутина записала до `Done()`, видны ожидающей горутине после возврата соответствующего `Wait()`.

Вспомним предыдущий пример:

```go
go func(index int, current file) {
	defer wg.Done()
	sizes[index] = current.size
}(i, item)
```

Горутина сначала выполняет запись:

```go
sizes[index] = current.size
```

Затем, когда функция завершается, выполняется:

```go
wg.Done()
```

А `main` читает `sizes` только после того, как:

```go
wg.Wait()
```

вернётся.

Поток такой:

```text
worker:
sizes[index] = value
        |
        v
     Done()

        синхронизация

        |
        v
main:
Wait() возвращается
        |
        v
sizes[index] читается
```

По этой причине чтение после `Wait()` видит предыдущую запись воркера.

Если `main` прочитает `sizes` до `Wait()`, возникает другая ситуация.

Например:

```go
go func() {
	sizes[0] = 10
	wg.Done()
}()

fmt.Println(sizes[0]) // может быть прочитано слишком рано
wg.Wait()
```

Здесь чтение `main` и запись воркера могут совпасть по времени.

В результате есть вероятность гонки данных.

Важное различие:

`WaitGroup` обеспечивает нужную синхронизацию между воркерами и ожидающей горутиной.

Но он не делает автоматически безопасными конкурентные записи рабочих горутин друг относительно друга.

Например:

```text
горутина A -> пишет в x
горутина B -> пишет в x
```

если обе одновременно пишут в одно значение, `WaitGroup` этого не предотвращает.

В таком случае нужен mutex, канал или другая подходящая синхронизация.

## Не копируйте `WaitGroup`

После начала использования `WaitGroup` его нельзя копировать.

Важно понимать причину этого правила.

Представьте, что внутри `main` есть один `WaitGroup`:

```go
var wg sync.WaitGroup
wg.Add(1)
```

Затем мы передаём его в функцию по значению:

```go
work(wg)
```

Если сигнатура функции такая:

```go
func work(wg sync.WaitGroup)
```

функция работает не с исходным `WaitGroup`, а с его копией.

Неправильный пример:

```go
// Неправильно: WaitGroup копируется по значению.
// func work(wg sync.WaitGroup) {
//     defer wg.Done()
// }
```

В этом случае возникает примерно такая ситуация:

```text
wg в main:
counter = 1

копия внутри work():
counter = 1
```

Когда воркер вызывает:

```go
wg.Done()
```

меняется только счётчик копии:

```text
копия воркера:
1 -> 0
```

А исходный объект в `main` остаётся в состоянии:

```text
wg в main:
counter = 1
```

В результате:

```go
wg.Wait()
```

может никогда не вернуться.

Правильный вариант принимает указатель:

```go
func work(wg *sync.WaitGroup) {
	defer wg.Done()
}
```

Вызов:

```go
go work(&wg)
```

Теперь и `work()`, и `main()` работают с одним и тем же `WaitGroup`.

`go vet` помогает найти некоторые случаи копирования `WaitGroup`:

```bash
go vet ./...
```

`go vet` статически анализирует конструкции кода, которые проходят обычную компиляцию, но могут быть подозрительными.

Поэтому при работе с типами, которые нельзя копировать, например `WaitGroup`, `go vet` — полезная проверка.

## Повторное использование `WaitGroup`

Один `WaitGroup` не обязательно использовать только один раз.

После того как группа работ полностью завершилась, его можно повторно использовать для новой независимой группы.

Например:

```go
wg.Add(1)

go func() {
	defer wg.Done()
	// первая работа
}()

wg.Wait()
```

Здесь первая группа полностью завершилась.

После этого его можно снова использовать:

```go
wg.Add(1)

go func() {
	defer wg.Done()
	// вторая работа
}()

wg.Wait()
```

Важное условие: нельзя начинать положительные `Add` для новой независимой группы, пока вызовы `Wait()` предыдущей группы ещё ждут.

Логически группы должны быть разделены так:

```text
группа 1:
Add
горутина
Done
Wait возвращается

группа 2:
Add
горутина
Done
Wait возвращается
```

А такой жизненный цикл усложняет понимание:

```text
Wait группы 1 ещё ждёт
        |
        +--> Add для новой независимой группы
```

В практическом коде часто проще создавать локальный `WaitGroup` для каждой отдельной операции.

Например:

```go
func processBatch() {
	var wg sync.WaitGroup
	// ...
}
```

Этот подход ясно показывает, где `WaitGroup` создаётся и где заканчивается.

Делать его глобальной переменной или долго хранить между несвязанными работами — значит усложнить понимание жизненного цикла кода.

## Частые ошибки

### Вызов `Add` внутри горутины

Неправильный подход:

```go
go func() {
	wg.Add(1)
	defer wg.Done()
	work()
}()

wg.Wait()
```

Здесь `Wait()` может выполниться до увеличения счётчика.

В результате `Wait()` увидит счётчик равным `0` и сразу вернётся.

Правильный подход:

```go
wg.Add(1)

go func() {
	defer wg.Done()
	work()
}()
```

Главное правило:

> Сначала добавьте работу в счётчик, потом запускайте горутину.

### Забытый `Done`

Если был вызван:

```go
wg.Add(1)
```

соответствующая работа в итоге должна уменьшить счётчик.

Иначе:

```go
wg.Wait()
```

так и не вернётся.

Поэтому в начале рабочей функции обычно пишут:

```go
defer wg.Done()
```

Это особенно полезно в функциях с несколькими `return`.

### Передача `WaitGroup` по значению

Неправильно:

```go
func work(wg sync.WaitGroup)
```

Это может создать отдельную копию.

Правильно:

```go
func work(wg *sync.WaitGroup)
```

и:

```go
go work(&wg)
```

Не копируйте `WaitGroup`, который уже начали использовать.

### Думать, что `WaitGroup` защищает результаты

`WaitGroup` только ждёт завершения работ.

Например, если несколько горутин пишут в один общий `map`, наличие `WaitGroup` не делает эту операцию безопасной.

Следующая мысль неверна:

```text
есть WaitGroup -> значит, конкурентная запись безопасна
```

Правильное понимание:

```text
есть WaitGroup -> можно дождаться завершения всех зарегистрированных работ
```

Для защиты общей памяти нужна отдельная синхронизация.

### Угадывание количества `Add` и `Done`

Управление счётчиком в месте, оторванном от количества выполняемых работ, может привести к ошибке.

Например:

```go
wg.Add(10)

for _, job := range jobs {
	go ...
}
```

Если позже количество `jobs` будет отличаться от `10`, счётчик и реальное количество работ разойдутся.

Часто безопаснее написать:

```go
wg.Add(len(jobs))
```

или в одном месте с каждой работой:

```go
for _, job := range jobs {
	wg.Add(1)

	go func() {
		defer wg.Done()
		// ...
	}()
}
```

Тогда при изменении кода меньше вероятность, что счётчик оторвётся от количества работ.

## На что обращают внимание на собеседовании?

Когда спрашивают о `sync.WaitGroup`, знания одного синтаксиса недостаточно.

Важно понимать следующее:

* `WaitGroup` управляет внутренним счётчиком;
* `Add(n)` увеличивает счётчик;
* `Done()` уменьшает счётчик на единицу;
* когда счётчик становится нулём, `Wait()` возвращается;
* положительный `Add(1)` должен выполняться до запуска горутины;
* `Done()` обычно пишут с `defer`;
* если `Done()` не хватает, `Wait()` может не вернуться;
* если `Done()` лишний, счётчик становится отрицательным, и происходит panic во время выполнения;
* `WaitGroup` нельзя копировать после начала использования;
* во вспомогательную функцию обычно передают `*sync.WaitGroup`;
* `WaitGroup` не возвращает результаты;
* он не обрабатывает ошибки;
* он не даёт отмены;
* он не задаёт предел конкурентности;
* он не защищает общую память от гонок данных;
* записи до `Done()` видны ожидающей горутине после возврата соответствующего `Wait()`;
* если рабочие горутины конкурентно пишут в одну и ту же память, отдельная синхронизация всё равно нужна.

## Примеры

### 1. Ожидание одной горутины

Этот пример показывает самый простой случай `WaitGroup`.

Запускается одна вспомогательная горутина. А `main()` ждёт её завершения.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	wg.Add(1)

	go func() {
		defer wg.Done()
		fmt.Println("Работа выполнена")
	}()

	wg.Wait()
	fmt.Println("main завершилась")
}
```

Сначала через:

```go
var wg sync.WaitGroup
```

создаётся `WaitGroup` с нулевым значением.

Затем:

```go
wg.Add(1)
```

регистрирует одну незавершённую работу.

Счётчик становится:

```text
0 -> 1
```

Внутри горутины написано:

```go
defer wg.Done()
```

Когда горутина завершается, счётчик падает:

```text
1 -> 0
```

А `main()` ждёт именно этого состояния через:

```go
wg.Wait()
```

Только после этого выводится:

```text
main завершилась
```

Главное правило этого примера: `Add(1)` выполняется до начала работы, а `Done()` — когда работа завершается.

### 2. Регистрация каждой работы в цикле

В этом примере создаются три горутины.

Перед запуском каждой горутины соответствующая работа добавляется в `WaitGroup`.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup

	for id := 1; id <= 3; id++ {
		wg.Add(1)

		go func(workerID int) {
			defer wg.Done()
			fmt.Println("Воркер:", workerID)
		}(id)
	}

	wg.Wait()
}
```

Цикл выполняется три раза:

```text
id = 1
id = 2
id = 3
```

На каждой итерации выполняется:

```go
wg.Add(1)
```

Поэтому после создания трёх горутин счётчик логически равен `3`.

Каждая горутина один раз вызывает `Done()`:

```text
3 -> 2 -> 1 -> 0
```

Значение `id` передаётся анонимной функции как аргумент:

```go
}(id)
```

и принимается через:

```go
func(workerID int)
```

Это явно показывает, с каким ID воркера работает каждая горутина.

Порядок вывода строк `Воркер:` не гарантирован. Например, они могут выйти в порядке `3`, `1`, `2`.

Главное правило в этом примере: `Add(1)` выполняется не внутри горутины, а до вызова `go`.

### 3. Добавление количества работ сразу

Вызывать `Add(1)` на каждой итерации цикла не обязательно.

Если количество работ известно заранее, их можно сразу добавить в счётчик.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	files := []string{"a.txt", "b.txt", "c.txt"}

	var wg sync.WaitGroup
	wg.Add(len(files))

	for _, file := range files {
		go func(name string) {
			defer wg.Done()
			fmt.Println("Проверен:", name)
		}(file)
	}

	wg.Wait()
}
```

Здесь значение:

```go
len(files)
```

равно:

```text
3
```

Поэтому:

```go
wg.Add(len(files))
```

даёт тот же результат, что и:

```go
wg.Add(3)
```

Счётчик ждёт три работы.

Каждая горутина должна один раз вызвать `Done()`.

Если позже в список `files` добавится новый элемент:

```go
files := []string{"a.txt", "b.txt", "c.txt", "d.txt"}
```

`len(files)` автоматически станет `4`.

Это безопаснее, чем жёстко записанное:

```go
wg.Add(3)
```

Главное правило этого примера: если количество работ известно, счётчик можно вычислить из этого источника.

### 4. Передача `WaitGroup` во вспомогательную функцию по указателю

В этом примере логика воркера вынесена в отдельную функцию `process()`.

```go
package main

import (
	"fmt"
	"sync"
)

func process(name string, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("Обработано:", name)
}

func main() {
	var wg sync.WaitGroup
	items := []string{"изображение", "видео"}

	for _, item := range items {
		wg.Add(1)
		go process(item, &wg)
	}

	wg.Wait()
}
```

Функция `process()` принимает:

```go
wg *sync.WaitGroup
```

Это значит, что `WaitGroup` не копируется по значению.

При вызове используется:

```go
go process(item, &wg)
```

`&wg` — адрес исходного `WaitGroup` внутри `main()`.

Поэтому внутри `process()`:

```go
wg.Done()
```

уменьшает именно тот счётчик, который ждёт `main()`.

Если бы функция была написана так:

```go
func process(name string, wg sync.WaitGroup)
```

`wg` мог бы скопироваться, и воркер не изменил бы исходный счётчик.

Главное правило этого примера: передавайте уже используемый `WaitGroup` во вспомогательную функцию через указатель.

### 5. Выполнение `Done()` и при раннем возврате

Этот пример показывает, чем полезен `defer wg.Done()`.

Некоторые значения не проходят проверку, и функция делает ранний `return`.

```go
package main

import (
	"fmt"
	"sync"
)

func validate(value int, wg *sync.WaitGroup) {
	defer wg.Done()

	if value < 0 {
		fmt.Println("Отрицательное значение пропущено:", value)
		return
	}

	fmt.Println("Принято:", value)
}

func main() {
	values := []int{5, -2, 8}

	var wg sync.WaitGroup
	wg.Add(len(values))

	for _, value := range values {
		go validate(value, &wg)
	}

	wg.Wait()
}
```

Значения:

```text
5
-2
8
```

Для `-2` выполняется условие:

```go
if value < 0
```

и функция досрочно завершается через:

```go
return
```

Но `Done()` заранее отложен:

```go
defer wg.Done()
```

Поэтому даже при раннем `return` вызывается `Done()`.

Если бы `Done()` был написан только в конце функции:

```go
func validate(value int, wg *sync.WaitGroup) {
	if value < 0 {
		return
	}

	wg.Done()
}
```

на пути с отрицательным значением он бы вообще не выполнился.

В результате счётчик мог бы так и не упасть до нуля.

Главное правило этого примера: в рабочей функции `defer wg.Done()` безопаснее обрабатывает случаи раннего `return`.

### 6. Запись результатов в разные элементы slice

В этом примере несколько горутин параллельно выполняют вычисления.

Каждая записывает результат в свой индекс заранее созданного slice.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	numbers := []int{2, 3, 4}
	results := make([]int, len(numbers))

	var wg sync.WaitGroup
	wg.Add(len(numbers))

	for index, number := range numbers {
		go func(i, value int) {
			defer wg.Done()
			results[i] = value * value
		}(index, number)
	}

	wg.Wait()
	fmt.Println(results)
}
```

Начальные значения:

```text
numbers = [2 3 4]
results = [0 0 0]
```

Горутины выполняют примерно такую работу:

```text
results[0] = 2 * 2
results[1] = 3 * 3
results[2] = 4 * 4
```

В результате получаем:

```text
[4 9 16]
```

Здесь каждая горутина пишет в свой индекс:

```text
goroutine A -> results[0]
goroutine B -> results[1]
goroutine C -> results[2]
```

Длина `results` задана заранее:

```go
make([]int, len(numbers))
```

Поэтому конкурентного `append` не происходит.

А `main()` не читает результаты, пока:

```go
wg.Wait()
```

не вернётся.

Это не даёт записям воркеров и чтению `main` выполняться одновременно.

Главное правило этого примера: `WaitGroup` сам не хранит результаты, но помогает определить момент, когда их можно читать после завершения всех воркеров.

### 7. Повторное использование `WaitGroup` на последовательных этапах

В этом примере один `WaitGroup` последовательно используется для двух независимых этапов.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup

	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("Первый этап")
	}()
	wg.Wait()

	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("Второй этап")
	}()
	wg.Wait()
}
```

На первом этапе:

```text
Add(1)
counter = 1
```

Когда горутина завершается:

```text
Done()
counter = 0
```

Первый:

```go
wg.Wait()
```

возвращается.

В этот момент первая группа полностью завершена.

Затем начинается второй этап:

```go
wg.Add(1)
```

Счётчик снова становится:

```text
0 -> 1
```

Когда вторая горутина завершается:

```text
1 -> 0
```

и второй `Wait()` возвращается.

Важный момент: новая группа начинается после полного завершения первой.

Главное правило этого примера: `WaitGroup` можно использовать повторно, но цикл ожидания предыдущей группы должен быть завершён.

### 8. Ожидание одной группы из нескольких мест

Несколько горутин могут вызывать метод `Wait()` одного `WaitGroup`.

В следующем примере два наблюдателя ждут завершения одного воркера.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var workers sync.WaitGroup
	var observers sync.WaitGroup

	workers.Add(1)

	go func() {
		defer workers.Done()
		fmt.Println("Основная работа завершена")
	}()

	observers.Add(2)

	for id := 1; id <= 2; id++ {
		go func(observerID int) {
			defer observers.Done()

			workers.Wait()
			fmt.Println("Наблюдатель уведомлён:", observerID)
		}(id)
	}

	observers.Wait()
}
```

Здесь два отдельных `WaitGroup`.

Первый:

```go
workers
```

отслеживает работу основного воркера.

Второй:

```go
observers
```

отслеживает завершение двух горутин-наблюдателей.

Для основного воркера выполняется:

```go
workers.Add(1)
```

А два наблюдателя вызывают:

```go
workers.Wait()
```

Когда счётчик падает до нуля, оба `Wait()` могут продолжить.

Затем каждый наблюдатель выводит строку:

```go
fmt.Println("Наблюдатель уведомлён:", observerID)
```

А `main()` ждёт завершения обоих наблюдателей через:

```go
observers.Wait()
```

Вывод может быть примерно таким:

```text
Основная работа завершена
Наблюдатель уведомлён: 2
Наблюдатель уведомлён: 1
```

Порядок наблюдателей не гарантирован.

Главное правило этого примера: один `WaitGroup` могут ждать несколько горутин.

### 9. Создание внутренней группы для каждой внешней работы

Иногда параллельная работа сама делится на несколько небольших параллельных работ.

В таком случае можно использовать внешний и внутренний `WaitGroup`.

```go
package main

import (
	"fmt"
	"sync"
)

func section(name string, outer *sync.WaitGroup) {
	defer outer.Done()

	var inner sync.WaitGroup
	inner.Add(2)

	for part := 1; part <= 2; part++ {
		go func(number int) {
			defer inner.Done()
			fmt.Println(name, "часть", number)
		}(part)
	}

	inner.Wait()
}

func main() {
	var outer sync.WaitGroup

	outer.Add(2)

	go section("A", &outer)
	go section("B", &outer)

	outer.Wait()
}
```

`main()` создаёт две внешние работы:

```text
section A
section B
```

Поэтому вызывается:

```go
outer.Add(2)
```

Внутри каждого `section()` создаётся отдельный локальный:

```go
var inner sync.WaitGroup
```

Важный момент: значения `inner` у секций `A` и `B` независимы друг от друга.

В каждой секции две части:

```go
inner.Add(2)
```

Затем создаются отдельные горутины для:

```text
A часть 1
A часть 2

B часть 1
B часть 2
```

Каждый `section()` ждёт свои две внутренние горутины через:

```go
inner.Wait()
```

Только после их завершения функция `section()` возвращается.

При возврате функции выполняется:

```go
defer outer.Done()
```

Значит, `outer` уменьшается только после того, как вся работа внутри секции полностью завершена.

Логическая структура такая:

```text
outer
├── section A
│   ├── part 1
│   └── part 2
│
└── section B
    ├── part 1
    └── part 2
```

Главное правило этого примера: каждая работа верхнего уровня может ждать свои внутренние горутины через собственный локальный `WaitGroup`.

### 10. Безопасное ожидание пустого списка работ

`WaitGroup` работает с нулевым значением. Поэтому даже если выполнять нечего, отдельное особое условие писать не нужно.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	jobs := []string{}

	var wg sync.WaitGroup
	wg.Add(len(jobs))

	for _, job := range jobs {
		go func(name string) {
			defer wg.Done()
			fmt.Println(name)
		}(job)
	}

	wg.Wait()
	fmt.Println("Нет работ для выполнения")
}
```

Здесь:

```go
jobs := []string{}
```

— пустой slice.

Значит, значение:

```go
len(jobs)
```

равно:

```text
0
```

Поэтому:

```go
wg.Add(len(jobs))
```

на деле равно:

```go
wg.Add(0)
```

Счётчик не меняется:

```text
counter = 0
```

Цикл:

```go
for _, job := range jobs
```

не выполняется ни разу.

Следующий:

```go
wg.Wait()
```

сразу возвращается, потому что счётчик уже равен нулю.

Результат:

```text
Нет работ для выполнения
```

Для этого отдельная проверка:

```go
if len(jobs) == 0 {
	// ...
}
```

не нужна.

Главное правило этого примера: `WaitGroup` естественно работает и с пустой группой. Если счётчик равен нулю, `Wait()` сразу возвращается.
