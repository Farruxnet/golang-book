# Worker pool

Worker pool (пул воркеров) — способ выполнять много задач ограниченным числом горутин-воркеров.

При этом подходе не все задачи сразу запускаются в отдельных горутинах. Вместо этого создаётся заранее известное число горутин-воркеров. Задачи ставятся в очередь. Освободившийся воркер берёт следующую задачу.

Например, нужно обработать 1000 файлов. В самом простом варианте для каждого файла можно создать одну горутину. Но это не всегда хорошее решение.

Если одновременно начнёт работать слишком много горутин:

* может одновременно открыться слишком много файлов;
* может вырасти расход памяти;
* может исчерпаться лимит пула соединений с базой данных;
* может быть превышен rate limit внешнего API;
* на сервер или другой внешний ресурс может лечь избыточная нагрузка.

Worker pool ограничивает число одновременно выполняемых задач.

Например, если задач 1000, а работают только 10 воркеров, одновременно выполняется не более 10 задач. Закончив одну, воркер берёт следующую.

Это можно представить как службу такси. Клиенты — задачи, которые нужно выполнить. Водители — воркеры.

Клиентов может быть больше, чем водителей. Но один водитель одновременно обслуживает только одного клиента. Освободившись, водитель берёт следующего клиента.

Основная идея worker pool точно такая же.

## Основные части структуры

Простой worker pool обычно состоит из четырёх основных частей:

* producer создаёт задачи и отправляет их в канал `jobs`;
* несколько воркеров берут задачи из канала `jobs`;
* воркеры отправляют результаты работы в канал `results`;
* coordinator ждёт завершения всех воркеров и закрывает канал `results`.

Рассмотрим задачу каждой части отдельно.

**Producer** создаёт новую работу. Например, имена файлов, URL, записи базы данных или значения для вычисления producer может отправлять в канал `jobs`.

**Воркер** берёт одну задачу из канала `jobs`, выполняет её и при необходимости отправляет результат в канал `results`.

**Coordinator** отслеживает момент, когда все воркеры завершились. Для этого часто используется `sync.WaitGroup`.

Здесь важно и то, кто закрывает канал.

Канал `jobs` должна закрывать сторона, которая точно знает, что новых задач больше не будет. Обычно это producer.

Канал `results` должна закрывать сторона, которая точно знает, что все воркеры завершились. Обычно это coordinator, ожидающий `WaitGroup`.

Отдельные воркеры не должны пытаться сами закрыть канал `results`.

Причина в том, что после того как один воркер закроет канал, другой воркер может ещё попытаться отправить результат:

```go
results <- result
```

А отправка в закрытый канал вызывает panic:

```text
send on closed channel
```

Поэтому в worker pool владелец каждого канала и порядок закрытия должны быть понятны заранее.

## Первый рабочий пример

В следующем примере есть 5 задач и 3 воркера:

```go
package main

import (
	"fmt"
	"sync"
)

type Result struct {
	JobID  int
	Worker int
	Value  int
}

func worker(id int, jobs <-chan int, results chan<- Result, wg *sync.WaitGroup) {
	defer wg.Done()

	for job := range jobs {
		results <- Result{
			JobID:  job,
			Worker: id,
			Value:  job * 2,
		}
	}
}

func main() {
	const jobCount = 5
	const workerCount = 3

	jobs := make(chan int, jobCount)
	results := make(chan Result, jobCount)

	var wg sync.WaitGroup
	wg.Add(workerCount)

	for id := 1; id <= workerCount; id++ {
		go worker(id, jobs, results, &wg)
	}

	go func() {
		for job := 1; job <= jobCount; job++ {
			jobs <- job
		}
		close(jobs)
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	for result := range results {
		fmt.Printf(
			"задача=%d воркер=%d результат=%d\n",
			result.JobID,
			result.Worker,
			result.Value,
		)
	}
}
```

Возможный вывод:

```text
задача=1 воркер=1 результат=2
задача=2 воркер=2 результат=4
задача=3 воркер=3 результат=6
задача=4 воркер=1 результат=8
задача=5 воркер=2 результат=10
```

Этот вывод — только один из возможных вариантов.

Воркеры работают конкурентно. Поэтому заранее неизвестно, какой воркер возьмёт какую задачу.

Например, при другом запуске вывод может быть таким:

```text
задача=2 воркер=2 результат=4
задача=1 воркер=1 результат=2
задача=4 воркер=2 результат=8
задача=3 воркер=3 результат=6
задача=5 воркер=1 результат=10
```

Это не ошибка.

Важен не порядок результатов. Важная гарантия в том, что каждую задачу, отправленную в канал `jobs`, берёт один воркер и, если в коде воркера нет другой ошибки, её результат отправляется в канал `results`.

Теперь рассмотрим основные части кода.

### Направленные каналы

Сигнатура функции воркера:

```go
func worker(
	id int,
	jobs <-chan int,
	results chan<- Result,
	wg *sync.WaitGroup,
)
```

Здесь:

```go
jobs <-chan int
```

означает, что из канала `jobs` можно только читать.

Воркер может сделать:

```go
job := <-jobs
```

Но не может сделать:

```go
jobs <- 10
```

Потому что для воркера `jobs` — канал только для получения.

Канал результатов передаётся в виде:

```go
results chan<- Result
```

Это канал только для отправки. Воркер может отправлять в него значения:

```go
results <- result
```

Но не может читать из него.

Направленные каналы полезны не для оптимизации во время выполнения, а для API и безопасности на этапе компиляции.

По сигнатуре функции видно, что она может делать с каким каналом. Если воркер случайно сделает что-то неправильное, компилятор поймает ошибку.

### Цикл воркера

Внутри воркера используется:

```go
for job := range jobs {
	// ...
}
```

`range` по каналу означает получение значений, пока канал не закрыт.

Когда producer делает:

```go
close(jobs)
```

воркер не выходит из цикла сразу.

Если в буфере канала ещё остались задачи, сначала берутся они. Когда буфер опустеет и станет ясно, что других значений не будет, `range` завершается.

То есть старые значения в закрытом канале не теряются.

### Зачем нужна `WaitGroup`?

В начале каждого воркера мы написали:

```go
defer wg.Done()
```

А `main` перед запуском воркеров вызывает:

```go
wg.Add(workerCount)
```

Если `workerCount == 3`, счётчик `WaitGroup` устанавливается в 3.

Когда каждый воркер завершается:

```go
wg.Done()
```

уменьшает счётчик на единицу.

Процесс выглядит так:

```text
Начало:
WaitGroup = 3

worker 1 завершился:
WaitGroup = 2

worker 2 завершился:
WaitGroup = 1

worker 3 завершился:
WaitGroup = 0
```

`wg.Wait()` ждёт, пока счётчик не станет `0`.

Coordinator через:

```go
go func() {
	wg.Wait()
	close(results)
}()
```

ждёт завершения всех воркеров.

Только после этого выполняется:

```go
close(results)
```

Это очень важно. Если закрыть канал `results`, пока воркеры ещё отправляют в него значения, возникнет panic `send on closed channel`.

### Получение результатов

`main` собирает результаты таким циклом:

```go
for result := range results {
	fmt.Printf(
		"задача=%d воркер=%d результат=%d\n",
		result.JobID,
		result.Worker,
		result.Value,
	)
}
```

Этот цикл работает, пока канал `results` не закрыт.

Поток выглядит так:

```text
producer
   |
   v
jobs
   |
   +------> worker 1 ----+
   +------> worker 2 ----+----> results ----> main
   +------> worker 3 ----+
              |
              v
          WaitGroup
              |
              v
       close(results)
```

Этот поток предотвращает несколько частых проблем:

* воркеры не ждут вечно на канале `jobs`;
* `results` не закрывается до завершения воркеров;
* `main` выходит из цикла `range`, когда канал закрыт;
* воркеры не застревают из-за того, что результаты никто не принимает.

## Буфер и backpressure

В примере выше каналы созданы так:

```go
jobs := make(chan int, jobCount)
results := make(chan Result, jobCount)
```

Если `jobCount == 5`, оба канала могут вместить 5 значений.

В маленьком примере это упрощает понимание кода. Но в реальном проекте создавать очень большой буфер, в который поместятся все задачи, не всегда хорошо.

Например, если в систему может прийти миллион задач:

```go
jobs := make(chan Job, 1_000_000)
```

может привести к хранению огромной очереди в памяти.

Если воркеры не успевают за задачами, очередь растёт ещё больше.

Поэтому буфер часто делают ограниченного размера.

Например:

```go
jobs := make(chan Job, 100)
```

В этом случае producer может поставить в очередь до 100 задач. Когда буфер заполнен, следующая отправка блокируется:

```go
jobs <- job
```

Producer ждёт на этой строке, пока какой-нибудь воркер не заберёт значение из канала.

Это называется **backpressure** (обратное давление).

Проще говоря, если потребители не успевают выполнять задачи, producer тоже вынужден замедлиться.

Это очень полезное свойство.

Иначе producer мог бы создавать новую работу с неограниченной скоростью и копить её в памяти.

### Небуферизованный канал

Если написать:

```go
jobs := make(chan Job)
```

канал будет небуферизованным.

Когда producer делает:

```go
jobs <- job
```

отправка не завершится, пока какой-нибудь воркер не будет готов принять значение.

То есть producer и воркер синхронизируются напрямую.

### Буферизованный канал

Если написать:

```go
jobs := make(chan Job, 100)
```

producer может продолжать, пока в буфере есть свободное место, даже если ни один воркер сразу не берёт значение.

Например:

```text
ёмкость буфера = 3

producer -> job1
producer -> job2
producer -> job3
```

Теперь буфер заполнен.

Если producer хочет отправить `job4`:

```text
producer -> job4
```

producer блокируется, пока какой-нибудь воркер не заберёт из канала хотя бы одну из прежних задач.

### Размер буфера не обязан равняться числу воркеров

Например, если воркеров 10:

```go
const workerCount = 10
```

буфер канала тоже не обязан быть ровно `10`.

Технически возможны все следующие варианты:

```go
jobs := make(chan Job)
```

```go
jobs := make(chan Job, 10)
```

```go
jobs := make(chan Job, 100)
```

```go
jobs := make(chan Job, 1000)
```

Какое значение правильное, нельзя определить только по числу воркеров.

При выборе размера буфера нужно учитывать:

* с какой скоростью приходят задачи;
* сколько времени занимает одна задача;
* бывают ли временные всплески нагрузки;
* сколько работы можно держать в очереди;
* сколько памяти можно использовать;
* допустимо ли, чтобы старая задача долго ждала в очереди.

То есть число воркеров управляет конкурентностью. А буфер канала управляет ёмкостью очереди.

Это не одно и то же.

## Обработка ошибок и отмены

В реальной системе не каждая задача завершается успешно.

Например:

* HTTP-запрос может вернуть ошибку;
* файл может не открыться;
* запрос к базе данных может завершиться неудачей;
* входное значение может быть некорректным.

Поэтому внутри результата полезно передавать вместе со значением и ошибку.

Например:

```go
type Result struct {
	JobID int
	Value int
	Err   error
}
```

Эта структура хранит три важные части результата:

* `JobID` — какая задача выполнена;
* `Value` — успешный результат;
* `Err` — ошибка, возникшая при выполнении.

В некоторых системах, даже если одна задача завершилась ошибкой, остальные задачи должны продолжаться.

В других системах после первой серьёзной ошибки нужно остановить весь пул.

Во втором случае помогает `context.Context`.

Следующий пример отменяет worker pool, когда встречается отрицательное значение:

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

type Job struct {
	ID    int
	Value int
}

type Result struct {
	JobID int
	Value int
	Err   error
}

func process(job Job) (int, error) {
	if job.Value < 0 {
		return 0, errors.New("отрицательные значения не допускаются")
	}

	return job.Value * job.Value, nil
}

func worker(
	ctx context.Context,
	jobs <-chan Job,
	results chan<- Result,
	wg *sync.WaitGroup,
) {
	defer wg.Done()

	for {
		select {
		case <-ctx.Done():
			return

		case job, ok := <-jobs:
			if !ok {
				return
			}

			value, err := process(job)

			result := Result{
				JobID: job.ID,
				Value: value,
				Err:   err,
			}

			select {
			case results <- result:
			case <-ctx.Done():
				return
			}
		}
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	jobs := make(chan Job)
	results := make(chan Result)

	var wg sync.WaitGroup

	const workerCount = 2

	wg.Add(workerCount)

	for id := 1; id <= workerCount; id++ {
		go worker(ctx, jobs, results, &wg)
	}

	go func() {
		defer close(jobs)

		input := []int{2, 3, -1, 4, 5}

		for id, value := range input {
			select {
			case jobs <- Job{
				ID:    id + 1,
				Value: value,
			}:
			case <-ctx.Done():
				return
			}
		}
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	for result := range results {
		if result.Err != nil {
			fmt.Printf(
				"задача=%d ошибка: %v\n",
				result.JobID,
				result.Err,
			)

			cancel()
			continue
		}

		fmt.Printf(
			"задача=%d результат=%d\n",
			result.JobID,
			result.Value,
		)
	}
}
```

Порядок вывода заранее не гарантирован.

Например, следующая ошибка возникнет обязательно:

```text
задача=3 ошибка: отрицательные значения не допускаются
```

Но какие ещё результаты будут выведены до или после этой ошибки, зависит от планирования.

Например, может быть так:

```text
задача=1 результат=4
задача=2 результат=9
задача=3 ошибка: отрицательные значения не допускаются
```

Или, если другой воркер уже успел взять задачу `4`, может быть выведен и её результат.

### Как воркер следит за отменой?

Внутри воркера есть:

```go
select {
case <-ctx.Done():
	return

case job, ok := <-jobs:
	// ...
}
```

То есть воркер одновременно ждёт двух событий:

* прихода новой задачи;
* отмены контекста.

Если вызвать:

```go
cancel()
```

канал `ctx.Done()` становится готовым.

Воркер может получить из него сигнал и выполнить:

```go
return
```

### Зачем проверяется `ok`?

Канал читается так:

```go
job, ok := <-jobs
```

Если `jobs` открыт и пришло значение:

```text
ok == true
```

Если канал закрыт и в нём не осталось других значений:

```text
ok == false
```

Поэтому:

```go
if !ok {
	return
}
```

сообщает воркеру, что работы больше нет.

### Контекст проверяется и при отправке результата

В коде результат не отправляется просто так:

```go
results <- result
```

Вместо этого используется:

```go
select {
case results <- result:
case <-ctx.Done():
	return
}
```

Это важно.

Представьте, что потребитель перестал принимать результаты. А `results` небуферизованный или его буфер заполнен.

Если воркер застрял на строке:

```go
results <- result
```

он блокируется, пока другая сторона не примет результат.

Даже если контекст отменён, обычная операция отправки этого автоматически не заметит.

При использовании `select` у воркера два варианта:

* отправить результат;
* выйти, если контекст отменён.

Поэтому сигнал отмены нужно проверять не только при ожидании `jobs`, но и в других потенциально блокирующих местах.

### Producer тоже следит за контекстом

Producer делает:

```go
select {
case jobs <- Job{
	ID:    id + 1,
	Value: value,
}:
case <-ctx.Done():
	return
}
```

Это нужно по той же причине.

Если воркеры остановились из-за отмены, producer не должен вечно ждать на обычной строке:

```go
jobs <- job
```

### `cancel()` не останавливает всё сразу

Здесь есть важная тонкость.

Отмена контекста — это сигнал.

Это не команда, принудительно останавливающая работающую горутину на уровне операционной системы.

Например, пусть вызвана:

```go
value, err := process(job)
```

Если `process` работает долго:

```go
func process(job Job) (int, error) {
	// 30 секунд работы
}
```

даже если в этот момент другая горутина сделала:

```go
cancel()
```

`process` сама не остановится.

Если долгую операцию тоже нужно отменять, ей тоже нужно передать `context`:

```go
func process(ctx context.Context, job Job) (int, error) {
	// проверять ctx.Done() в нужных местах
}
```

Методы, принимающие контекст, в HTTP, базах данных и многих других стандартных API используются именно для этой цели.

### Выбор `select` тоже не детерминирован

Если одновременно:

```go
ctx.Done()
```

готов и в канале:

```go
jobs
```

тоже есть значение, `select` выбирает один из готовых вариантов.

Поэтому нельзя строго гарантировать, что после вызова `cancel()` ни одна новая задача не начнётся.

Некоторые воркеры могут уже успеть взять готовую задачу.

Отмену правильнее понимать как «остановиться как можно скорее».

## Сохранение порядка результатов

Worker pool не гарантирует порядок выполнения.

Например, отправлены такие задачи:

```text
1
2
3
4
```

Задача `1` может занять 500 ms.

Задача `2` может завершиться за 20 ms.

Тогда естественно, что результаты придут в порядке:

```text
2
1
```

Именно в этом польза конкурентного выполнения: одна медленная задача не задерживает полностью остальные.

Но иногда результаты нужно вернуть точно в порядке входных данных.

В таком случае каждой задаче можно дать индекс.

Например:

```go
ordered := make([]int, jobCount)

for result := range results {
	ordered[result.JobID-1] = result.Value
}
```

Если:

```text
JobID = 1
```

то записывается:

```go
ordered[0] = result.Value
```

Если:

```text
JobID = 5
```

то записывается:

```go
ordered[4] = result.Value
```

Результаты могут приходить из канала в любом порядке, но внутри slice они размещаются по своему исходному индексу.

Например, пусть результаты пришли так:

```text
JobID=3 Value=30
JobID=1 Value=10
JobID=2 Value=20
```

После сбора:

```text
ordered[0] = 10
ordered[1] = 20
ordered[2] = 30
```

В итоге восстанавливается порядок:

```text
[10 20 30]
```

У этого приёма тоже есть недостаток.

Все результаты хранятся в памяти:

```go
ordered := make([]int, jobCount)
```

Если результатов миллионы и они большие, это может потребовать заметного объёма памяти.

В такой ситуации может понадобиться отдельный этап-сборщик, восстанавливающий порядок.

Например, сборщик хранит следующий ожидаемый индекс. Будущие результаты, пришедшие раньше него, держатся в ограниченном временном буфере.

Если порядок вообще не требуется, обычно лучше обрабатывать результат сразу, как только он пришёл.

Это:

* расходует меньше памяти;
* позволяет быстрее обработать первый результат;
* уменьшает необходимость ждать завершения всех задач.

## Выбор числа воркеров

Один из самых важных вопросов в worker pool — сколько воркеров создавать.

Универсального числа здесь нет.

Правило «чем больше воркеров, тем быстрее работает программа» неверно.

Много воркеров иногда помогает. А иногда, наоборот, замедляет систему или перегружает внешние ресурсы.

### CPU-bound работа

CPU-bound задача тратит основную часть времени на вычисления.

Например:

* большие математические вычисления;
* обработка изображений;
* сжатие;
* хеширование;
* кодирование;
* парсинг больших объёмов данных.

Для таких задач держать число воркеров близким к доступному параллелизму часто бывает хорошей отправной точкой.

Создание очень большого числа воркеров не умножает CPU.

Наоборот:

* растут накладные расходы планирования;
* горутины больше ждут в очереди;
* может снизиться эффективность кеша;
* может увеличиться переключение контекста.

Поэтому в CPU-bound работе «тысяча воркеров» не означает автоматически «быстрее».

### I/O-bound работа

I/O-bound задачи тратят основную часть времени на ожидание внешней операции.

Например:

* HTTP-запрос;
* чтение с диска;
* запрос к базе данных;
* сетевой сокет;
* ответ внешнего сервиса.

В таком случае число воркеров может быть больше числа CPU.

Причина в том, что многие горутины не используют CPU одновременно. Большинство из них ждёт ответа I/O.

Например, воркеров может быть 100, но в каждый момент реальную работу на CPU могут выполнять лишь несколько из них.

Но и это не значит «чем больше, тем лучше».

Нужно учитывать ограничения внешней системы.

### Работа с базой данных

Для базы данных число воркеров может быть связано с пулом соединений.

Например, если:

```text
worker = 100
DB max connections = 10
```

не все воркеры смогут выполнять запросы одновременно.

Большинство воркеров в итоге ждёт соединения.

Такой пул иногда может увеличить бесполезное ожидание и тайм-ауты.

### Работа с внешним API

API может установить такой лимит:

```text
20 requests per second
```

Если запустить 500 воркеров, программа внутри может быстро отправлять запросы, но внешний сервис может вернуть:

```text
429 Too Many Requests
```

Поэтому число воркеров выбирают вместе с:

* rate limit API;
* рекомендуемым сервером лимитом конкурентности;
* тайм-аутом;
* стратегией повторов (retry);
* пропускной способностью сети.

### Лучшее значение измеряется

Выбирать число воркеров только по теоретическим догадкам недостаточно.

На практике нужно смотреть на такие показатели:

* бенчмарки;
* профилирование;
* метрики задержки (latency);
* пропускная способность (throughput);
* CPU;
* память;
* число соединений;
* доля ошибок.

Например, можно попробовать увеличивать число воркеров:

```text
10 -> 20 -> 50 -> 100
```

Если после `50` воркеров throughput почти не растёт, а память и latency ухудшаются, добавлять ещё воркеры может быть бесполезно.

### Когда число воркеров `0`

Нельзя забывать и этот граничный случай.

Например, если:

```go
const workerCount = 0
```

ни один воркер не создаётся.

А producer пытается сделать:

```go
jobs <- job
```

Если канал никто не читает, producer блокируется.

Поэтому при создании общего API для worker pool нужно проверять условие:

```go
workerCount > 0
```

Например:

```go
if workerCount <= 0 {
	return errors.New("workerCount должен быть положительным")
}
```

### Очень большая очередь — тоже проблема

Даже если конкурентность ограничена, очередь может быть очень большой.

Например:

```text
worker = 10
jobs buffer = 1 000 000
```

Это гарантирует, что одновременно выполняются только 10 задач. Но в памяти в очереди может ждать до миллиона задач.

В результате:

* расходуется много памяти;
* старые задачи очень долго ждут;
* задачи, которые пользователь уже отменил, тоже могут оставаться в очереди;
* система поздно замечает перегрузку.

Поэтому лимит конкурентности и лимит очереди управляются отдельно.

## Panic и очистка ресурсов

В воркерах часто используется:

```go
defer wg.Done()
```

Это хорошая практика.

Каким бы обычным путём ни выходила функция воркера, например через:

```go
return
```

или по завершении цикла, `wg.Done()` выполнится.

Например:

```go
func worker(wg *sync.WaitGroup) {
	defer wg.Done()

	// работа
}
```

Это помогает не забыть уменьшить счётчик `WaitGroup`.

Но panic — отдельный вопрос.

Если внутри воркера возникла panic и её нигде не перехватили через `recover`, обычно останавливается вся Go-программа.

Например:

```go
func worker() {
	panic("непредвиденная ошибка")
}
```

Неперехваченная panic в горутине не просто тихо завершает эту горутину. Runtime выводит stack trace и завершает процесс.

В некоторых серверах или системах обработки задач может понадобиться использовать `recover` на границе воркера.

Но просто проглотить panic через:

```go
recover()
```

тоже нехорошее решение.

Когда происходит panic, обычно как минимум нужно:

* залогировать значение panic;
* сохранить stack trace;
* решить, превращать ли её в результат-ошибку;
* проверить, не нарушено ли состояние системы.

Например, если воркер записал половину операции, а потом произошла panic, простой повтор задачи тоже может быть опасен.

### Каждый ресурс, открытый задачей, нужно закрывать

Поскольку воркеры выполняют много задач, утечка ресурсов может быстро расти.

Например, каждая задача открывает файл:

```go
file, err := os.Open(name)
```

Если файл не закрывать, после многих задач процесс может упереться в лимит файловых дескрипторов.

Или если получен HTTP-ответ:

```go
resp, err := client.Do(req)
```

то там, где нужно, необходимо сделать:

```go
resp.Body.Close()
```

Это относится и к строкам базы данных, транзакциям, сокетам и другим ресурсам.

Worker pool управляет конкурентностью. Но он не очищает автоматически ресурсы внутри воркера.

## Частые ошибки

### Не закрыть канал `jobs`

Если воркер использует:

```go
for job := range jobs {
	// ...
}
```

он продолжает ждать новых значений, пока канал не закрыт.

Даже если producer отправил все задачи, но не сделал:

```go
close(jobs)
```

воркеры не выйдут из цикла.

В результате:

```go
wg.Wait()
```

тоже может не завершиться.

### Закрывать канал из нескольких воркеров

Например, если каждый воркер в конце делает:

```go
close(results)
```

это неправильно.

Первый завершившийся воркер закроет канал.

Если следующий воркер сделает:

```go
results <- result
```

возникнет:

```text
panic: send on closed channel
```

Правило закрытия канала простое:

> Канал должна закрывать сторона, которая точно знает, что новых значений больше не будет.

В канале с множеством отправителей отдельный воркер обычно этого не знает.

### Закрыть `results` до завершения воркеров

Например, такой порядок неправильный:

```go
close(results)
wg.Wait()
```

Правильный порядок:

```go
wg.Wait()
close(results)
```

Сначала все отправляющие воркеры завершаются. Затем канал закрывается.

### Результаты никто не принимает

Представьте, что есть:

```go
results := make(chan Result, 10)
```

Воркеры отправляют результаты, но никто не делает:

```go
<-results
```

Первые 10 значений могут попасть в буфер.

Следующий воркер блокируется на строке:

```go
results <- result
```

Поскольку воркер не завершается:

```go
wg.Done()
```

тоже не вызывается.

А coordinator ждёт на строке:

```go
wg.Wait()
```

Так возникает ситуация, похожая на deadlock.

### Считать, что результаты приходят в порядке ввода

Конкурентные воркеры работают не с одинаковой скоростью.

Поэтому, если отправлены:

```text
job1
job2
job3
```

результаты могут прийти в порядке:

```text
job2
job3
job1
```

Если порядок нужен, его нужно восстанавливать отдельно.

### Создавать ещё неконтролируемые горутины для каждой задачи

Например, чтобы ограничить конкурентность до `10`, создали 10 воркеров.

Но если внутри воркера сделать:

```go
for job := range jobs {
	go process(job)
}
```

лимит пула фактически ломается.

Воркер сам может быстро забрать все задачи и создать для каждой новую горутину.

В результате даже при:

```text
workerCount = 10
```

одновременно могут работать сотни или тысячи горутин `process`.

Если внутренние горутины тоже нужны, для них должен быть отдельный контроль конкурентности.

### Вызывать `WaitGroup.Add` после запуска горутины

Следующего порядка нужно избегать:

```go
go worker(&wg)
wg.Add(1)
```

Воркер может очень быстро завершиться и вызвать:

```go
wg.Done()
```

раньше `Add`.

Поэтому счётчик увеличивают до запуска горутины:

```go
wg.Add(1)
go worker(&wg)
```

Для многих воркеров форма:

```go
wg.Add(workerCount)

for i := 0; i < workerCount; i++ {
	go worker(&wg)
}
```

понятна и безопасна.

### Копировать использованную `WaitGroup`

`sync.WaitGroup` нельзя копировать после первого использования.

Например, передача её в функцию по значению ведёт к неправильному дизайну:

```go
func worker(wg sync.WaitGroup) {
	// ...
}
```

Здесь воркер может работать с копией `WaitGroup`.

Обычно передаётся указатель:

```go
func worker(wg *sync.WaitGroup) {
	defer wg.Done()
}
```

Поэтому в примерах worker pool выше тоже используется:

```go
wg *sync.WaitGroup
```

## Важные моменты для собеседований

Когда спрашивают о worker pool, нужно чётко различать несколько понятий.

Во-первых, worker pool управляет конкурентностью.

Например, при:

```text
1000 jobs
10 workers
```

worker pool гарантирует, что одновременно выполняется работа примерно не более чем 10 воркеров.

Буфер канала управляет другим.

Например, при:

```text
10 workers
буфер 100
```

10 задач могут выполняться, а ещё до 100 задач могут ждать в очереди канала.

То есть:

```text
число воркеров != размер очереди
```

Во-вторых, закрытие канала не удаляет значения.

Если, пока в буфере есть:

```text
job1
job2
job3
```

сделать:

```go
close(jobs)
```

получатели сначала могут забрать эти значения.

Только когда буфер закончится, операция получения:

```go
value, ok := <-jobs
```

даст:

```text
ok == false
```

В-третьих, worker pool не гарантирует порядок результатов.

При конкурентном выполнении результат быстро завершившейся задачи приходит раньше.

В-четвёртых, `sync.WaitGroup` только ждёт завершения горутин.

Она не:

* передаёт ошибки;
* создаёт контекст;
* отправляет сигнал отмены;
* автоматически закрывает каналы;
* обрабатывает panic.

Для этих задач нужны отдельные механизмы.

В-пятых, проверять отмену только в начале воркера недостаточно.

Если producer может блокироваться при отправке, он тоже должен следить за контекстом.

Если воркер может блокироваться при отправке результата, там тоже нужно проверять контекст.

Если `process` работает долго, она тоже должна понимать сигнал отмены.

Поэтому полный поток отмены выглядит примерно так:

```text
cancel()
   |
   v
context
   |
   +----> producer останавливается
   |
   +----> воркер, ожидающий jobs, останавливается
   |
   +----> воркер, отправляющий результат, останавливается
   |
   +----> долгий process, принимающий context, тоже может остановиться
```

При написании надёжного worker pool недостаточно просто создать горутины-воркеры. Очередь задач, владение каналами, порядок закрытия, приём результатов, backpressure, ошибки, отмена и ограничения внешних ресурсов учитываются вместе.
