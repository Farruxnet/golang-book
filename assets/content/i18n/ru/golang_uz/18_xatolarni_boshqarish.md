# Обработка ошибок в Go

Во время работы программы не каждое действие завершается успешно. Например, файл, который программа хочет открыть, может не существовать. Пользователь может ввести неправильное значение. Запрос, отправленный по сети, тоже может не выполниться по разным причинам.

Это естественные для программы ситуации. В Go такие ожидаемые проблемы обычно обрабатываются через значение `error`.

Не каждая функция обязана возвращать `error`. Если выполнение функции может завершиться неудачно, она обычно возвращает `error` вместе с основным результатом.

Например, простой функции вроде сложения двух чисел обычно не нужно возвращать ошибку. Но такие действия, как открытие файла, подключение к базе данных или проверка значения, введённого пользователем, могут завершиться неудачей. Для таких функций возврат `error` естественен.

## Что такое `error`?

В Go `error` — отдельный встроенный интерфейс. Он требует только один метод:

```go
type error interface {
	Error() string
}
```

Интерфейс определяет не то, какие данные хранит тип, а то, какие методы у него должны быть. Пока достаточно понимать
`error` как значение с методом `Error() string`. В следующем уроке об интерфейсах это понятие и то, как тип
соответствует требованию интерфейса, рассматриваются подробно.

Главная мысль здесь очень проста: метод `Error()` представляет ошибку в виде понятной человеку строки `string`.

Если у какого-либо типа есть метод со следующей сигнатурой:

```go
Error() string
```

он может реализовывать интерфейс `error`.

Когда функция выполнилась успешно, вместо `error` она обычно возвращает `nil`. А при ошибке возвращается настоящее значение `error`, описывающее причину проблемы.

Следующая функция делит два числа `float64`:

```go
package main

import (
	"errors"
	"fmt"
)

func divide(a, b float64) (float64, error) {
	if b == 0 {
		return 0, errors.New("делить на ноль нельзя")
	}

	return a / b, nil
}

func main() {
	result, err := divide(10, 4)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}

	fmt.Println("Результат:", result)
}
```

Результат:

```text
Результат: 2.5
```

`divide()` возвращает два значения:

```go
(float64, error)
```

Первое значение — результат вычисления.

Второе значение — информация об ошибке.

Если `b` не равно нулю, деление выполняется успешно:

```go
return a / b, nil
```

Здесь возвращаются настоящий результат и `nil`. `nil` означает отсутствие ошибки.

Если `b == 0`:

```go
return 0, errors.New("делить на ноль нельзя")
```

функция не продолжает вычисление. Возвращаются `0` — нулевое значение типа `float64` — и ошибка.

Здесь есть важное правило: если возвращена ошибка, первому результату обычно доверять нельзя. Вызывающий код должен сначала проверить `err`.

## Проверка ошибки

При вызове функции, которая возвращает `error`, первое, что обычно делают, — проверяют значение `err`.

Например:

```go
result, err := divide(10, 0)
if err != nil {
	fmt.Println("Ошибка:", err)
	return
}

fmt.Println(result)
```

Результат:

```text
Ошибка: делить на ноль нельзя
```

Здесь `divide(10, 0)` вернула ошибку.

Поэтому условие:

```go
if err != nil {
```

становится `true`, и ошибка обрабатывается.

А благодаря `return` оставшийся код не выполняется:

```go
fmt.Println(result)
```

Это хорошая практика. Ведь основной результат, возвращённый после ошибки, обычно непригоден к использованию.

Например, если функция чтения файла вернула ошибку, работать как обычно с полученными от неё `data` может быть неправильно.

Поэтому при обнаружении ошибки обычно принимают одно из следующих решений:

* вернуть ошибку вызывающей функции;
* показать пользователю понятное сообщение;
* повторить действие другим способом;
* использовать отдельный запасной вариант (fallback) для определённого вида ошибки;
* записать ошибку в лог на границе системы.

Это не значит, что «в каждой функции обязательно проверяется `err`». Просто если функция возвращает `error`, вызывающий код должен осознанно решить, что делать с этим значением.

В некоторых случаях ошибку можно и намеренно проигнорировать. Но хорошо, если причина такого решения видна из кода.

Например:

```go
_ = file.Close()
```

Здесь `_` показывает, что ошибка отброшена сознательно. Но если ошибка при закрытии ресурса важна, её тоже может понадобиться проверить.

## Создание ошибки

Для создания простой ошибки с неизменным текстом используется `errors.New()`.

Например:

```go
if age < 0 {
	return errors.New("возраст не может быть отрицательным")
}
```

`errors.New()` создаёт новое значение `error` из заданного текста.

Этот способ удобен, когда текст ошибки известен заранее.

Но иногда в сообщение об ошибке нужно добавить значение, полученное во время выполнения. Например, мы хотим показать, какой именно возраст неправильный.

Тогда удобна `fmt.Errorf()`:

```go
func checkAge(age int) error {
	if age < 0 {
		return fmt.Errorf("неправильный возраст: %d", age)
	}
	return nil
}
```

Если `age == -5`, ошибка будет примерно такой:

```text
неправильный возраст: -5
```

Значение `age` добавлено в текст ошибки через `%d`.

При написании текста ошибки обычно соблюдают несколько небольших правил.

Сообщение должно быть коротким, но объяснять причину проблемы.

Обычно текст ошибки начинается со строчной буквы:

```text
файл не найден
```

и в конце точка не ставится.

Причина в том, что на верхних уровнях ошибка может объединяться с другим текстом.

Например:

```text
загрузка настроек: файл не найден
```

Если бы внутренняя ошибка была написана с заглавной буквы и с точкой, цепочка сообщений выглядела бы менее естественно.

## Передача ошибки наверх

Если функция не может сама обработать ошибку, она возвращает её вызывающему коду.

Самый простой вариант:

```go
if err != nil {
	return err
}
```

Это работает. Но проблема в том, что верхний уровень видит только исходную ошибку. Может остаться непонятным, во время какого именно действия она произошла.

Поэтому полезно добавлять к ошибке контекст.

В следующем примере ошибка передаётся наверх через несколько уровней:

```go
package main

import (
	"fmt"
	"os"
)

func readFile(name string) ([]byte, error) {
	data, err := os.ReadFile(name)
	if err != nil {
		return nil, fmt.Errorf("чтение файла %q: %w", name, err)
	}
	return data, nil
}

func loadConfig() ([]byte, error) {
	data, err := readFile("config.json")
	if err != nil {
		return nil, fmt.Errorf("загрузка настроек: %w", err)
	}
	return data, nil
}

func run() error {
	data, err := loadConfig()
	if err != nil {
		return err
	}

	fmt.Println(string(data))
	return nil
}

func main() {
	if err := run(); err != nil {
		fmt.Println("Программа не запустилась:", err)
	}
}
```

Разберём этот поток по шагам.

Сначала вызывается:

```go
loadConfig()
```

Она вызывает функцию:

```go
readFile("config.json")
```

Внутри `readFile()` выполняется:

```go
os.ReadFile(name)
```

Если `config.json` не существует, `os.ReadFile()` возвращает ошибку.

`readFile()` не просто передаёт эту ошибку дальше. Она добавляет дополнительный контекст:

```go
fmt.Errorf("чтение файла %q: %w", name, err)
```

В результате внутренняя ошибка теперь возвращается вместе с тем, во время какого действия она произошла.

Затем `loadConfig()` тоже добавляет свой контекст:

```go
fmt.Errorf("загрузка настроек: %w", err)
```

В конце `main()` на верхней границе системы выводит ошибку пользователю.

Если `config.json` не существует, сообщение будет примерно таким:

```text
Программа не запустилась: загрузка настроек: чтение файла "config.json": open config.json: no such file or directory
```

Это сообщение можно читать изнутри наружу:

```text
open config.json: no such file or directory
```

— исходная причина на уровне операционной системы.

```text
чтение файла "config.json"
```

— какое действие выполнялось.

```text
загрузка настроек
```

— частью какого большего процесса было это действие.

```text
Программа не запустилась
```

— в каком контексте ошибка показывается пользователю.

Каждый уровень добавил только ту информацию, которая относится к нему.

Ещё один важный момент: нижние функции не выводят ошибку на экран, чтобы потом снова вернуть её наверх.

Например, в `readFile()` так не сделано:

```go
fmt.Println(err)
return nil, err
```

Если каждый уровень будет записывать ошибку в лог и затем возвращать её, одна и та же ошибка может несколько раз повториться в логах.

Обычно хороший подход — добавлять контекст к ошибке на нижних уровнях, а на верхней границе системы один раз вывести её или записать в лог.

### Что делает `%w`?

`%w` внутри `fmt.Errorf()` имеет особый смысл:

```go
fmt.Errorf("загрузка настроек: %w", err)
```

Он оборачивает (wrap) исходную ошибку в новую ошибку.

В результате происходят две вещи:

1. к тексту ошибки добавляется дополнительный контекст;
2. исходная ошибка сохраняется внутри цепочки.

Поэтому позже внутреннюю причину можно найти через `errors.Is()` или `errors.As()`.

Если вместо `%w` использовать `%v`:

```go
fmt.Errorf("загрузка настроек: %v", err)
```

текст ошибки может выглядеть почти так же.

Но исходная `error` не сохраняется как цепочка. А это лишает возможности в дальнейшем проверять ошибку по её типу или причине.

## Проверка причины через `errors.Is()`

Проверять ошибку по её тексту — плохой способ.

Например, такой код считается хрупким:

```go
if err.Error() == "file does not exist" {
	// ...
}
```

Текст ошибки может меняться в зависимости от платформы, библиотеки или добавленного контекста.

Чтобы проверить, есть ли определённое значение ошибки в цепочке, используется `errors.Is()`.

```go
package main

import (
	"errors"
	"fmt"
	"os"
)

func readFile(name string) ([]byte, error) {
	data, err := os.ReadFile(name)
	if err != nil {
		return nil, fmt.Errorf("чтение файла %q: %w", name, err)
	}
	return data, nil
}

func main() {
	_, err := readFile("config.json")
	if errors.Is(err, os.ErrNotExist) {
		fmt.Println("Файл настроек не найден")
		return
	}
	if err != nil {
		fmt.Println("Ошибка:", err)
	}
}
```

Здесь ошибка из `os.ReadFile()` обёрнута через `fmt.Errorf()` и `%w`:

```go
fmt.Errorf("чтение файла %q: %w", name, err)
```

Несмотря на это:

```go
errors.Is(err, os.ErrNotExist)
```

проверяет цепочку ошибок вглубь.

Если в цепочке найдена ошибка, соответствующая `os.ErrNotExist`, возвращается `true`.

Значит, сколько бы контекста ни было добавлено к ошибке, программа может принять решение по исходной причине.

### Sentinel error

Для постоянного и отдельного случая ошибки, относящегося к программе, значение ошибки можно объявить заранее:

```go
var ErrUserNotFound = errors.New("пользователь не найден")
```

Такое значение часто называют **sentinel error** (сигнальной ошибкой).

Например, если вызывающему коду нужно отличить случай «пользователь не найден» от других ошибок:

```go
if errors.Is(err, ErrUserNotFound) {
	// особое решение
}
```

Sentinel error нужна не для каждой ошибки.

Она обычно полезна, когда вызывающему коду нужно программно распознать именно этот случай и отдельно на него отреагировать.

Если ошибка нужна только для того, чтобы показать пользователю текст, создание отдельного sentinel-значения может быть излишним.

## Пользовательская ошибка и `errors.As()`

Иногда одного текста в ошибке недостаточно.

Например, при проверке формы мы хотим отдельно хранить, какое именно поле неправильное, и причину проблемы.

В такой ситуации можно создать пользовательский тип ошибки (custom error type).

```go
package main

import (
	"errors"
	"fmt"
)

type ValidationError struct {
	Field   string
	Message string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("%s: %s", e.Field, e.Message)
}

func createUser(name string, age int) error {
	if name == "" {
		return &ValidationError{
			Field:   "name",
			Message: "не должно быть пустым",
		}
	}
	if age < 0 {
		return &ValidationError{
			Field:   "age",
			Message: "не должно быть отрицательным",
		}
	}
	return nil
}

func register(name string, age int) error {
	if err := createUser(name, age); err != nil {
		return fmt.Errorf("регистрация пользователя: %w", err)
	}
	return nil
}

func main() {
	err := register("", 20)
	if err == nil {
		return
	}

	var validationErr *ValidationError
	if errors.As(err, &validationErr) {
		fmt.Printf("ошибка в поле %s: %s\n", validationErr.Field, validationErr.Message)
		return
	}

	fmt.Println("Непредвиденная ошибка:", err)
}
```

Результат:

```text
ошибка в поле name: не должно быть пустым
```

Сначала создана специальная структура:

```go
type ValidationError struct {
	Field   string
	Message string
}
```

Эта структура хранит две отдельные части информации:

* `Field` — в каком поле произошла ошибка;
* `Message` — пояснение проблемы.

Затем с получателем-указателем написан метод `Error()`:

```go
func (e *ValidationError) Error() string
```

Поэтому `*ValidationError` реализует интерфейс `error`.

Например:

```go
return &ValidationError{
	Field:   "name",
	Message: "не должно быть пустым",
}
```

можно вернуть как обычную `error`.

На следующем уровне ошибка оборачивается:

```go
return fmt.Errorf("регистрация пользователя: %w", err)
```

Значит, `err`, пришедшая в `main()`, может быть не напрямую `*ValidationError`. Снаружи находится ошибка, созданная `fmt.Errorf()`.

Поэтому вместо обычного утверждения типа (type assertion) используется `errors.As()`:

```go
var validationErr *ValidationError
if errors.As(err, &validationErr) {
```

`errors.As()` проверяет цепочку ошибок.

Если внутри найдена `*ValidationError`, её значение записывается в переменную:

```go
validationErr
```

После этого можно использовать структурированные данные внутри пользовательской ошибки:

```go
validationErr.Field
validationErr.Message
```

Это гораздо надёжнее, чем разбирать только текст ошибки.

### Разница между `errors.Is()` и `errors.As()`

Хотя их задачи выглядят похожими, цели у них разные.

`errors.Is()`:

```go
errors.Is(err, ErrUserNotFound)
```

проверяет, есть ли в цепочке определённое значение ошибки или причина.

`errors.As()`:

```go
errors.As(err, &validationErr)
```

находит в цепочке определённый тип ошибки и позволяет получить значение этого типа.

Кратко:

* `errors.Is()` — «есть ли эта ошибка среди причин?»;
* `errors.As()` — «есть ли ошибка такого типа и можешь ли ты дать её данные?».

## `defer` и закрытие ресурсов

Если программа открывает файл, сокет, соединение с базой данных или другой ресурс, важно и вовремя его закрыть.

В Go `defer` позволяет запланировать вызов, который должен выполниться позже.

Отложенный вызов выполняется перед завершением текущей функции.

Это особенно удобно при работе с файлами:

```go
package main

import (
	"fmt"
	"os"
)

func fileSize(name string) (int64, error) {
	file, err := os.Open(name)
	if err != nil {
		return 0, fmt.Errorf("открытие файла: %w", err)
	}
	defer file.Close()

	info, err := file.Stat()
	if err != nil {
		return 0, fmt.Errorf("получение сведений о файле: %w", err)
	}

	return info.Size(), nil
}

func main() {
	size, err := fileSize("config.json")
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	fmt.Println("Размер файла:", size)
}
```

Здесь сначала открывается файл:

```go
file, err := os.Open(name)
```

Если само открытие файла не удалось:

```go
if err != nil {
	return 0, fmt.Errorf("открытие файла: %w", err)
}
```

функция сразу возвращается.

Важный момент: `defer file.Close()` написан только после успешного открытия файла:

```go
defer file.Close()
```

Это правильно, ведь если `os.Open()` вернула ошибку, открытого ресурса `file`, который можно использовать, нет.

Затем выполняется:

```go
info, err := file.Stat()
```

Даже если здесь произойдёт ошибка:

```go
return 0, fmt.Errorf("получение сведений о файле: %w", err)
```

перед завершением функции выполнится отложенный `file.Close()`.

В успешном случае происходит то же самое.

Поэтому `defer` упрощает закрытие ресурса на всех путях выхода.

Иначе перед каждым `return` пришлось бы отдельно писать:

```go
file.Close()
```

### Несколько `defer`

В одной функции может быть несколько `defer`.

Они выполняются в порядке **LIFO**: последний добавленный `defer` выполняется первым.

Например:

```go
defer first()
defer second()
defer third()
```

при завершении функции порядок выполнения такой:

```text
third
second
first
```

Это удобно для закрытия ресурсов в обратном порядке.

Например, если сначала открыли ресурс A, а потом ресурс B, естественно сначала закрыть B, а потом A.

### `defer` и длинные циклы

`defer` выполняется не при завершении текущего блока, а при завершении **функции**.

Поэтому накопление большого количества `defer` внутри долгого цикла требует осторожности.

Например:

```go
for _, name := range names {
	file, err := os.Open(name)
	if err != nil {
		continue
	}
	defer file.Close()
}
```

Здесь каждый файл закрывается не в конце итерации, а при завершении всей функции.

Если файлов много, одновременно может оставаться открытым очень много ресурсов.

В такой ситуации лучше вынести тело цикла в отдельную функцию или закрывать ресурс прямо в нужном месте.

## `panic` и `recover`

В Go есть `panic`, но он не заменяет возврат обычных ошибок.

Ожидаемые проблемы обычно должны возвращаться через `error`.

Например:

* файл не найден;
* пользователь ввёл неправильное значение;
* сеть оборвалась;
* нужная запись в базе данных не найдена.

Это часть обычного потока ошибок.

А `panic` можно использовать в ситуациях, когда программа не может продолжать работу как обычно, или для серьёзных логических ошибок программиста.

При возникновении `panic` обычное выполнение текущей функции останавливается и начинается распространение вверх по стеку. В этом процессе выполняются отложенные функции.

А `recover()` может перехватить значение panic внутри отложенной функции.

```go
package main

import "fmt"

func runSafely(fn func()) {
	defer func() {
		if value := recover(); value != nil {
			fmt.Println("Panic перехвачен:", value)
		}
	}()

	fn()
}

func main() {
	runSafely(func() {
		panic("непредвиденное внутреннее состояние")
	})
}
```

Результат:

```text
Panic перехвачен: непредвиденное внутреннее состояние
```

Разберём поток по шагам.

Сначала вызывается:

```go
runSafely(...)
```

Внутри функции регистрируется отложенная анонимная функция:

```go
defer func() {
	if value := recover(); value != nil {
		fmt.Println("Panic перехвачен:", value)
	}
}()
```

Затем выполняется:

```go
fn()
```

Внутри переданной функции вызывается:

```go
panic("непредвиденное внутреннее состояние")
```

В этой точке обычное выполнение останавливается.

Перед завершением `runSafely()` выполняется её отложенная функция.

`recover()` получает значение, переданное вместе с panic:

```go
"непредвиденное внутреннее состояние"
```

и останавливает распространение panic внутри этой горутины.

Здесь есть важная тонкость.

`recover()` не продолжает выполнение со строки после `panic(...)`.

Например:

```go
func test() {
	panic("ошибка")
	fmt.Println("это не выполнится")
}
```

Даже если `recover()` перехватит panic на верхнем уровне:

```go
fmt.Println("это не выполнится")
```

не запустится.

Функция, в которой произошёл panic, считается завершённой. Управление может вернуться в обычный поток выше после завершения отложенной функции, перехватившей panic.

### Где используется `recover()`?

Ставить `recover()` в каждую функцию не нужно.

Обычно его используют на границе системы.

Например, HTTP-сервер может не захотеть, чтобы непредвиденный `panic` в одном обработчике запроса остановил весь процесс сервера.

На такой границе `recover()` может перехватить panic, записать ошибку в лог и завершить этот запрос с ошибкой.

Но это не значит, что обычные бизнес-ошибки нужно передавать через `panic`.

Например, такой подход не рекомендуется:

```go
if user == nil {
	panic("пользователь не найден")
}
```

если отсутствие `user` — обычный и ожидаемый случай.

В такой ситуации правильнее вернуть обычную `error`.

## Порядок работы с ошибками

В практическом коде для работы с ошибками полезен такой порядок.

1. Функция, в которой может произойти ошибка, возвращает `error`.

2. Если вызывающий код может осмысленно обработать ошибку на своём уровне, пусть принимает решение прямо там.

Например, если при отсутствии файла можно использовать конфигурацию по умолчанию, это можно решить именно на этом уровне.

3. Если уровень не может обработать ошибку, пусть добавит полезный контекст и вернёт её наверх.

Например:

```go
return fmt.Errorf("загрузка настроек: %w", err)
```

4. Если верхнему уровню нужно отдельно отреагировать на определённую причину ошибки, пусть использует `errors.Is()`.

Например:

```go
if errors.Is(err, os.ErrNotExist) {
	// ...
}
```

5. Если из ошибки нужно получить структурированные данные, пусть использует `errors.As()`.

6. Показ ошибки пользователю или запись в лог обычно выполняйте один раз — на границе системы.

7. Не используйте `panic` для ожидаемых ошибок.

Такой подход сохраняет поток ошибок понятным. Нижние уровни не теряют техническую причину, а верхние могут принять подходящее решение для пользователя или системы.

В одном из следующих практических уроков мы увидим на примере программы командной строки запись ошибки в `stderr` и возврат подходящего кода завершения.

## Примеры

### 1. Создание неизменной ошибки

Этот пример показывает повторное использование заранее созданного значения ошибки.

Пустое имя — отдельный случай ошибки:

```go
package main

import (
	"errors"
	"fmt"
)

var ErrEmptyName = errors.New("имя не должно быть пустым")

func validateName(name string) error {
	if name == "" {
		return ErrEmptyName
	}
	return nil
}

func main() {
	err := validateName("")
	if err != nil {
		fmt.Println("Ошибка:", err)
	}
}
```

Здесь:

```go
var ErrEmptyName = errors.New("имя не должно быть пустым")
```

создаёт одно значение ошибки на уровне пакета.

`validateName()` проверяет имя:

```go
if name == "" {
	return ErrEmptyName
}
```

Пустое значение `string`:

```go
""
```

— нулевое значение типа `string`.

В этом примере оно означает случай «имя не введено».

Если имя есть, возвращается:

```go
return nil
```

А если имя пустое, возвращается именно `ErrEmptyName`.

Польза такого заранее объявленного значения ошибки в том, что при необходимости вызывающий код может позже проверить его через:

```go
errors.Is(err, ErrEmptyName)
```

### 2. Добавление значения в сообщение об ошибке

В этом примере с помощью `fmt.Errorf()` добавим в сообщение, какое именно значение возраста неправильное.

```go
package main

import "fmt"

func validateAge(age int) error {
	if age < 0 {
		return fmt.Errorf("возраст не должен быть отрицательным: %d", age)
	}
	return nil
}

func main() {
	if err := validateAge(-4); err != nil {
		fmt.Println("Ошибка:", err)
		return
	}

	fmt.Println("Возраст принят")
}
```

Условие внутри `validateAge()`:

```go
if age < 0 {
```

отклоняет только отрицательные значения.

Например:

```text
-1
-4
-100
```

считаются ошибкой.

Но `0` автоматически ошибкой не считается.

Поэтому используется:

```go
age < 0
```

а не `age <= 0`.

Это зависит от бизнес-правила. Если в системе возраст обязательно должен быть `1` или больше, условие могло бы быть другим.

Место, где создаётся ошибка:

```go
fmt.Errorf("возраст не должен быть отрицательным: %d", age)
```

Здесь `%d` добавляет пришедшее значение `int` в сообщение.

Если `age == -4`, получится:

```text
возраст не должен быть отрицательным: -4
```

Для отладки и объяснения проблемы пользователю это может быть полезнее простого статического текста.

### 3. Возврат ошибки вместе с результатом

Этот пример показывает, как функция одновременно возвращает основной результат и `error`.

Если запрошено больше товара, чем есть на складе, действие не выполняется.

```go
package main

import (
	"errors"
	"fmt"
)

func remaining(stock, requested int) (int, error) {
	if requested < 1 {
		return 0, errors.New("запрошенное количество должно быть положительным")
	}
	if requested > stock {
		return 0, errors.New("на складе недостаточно товара")
	}
	return stock - requested, nil
}

func main() {
	left, err := remaining(12, 5)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}

	fmt.Println("Осталось:", left)
}
```

Сначала проверяется запрошенное количество:

```go
if requested < 1 {
```

`requested` должно быть не меньше `1`.

Затем проверяется, достаточно ли товара на складе:

```go
if requested > stock {
```

Если `requested` больше `stock`, вычисление не имеет смысла.

В обоих случаях ошибки возвращается:

```go
return 0, ...
```

Нулевое значение типа `int` — `0`.

Но вызывающий код сначала проверяет:

```go
if err != nil {
```

Поэтому `0` из случая ошибки не используется как настоящий результат.

В успешном случае выполняется:

```go
return stock - requested, nil
```

Заданные значения:

```text
stock = 12
requested = 5
```

Вычисление:

```text
12 - 5 = 7
```

Поэтому функция возвращает:

```text
7, nil
```

Результат:

```text
Осталось: 7
```

### 4. Обёртывание и передача sentinel-ошибки

Этот пример показывает передачу sentinel error на верхний уровень с контекстом и последующее определение исходной причины через `errors.Is()`.

```go
package main

import (
	"errors"
	"fmt"
)

var ErrProductNotFound = errors.New("товар не найден")

func findProduct(id int) error {
	if id != 10 {
		return ErrProductNotFound
	}
	return nil
}

func loadProduct(id int) error {
	if err := findProduct(id); err != nil {
		return fmt.Errorf("загрузка товара с идентификатором %d: %w", id, err)
	}
	return nil
}

func main() {
	err := loadProduct(25)
	if errors.Is(err, ErrProductNotFound) {
		fmt.Println("Выберите другой товар")
		return
	}
	fmt.Println("Товар загружен")
}
```

Sentinel error:

```go
var ErrProductNotFound = errors.New("товар не найден")
```

выражает конкретный бизнес-случай.

Для простоты примера существующим считается только товар с `id == 10`:

```go
if id != 10 {
	return ErrProductNotFound
}
```

При вызове `loadProduct(25)` функция `findProduct(25)` возвращает ошибку.

Но `loadProduct()` не передаёт эту ошибку напрямую:

```go
return fmt.Errorf("загрузка товара с идентификатором %d: %w", id, err)
```

В результате получается примерно такая ошибка:

```text
загрузка товара с идентификатором 25: товар не найден
```

Здесь `%w` очень важен.

Он сохраняет `ErrProductNotFound` как внутреннюю причину.

Поэтому:

```go
errors.Is(err, ErrProductNotFound)
```

возвращает `true`.

Вызывающий код не сравнивает текст ошибки. Он принимает решение по настоящей причине ошибки:

```go
fmt.Println("Выберите другой товар")
```

Это типичный пример того, как sentinel error и обёртывание работают вместе.

### 5. Получение данных из пользовательского типа ошибки

В этом примере ошибка — не просто текст: она хранит структурированные данные в отдельных полях.

```go
package main

import (
	"errors"
	"fmt"
)

type FieldError struct {
	Field string
	Value int
}

func (e *FieldError) Error() string {
	return fmt.Sprintf("неправильное значение в поле %s: %d", e.Field, e.Value)
}

func validateCount(count int) error {
	if count < 1 {
		return &FieldError{Field: "count", Value: count}
	}
	return nil
}

func main() {
	err := validateCount(0)
	var fieldErr *FieldError
	if errors.As(err, &fieldErr) {
		fmt.Println("Поле:", fieldErr.Field)
		fmt.Println("Значение:", fieldErr.Value)
	}
}
```

Пользовательский тип ошибки:

```go
type FieldError struct {
	Field string
	Value int
}
```

хранит две части информации по отдельности.

`Field` показывает, какое поле неправильное.

`Value` хранит, какое именно неправильное значение пришло.

Затем написан метод `Error()`:

```go
func (e *FieldError) Error() string
```

Поэтому `*FieldError` соответствует интерфейсу `error`.

`count` должно быть не меньше `1`:

```go
if count < 1 {
```

В примере передан `0`:

```go
err := validateCount(0)
```

Поэтому возвращается ошибка с содержимым:

```go
&FieldError{
	Field: "count",
	Value: 0,
}
```

Затем объявляется переменная:

```go
var fieldErr *FieldError
```

`errors.As()`:

```go
errors.As(err, &fieldErr)
```

проверяет, соответствует ли ошибка типу `*FieldError`.

Если соответствует, найденное значение записывается в `fieldErr`.

После этого разбирать текст ошибки не нужно:

```go
fieldErr.Field
fieldErr.Value
```

напрямую дают нужные данные.

### 6. Просмотр цепочки обёрнутых ошибок

Этот пример показывает, что ошибки, обёрнутые через `%w`, образуют вложенную цепочку и её можно развернуть с помощью `errors.Unwrap()`.

```go
package main

import (
	"errors"
	"fmt"
)

func prepareReport() error {
	base := errors.New("данные недоступны")
	loadErr := fmt.Errorf("загрузка данных: %w", base)
	return fmt.Errorf("подготовка отчёта: %w", loadErr)
}

func main() {
	err := prepareReport()
	for err != nil {
		fmt.Println(err)
		err = errors.Unwrap(err)
	}
}
```

Сначала создаётся самая внутренняя ошибка:

```go
base := errors.New("данные недоступны")
```

Затем она оборачивается:

```go
loadErr := fmt.Errorf("загрузка данных: %w", base)
```

Теперь цепочка примерно такая:

```text
загрузка данных
    ↓
данные недоступны
```

Потом добавляется ещё один уровень:

```go
return fmt.Errorf("подготовка отчёта: %w", loadErr)
```

В результате цепочка:

```text
подготовка отчёта
    ↓
загрузка данных
    ↓
данные недоступны
```

В `main()` цикл:

```go
for err != nil {
```

продолжает работу, пока есть ошибка.

Сначала выводится текущая внешняя ошибка:

```go
fmt.Println(err)
```

Затем через:

```go
err = errors.Unwrap(err)
```

происходит переход на один внутренний уровень.

Процесс примерно такой:

```text
1. подготовка отчёта: загрузка данных: данные недоступны

2. загрузка данных: данные недоступны

3. данные недоступны

4. nil
```

Поскольку самая внутренняя простая ошибка не обёрнута, после неё:

```go
errors.Unwrap(err)
```

возвращает `nil`.

Тогда цикл заканчивается.

В практическом коде обычно не нужно вручную разворачивать цепочку через `Unwrap()`. `errors.Is()` и `errors.As()` обычно сами выполняют нужную проверку. Но этот пример полезен для понимания того, как устроено обёртывание.

### 7. Объединение нескольких ошибок

Иногда нужно выполнить несколько независимых проверок и вернуть все найденные ошибки вместе.

Для этого можно использовать `errors.Join()`.

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNameRequired = errors.New("нужно имя")
var ErrPriceInvalid = errors.New("цена должна быть положительной")

func validateProduct(name string, price int) error {
	var nameErr error
	var priceErr error

	if name == "" {
		nameErr = ErrNameRequired
	}
	if price < 1 {
		priceErr = ErrPriceInvalid
	}

	return errors.Join(nameErr, priceErr)
}

func main() {
	err := validateProduct("", 0)
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrNameRequired))
	fmt.Println(errors.Is(err, ErrPriceInvalid))
}
```

Функция выполняет две независимые проверки:

```go
if name == "" {
```

и:

```go
if price < 1 {
```

Важно, что при обнаружении первой ошибки функция не возвращается сразу.

Вместо этого ошибки сохраняются в отдельных переменных:

```go
var nameErr error
var priceErr error
```

Нулевое значение интерфейсного типа `error` — `nil`.

Значит, в начале:

```text
nameErr  = nil
priceErr = nil
```

Если имя пустое:

```go
nameErr = ErrNameRequired
```

Если цена неправильная:

```go
priceErr = ErrPriceInvalid
```

В конце вызывается:

```go
return errors.Join(nameErr, priceErr)
```

`errors.Join()` отбрасывает элементы, равные `nil`, и объединяет оставшиеся ошибки в одно значение `error`.

В примере обе проверки не проходят:

```go
validateProduct("", 0)
```

Поэтому в объединённой ошибке есть обе причины.

В результате:

```go
errors.Is(err, ErrNameRequired)
```

равно `true`, и:

```go
errors.Is(err, ErrPriceInvalid)
```

тоже `true`.

Это важное свойство `errors.Join()`: причины внутри объединённой ошибки можно проверять через `errors.Is()` и `errors.As()`.

### 8. Выполнение `defer` при раннем возврате

Этот пример показывает, что `defer` работает, даже если функция завершается раньше из-за ошибки.

```go
package main

import (
	"errors"
	"fmt"
)

func process(value int) error {
	fmt.Println("Процесс начался")
	defer fmt.Println("Очистка выполнена")

	if value < 0 {
		return errors.New("значение не должно быть отрицательным")
	}

	fmt.Println("Значение:", value)
	return nil
}

func main() {
	if err := process(-1); err != nil {
		fmt.Println("Ошибка:", err)
	}
}
```

Сначала выполняется:

```go
fmt.Println("Процесс начался")
```

Затем:

```go
defer fmt.Println("Очистка выполнена")
```

регистрируется как отложенный вызов.

В этот момент он не выполняется.

Затем проверяется `value`:

```go
if value < 0 {
```

В примере:

```text
value = -1
```

Поэтому функция завершается раньше через:

```go
return errors.New("значение не должно быть отрицательным")
```

Но перед выполнением `return` срабатывает отложенный вызов:

```text
Очистка выполнена
```

Только после этого управление возвращается в `main()`.

Результат примерно такой:

```text
Процесс начался
Очистка выполнена
Ошибка: значение не должно быть отрицательным
```

Значит, `defer` работает не только при успешном `return nil`, но и при раннем `return` из-за ошибки.

Именно поэтому `defer` так удобен для очистки ресурсов.

### 9. Порядок нескольких `defer`

Этот пример показывает, в каком порядке выполняются отложенные вызовы.

```go
package main

import "fmt"

func steps() {
	defer fmt.Println("шаг 1 закрыт")
	defer fmt.Println("шаг 2 закрыт")
	defer fmt.Println("шаг 3 закрыт")

	fmt.Println("Основная работа выполнена")
}

func main() {
	steps()
}
```

Во время работы функции `defer` регистрируются в таком порядке:

```text
шаг 1 закрыт
шаг 2 закрыт
шаг 3 закрыт
```

Но выполняются они не в этом порядке.

`defer` работают, как стек, в порядке LIFO:

```text
Last In, First Out
```

То есть последний добавленный вызов выполняется первым.

Сначала выполняется обычный код:

```text
Основная работа выполнена
```

Затем отложенные вызовы выполняются в порядке:

```text
шаг 3 закрыт
шаг 2 закрыт
шаг 1 закрыт
```

Полный результат:

```text
Основная работа выполнена
шаг 3 закрыт
шаг 2 закрыт
шаг 1 закрыт
```

Этот порядок полезен при работе с ресурсами.

Например, если ресурсы были открыты в таком порядке:

```text
A
B
C
```

закрывать их обычно нужно в обратном порядке:

```text
C
B
A
```

Свойство LIFO у `defer` как раз этому соответствует.

### 10. Превращение `panic` в ошибку

В этом примере функция на границе системы превращает непредвиденное значение `panic` в обычную `error`.

```go
package main

import "fmt"

func safeRun(action func()) (err error) {
	defer func() {
		if value := recover(); value != nil {
			err = fmt.Errorf("действие прервано: %v", value)
		}
	}()

	action()
	return nil
}

func main() {
	err := safeRun(func() {
		panic("внутреннее состояние нарушено")
	})
	if err != nil {
		fmt.Println("Ошибка:", err)
	}
}
```

Обратите внимание на сигнатуру функции в этом примере:

```go
func safeRun(action func()) (err error)
```

`err` — именованное возвращаемое значение.

Это значит, что отложенная функция может записать значение в переменную `err`.

Сначала регистрируется `defer`:

```go
defer func() {
	if value := recover(); value != nil {
		err = fmt.Errorf("действие прервано: %v", value)
	}
}()
```

Затем вызывается:

```go
action()
```

Переданная функция выполняет:

```go
panic("внутреннее состояние нарушено")
```

Тут же обычное выполнение `action()` останавливается.

Стек начинает раскручиваться, и выполняется отложенная функция `safeRun()`.

`recover()` получает значение panic:

```go
value == "внутреннее состояние нарушено"
```

Затем это значение превращается в обычную `error`:

```go
err = fmt.Errorf("действие прервано: %v", value)
```

В результате из `safeRun()` возвращается примерно такая ошибка:

```text
действие прервано: внутреннее состояние нарушено
```

А `main()` обрабатывает её как обычную `error`:

```go
if err != nil {
	fmt.Println("Ошибка:", err)
}
```

Результат:

```text
Ошибка: действие прервано: внутреннее состояние нарушено
```

Этот подход не нужно использовать для обычных проверок.

Например, если пользователь прислал неправильное значение, вместо:

```go
panic("неправильное значение")
```

функция должна напрямую вернуть `error`.

Превращение `panic` в `error` используется скорее на границах серверов, воркеров или других систем, чтобы непредвиденный внутренний сбой не обрушил весь процесс.
