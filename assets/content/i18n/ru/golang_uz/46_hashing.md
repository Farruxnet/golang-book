# Работа с хешированием и Base64 в Go

Хеширование (hashing) — процесс получения из данных произвольной длины хеш-значения фиксированной длины, то есть **digest** (дайджеста).

Проще говоря, хеш-функция принимает данные и вычисляет из них короткое значение фиксированной длины.

Например, хеши используются для таких задач:

* проверка, что скачанный файл не повреждён;
* создание ключа для кеша;
* определение, изменились ли данные;
* проверка целостности сообщения;
* аутентификация сообщения через HMAC.

Здесь есть несколько понятий, которые выглядят похоже, но имеют совершенно разное назначение. Важно их не смешивать:

* **хеш** — обычно одностороннее преобразование;
* **Base64** — обратимое текстовое кодирование;
* **шифрование (`encryption`)** — защита, обратимая с помощью ключа;
* **HMAC** — способ проверить целостность и подлинность сообщения с помощью секретного ключа.

Например, данные, закодированные в Base64, нельзя считать секретными. Их может декодировать кто угодно. Точно так же обычный digest SHA-256 не доказывает, кто отправил сообщение.

## Основные свойства хеш-функции

Хорошая криптографическая хеш-функция обладает несколькими важными свойствами.

Во-первых, одинаковый вход всегда даёт одинаковый digest.

Например:

```text
"привет" -> одинаковый digest
"привет" -> снова тот же digest
```

Это свойство позволяет позже проверить, изменился ли файл или текст.

Во-вторых, очень маленькое изменение входа резко меняет digest. Например, даже замена одной буквы на заглавную может дать совершенно другой результат.

В-третьих, восстановить исходные данные из digest должно быть практически трудно. Хеш — это не шифрование, поэтому ключа для его «расшифровки» не существует.

В-четвёртых, должно быть трудно найти одинаковый digest для двух разных входов. Такая ситуация называется **коллизией (`collision`)**.

Например:

```text
данные A -> abc123...
данные B -> abc123...
```

Если `A` и `B` разные, а digest одинаковый, произошла коллизия.

От криптографического хеш-алгоритма требуется, чтобы намеренно создать такую коллизию было очень трудно.

Длина digest не зависит от размера входа.

Например, SHA-256:

* и для пустого текста;
* и для короткого текста вроде `"привет"`;
* и для файла в несколько гигабайт

всегда даёт 256-битный digest.

256 бит означает:

```text
256 / 8 = 32 байта
```

Поэтому результат SHA-256 всегда 32 байта.

> **Внимание**
>
> Хеш-значение не скрывает данные.
>
> Если входные значения легко угадать, атакующий может сам хешировать вероятные значения и сравнить их с digest.
>
> Например, если пароль `"123456"`, атакующий может вычислить через SHA-256 список распространённых паролей. Поэтому обычный SHA-256 не подходит для хранения паролей.

## Первый пример с SHA-256

Пакет `crypto/sha256` из стандартной библиотеки Go позволяет вычислить digest SHA-256.

В следующем примере вычислим значение SHA-256 текста `"привет мир"`:

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

func main() {
	data := []byte("привет мир")
	sum := sha256.Sum256(data)

	fmt.Println("Количество байтов:", len(sum))
	fmt.Println("SHA-256:", hex.EncodeToString(sum[:]))
}
```

Результат:

```text
Количество байтов: 32
SHA-256: 527c01ee137e87eaba739dc590ea562e9114057d3f7aba84ff429ba8ccf3b6ad
```

Теперь рассмотрим важные строки по отдельности.

```go
data := []byte("привет мир")
```

SHA-256 работает не с текстом, а с байтами. Поэтому `string` сначала преобразована в `[]byte`.

Затем:

```go
sum := sha256.Sum256(data)
```

`sha256.Sum256()` принимает `[]byte` и возвращает значение `[32]byte`.

Это не `slice`, а массив, длина которого известна на этапе компиляции:

```go
[32]byte
```

32 байта вытекают именно из длины digest SHA-256 в 256 бит:

```text
256 бит / 8 = 32 байта
```

В следующей строке:

```go
len(sum)
```

результат будет `32`.

Сам digest состоит из бинарных байтов. Чтобы его было удобно читать в терминале, его часто переводят в шестнадцатеричный вид:

```go
hex.EncodeToString(sum[:])
```

Здесь:

```go
sum[:]
```

создаёт slice `[]byte` из массива `[32]byte`.

А `hex.EncodeToString()` записывает каждый байт двумя шестнадцатеричными символами.

Например, один байт:

```text
255
```

в шестнадцатеричном виде:

```text
ff
```

Поскольку SHA-256 — 32 байта, длина шестнадцатеричной строки:

```text
32 × 2 = 64 символа
```

Поэтому, видя digest SHA-256 в hex-формате, вы обычно видите 64 символа.

Если снова захешировать тот же текст, результат не изменится. Но даже малейшее различие во входе меняет digest.

Например:

```text
привет
Привет
привет 
```

хотя эти три текста на вид очень похожи, их байты не одинаковы. В результате и digest получаются разными.

Это правило важно и при работе с Unicode. Тексты, которые выглядят одинаково, иногда могут быть выражены разными кодовыми точками Unicode. Хеш вычисляется не по видимым символам, а именно по последовательности байтов.

Для вывода digest SHA-256 не обязательно использовать пакет `encoding/hex`. `fmt` тоже умеет показывать байты в шестнадцатеричном формате:

```go
sum := sha256.Sum256([]byte("go-lang.uz"))
fmt.Printf("%x\n", sum)
```

Здесь:

```text
%x
```

выводит байты в шестнадцатеричном формате строчными буквами.

Такой способ очень удобен, когда нужно только показать digest.

Если hex-строку потом нужно использовать как отдельную переменную, больше подходит `hex.EncodeToString()`.

## Потоковое хеширование больших данных

Небольшой текст или небольшой файл удобно хешировать одним вызовом `sha256.Sum256()`.

Но при работе с большим файлом загружать его целиком в RAM — плохой подход.

Например, чтение файла на 10 GB так:

```go
data, err := os.ReadFile("big-file.iso")
```

пытается загрузить весь файл в память.

А для вычисления хеша это не нужно. Хеш-алгоритм умеет принимать данные по частям.

В Go для этого используется `sha256.New()`. Он возвращает объект, реализующий интерфейс `hash.Hash`.

```go
package main

import (
	"crypto/sha256"
	"fmt"
	"io"
	"log"
	"strings"
)

func main() {
	source := strings.NewReader("данные из большого файла")
	hasher := sha256.New()

	if _, err := io.Copy(hasher, source); err != nil {
		log.Fatal(err)
	}

	fmt.Printf("%x\n", hasher.Sum(nil))
}
```

Результат — digest SHA-256 из 64 символов:

```text
a5c1a8636fb1d52fbdf3c1fbfc6024f6694d0d06db8bbf7091d1d01d536c0b03
```

В этом примере:

```go
source := strings.NewReader("данные из большого файла")
```

создаёт источник, выполняющий роль `io.Reader`.

В реальной программе это часто файл:

```go
file, err := os.Open("big-file.iso")
```

Затем:

```go
hasher := sha256.New()
```

создаёт новый hasher, вычисляющий SHA-256.

Результат `sha256.New()` реализует интерфейс `hash.Hash`. А `hash.Hash` может работать и как `io.Writer`.

Поэтому возможен такой код:

```go
io.Copy(hasher, source)
```

`io.Copy()` читает данные из `source` по частям и записывает их в `hasher`.

Процесс идёт примерно так:

```text
source
  ↓
первая часть
  ↓
hasher.Write(...)

source
  ↓
вторая часть
  ↓
hasher.Write(...)

source
  ↓
следующие части
  ↓
hasher.Write(...)
```

Hasher обновляет своё внутреннее состояние при поступлении каждой части.

Здесь есть важный момент:

```go
hasher.Write(data)
```

не возвращает digest сразу.

Он только обновляет внутреннее состояние вычисления.

В конце:

```go
hasher.Sum(nil)
```

возвращает digest всех данных, записанных к этому моменту.

`Sum(nil)` не сбрасывает состояние hasher.

Например:

```go
hasher.Write([]byte("привет"))
sum1 := hasher.Sum(nil)

hasher.Write([]byte(" мир"))
sum2 := hasher.Sum(nil)
```

`sum2` вычислен не только для `" мир"`. Это digest для:

```text
"привет мир"
```

Если нужно начать новое, независимое вычисление хеша, есть два варианта:

```go
hasher.Reset()
```

или создать новый hasher:

```go
hasher = sha256.New()
```

Главная польза потокового подхода в том, что расход памяти не привязан напрямую к размеру файла.

Например, для хеширования файла на 10 GB не нужно 10 GB RAM. Файл читается небольшими частями, и digest вычисляется поэтапно.

## Почему MD5 и SHA-1 небезопасны?

MD5 и SHA-1 — старые хеш-алгоритмы.

MD5 даёт digest:

```text
128 bit = 16 байт
```

А SHA-1 даёт digest:

```text
160 bit = 20 байт
```

Проблема не только в том, что digest короче, чем у SHA-256. Самая важная проблема — для этих алгоритмов существуют практические атаки на коллизии.

То есть атакующий может получить одинаковый digest для двух разных специально подготовленных файлов.

Если система безопасности опирается на предположение:

```text
digest одинаковый -> файл одинаковый
```

такая коллизия создаёт большую проблему.

Поэтому MD5 и SHA-1 не рекомендуются для новых решений в области безопасности.

MD5 иногда может встречаться для совместимости с legacy-системой или в старых форматах контрольных сумм, не связанных с безопасностью.

Вычислить MD5 в Go технически очень просто:

```go
package main

import (
	"crypto/md5"
	"fmt"
)

func main() {
	sum := md5.Sum([]byte("привет мир"))
	fmt.Printf("%x\n", sum)
}
```

Результат:

```text
0d171f26ea8de897e8aeb0c261b70c7f
```

Результат MD5 — 16 байт:

```text
128 бит / 8 = 16 байт
```

Поскольку в шестнадцатеричном виде каждый байт превращается в два символа, выходит:

```text
16 × 2 = 32 символа
```

Код работает правильно. Проблема не в API, а в свойствах безопасности алгоритма.

Не используйте MD5 для таких задач:

* хранение паролей;
* проверка безопасности цифровой подписи;
* решения безопасности, связанные с сертификатами;
* проверка подлинности файла, который атакующий может изменить.

Если legacy-протокол требует именно MD5, возможно, придётся его использовать. Но такая ситуация не означает, что MD5 — хороший выбор для нового дизайна безопасности.

## Обычный хеш не даёт аутентификации

SHA-256 помогает обнаружить, что данные изменились.

Например, пусть сервер дал digest для файла:

```text
file.zip
SHA-256: abc123...
```

После скачивания файла можно вычислить SHA-256 и сравнить результат с ожидаемым digest.

Это хорошо обнаруживает случайные повреждения.

Но здесь есть важное ограничение.

Если атакующий:

* может изменить сообщение;
* может изменить и digest,

он сам вычислит новый digest SHA-256 для нового сообщения.

Например:

```text
исходное сообщение:
amount=150000

исходный digest:
SHA256(amount=150000)
```

Атакующий может заменить и то и другое:

```text
новое сообщение:
amount=1

новый digest:
SHA256(amount=1)
```

Если получатель проверяет через обычный SHA-256, digest окажется правильным.

Значит, обычный хеш не доказывает, **кем отправлено** сообщение.

Для этого используется HMAC.

HMAC использует вместе с хеш-функцией секретный ключ, известный только доверенным сторонам.

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

func sign(message, key []byte) []byte {
	mac := hmac.New(sha256.New, key)
	mac.Write(message)
	return mac.Sum(nil)
}

func main() {
	message := []byte("order_id=42&amount=150000")
	key := []byte("server-secret-key")

	signature := sign(message, key)
	fmt.Println("Подпись:", hex.EncodeToString(signature))
	fmt.Println("Совпадает:", hmac.Equal(signature, sign(message, key)))
	fmt.Println("Изменённое сообщение:", hmac.Equal(signature, sign([]byte("order_id=42&amount=1"), key)))
}
```

Результат:

```text
Подпись: babc8e66e258fc5c0b4ed823d4bbbf7c3989e2bb84b2e884c6ae6e1d51270b9c
Совпадает: true
Изменённое сообщение: false
```

Сначала рассмотрим функцию `sign()`:

```go
func sign(message, key []byte) []byte {
	mac := hmac.New(sha256.New, key)
	mac.Write(message)
	return mac.Sum(nil)
}
```

Здесь:

```go
hmac.New(sha256.New, key)
```

создаёт HMAC на основе SHA-256.

Первый аргумент:

```go
sha256.New
```

— функция, создающая хеш-функцию.

Второй аргумент:

```go
key
```

— секретный ключ.

Затем:

```go
mac.Write(message)
```

добавляет подписываемое сообщение в вычисление HMAC.

В конце:

```go
mac.Sum(nil)
```

возвращает результат HMAC.

В HMAC результат зависит не только от сообщения, но и от ключа.

Поэтому:

```text
одинаковое сообщение + одинаковый ключ -> одинаковый HMAC
```

но:

```text
другое сообщение + одинаковый ключ -> другой HMAC
```

и:

```text
одинаковое сообщение + другой ключ -> другой HMAC
```

Главная идея: если атакующий не знает секретный ключ, он не может вычислить правильное значение HMAC для изменённого сообщения.

Для проверки используется:

```go
hmac.Equal(signature, calculatedSignature)
```

В примере:

```go
hmac.Equal(signature, sign(message, key))
```

возвращает `true`, потому что и сообщение, и ключ те же самые.

Но:

```go
hmac.Equal(
	signature,
	sign([]byte("order_id=42&amount=1"), key),
)
```

возвращает `false`, потому что сообщение изменилось.

Почему не используется обычный `==` или обычное сравнение строк?

При сравнении значений, связанных с безопасностью, информация может утечь через время выполнения. `hmac.Equal()` специально написан для такой проверки.

Поэтому при проверке подписи HMAC нужно использовать:

```go
hmac.Equal(a, b)
```

Использование обычного:

```go
a == b
```

или `==` для hex-строк — плохая практика с точки зрения безопасности.

В примере секретный ключ записан в коде:

```go
key := []byte("server-secret-key")
```

Это только для объяснения.

В реальном production-проекте не храните секреты в исходном коде.

Ключ обычно получают через:

* переменную окружения;
* менеджер секретов;
* секрет контейнера;
* Kubernetes Secret;
* другую защищённую конфигурацию.

## Base64 — не хеш

Поскольку Base64 часто встречается рядом с темами безопасности, его легко спутать с хешированием или шифрованием.

На самом деле Base64 — способ **кодирования (`encoding`)**.

Он выражает бинарные данные только с помощью текстовых символов.

Например, если бинарные данные нужно передать внутри:

* JSON;
* XML;
* email;
* URL;
* другого текстового протокола,

Base64 может быть полезен.

Но Base64 не даёт никакой секретности.

Закодированные данные может снова декодировать кто угодно.

В следующем примере сначала кодируем текст через Base64, а затем восстанавливаем его:

```go
package main

import (
	"encoding/base64"
	"fmt"
)

func main() {
	data := []byte("привет мир")
	encoded := base64.StdEncoding.EncodeToString(data)

	decoded, err := base64.StdEncoding.DecodeString(encoded)
	if err != nil {
		fmt.Println("Ошибка декодирования:", err)
		return
	}

	fmt.Println("Закодировано:", encoded)
	fmt.Println("Восстановлено:", string(decoded))
}
```

Результат:

```text
Закодировано: 0L/RgNC40LLQtdGCINC80LjRgA==
Восстановлено: привет мир
```

Строка кодирования:

```go
encoded := base64.StdEncoding.EncodeToString(data)
```

превращает байты внутри `data` в текст Base64.

Результат:

```text
0L/RgNC40LLQtdGCINC80LjRgA==
```

Это значение не зашифровано. Для его декодирования секретный ключ не нужен.

Следующая строка:

```go
decoded, err := base64.StdEncoding.DecodeString(encoded)
```

возвращает строку Base64 обратно в исходные байты.

Если строка не в правильном формате Base64, `DecodeString()` возвращает ошибку.

Например, при неверном символе или неправильном padding:

```go
decoded, err := base64.StdEncoding.DecodeString("###")
```

`err` не будет `nil`.

Base64 также немного увеличивает объём данных.

Основное правило:

```text
3 байта -> 4 символа Base64
```

Например:

```text
24 бита на входе
↓
4 × 6 бит
↓
4 символа Base64
```

Поэтому результат обычно примерно на треть больше исходных данных.

Точнее, длина обычно округляется до блоков по 4 байта.

Символ в конце Base64:

```text
=
```

— это **padding**, то есть символ-заполнитель.

Он помогает показать, что последний блок не был полными 3 байтами.

## Стандартный и URL-safe Base64

У Base64 есть несколько вариантов.

В Go чаще всего используются:

```go
base64.StdEncoding
base64.URLEncoding
base64.RawURLEncoding
```

Их различие особенно важно внутри URL.

В стандартном алфавите Base64 есть символы:

```text
+
/
```

Внутри URL эти символы могут иметь особый смысл или требовать дополнительного экранирования.

Поэтому URL-safe вариант использует замену:

```text
+ -> -
/ -> _
```

Следующий пример показывает разницу:

```go
package main

import (
	"encoding/base64"
	"fmt"
)

func main() {
	data := []byte{251, 255, 239}

	fmt.Println(base64.StdEncoding.EncodeToString(data))
	fmt.Println(base64.RawURLEncoding.EncodeToString(data))
}
```

Результат:

```text
+//v
-__v
```

Первый результат:

```text
+//v
```

получен через `StdEncoding`.

Второй результат:

```text
-__v
```

получен через `RawURLEncoding`.

Здесь заменены:

```text
+ -> -
/ -> _
```

А `Raw` в названии `RawURLEncoding` означает, что padding не используется.

Например, обычный URL-safe вариант:

```go
base64.URLEncoding
```

может работать с padding.

А raw-вариант:

```go
base64.RawURLEncoding
```

не записывает символы padding `=` в конце.

Raw URL-safe формат часто встречается в URL-токенах, частях JWT или значениях, подходящих для имён файлов.

Важно использовать один и тот же вариант при кодировании и декодировании.

Например, если значение создано через:

```go
base64.RawURLEncoding.EncodeToString(data)
```

декодировать его обычно нужно через:

```go
base64.RawURLEncoding.DecodeString(value)
```

Если использовать другой вариант, алфавит или правило padding могут не совпасть, и `DecodeString()` вернёт ошибку.

## Как нужно хранить пароли?

SHA-256 и SHA-512 — сильные криптографические хеш-алгоритмы.

Но это не делает их автоматически хорошими для хранения паролей.

Проблема в том, что SHA-256 работает очень быстро.

При проверке целостности файла это преимущество:

```text
много данных -> быстрый digest
```

Но для паролей именно эта скорость создаёт опасность.

Если хеши паролей утекут из базы данных, атакующий может попытаться быстро проверить миллионы или миллиарды вероятных паролей.

Например:

```text
123456
password
qwerty
admin
...
```

Вычисление SHA-256 для каждой догадки очень дёшево.

Поэтому для паролей используются специальные алгоритмы **password hashing**.

Распространённые варианты:

* Argon2id;
* scrypt;
* bcrypt;
* PBKDF2, если этого требует организация или стандарт.

Эти алгоритмы намеренно сделаны медленнее и требовательнее к ресурсам.

Цель — не замедлить вход в систему. Цель — увеличить затраты атакующего на проверку огромного числа догадок.

Password hashing обычно работает и с **солью (salt)**.

Соль — отдельное случайное значение, создаваемое для каждого пароля.

Например, пусть у двух пользователей одинаковый пароль:

```text
пользователь A: secret123
пользователь B: secret123
```

Если соль не используется:

```text
hash(secret123) == hash(secret123)
```

При утечке базы данных одинаковые digest покажут, что у пользователей может быть одинаковый пароль.

А с солью:

```text
hash(secret123 + saltA)
hash(secret123 + saltB)
```

дают разные результаты.

Важный момент: соль не обязана быть секретной.

Обычно она хранится в базе данных вместе с хешем пароля.

Задача соли:

* не превращать одинаковые пароли в одинаковые digest;
* уменьшать пользу больших заранее вычисленных хеш-таблиц.

У алгоритмов вроде Argon2id, scrypt, bcrypt есть ещё параметр **cost**, управляющий стоимостью вычисления.

Например, если сервер мощнее, алгоритм можно настроить дороже.

В экосистеме Go практические реализации этих алгоритмов есть в модуле `golang.org/x/crypto`.

При выборе алгоритма и параметров учитываются:

* требования безопасности;
* возможности CPU сервера;
* память;
* объём трафика входа в систему;
* актуальные рекомендации по безопасности.

Не создавайте самодельную схему вроде:

```text
SHA-256(password + salt)
```

Даже с добавленной солью SHA-256 всё равно остаётся очень быстрым алгоритмом.

Для password hashing нужно использовать алгоритм, созданный именно для этой задачи.

## Проверка контрольной суммы файла

SHA-256 очень полезен для проверки того, что файл не повреждён.

Например, если вы скачиваете дистрибутив программы, официальный сайт может дать digest вроде:

```text
SHA256:
6b7e...
```

Вы вычисляете SHA-256 для скачанного файла и сравниваете с ожидаемым значением.

Если digest совпадают, очень вероятно, что байты файла соответствуют ожидаемому файлу.

Но здесь важно, **откуда взят digest**.

Если и файл, и digest берутся с одного и того же недоверенного сервера, атакующий может заменить оба.

Например:

```text
исходный файл     -> вредоносный файл
исходный SHA-256  -> новое значение SHA-256 вредоносного файла
```

Когда вы проверите, digest совпадёт, потому что атакующий обновил и его.

Поэтому, чтобы контрольная сумма была полезна для безопасности, ожидаемый digest нужно брать из доверенного источника.

Например:

* доверенная HTTPS-страница;
* подписанный release-манифест;
* отдельно проверенный источник.

Перед сравнением полезно проверить и формат текста digest.

Digest SHA-256 должен быть:

```text
32 байта
```

а в шестнадцатеричном формате:

```text
64 символа
```

Например, значение из внешнего источника может выглядеть так:

```text
ABCDEF...
```

или так:

```text
abcdef...
```

В шестнадцатеричных цифрах регистр букв не меняет значение.

Поэтому вместо сравнения строк как обычных строк ожидаемый digest можно сначала декодировать в байты:

```go
expected, err := hex.DecodeString(expectedHex)
```

Затем можно проверить, что это 32 байта:

```go
if len(expected) != sha256.Size {
	// неверная длина SHA-256
}
```

Значение `sha256.Size` равно:

```text
32
```

После этого можно сравнить с вычисленным digest в виде байтов.

Такой подход помогает точнее справляться с вопросами формата.

## Частые ошибки

### Считать Base64 шифрованием

Base64 не скрывает данные.

Например:

```text
0L/RgNC40LLQtdGCINC80LjRgA==
```

может выглядеть непонятно. Но для декодирования не нужен никакой секрет или ключ.

Обычным Base64-декодером это значение превращается обратно в:

```text
привет мир
```

Поэтому не используйте Base64 для защиты секретных данных.

### Применение обычного SHA-256 к паролю

SHA-256 — сильная хеш-функция, но для паролей слишком быстрая.

Атакующий может проверить огромное число догадок пароля за короткое время.

Для паролей выбирайте алгоритм password hashing, например:

* Argon2id;
* scrypt;
* bcrypt;
* PBKDF2 при необходимости.

### Использование MD5 или SHA-1 для решений безопасности

Для MD5 и SHA-1 известны практические атаки на коллизии.

Поэтому не полагайтесь на эти алгоритмы для проверки безопасности данных, которые может контролировать атакующий.

Совместимость с legacy — другой вопрос. Но в новом дизайне безопасности нужно использовать современный алгоритм.

### Самодельная схема для аутентификации сообщений

Иногда встречается такой код:

```text
SHA-256(key || message)
```

или:

```text
SHA-256(message || key)
```

Это не стандартная схема, заменяющая HMAC.

Создание криптографических конструкций вручную может привести к тонким ошибкам.

Для аутентификации сообщений используйте стандартный HMAC:

```go
hmac.New(sha256.New, key)
```

### Загрузка большого файла целиком в RAM

Следующий код удобен для небольших файлов:

```go
data, err := os.ReadFile(path)
```

Но для очень большого файла он загружает весь файл в RAM.

Для вычисления хеша это не нужно.

Вместо этого используйте потоковый подход вроде:

```go
file, err := os.Open(path)
```

и:

```go
io.Copy(hasher, file)
```

### Сравнение подписи безопасности обычным `==`

При проверке значений безопасности вроде HMAC нужно использовать:

```go
hmac.Equal(a, b)
```

Эта функция предназначена именно для безопасного сравнения значений MAC.

### Думать, что у одинаково выглядящего текста одинаковые байты

Хеш вычисляется не по изображению символов, а по байтам.

Например, в Unicode текст, который пользователю кажется одинаковым, может быть выражен разными последовательностями кодовых точек.

Поэтому в протоколе нужно чётко определить, как кодируется текст и, если нужно, как выполняется нормализация Unicode.

Иначе две системы могут вычислить разные digest для текста, который выглядит одинаково.

## На что обращают внимание на собеседовании?

На собеседовании знания только синтаксиса `sha256.Sum256()` может быть недостаточно. Обычно важно уметь правильно различать понятия.

### Разница между хешем, кодированием, шифрованием и HMAC

Нужно чётко различать следующее:

```text
Hash:
данные -> digest
обычно необратимо

Base64:
данные -> текстовое кодирование
легко декодируется

Encryption:
данные + ключ -> ciphertext
обратимо с помощью ключа

HMAC:
сообщение + секретный ключ -> код аутентификации
```

Называть Base64 шифрованием — техническая ошибка.

### Понятия коллизии и прообраза

**Коллизия** — нахождение одинакового digest для двух разных входов:

```text
hash(A) == hash(B)
A != B
```

А задача **прообраза (preimage)** связана с поиском входа, соответствующего заданному digest:

```text
дан digest
↓
найти подходящий input
```

В криптографической хеш-функции такие вычисления должны быть практически очень трудными.

### Длина digest не зависит от входа

Для SHA-256:

```text
1 байт input  -> 32 байта digest
1 MB input    -> 32 байта digest
10 GB input   -> 32 байта digest
```

Размер digest не растёт с размером входа.

### Почему SHA-256 не подходит для паролей?

Причина не в том, что SHA-256 — слабый алгоритм.

Причина в том, что он работает **очень быстро**.

При хешировании файлов скорость полезна. А при проверке догадок пароля она помогает и атакующему.

Поэтому алгоритмы password hashing намеренно работают дороже.

### Разница между `sha256.Sum256()` и `sha256.New()`

`sha256.Sum256()` удобен для однократного вычисления:

```go
sum := sha256.Sum256(data)
```

Он возвращает:

```go
[32]byte
```

А `sha256.New()` используется для потокового вычисления:

```go
h := sha256.New()
```

Он возвращает объект, реализующий интерфейс `hash.Hash`.

Затем в него по частям записываются данные:

```go
h.Write(part1)
h.Write(part2)
h.Write(part3)
```

В конце digest получается через:

```go
sum := h.Sum(nil)
```

### Размер Base64

В Base64 действует правило:

```text
3 байта -> 4 символа
```

Поэтому результат обычно примерно на 33% больше оригинала.

Из-за padding точная длина дополняется до блоков по 4 символа.

### Варианты Base64

Основные варианты:

```go
base64.StdEncoding
base64.URLEncoding
base64.RawURLEncoding
```

`StdEncoding` использует символы:

```text
+
/
```

`URLEncoding` использует символы:

```text
-
_
```

`RawURLEncoding` тоже URL-safe, но не записывает padding.

### Почему для HMAC используется `hmac.Equal()`

При проверке подписи HMAC нужно использовать:

```go
hmac.Equal(expected, actual)
```

Это специальная функция для безопасного сравнения значений MAC.

Использовать этот API для HMAC вместо сравнения обычных строк или байтов через `==` считается правильной практикой.
