# Горутины

**Горутина** (goroutine) — лёгкая единица выполнения, которой управляет Go runtime. Проще говоря, с помощью горутины функцию можно выполнять одновременно с другой работой, то есть конкурентно.

Например, backend-сервер может одновременно ждать множество HTTP-запросов. CLI-программа может обрабатывать несколько файлов. Другой сервис может собирать данные из нескольких внешних API.

Если такие задачи независимы друг от друга, их удобно выполнять в отдельных горутинах.

Здесь есть важное различие: горутина — это не сам поток операционной системы.

Go runtime планирует множество горутин на нескольких потоках операционной системы. То есть разработчик не создаёт отдельный поток ОС для каждой горутины. Поэтому создание горутины обычно дешевле создания нового потока.

Но из этого не следует, что горутина совершенно бесплатна. Каждая горутина:

* использует память для стека;
* управляется планировщиком;
* может быть связана с определёнными ресурсами;
* может вызвать утечку горутин, если её неправильно завершить.

Поэтому, хотя создать горутину легко, правильное проектирование её жизненного цикла остаётся задачей разработчика.

## Как запускается горутина?

При обычном вызове функции программа ждёт её завершения:

```go
work()
```

В этом случае строка после него не выполняется, пока `work()` не завершится.

Если перед вызовом написать ключевое слово `go`:

```go
go work()
```

`work()` запускается как новая горутина. А вызывающая горутина переходит к следующей строке, не дожидаясь её завершения.

Например:

```go
go sendEmail()
fmt.Println("Продолжаем")
```

В этом коде не нужно ждать завершения `sendEmail()`. `fmt.Println()` может выполниться почти сразу.

Но какая горутина первой получит CPU, решает планировщик. Поэтому, даже если написано:

```go
go sendEmail()
fmt.Println("Продолжаем")
```

часть кода внутри `sendEmail()` может выполниться раньше `fmt.Println()`.

После оператора `go` должен идти **вызов** функции или метода.

Например, это правильно:

```go
go work()
```

Это тоже правильно:

```go
go printer.Print("Привет")
```

Но простое значение с `go` использовать нельзя.

Есть ещё одно тонкое правило: аргументы, передаваемые функции, вычисляются в вызывающей горутине до того, как новая горутина начнёт работу.

Например:

```go
go process(calculate())
```

Здесь сначала в вызывающей горутине выполняется `calculate()`. Когда его результат готов, `process(...)` планируется как новая горутина.

## Первый пример

Следующая программа создаёт новую горутину. В этом первом примере средство ожидания вспомогательной горутины намеренно
не используется:

```go
package main

import "fmt"

func greet(name string) {
	fmt.Println("Привет,", name)
}

func main() {
	go greet("Go")
	fmt.Println("main продолжила работу")
}
```

Один из возможных вариантов вывода:

```text
Привет, Go
main продолжила работу
```

Следующая строка запускает функцию `greet()` в новой горутине:

```go
go greet("Go")
```

`main` не ждёт её завершения и переходит к следующей строке:

```go
fmt.Println("main продолжила работу")
```

Поэтому не гарантируется, какая из двух следующих строк будет выведена первой:

```text
Привет, Go
main продолжила работу
```

Если `main()` завершится очень быстро, `Привет, Go` может вообще не вывестись. Это не ошибка: Go runtime не ждёт
вспомогательные горутины автоматически. Пока главная цель — увидеть, что ключевое слово `go` не заставляет вызывающий код ждать.
В следующем уроке мы научимся надёжно дожидаться завершения горутин с помощью `sync.WaitGroup`.

## `main` тоже работает как горутина

Go-программа начинается с выполнения функции `main()` в горутине `main`.

То есть `main()` тоже работает внутри горутины, как и другие горутины. Просто у неё особое значение: когда `main()` завершается, завершается весь процесс.

Runtime не ждёт автоматически другие горутины, даже если они ещё работают.

Следующая программа намеренно написана ненадёжно:

```go
package main

import "fmt"

func main() {
	go fmt.Println("Эта строка может не вывестись")
	fmt.Println("main завершилась")
}
```

Гарантированная строка в этой программе:

```text
main завершилась
```

А следующая строка может и вывестись, и не вывестись:

```text
Эта строка может не вывестись
```

Причина:

```go
go fmt.Println("Эта строка может не вывестись")
```

создаёт новую горутину.

Но `main()` может сразу выполнить следующую строку:

```go
fmt.Println("main завершилась")
```

и после этого завершиться.

Если новая горутина ещё не запущена планировщиком, процесс завершится, и она не успеет выполнить свой код.

Поэтому нельзя полагаться на то, как планировщик случайно сработает.

### Почему `time.Sleep` — не решение?

Новички часто пишут такой код:

```go
go work()
time.Sleep(time.Second)
```

В небольшой демонстрационной программе это может работать. Потому что `main` ждёт одну секунду, и вспомогательная горутина успевает поработать.

Но это не настоящая синхронизация.

`time.Sleep` просто ждёт определённое время. Он не знает, закончила ли горутина свою работу.

Например, если работа обычно длится 500 миллисекунд, можно написать:

```go
go work()
time.Sleep(time.Second)
```

На первый взгляд этого достаточно.

Но если внешний API замедлится и `work()` будет длиться 2 секунды, `main` завершится через секунду. А горутина остановится на полпути.

С другой стороны, если `work()` завершится за 10 миллисекунд, программа будет впустую ждать оставшиеся 990 миллисекунд.

Поэтому завершения работы нужно ждать не по оценке времени, а по конкретному событию.

Часто используемые средства:

* `sync.WaitGroup` — только для ожидания завершения горутин;
* канал — для передачи значения или ошибки;
* `context.Context` — для отмены и тайм-аутов.

В следующем уроке мы рассмотрим, как дождаться завершения нескольких горутин с помощью `sync.WaitGroup`.

## Работа с несколькими горутинами

Представьте, что программе нужно получить данные от трёх независимых сервисов:

* сервиса профилей;
* сервиса заказов;
* платёжного сервиса.

Если вызывать их по очереди, время ожидания каждого сервиса складывается.

Например:

```text
профиль:  30 ms
заказ:    10 ms
платёж:   20 ms
```

При последовательном выполнении примерное общее ожидание:

```text
30 + 10 + 20 = 60 ms
```

Если они независимы, все три можно запустить в отдельных горутинах. Тогда большая часть времени ожидания ввода-вывода перекрывается.

Следующий пример показывает эту ситуацию:

```go
package main

import (
	"fmt"
	"time"
)

type result struct {
	service string
	value   string
}

func fetch(service string, delay time.Duration, results chan<- result) {
	time.Sleep(delay)
	results <- result{
		service: service,
		value:   service + ": данные",
	}
}

func main() {
	services := []string{"профиль", "заказ", "платёж"}
	delays := []time.Duration{
		30 * time.Millisecond,
		10 * time.Millisecond,
		20 * time.Millisecond,
	}
	results := make(chan result, len(services))

	for i, service := range services {
		go fetch(service, delays[i], results)
	}

	values := make(map[string]string, len(services))
	for range services {
		item := <-results
		values[item.service] = item.value
	}

	for _, service := range services {
		fmt.Println(values[service])
	}
}
```

Результат:

```text
профиль: данные
заказ: данные
платёж: данные
```

Сначала задан список сервисов:

```go
services := []string{"профиль", "заказ", "платёж"}
```

Затем для каждого сервиса задана искусственная задержка:

```go
delays := []time.Duration{
	30 * time.Millisecond,
	10 * time.Millisecond,
	20 * time.Millisecond,
}
```

Здесь `time.Sleep` не используется для синхронизации.

Он только моделирует настоящую операцию ввода-вывода, например ожидание ответа от внешнего API.

Для получения результатов создан буферизованный канал:

```go
results := make(chan result, len(services))
```

Значение `len(services)` — `3`.

Значит, ёмкость канала тоже `3`.

Каждая горутина отправляет свой результат в канал:

```go
results <- result{
	service: service,
	value:   service + ": данные",
}
```

Поскольку канал буферизованный, горутина может положить результат в буфер, даже если `main` в этот момент не готова принять. Конечно, в буфере должно быть место.

Затем запускаются три горутины:

```go
for i, service := range services {
	go fetch(service, delays[i], results)
}
```

Этот цикл выполняется три раза.

В результате примерно одновременно начинают ждать:

```text
профиль  -> 30 ms
заказ    -> 10 ms
платёж   -> 20 ms
```

Поэтому первым в канал может прийти результат `заказ`. Затем `платёж`, а после него `профиль`.

Но программа не выводит результаты напрямую в порядке поступления.

Сначала они помещаются в `map`:

```go
values := make(map[string]string, len(services))

for range services {
	item := <-results
	values[item.service] = item.value
}
```

Программа запустила ровно три горутины. Поэтому она ждёт ровно три результата.

Затем результаты снова выводятся в порядке slice `services`:

```go
for _, service := range services {
	fmt.Println(values[service])
}
```

Поэтому независимо от того, в каком порядке завершаются горутины, порядок на экране стабилен:

```text
профиль: данные
заказ: данные
платёж: данные
```

В реальном проекте передачи одного значения часто недостаточно.

Например, результат может быть таким:

```go
type result struct {
	service string
	value   string
	err     error
}
```

Тогда каждая горутина может отправлять вместе со значением и свою ошибку.

Для долгих внешних запросов нужны также тайм-аут или отмена. Иначе, если один сервис не ответит, вся операция может ждать бесконечно.

Конкурентность в этом примере не означает автоматически параллельных вычислений на CPU.

**Конкурентность** — управление несколькими работами в пределах одного интервала времени.

**Параллелизм** же означает выполнение нескольких работ ровно в одно и то же время на разных ядрах CPU.

Когда горутина, ожидающая ввода-вывода, блокируется, runtime может выполнить другую готовую горутину. А выполняются ли горутины ровно в один момент на разных ядрах CPU, зависит от runtime, `GOMAXPROCS`, доступных ядер CPU и других факторов.

## Анонимная функция и аргументы

Горутина не обязана работать только с именованной функцией.

Анонимную функцию тоже можно запустить как горутину:

```go
go func(id int) {
	fmt.Println("Работа:", id)
}(id)
```

Этот синтаксис удобно разобрать на две части.

Первая часть создаёт анонимную функцию:

```go
func(id int) {
	fmt.Println("Работа:", id)
}
```

Следующая часть вызывает её:

```go
(id)
```

Поэтому общий вид такой:

```go
go func(id int) {
	fmt.Println("Работа:", id)
}(id)
```

`(id)` в конце передаёт текущее значение `id` в параметр `id int` анонимной функции.

Этот приём явно показывает, с каким именно значением работает горутина.

Например:

```go
for id := 1; id <= 3; id++ {
	go func(value int) {
		fmt.Println(value)
	}(id)
}
```

При каждом вызове текущее значение `id` вычисляется как аргумент и передаётся в параметр `value`.

Использование переменной цикла напрямую из внешней области видимости внутри замыкания было одной из распространённых ошибок в старых версиях Go.

Например:

```go
for _, value := range values {
	go func() {
		fmt.Println(value)
	}()
}
```

В старой семантике замыкание могло ссылаться на одну и ту же переменную цикла. Пока горутина успевала запуститься, эта переменная уже переходила к следующему значению.

В современных версиях Go семантика переменных итерации в цикле `for` улучшена. Тем не менее передача значения через параметр часто яснее показывает намерение:

```go
go func(value string) {
	fmt.Println(value)
}(value)
```

Кроме того, этот приём безопаснее и понятнее и при чтении модуля, работающего со старой версией Go.

## Возврат результата из горутины

В обычной функции возвращённое значение можно записать в переменную:

```go
value := calculate()
```

Но из функции, запущенной через `go`, так результат получить нельзя.

Следующая запись неправильна:

```go
// Неправильный пример:
// value := go calculate()
```

Этот код не компилируется.

Причина в том, что вызов `go calculate()` не ждёт завершения `calculate()`.

Если `calculate()` подготовит результат через 10 миллисекунд, вызывающая горутина за это время уже может уйти выполнять другой код.

Значит, моментом готовности результата нужно управлять отдельно.

Один из самых естественных способов — канал:

```go
result := make(chan int)

go func() {
	result <- calculate()
}()

value := <-result
```

Здесь вспомогательная горутина отправляет результат в канал. А вызывающая горутина ждёт, пока придёт значение.

Ещё один способ — записать результат в общую структуру данных.

Но при работе с общей памятью нужно быть осторожным.

Если две горутины одновременно обращаются к одному месту памяти и хотя бы одна из них пишет, без синхронизации может возникнуть **гонка данных** (data race).

Например:

```go
counter := 0

go func() {
	counter++
}()

go func() {
	counter++
}()
```

Этот код внешне прост.

Но `counter++` не обязательно одна атомарная операция. Она может включать несколько шагов, например чтение значения, увеличение и обратную запись.

Поэтому две горутины могут потерять изменения друг друга.

То, что такой код 100 раз правильно отработал в тесте, не доказывает его безопасность.

Для обнаружения гонок данных в Go есть race detector:

```bash
go test -race ./...
go run -race main.go
```

Первая команда запускает тесты пакетов с race detector:

```bash
go test -race ./...
```

Вторая выполняет обычную программу с race detector:

```bash
go run -race main.go
```

Race detector помогает обнаружить неправильные конкурентные обращения к памяти, замеченные во время выполнения программы.

Но он не перебирает все возможные порядки планировщика.

Поэтому:

```text
race detector не нашёл ошибок
```

не значит:

```text
в коде никогда не будет гонки данных
```

То, что доступ к общей памяти правильно защищён, нужно проверять и по самому коду.

Для этого можно использовать такие средства, как `sync.Mutex`, `sync.RWMutex`, операции `atomic` или управление владением (ownership) через каналы.

## Как Go runtime управляет горутиной?

Одна из главных причин лёгкости горутин связана с управлением их стеком.

Каждая горутина начинается с относительно небольшого стека.

Если вызовов функций становится больше и нужен больший стек, Go runtime может его увеличить.

Позже, когда потребность уменьшается, runtime может и уменьшить размер стека.

Это важное отличие от потоков ОС.

Потоки часто связаны с большим резервом стека. А горутине в начале не нужен очень большой стек.

Поэтому работа с тысячами горутин и даже больше практически возможна.

Но логику программы не нужно привязывать к точному начальному размеру стека.

Например, писать программу, исходя из предположения:

```text
"Каждая горутина получает ровно N килобайт стека"
```

неправильно.

Это внутренняя деталь реализации runtime, и она может меняться между версиями Go.

### Планировщик

Планировщик Go runtime распределяет горутины по потокам ОС.

Для простого представления:

```text
goroutine 1 ─┐
goroutine 2 ─┼──> Go scheduler ───> OS threads
goroutine 3 ─┤
goroutine 4 ─┘
```

Если горутина ждёт канал:

```go
value := <-ch
```

она пока не может продолжить.

Тогда runtime может выполнить другую готовую горутину.

Так же бывает с mutex, таймером или некоторыми операциями ввода-вывода.

Важное правило: планировщик не гарантирует порядок выполнения горутин.

Например, даже если написано:

```go
go first()
go second()
```

порядок:

```text
first завершается
second завершается
```

не гарантируется.

Код внутри `second()` может даже выполниться раньше кода внутри `first()`.

### Переключение горутин тоже не бесплатно

Горутина может быть легче потока, но и у неё есть затраты.

Runtime:

* отслеживает состояние горутин;
* управляет очередями планировщика;
* управляет стеками;
* отслеживает заблокированные и готовые горутины;
* распределяет их по потокам ОС.

Поэтому выносить каждую очень маленькую задачу в отдельную горутину не всегда полезно.

Например, разбиение миллиона ничтожных вычислений на миллион горутин может увеличить затраты планировщика.

Конкурентность даёт хороший результат, только если работы по своей природе независимы или если перекрытие времени ожидания приносит пользу.

## Жизненный цикл горутины

Для каждой созданной горутины нужно ответить как минимум на такие вопросы:

1. Когда она завершается?
2. Куда передаются результат или ошибка?
3. Как отменяется ожидание?
4. Кто закрывает используемые ею ресурсы?

Эти вопросы особенно важны в долгоработающих серверах.

Небольшая одноразовая программа может вернуть все ресурсы ОС при завершении процесса. Но в сервере, работающем неделями, неправильно управляемые горутины постепенно накапливаются.

Функция горутины естественно завершается в следующих случаях:

* когда функция доходит до конца;
* когда выполняется `return`.

Например:

```go
func worker() {
	doWork()
	return
}
```

или:

```go
func worker() {
	doWork()
}
```

В обоих случаях с завершением функции завершается и горутина.

В Go нет специального оператора, чтобы безопасно «убить» другую горутину снаружи.

Например, нет стандартного механизма вроде:

```text
kill(goroutine)
```

Отмена обычно работает по принципу **кооперативной отмены** (cooperative cancellation).

То есть горутина получает сигнал отмены и сама делает `return`.

Для этого обычно используют:

* канал;
* `context.Context`.

Например, концептуальный вид:

```go
select {
case <-ctx.Done():
	return
case item := <-jobs:
	process(item)
}
```

Здесь, если `ctx.Done()` закрыт, горутина получает сигнал отмены и сама завершается.

### Утечка горутин

**Утечка горутин** (goroutine leak) — ситуация, когда горутина уже не выполняет полезной работы, но не завершается и остаётся внутри процесса.

Например:

```go
ch := make(chan int)

go func() {
	value := <-ch
	fmt.Println(value)
}()
```

Если никто никогда не отправит значение в канал `ch`, горутина будет вечно ждать на строке:

```go
value := <-ch
```

Это может быть утечкой горутины.

Похожая ситуация бывает и при отправке:

```go
ch := make(chan int)

go func() {
	ch <- 10
}()
```

Если канал небуферизованный и никто не принимает из него значение, отправляющая горутина остаётся заблокированной.

Если долгая операция ввода-вывода тоже осталась без возможности отмены, горутина может жить очень долго.

Даже если горутина не выполняет полезной работы, она всё ещё может удерживать:

* свой стек;
* связанные с ней объекты;
* некоторые открытые ресурсы.

Поэтому в серверном коде важно проверять:

* есть ли тайм-аут для долгой операции;
* есть ли путь отмены;
* не может ли отправка в канал навсегда заблокироваться;
* не может ли приём из канала ждать вечно;
* завершаются ли горутины, связанные с запросом, когда запрос завершается.

Например, если фоновая горутина, относящаяся к HTTP-запросу, продолжает работать после его завершения, со временем это может превратиться в утечку.

### `panic` внутри горутины

`panic` требует особого внимания при работе с горутинами.

Если внутри горутины произошёл `panic` и он не перехвачен, останавливается не только эта горутина, а вся программа.

Например:

```go
go func() {
	panic("ошибка")
}()
```

Если этот panic не восстановить (recover), процесс завершится.

`recover()` работает только через отложенную функцию внутри **той же горутины**, где произошёл panic.

Например:

```go
func worker() {
	defer func() {
		if value := recover(); value != nil {
			fmt.Println("Panic:", value)
		}
	}()

	panic("ошибка")
}
```

Здесь `recover()` находится в горутине, в которой выполняется `worker()`.

`recover()` в другой горутине не может перехватить этот panic.

Например, нельзя поставить `recover()` внутри `main` и поймать panic из другой горутины.

Ставить `recover()` везде — тоже не лучшее решение.

Это может скрыть ошибки программирования.

`recover()` обычно используют на чётких границах. Например:

* обработчик серверного запроса;
* воркер;
* исполнитель задач;
* задача, управляемая фреймворком.

Цель — не молча проглотить panic.

Обычно panic:

* записывается в лог;
* нужные ресурсы закрываются;
* возвращается управляемый ответ об ошибке или задача завершается.

## Частые ошибки

### Думать, что горутины выполняются по порядку

Следующий код:

```go
go first()
go second()
```

не означает, что `first()` обязательно завершится раньше, потому что написан первым.

Планировщик может получить любой из следующих порядков:

```text
first начинается
second начинается
second завершается
first завершается
```

или:

```text
second начинается
second завершается
first начинается
first завершается
```

или другой порядок.

Если порядок выполнения важен, его нужно явно выразить в коде.

Для этого используют канал, mutex, `WaitGroup` или другое подходящее средство синхронизации.

Полагаться на то, как планировщик «обычно работает», — ошибка.

### Неограниченное создание горутин

Следующий шаблон может быть опасен:

```go
for item := range items {
	go process(item)
}
```

Если элементы в `items` поступают очень быстро, программа может создать тысячи или миллионы горутин.

Это влияет не только на память горутин.

Например, если внутри `process()` нужно соединение с базой данных, количество горутин может расти быстрее, чем пул соединений.

Или если внешний API разрешает 100 запросов в секунду, тысячи горутин, одновременно отправляющих запросы, нарушат rate limit.

Поэтому количество параллельных работ часто нужно ограничивать.

Распространённые подходы:

* worker pool;
* семафор;
* ограниченная очередь (bounded queue).

Главная мысль: даже если создание горутины дёшево, внешние ресурсы, которые она использует, не бесконечны.

### Потеря ошибки и результата

Горутина не может вернуть результат или ошибку вызывающему коду через обычный `return`.

Например:

```go
go save()
```

если `save()` возвращает `error`, вызывающий код не может получить эту ошибку напрямую.

Результат и ошибку нужно передавать отдельно.

Например:

```go
type result struct {
	value string
	err   error
}
```

Затем:

```go
results <- result{
	value: value,
	err:   err,
}
```

Есть ещё один важный вопрос: если одна горутина завершилась ошибкой, что должны делать остальные?

Варианты могут быть разными:

* оставшиеся работы продолжаются;
* при первой ошибке всё отменяется;
* все результаты собираются, а ошибки возвращаются в конце.

Это решение не должно возникать случайно. Его нужно спроектировать заранее.

### Синхронизация через `time.Sleep`

Следующий код — частая ошибка в тестах:

```go
go work()
time.Sleep(100 * time.Millisecond)
checkResult()
```

Этот код предполагает, что `work()` завершится за 100 миллисекунд.

Но CI-сервер может быть медленнее. Внешний ввод-вывод может длиться дольше. Планировщик может работать иначе.

В результате тест иногда проходит, а иногда падает.

Такой тест может превратиться в **нестабильный тест** (flaky test).

Завершения работы нужно ждать с помощью:

* `WaitGroup`;
* канала.

А тайм-аут используется для отдельной цели: чтобы контролировать, что операция не превышает допустимое время.

### Незащищённая запись в общую переменную

Если несколько горутин изменяют одни и те же данные, может возникнуть гонка данных.

Например:

```go
values := map[string]int{}

go func() {
	values["a"] = 1
}()

go func() {
	values["b"] = 2
}()
```

Запись в `map` Go из нескольких горутин без синхронизации небезопасна.

Такая же проблема может возникнуть с:

* элементами slice;
* счётчиком;
* полями struct;
* общими указателями.

Есть два распространённых способа решить проблему.

Первый — защитить общую память mutex:

```go
var mu sync.Mutex
```

Второй — передать владение данными одной горутине и общаться с остальными горутинами через каналы.

Какой подход лучше, зависит от задачи.

Важное правило: если несколько горутин работают с общим изменяемым состоянием, вопрос синхронизации нужно обязательно проверить.

## На что обращают внимание на собеседовании?

В вопросах о горутинах на собеседовании знания одного синтаксиса:

```go
go f()
```

недостаточно.

Важно чётко различать следующие понятия:

* горутина — не поток ОС, ею управляет Go runtime;
* `go f()` планирует функцию как новую горутину;
* вызывающая горутина не ждёт её завершения;
* когда `main()` возвращается, другие горутины автоматически не ожидаются;
* порядок выполнения горутин не гарантирован из-за планировщика;
* результат или `error` не передаются вызывающему коду из горутины обычным `return`;
* для результата нужен канал или другой механизм синхронизации;
* общее изменяемое состояние может вызвать гонку данных;
* утечка горутин — серьёзная проблема в долгоработающих программах;
* неконтролируемый fan-out может исчерпать ресурсы;
* вместо принудительного «убийства» горутины снаружи её нужно завершать кооперативно по сигналу отмены.

На собеседовании может прозвучать и такой вопрос:

> Если создать горутину так легко, почему бы не выносить каждую работу в горутину?

Ответ: хотя горутина лёгкая, у неё есть затраты на планирование и память. Кроме того, внешние ресурсы, которые она использует, например соединения с базой данных, сокеты, квоты API или CPU, могут быть ограничены.

Поэтому конкурентность тоже используют под контролем.

## Примеры

### 1. Запуск именованной функции как горутины

Этот пример показывает конкурентный запуск обычной именованной функции с ключевым словом `go`.

```go
package main

import (
	"fmt"
	"time"
)

func greet() {
	fmt.Println("Привет из горутины")
}

func main() {
	go greet()
	time.Sleep(20 * time.Millisecond)
}
```

Главная строка:

```go
go greet()
```

Если бы не было `go`:

```go
greet()
```

`main()` ждала бы завершения `greet()`.

С добавлением `go` функция `greet()` планируется как отдельная горутина. А `main()` сразу переходит к следующей строке:

```go
time.Sleep(20 * time.Millisecond)
```

В этом примере `Sleep()` используется только для демонстрации. Он ненадолго удерживает `main`, чтобы вспомогательная горутина успела вывести текст на экран.

Это не надёжная синхронизация для production-кода.

Если выполнение `greet()` займёт больше 20 миллисекунд, `main()` всё равно может завершиться.

Главное правило: `go f()` планирует функцию к конкурентному выполнению, но не ждёт её завершения.

### 2. Выполнение анонимной функции в горутине

В этом примере вместо создания отдельной именованной функции для одноразовой работы используется анонимная функция.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	go func() {
		fmt.Println("Анонимная горутина выполнилась")
	}()

	time.Sleep(20 * time.Millisecond)
}
```

Анонимная функция объявлена так:

```go
func() {
	fmt.Println("Анонимная горутина выполнилась")
}
```

Но само объявление функции её не выполняет.

Поэтому в конце написано:

```go
()
```

то есть:

```go
func() {
	fmt.Println("Анонимная горутина выполнилась")
}()
```

Это сразу вызывает анонимную функцию.

А `go` стоит перед всем вызовом:

```go
go func() {
	fmt.Println("Анонимная горутина выполнилась")
}()
```

Если эта функция нужна только в этом месте, давать ей отдельное имя не обязательно.

Этот шаблон часто встречается в коротких фоновых задачах, при использовании замыканий или значений из той же области видимости.

### 3. Передача аргумента горутине

В этом примере именованной функции передаётся аргумент, и каждая горутина работает со своим значением.

```go
package main

import (
	"fmt"
	"time"
)

func printNumber(number int) {
	fmt.Println("Число:", number)
}

func main() {
	for number := 1; number <= 3; number++ {
		go printNumber(number)
	}
	time.Sleep(20 * time.Millisecond)
}
```

Цикл:

```go
for number := 1; number <= 3; number++ {
```

даёт `number` такие значения:

```text
1
2
3
```

На каждой итерации вызывается:

```go
go printNumber(number)
```

Аргумент функции вычисляется до того, как горутина начнёт работу.

Поэтому каждый вызов получает значение, актуальное в тот момент.

В результате три горутины работают примерно с:

```text
printNumber(1)
printNumber(2)
printNumber(3)
```

Но порядок на экране не гарантирован.

Например, результат может быть:

```text
Число: 2
Число: 1
Число: 3
```

Или:

```text
Число: 3
Число: 2
Число: 1
```

Порядок цикла не определяет порядок завершения горутин.

### 4. Передача значения анонимной функции через параметр

В этом примере значение из цикла передаётся анонимной функции через параметр.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	words := []string{"Go", "быстрый", "простой"}

	for _, word := range words {
		go func(value string) {
			fmt.Println(value)
		}(word)
	}

	time.Sleep(20 * time.Millisecond)
}
```

На каждой итерации цикла `word` получает очередное значение:

```text
Go
быстрый
простой
```

А у анонимной функции есть параметр:

```go
func(value string) {
	fmt.Println(value)
}
```

Часть в конце:

```go
(word)
```

передаёт текущее значение `word` в параметр `value`.

То есть логически это похоже на:

```text
value = "Go"
value = "быстрый"
value = "простой"
```

отдельно для каждой горутины.

Этот подход ясно показывает намерение кода: горутина должна работать именно со значением этой итерации.

Порядок вывода не обязан совпадать с порядком в slice.

Например:

```text
простой
Go
быстрый
```

— тоже правильный результат.

Главное правило: значение аргумента берётся в момент вызова, но порядок выполнения горутин зависит от планировщика.

### 5. Выполнение одной функции в нескольких горутинах

В этом примере одна и та же функция `download()` используется в нескольких горутинах с разными аргументами.

```go
package main

import (
	"fmt"
	"time"
)

func download(file string, delay time.Duration) {
	time.Sleep(delay)
	fmt.Println(file, "загружен")
}

func main() {
	go download("small.txt", 10*time.Millisecond)
	go download("large.zip", 40*time.Millisecond)
	time.Sleep(60 * time.Millisecond)
}
```

Первая горутина:

```go
go download("small.txt", 10*time.Millisecond)
```

ждёт `10` миллисекунд.

Вторая горутина:

```go
go download("large.zip", 40*time.Millisecond)
```

ждёт `40` миллисекунд.

Из-за этой искусственной задержки `small.txt` обычно выводится первым:

```text
small.txt загружен
large.zip загружен
```

Но реальное время загрузки нельзя знать заранее.

Маленький файл может прийти с далёкого сервера. А большой файл может быть получен из очень быстрой локальной сети.

Поэтому программа не должна полагаться на предположение «горутина, запущенная первой, обязательно первой и завершится».

`Sleep()` в этом примере моделирует время ввода-вывода. А `Sleep()` на `60` миллисекунд в конце `main()` добавлен только для того, чтобы демонстрационная программа не завершила процесс раньше времени.

### 6. Раннее завершение `main()`

Этот пример показывает, что `main()` не ждёт вспомогательную горутину автоматически.

```go
package main

import (
	"fmt"
	"time"
)

func delayedMessage() {
	time.Sleep(100 * time.Millisecond)
	fmt.Println("Эта строка может не вывестись")
}

func main() {
	go delayedMessage()
	fmt.Println("main завершилась")
}
```

`main()` запускает вспомогательную горутину:

```go
go delayedMessage()
```

А `delayedMessage()` сразу ждёт 100 миллисекунд через:

```go
time.Sleep(100 * time.Millisecond)
```

Тем временем `main()` продолжает:

```go
fmt.Println("main завершилась")
```

и функция завершается.

Как только `main()` завершается, процесс заканчивается.

Поэтому вспомогательная горутина может не дойти до строки:

```go
fmt.Println("Эта строка может не вывестись")
```

В большинстве случаев вывод будет только:

```text
main завершилась
```

Этот пример показывает, что работу горутины нужно рассматривать отдельно от жизненного цикла `main`.

Решение — не «поставить большой `Sleep()`». Для явного ожидания нужно использовать `WaitGroup` или канал.

### 7. Наблюдение за количеством горутин

В этом примере с помощью `runtime.NumGoroutine()` получается количество горутин, существующих в данный момент.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	fmt.Println("В начале:", runtime.NumGoroutine())

	go func() {
		time.Sleep(50 * time.Millisecond)
	}()

	time.Sleep(10 * time.Millisecond)
	fmt.Println("Во время работы:", runtime.NumGoroutine())
}
```

В начале программы:

```go
runtime.NumGoroutine()
```

возвращает текущее количество горутин.

В обычной маленькой программе при этом обычно учитывается горутина `main`.

Затем создаётся новая горутина:

```go
go func() {
	time.Sleep(50 * time.Millisecond)
}()
```

Эта горутина живёт 50 миллисекунд.

А `main()` ждёт 10 миллисекунд:

```go
time.Sleep(10 * time.Millisecond)
```

Значит, в момент второго вызова `NumGoroutine()` вспомогательная горутина, скорее всего, ещё не завершилась.

Результат может быть примерно таким:

```text
В начале: 1
Во время работы: 2
```

Но логику программы не нужно привязывать к точному числу.

`runtime.NumGoroutine()` даёт лишь снимок на тот момент. Значение может отличаться в зависимости от устройства программы и активности runtime.

Эта функция может быть полезна при отладке или мониторинге. Например, при подозрении на утечку горутин можно наблюдать, растёт ли их количество со временем.

### 8. Фиксация ошибки внутри горутины

В этом примере функция, вызванная горутиной, возвращает `error`. Ошибка проверяется в самой горутине.

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

func save(name string) error {
	if name == "" {
		return errors.New("имя пустое")
	}
	return nil
}

func main() {
	go func() {
		if err := save(""); err != nil {
			fmt.Println("Ошибка сохранения:", err)
		}
	}()

	time.Sleep(20 * time.Millisecond)
}
```

`save()` имеет такую сигнатуру:

```go
func save(name string) error
```

Значит, она может вернуть ошибку.

При передаче пустой строки:

```go
save("")
```

возвращается ошибка:

```go
errors.New("имя пустое")
```

А внутри горутины:

```go
if err := save(""); err != nil {
	fmt.Println("Ошибка сохранения:", err)
}
```

ошибка сразу проверяется.

Результат:

```text
Ошибка сохранения: имя пустое
```

В этом маленьком примере достаточно просто записать ошибку в лог.

Но в реальной системе о ней может понадобиться знать и вызывающему коду.

В таком случае ошибку можно вернуть через канал:

```go
errorsCh <- err
```

или передать результат и `error` вместе в одной структуре.

Главное правило: внутри горутины можно сделать `return err`, но код, запустивший вызов `go`, не получает эту `error` автоматически, как при обычном вызове функции.

### 9. Перехват panic внутри горутины на месте

Этот пример показывает, что `recover()` работает только внутри горутины, в которой произошёл panic.

```go
package main

import (
	"fmt"
	"time"
)

func riskyWork() {
	defer func() {
		if value := recover(); value != nil {
			fmt.Println("Panic перехвачен:", value)
		}
	}()

	panic("неожиданная ситуация")
}

func main() {
	go riskyWork()
	time.Sleep(20 * time.Millisecond)
	fmt.Println("Программа продолжила работу")
}
```

В начале `riskyWork()` регистрируется отложенная функция:

```go
defer func() {
	if value := recover(); value != nil {
		fmt.Println("Panic перехвачен:", value)
	}
}()
```

Затем выполняется:

```go
panic("неожиданная ситуация")
```

Из-за panic функция не продолжает обычный поток выполнения. Но во время раскрутки стека (stack unwinding) запускается отложенная функция.

Внутри этой отложенной функции:

```go
recover()
```

перехватывает значение panic.

Результат может быть примерно таким:

```text
Panic перехвачен: неожиданная ситуация
Программа продолжила работу
```

Важное правило: `recover()` не может перехватить panic в другой горутине.

Например, отложенный `recover()` внутри `main()` не поймает panic внутри вспомогательной горутины.

Поэтому в этом примере отложенная функция помещена именно внутрь `riskyWork()`.

В production-коде ставить `recover()` в каждую функцию не рекомендуется. Его обычно используют на чёткой границе задачи или запроса.

### 10. Вызов метода как горутины

Горутина может выполнять не только обычную функцию, но и вызов метода.

```go
package main

import (
	"fmt"
	"time"
)

type Printer struct {
	Prefix string
}

func (printer Printer) Print(message string) {
	fmt.Println(printer.Prefix, message)
}

func main() {
	printer := Printer{Prefix: "LOG:"}
	go printer.Print("сообщение готово")
	time.Sleep(20 * time.Millisecond)
}
```

Здесь:

```go
printer.Print("сообщение готово")
```

— обычный вызов метода.

Когда перед ним пишется `go`:

```go
go printer.Print("сообщение готово")
```

метод выполняется как новая горутина.

`Print()` написан с value receiver:

```go
func (printer Printer) Print(message string)
```

Значит, метод получает в качестве получателя значение `Printer`.

В этом примере `Printer` — очень простая структура:

```go
type Printer struct {
	Prefix string
}
```

Значение `Prefix`:

```text
LOG:
```

Поэтому метод:

```go
fmt.Println(printer.Prefix, message)
```

выводит примерно следующее:

```text
LOG: сообщение готово
```

Поскольку используется value receiver, метод работает с копией значения получателя.

Но о value receiver нужно помнить одну тонкость: сама структура копируется, но если в ней есть значения вроде slice, map или указателей, семантика обращения через них к другим данным может быть иной.

В этом примере есть только поле `string`. Поэтому вопрос копирования получателя простой.

Главное правило: вызов метода, как и вызов функции, можно запустить как новую горутину с помощью ключевого слова `go`.
