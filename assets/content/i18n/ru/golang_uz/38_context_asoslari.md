# Основы `context`

`context.Context` в Go помогает управлять долгими операциями. Он в основном передаёт по цепочке вызовов три вида информации:

* сигнал отмены работы;
* `deadline` (крайний срок) или `timeout` (тайм-аут);
* небольшие значения метаданных, относящиеся к запросу.

Например, HTTP-сервер принял запрос и в рамках этого запроса обратился к базе данных. Если клиент разорвал соединение, серверу больше не нужно ждать результата из базы данных. В этом случае через `context` можно отменить и операцию с базой данных.

Точно так же, если одна горутина запускает другую, через `context` можно сообщить ей, что вызывающий код больше не ждёт результата.

Важно, что `context` не останавливает горутину принудительно. Работающий код должен сам следить за сигналом `ctx.Done()` и завершать работу, когда сигнал приходит.

## Начальный контекст

Новая цепочка контекстов обычно начинается с `context.Background()` или `context.TODO()`.

`context.Background()` — пустой корневой контекст, который никогда не отменяется. Его часто используют:

* в функции `main`;
* в тестах;
* на самом верхнем уровне сервера;
* там, где нет другого родительского контекста.

Например:

```go
ctx := context.Background()
```

У самого этого контекста нет `deadline`, сигнала отмены или дополнительного значения. Позже из него можно получить новые контексты с помощью `WithCancel`, `WithTimeout`, `WithDeadline` или `WithValue`.

`context.TODO()` на практике тоже пустой контекст. Но его смысл другой. Его обычно используют во временном месте, где ещё не ясно, какой контекст нужно передать.

Например, если вы постепенно переводите старый код на работу с `context`, можно временно использовать `context.TODO()`.

Если функция принимает `context`, в Go-коде принято передавать его первым параметром:

```go
func LoadUser(ctx context.Context, id int64) error
```

В этой строке `ctx` — первый параметр. Затем идут собственные аргументы функции.

Такой порядок широко используется в экосистеме Go. Поэтому разработчик, увидевший функцию, сразу понимает, что она может работать с отменой или `deadline`.

Хранить `Context` внутри структуры обычно не рекомендуется.

Например, такого подхода нужно избегать:

```go
type Service struct {
	ctx context.Context
}
```

Причина в том, что `context` обычно привязан к времени жизни определённой операции или запроса. А структура может жить гораздо дольше. Хранение контекста в структуре делает неясным, к какому запросу или операции он относится.

Лучший способ — передавать контекст нужному методу как параметр:

```go
func (s *Service) LoadUser(ctx context.Context, id int64) error
```

Кроме того, не передавайте `nil` вместо `context.Context`.

Например, вместо:

```go
LoadUser(nil, 10)
```

если другого подходящего контекста нет, нужно использовать:

```go
LoadUser(context.Background(), 10)
```

Это гарантирует, что внутри функции можно безопасно вызывать `ctx.Done()`, `ctx.Err()` или другие методы контекста.

## Отмена

Некоторые работы нужно остановить, когда снаружи приходит явный сигнал. Для этого используется `context.WithCancel()`.

Он создаёт из родительского контекста новый дочерний:

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
```

Здесь возвращаются два значения:

* `ctx` — новый контекст;
* `cancel` — функция, отменяющая этот контекст.

Когда вызывается `cancel()`, канал, получаемый через `ctx.Done()`, закрывается.

Например, рабочая функция может следить за сигналом так:

```go
select {
case <-ctx.Done():
	return ctx.Err()
default:
}
```

`ctx.Done()` не используется как канал, отправляющий обычные значения. Когда контекст отменяется, этот канал закрывается. Закрытие канала одновременно сигнализирует всем наблюдателям.

А `ctx.Err()` показывает, по какой причине контекст завершился.

Если `cancel()` вызван вручную:

```go
ctx.Err()
```

возвращает ошибку:

```go
context.Canceled
```

Здесь есть важное различие. `Done()` даёт только сигнал «контекст завершён». Чтобы узнать, почему он завершён, используется `Err()`.

Вызов `cancel()` через `defer` широко распространён:

```go
ctx, cancel := context.WithCancel(parent)
defer cancel()
```

Причина в том, что ресурсы, связанные с контекстом, обязательно очищаются, когда они больше не нужны.

Даже если работа закончится раньше по другой причине, `defer cancel()` гарантирует вызов `cancel()` при выходе из функции.

## Тайм-аут и крайний срок

`context` даёт два основных способа работы с ограничением по времени:

* `WithTimeout`;
* `WithDeadline`.

`timeout` показывает, сколько времени можно работать начиная с текущего момента.

Например:

```go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()
```

Этот контекст автоматически завершается примерно через две секунды.

Процесс можно упрощённо представить так:

```text
контекст создан
        |
        v
можно работать 2 секунды
        |
        v
тайм-аут истёк
        |
        v
ctx.Done() закрыт
        |
        v
ctx.Err() == context.DeadlineExceeded
```

А `deadline` обозначает не длительность, а точную точку во времени.

Например:

```go
ctx, cancel := context.WithDeadline(parent, time.Now().Add(2*time.Second))
defer cancel()
```

В этом примере крайний срок установлен через две секунды от текущего момента. В результате этот код на практике работает очень похоже на предыдущий пример с `WithTimeout`.

Разница — в том, какой смысл выражает API.

Если вам нужно правило:

> «Пусть эта работа длится не более двух секунд»

естественнее `WithTimeout`.

Если вам нужно точное ограничение по времени вроде:

> «Эта работа должна завершиться не позже 15:30»

подходит `WithDeadline`.

Когда время истекает, канал `Done()` закрывается.

После этого:

```go
ctx.Err()
```

возвращает:

```go
context.DeadlineExceeded
```

Это значение отличается от `context.Canceled`.

`context.Canceled` обычно означает, что контекст был отменён снаружи.

`context.DeadlineExceeded` означает, что заданное ограничение по времени истекло.

Даже если работа завершилась до крайнего срока, `cancel()` нужно вызвать:

```go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()
```

Причина не только в отмене. `WithTimeout` и `WithDeadline` могут управлять внутренним таймером и другими ресурсами. Если вызвать `cancel()`, их можно освободить раньше, не дожидаясь крайнего срока.

## Отменяемая рабочая функция

Следующая программа показывает, как тайм-аут и `ctx.Done()` работают вместе:

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func work(ctx context.Context) error {
	ticker := time.NewTicker(100 * time.Millisecond)
	defer ticker.Stop()

	for step := 1; step <= 10; step++ {
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-ticker.C:
			fmt.Println("Шаг:", step)
		}
	}
	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 250*time.Millisecond)
	defer cancel()

	if err := work(ctx); err != nil {
		fmt.Println("Работа завершена:", err)
	}
}
```

В этом примере `work()` пытается выполнить 10 шагов.

Для ожидания `100ms` между шагами создан `ticker`:

```go
ticker := time.NewTicker(100 * time.Millisecond)
defer ticker.Stop()
```

`time.NewTicker()` каждые `100ms` отправляет сигнал в канал `ticker.C`.

`ticker.Stop()` останавливает тикер, когда функция завершается. Вызывать его через `defer` нужно, чтобы ресурсы тикера не продолжали работать без надобности.

Затем начинается цикл:

```go
for step := 1; step <= 10; step++ {
```

Теоретически функция должна выполнить 10 шагов.

Но на каждой итерации `select` ждёт одно из двух событий:

```go
select {
case <-ctx.Done():
	return ctx.Err()
case <-ticker.C:
	fmt.Println("Шаг:", step)
}
```

Первый `case`:

```go
case <-ctx.Done():
	return ctx.Err()
```

ждёт завершения контекста.

Если тайм-аут истёк или контекст отменён вручную, `ctx.Done()` закрывается. Тогда функция сразу возвращается с `ctx.Err()`.

Второй `case`:

```go
case <-ticker.C:
	fmt.Println("Шаг:", step)
```

ждёт следующего интервала `100ms`. Когда приходит сигнал, выводится очередной шаг.

В `main()` для контекста задан тайм-аут `250ms`:

```go
ctx, cancel := context.WithTimeout(context.Background(), 250*time.Millisecond)
defer cancel()
```

Примерная шкала времени работы:

```text
0ms
контекст создан

100ms
Шаг: 1

200ms
Шаг: 2

250ms
тайм-аут контекста
ctx.Done() закрыт
work() завершилась с ctx.Err()
```

Поэтому функция обычно не выполняет все 10 шагов.

Если `work()` возвращает ошибку, `main()` выводит её:

```go
if err := work(ctx); err != nil {
	fmt.Println("Работа завершена:", err)
}
```

Из-за тайм-аута выводится примерно такой результат:

```text
Шаг: 1
Шаг: 2
Работа завершена: context deadline exceeded
```

Из-за точного планирования в случаях, очень близких к границе времени, не гарантируется, какая ветка `select` будет выбрана. Но главная цель примера не меняется: рабочая функция вместе с таймером следит и за сигналом отмены.

Этот шаблон особенно полезен:

* в HTTP-запросах;
* в запросах к базе данных;
* в вызовах внешних API;
* в фоновых воркерах;
* в долгих циклах.

Важное правило: само создание контекста не останавливает работу автоматически. Код вроде `work()` должен проверять `ctx.Done()`.

## Когда используется `WithValue()`?

`context.WithValue()` используется, чтобы передавать по цепочке контекстов небольшие значения, относящиеся к запросу.

Например:

* ID запроса;
* trace ID;
* данные, связанные с аутентификацией;
* метаданные, которые должны идти вместе с запросом.

Он используется так:

```go
ctx := context.WithValue(parent, key, value)
```

Затем код нижнего уровня может получить значение:

```go
value := ctx.Value(key)
```

Но `WithValue()` — не универсальная замена обычному параметру функции.

Например, если `userID` обязателен для функции, обычно лучше написать так:

```go
func LoadUser(ctx context.Context, userID int64) error
```

Если спрятать `userID` в контекст:

```go
func LoadUser(ctx context.Context) error
```

и потом получать его внутри через `ctx.Value()`, API станет менее понятным.

Точно так же не рекомендуется помещать в контекст конфигурацию или обязательные зависимости.

Например, если соединение с базой данных:

```go
*sql.DB
```

или логгер — постоянная зависимость сервиса, передавать его через структуру или явный параметр обычно правильнее.

`WithValue()` предназначен скорее для дополнительных метаданных, которые перемещаются вместе с потоком запроса.

При работе с ключами контекста есть ещё одна важная проблема: ключи могут конфликтовать.

Например, если два пакета используют один и тот же строковый ключ:

```go
"requestID"
```

они могут случайно увидеть значения друг друга.

Поэтому хорошей практикой считается создание внутри пакета отдельного неэкспортируемого типа:

```go
type contextKey string

const requestIDKey contextKey = "requestID"
```

Затем значение записывается:

```go
ctx := context.WithValue(parent, requestIDKey, "abc-123")
```

И читается:

```go
requestID, ok := ctx.Value(requestIDKey).(string)
if !ok {
	// значения нет или оно не того типа
}
```

Здесь используется утверждение типа:

```go
.(string)
```

`ctx.Value()` возвращает `any`. Поэтому нужно проверить, что полученное значение действительно `string`.

Слепое утверждение типа без проверки `ok` может быть опасным.

Например:

```go
requestID := ctx.Value(requestIDKey).(string)
```

если значения нет или оно другого типа, во время выполнения произойдёт panic.

Более безопасный вариант:

```go
requestID, ok := ctx.Value(requestIDKey).(string)
if !ok {
	// значение не найдено или неверного типа
}
```

Поэтому при работе с `WithValue()` важны два правила:

* помещайте в контекст только метаданные, относящиеся к запросу;
* при получении значения проверяйте его наличие и тип.
