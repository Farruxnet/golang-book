# Написание тестов в Go

Тест — это код, который автоматически проверяет, что другой код даёт ожидаемый результат.

Например, если функция `Add(2, 3)` должна возвращать `5`, не нужно каждый раз проверять это вручную. Если написать тест, Go выполнит эту проверку автоматически.

В Go для этого не нужно устанавливать отдельный тестовый фреймворк. Пакета `testing` из стандартной библиотеки и команды `go test` достаточно для написания основных тестов.

Тесты нужны не только для проверки того, что функция возвращает правильный результат. Они могут проверять и ошибочные случаи, граничные значения, работу с файлами, значения `error` и другое поведение.

## Первый тест

Начнём с очень простой функции.

Следующий пакет `calc` складывает два целых числа:

```go
package calc

func Add(a, b int) int {
	return a + b
}
```

`Add()` принимает два значения `int` и возвращает их сумму.

Например:

```text
Add(2, 3) → 5
```

Теперь проверим это поведение тестом.

Имена тестовых файлов Go должны заканчиваться на `_test.go`. Например:

```text
calc.go
calc_test.go
```

Тестовая функция обычно пишется в виде `TestXxx(t *testing.T)`:

```go
package calc

import "testing"

func TestAdd(t *testing.T) {
	got := Add(2, 3)
	want := 5

	if got != want {
		t.Errorf("Add(2, 3) = %d; ожидалось %d", got, want)
	}
}
```

Разберём этот тест по шагам.

Сначала получаем фактический результат:

```go
got := Add(2, 3)
```

`got` — значение, которое функция фактически вернула. Здесь оно должно быть `5`.

Затем записываем ожидаемый результат:

```go
want := 5
```

`want` — значение, которое тест считает правильным.

Потом оба значения сравниваются:

```go
if got != want {
	t.Errorf("Add(2, 3) = %d; ожидалось %d", got, want)
}
```

Если `got` и `want` не равны, тест считается проваленным.

Например, если `Add()` случайно написана так:

```go
func Add(a, b int) int {
	return a - b
}
```

результат `Add(2, 3)` будет `-1`. А тест ожидает `5`. Тогда `t.Errorf()` фиксирует ошибку.

Тесты текущего пакета можно запустить так:

```bash
go test
```

Чтобы запустить тесты всех пакетов модуля:

```bash
go test ./...
```

Между этими двумя командами есть важная разница:

```text
go test
```

тестирует только текущий пакет.

```text
go test ./...
```

проверяет пакеты текущего модуля и их подпакеты.

### Разница между `t.Errorf()` и `t.Fatalf()`

В тестах есть несколько способов зафиксировать ошибку. Два самых частых — `t.Errorf()` и `t.Fatalf()`.

`t.Errorf()` помечает тест как проваленный, но текущая тестовая функция продолжает выполняться:

```go
if got != want {
	t.Errorf("неверный результат")
}
```

Это используется, когда полезно выполнить и последующие проверки.

`t.Fatalf()` фиксирует ошибку и останавливает текущую тестовую функцию прямо в этом месте:

```go
if err != nil {
	t.Fatalf("неожиданная ошибка: %v", err)
}
```

Это обычно нужно, когда выполнять дальнейший код уже бессмысленно.

Например, если не удалось даже открыть файл, проверить данные внутри файла невозможно. В таком случае `t.Fatalf()` логически правильнее.

Важно, что `t.Fatalf()` не останавливает весь процесс `go test`. Он останавливает выполнение именно текущего теста. Другие тесты обычно продолжают выполняться.

## Табличные тесты и подтесты

Часто проверить функцию только одним значением недостаточно.

Например, мы можем захотеть проверить функцию `Add()` в следующих случаях:

* два положительных числа;
* два отрицательных числа;
* число и ноль.

Для каждого случая можно написать отдельную функцию `Test...`. Но в Go очень распространено хранить такие тесты в виде таблицы.

Этот приём называется **табличным тестом** (table-driven test).

```go
func TestAdd(t *testing.T) {
	tests := []struct {
		name       string
		a, b, want int
	}{
		{name: "positive", a: 2, b: 3, want: 5},
		{name: "negative", a: -2, b: -3, want: -5},
		{name: "zero", a: 4, b: 0, want: 4},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := Add(tt.a, tt.b)

			if got != tt.want {
				t.Errorf(
					"Add(%d, %d) = %d; ожидалось %d",
					tt.a,
					tt.b,
					got,
					tt.want,
				)
			}
		})
	}
}
```

Здесь `tests` — slice, в котором хранятся тестовые случаи.

Каждый элемент хранит следующие данные:

```go
name       string
a, b, want int
```

`name` — имя тестового случая.

`a` и `b` — аргументы, передаваемые в функцию `Add()`.

`want` — ожидаемый результат.

Например:

```go
{name: "negative", a: -2, b: -3, want: -5}
```

означает такую проверку:

```text
Add(-2, -3) → должно быть -5
```

Затем все случаи перебираются по одному через `for`:

```go
for _, tt := range tests {
	...
}
```

Для каждого случая вызывается `t.Run()`:

```go
t.Run(tt.name, func(t *testing.T) {
	...
})
```

`t.Run()` создаёт отдельный **подтест** (subtest).

В результате тесты отображаются примерно под такими именами:

```text
TestAdd/positive
TestAdd/negative
TestAdd/zero
```

Польза в том, что легко увидеть, какой именно случай упал.

Например, можно запустить только подтест `positive`:

```bash
go test -run 'TestAdd/positive'
```

Если один подтест падает, остальные подтесты обычно тоже продолжают выполняться.

Табличный тест особенно полезен, когда одно и то же правило нужно проверить на многих значениях. Чтобы добавить новый случай, не нужно писать новую тестовую функцию. Достаточно добавить в таблицу ещё один элемент.

## Независимость тестов

Хороший тест не должен зависеть от результата другого теста или от порядка выполнения.

Например, такой подход опасен:

```text
TestA меняет глобальное значение
↓
TestB полагается на это изменённое значение
```

Если порядок выполнения тестов изменится или `TestB` запустится отдельно, он может упасть.

Поэтому каждый тест должен по возможности сам готовить своё состояние и не оставлять лишних изменений во внешней среде после завершения.

Особенно осторожным нужно быть с:

* изменением глобального состояния;
* использованием настоящих файлов пользователя;
* опорой на общее состояние базы данных;
* лишними обращениями к внешним сетевым сервисам;
* зависимостью от файла или данных, созданных другим тестом.

Тестам, работающим с файлами, может понадобиться временная директория. Для этого Go предоставляет метод `t.TempDir()`.

```go
func TestSave(t *testing.T) {
	dir := t.TempDir()
	path := filepath.Join(dir, "result.txt")

	if err := os.WriteFile(path, []byte("привет"), 0o600); err != nil {
		t.Fatalf("файл не записан: %v", err)
	}

	data, err := os.ReadFile(path)
	if err != nil {
		t.Fatalf("файл не прочитан: %v", err)
	}

	if string(data) != "привет" {
		t.Errorf("результат = %q; ожидалось %q", data, "привет")
	}
}
```

Для этого фрагмента нужны такие импорты:

```go
import (
	"os"
	"path/filepath"
	"testing"
)
```

Разберём процесс по шагам.

Сначала для теста создаётся временная директория:

```go
dir := t.TempDir()
```

Эта директория принадлежит тесту. Когда тест завершится, Go автоматически её удалит.

Затем внутри этой директории создаётся путь к файлу:

```go
path := filepath.Join(dir, "result.txt")
```

`filepath.Join()` строит путь к файлу, подходящий для операционной системы.

Потом текст `"привет"` записывается в файл:

```go
os.WriteFile(path, []byte("привет"), 0o600)
```

`0o600` — значение прав в стиле Unix:

```text
владелец: чтение + запись
остальные: доступа нет
```

Если при записи произошла ошибка, вызывается:

```go
t.Fatalf("файл не записан: %v", err)
```

Причина использования `Fatalf` здесь важна. Если файл не записан, на следующем шаге нет смысла читать его и проверять данные.

Затем файл читается обратно:

```go
data, err := os.ReadFile(path)
```

И в конце проверяется значение внутри файла:

```go
if string(data) != "привет" {
	t.Errorf(...)
}
```

Благодаря `t.TempDir()` тест не зависит от настоящих файлов пользователя. Это делает тесты безопаснее и удобнее для повторного запуска.

## Покрытие (coverage)

**Покрытие** (coverage) показывает, какие части кода выполнили тесты.

Чтобы получить простой процент покрытия:

```bash
go test -cover ./...
```

Например, в результате может появиться такая информация:

```text
coverage: 82.4% of statements
```

Это означает, какая доля инструкций была выполнена во время прогона тестов.

Чтобы сохранить результат покрытия в файл:

```bash
go test -coverprofile=coverage.out ./...
```

Эта команда создаёт профиль с именем `coverage.out`.

Затем его можно открыть в виде HTML:

```bash
go tool cover -html=coverage.out
```

HTML-отчёт позволяет легко увидеть, какой код выполнили тесты, а какая часть не выполнялась.

Но процент покрытия не стоит считать полной мерой качества кода.

Например, тест может выполнить все строки функции и при этом не проверять неверные результаты. Такой тест может дать высокое покрытие, но пользы от него мало.

Поэтому в тестах нужно смотреть не только на процент покрытия, но и на проверяемое поведение.

Среди важных случаев обычно есть:

* обычный успешный путь;
* граничные значения;
* неверный ввод;
* пути, возвращающие `error`;
* нулевые или пустые значения;
* особые случаи, важные для бизнеса.

Высокое покрытие может быть полезным сигналом. Но само по себе оно не доказывает правильность кода.

## Примеры

### 1. Проверка простого результата

Этот пример показывает самую базовую форму написания теста. Фактическое значение, возвращённое функцией, сравнивается с ожидаемым.

```go
package main

import "testing"

func multiply(a, b int) int {
	return a * b
}

func TestMultiply(t *testing.T) {
	got := multiply(4, 3)
	want := 12

	if got != want {
		t.Errorf("multiply(4, 3) = %d; ожидалось %d", got, want)
	}
}
```

Первая важная строка теста:

```go
got := multiply(4, 3)
```

Здесь получаем, что функция фактически возвращает.

Вычисление:

```text
4 * 3 = 12
```

Следующая строка:

```go
want := 12
```

хранит результат, который ожидает тест.

Затем:

```go
if got != want {
	...
}
```

сравнивает фактическое и ожидаемое значения.

Если `multiply(4, 3)` возвращает `12`, тест проходит.

Если возвращает другое значение:

```go
t.Errorf("multiply(4, 3) = %d; ожидалось %d", got, want)
```

переводит тест в состояние failed.

Главное правило в этом примере очень простое:

```text
got = фактический результат
want = ожидаемый результат
```

Многие тесты Go основаны именно на этом подходе.

### 2. Проверка ошибки до результата

Если функция вместе со значением возвращает и `error`, часто сначала нужно проверить `error`.

Следующая функция делит два целых числа:

```go
package main

import (
	"errors"
	"testing"
)

func divide(a, b int) (int, error) {
	if b == 0 {
		return 0, errors.New("делить на ноль нельзя")
	}

	return a / b, nil
}

func TestDivide(t *testing.T) {
	got, err := divide(12, 3)
	if err != nil {
		t.Fatalf("divide() вернула неожиданную ошибку: %v", err)
	}

	want := 4
	if got != want {
		t.Errorf("divide(12, 3) = %d; ожидалось %d", got, want)
	}
}
```

`divide()` возвращает два результата:

```go
(int, error)
```

В случае успеха выполняется:

```go
return a / b, nil
```

Например:

```text
12 / 3 = 4
```

Поэтому после:

```go
got, err := divide(12, 3)
```

ожидается:

```text
got = 4
err = nil
```

Первая проверка написана именно для `err`:

```go
if err != nil {
	t.Fatalf("divide() вернула неожиданную ошибку: %v", err)
}
```

Здесь выбран `t.Fatalf()`. Причина в том, что если `divide()` вернула ошибку, проверять `got` как нормальный результат уже нелогично.

Только убедившись, что ошибки нет, выполняются:

```go
want := 4
```

и:

```go
if got != want {
	...
}
```

В этом примере `12` и `3` выбраны не случайно. `12 / 3` как целое число даёт ровно `4`. Поэтому тест не смешивает другие тонкости целочисленного деления.

Главное правило:

```text
Если смысл результата зависит от успешного выполнения,
сначала проверяйте ошибку.
```

### 3. Проверка граничных значений в таблице

Этот пример с помощью табличного теста проверяет несколько важных случаев функции.

```go
package main

import "testing"

func normalize(value int) int {
	if value < 0 {
		return 0
	}

	return value
}

func TestNormalize(t *testing.T) {
	tests := []struct {
		name  string
		value int
		want  int
	}{
		{name: "negative", value: -1, want: 0},
		{name: "boundary", value: 0, want: 0},
		{name: "positive", value: 5, want: 5},
	}

	for _, tt := range tests {
		got := normalize(tt.value)

		if got != tt.want {
			t.Errorf(
				"%s: normalize(%d) = %d; ожидалось %d",
				tt.name,
				tt.value,
				got,
				tt.want,
			)
		}
	}
}
```

Правило `normalize()`:

```text
если value < 0 → 0
иначе          → value
```

Поэтому тест проверяет три важных случая.

Первый:

```go
{name: "negative", value: -1, want: 0}
```

`-1 < 0` истинно. Функция должна вернуть `0`.

Второй:

```go
{name: "boundary", value: 0, want: 0}
```

Это ровно граница условия.

В функции написано:

```go
if value < 0
```

`0 < 0` ложно. Значит, `0` возвращается без изменений.

Третий:

```go
{name: "positive", value: 5, want: 5}
```

Поскольку `5` — положительное значение, функция должна вернуть его без изменений.

Тестировать граничные значения важно. Изменение одного символа в операторах вроде `<`, `<=`, `>`, `>=` может изменить поведение функции именно на границе.

Главное правило этого примера — проверять не только обычные значения, но и границу, где меняется условие.

### 4. Разбиение случаев на подтесты

Этот пример показывает, как выполнять каждый случай табличного теста как отдельный подтест.

```go
package main

import "testing"

func isEven(value int) bool {
	return value%2 == 0
}

func TestIsEven(t *testing.T) {
	tests := []struct {
		name  string
		value int
		want  bool
	}{
		{name: "even", value: 8, want: true},
		{name: "odd", value: 7, want: false},
		{name: "zero", value: 0, want: true},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := isEven(tt.value)

			if got != tt.want {
				t.Errorf(
					"isEven(%d) = %t; ожидалось %t",
					tt.value,
					got,
					tt.want,
				)
			}
		})
	}
}
```

`isEven()` проверяет чётность через остаток:

```go
value%2 == 0
```

Например:

```text
8 % 2 = 0
```

Поэтому `8` чётное.

```text
7 % 2 = 1
```

Поэтому `7` нечётное.

Для нуля:

```text
0 % 2 = 0
```

Значит, `0` тоже считается чётным числом.

Через `t.Run()` каждый случай получает своё имя:

```text
TestIsEven/even
TestIsEven/odd
TestIsEven/zero
```

Это упрощает чтение результата тестов.

Например, можно запустить только случай с чётным числом:

```bash
go test -run 'TestIsEven/even'
```

Это особенно удобно в большом наборе тестов. Если проблема только в одном случае, возможно, не нужно снова и снова запускать всю таблицу.

Главное правило — `t.Run()` даёт тестовым случаям отдельное имя и отдельный контекст подтеста.

### 5. Вынос повторяющейся проверки во вспомогательную функцию

Если одна и та же проверка повторяется во многих местах, её можно вынести во вспомогательную функцию (helper).

```go
package main

import "testing"

func add(a, b int) int {
	return a + b
}

func assertEqual(t *testing.T, got, want int) {
	t.Helper()

	if got != want {
		t.Errorf("результат = %d; ожидалось %d", got, want)
	}
}

func TestAdd(t *testing.T) {
	assertEqual(t, add(2, 3), 5)
	assertEqual(t, add(-2, 2), 0)
}
```

Вспомогательная функция:

```go
func assertEqual(t *testing.T, got, want int)
```

собирает одинаковую проверку на равенство в одном месте.

Важная строка:

```go
t.Helper()
```

Она сообщает пакету `testing`, что `assertEqual()` — не обычная логика теста, а вспомогательная тестовая функция.

Польза видна в отчёте об ошибке.

Если проверка внутри helper падает, Go по возможности привязывает место ошибки не к строке:

```go
t.Errorf(...)
```

внутри helper, а к строке теста, где helper был вызван.

Например:

```go
assertEqual(t, add(2, 3), 5)
```

Это помогает быстрее понять, какая проверка вызвала проблему.

Второй случай:

```go
assertEqual(t, add(-2, 2), 0)
```

проверяет противоположные значения:

```text
-2 + 2 = 0
```

Вспомогательные функции особенно полезны в больших тестах для выноса повторяющихся проверок, подготовки (setup) или других вспомогательных операций.

Главное правило — если вы пишете test helper, полезно там, где нужно, помечать его как вспомогательную функцию через `t.Helper()`.

### 6. Регистрация функции очистки теста

Во время теста может понадобиться создать временный ресурс.

Например:

* файл;
* временный сервер;
* состояние тестовой базы данных;
* изменённую глобальную конфигурацию.

Такой ресурс нужно очистить после завершения теста.

`t.Cleanup()` регистрирует функцию, которая выполняется после завершения теста или подтеста.

```go
package main

import "testing"

func TestCleanup(t *testing.T) {
	events := make([]string, 0, 2)

	t.Run("resource", func(t *testing.T) {
		t.Cleanup(func() {
			events = append(events, "очищен")
		})

		events = append(events, "использован")
	})

	if len(events) != 2 {
		t.Fatalf("число событий = %d; ожидалось 2", len(events))
	}

	if events[0] != "использован" || events[1] != "очищен" {
		t.Errorf("неверный порядок событий: %v", events)
	}
}
```

Сначала создаётся slice:

```go
events := make([]string, 0, 2)
```

Здесь:

```text
len = 0
cap = 2
```

`len` равен `0`, потому что в slice пока нет ни одного элемента.

`cap` равен `2`, потому что этот тест ожидает записи двух событий:

```text
использован
очищен
```

Затем начинается подтест:

```go
t.Run("resource", func(t *testing.T) {
	...
})
```

Внутри подтеста регистрируется функция очистки:

```go
t.Cleanup(func() {
	events = append(events, "очищен")
})
```

Эта функция не выполняется сразу.

Выполняется следующая строка:

```go
events = append(events, "использован")
```

В этот момент:

```text
events = ["использован"]
```

Когда подтест завершается, запускается его функция очистки:

```text
events = ["использован", "очищен"]
```

К моменту возврата из `t.Run()` функции очистки подтеста уже выполнены. Поэтому внешний тест может проверить такой порядок:

```go
events[0] == "использован"
events[1] == "очищен"
```

Сначала проверяется длина:

```go
if len(events) != 2 {
	t.Fatalf(...)
}
```

Использовать здесь `Fatalf` логично. Если в slice нет двух элементов, последующие обращения вроде `events[0]` или `events[1]` могут быть опасны.

Главное правило этого примера — тест, создавший ресурс, должен сам управлять и его очисткой.

### 7. Проверка файла во временной директории

В этом примере тест проверяет запись файла, не трогая настоящие директории пользователя.

```go
package main

import (
	"os"
	"path/filepath"
	"testing"
)

func TestWriteMessage(t *testing.T) {
	dir := t.TempDir()
	path := filepath.Join(dir, "message.txt")

	if err := os.WriteFile(path, []byte("привет"), 0o600); err != nil {
		t.Fatalf("файл не записан: %v", err)
	}

	data, err := os.ReadFile(path)
	if err != nil {
		t.Fatalf("файл не прочитан: %v", err)
	}

	if string(data) != "привет" {
		t.Errorf("файл = %q; ожидалось %q", data, "привет")
	}
}
```

Первый шаг:

```go
dir := t.TempDir()
```

Go создаёт для теста временную директорию.

Следующий шаг:

```go
path := filepath.Join(dir, "message.txt")
```

строит путь к файлу `message.txt` внутри этой директории.

Затем файл записывается:

```go
os.WriteFile(path, []byte("привет"), 0o600)
```

`[]byte("привет")` превращает текст в byte slice.

Права:

```text
0o600
```

дают владельцу право на чтение и запись.

Если файл не записан:

```go
t.Fatalf("файл не записан: %v", err)
```

продолжать тест нет смысла.

Затем файл читается обратно:

```go
data, err := os.ReadFile(path)
```

Если и это удалось, прочитанный byte slice превращается в текст:

```go
string(data)
```

и сравнивается с ожидаемым значением:

```go
if string(data) != "привет" {
	...
}
```

Этот тест не опирается на настоящий файл пользователя, например:

```text
/home/user/message.txt
```

`t.TempDir()` помогает лучше изолировать тесты друг от друга и от внешней среды. После завершения теста временная директория тоже удаляется автоматически.

### 8. Проверка sentinel-ошибки через `errors.Is()`

В Go некоторые ошибки создаются заранее на уровне пакета:

```go
var ErrNotFound = errors.New("не найдено")
```

Такие ошибки часто называют **sentinel error** (сигнальными ошибками).

В следующем примере функция оборачивает `ErrNotFound` дополнительным контекстом:

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

var ErrNotFound = errors.New("не найдено")

func find(id int) error {
	if id != 10 {
		return fmt.Errorf("идентификатор %d: %w", id, ErrNotFound)
	}

	return nil
}

func TestFindNotFound(t *testing.T) {
	err := find(25)

	if !errors.Is(err, ErrNotFound) {
		t.Fatalf("ошибка = %v; ожидалась ErrNotFound", err)
	}
}
```

Правило `find()` простое:

```text
id == 10 → найдено, nil
id != 10 → ErrNotFound
```

Но ошибка возвращается не просто как:

```go
return ErrNotFound
```

Она обёрнута через `%w`:

```go
fmt.Errorf("идентификатор %d: %w", id, ErrNotFound)
```

Например, если `id = 25`, текст ошибки будет примерно таким:

```text
идентификатор 25: не найдено
```

Но во внутренней цепочке ошибки сохраняется и `ErrNotFound`.

Поэтому вместо сравнения текста ошибки тест использует:

```go
errors.Is(err, ErrNotFound)
```

Эта проверка означает:

> является ли `ErrNotFound` самим `err` или находится ли он в цепочке обёрнутых ошибок?

Простое:

```go
err == ErrNotFound
```

в этом примере не работает, потому что `err` — другое значение ошибки, созданное внешним `fmt.Errorf()`.

Проверка текста ошибки в виде:

```go
err.Error() == "идентификатор 25: не найдено"
```

тоже обычно хрупкий подход. Если текст сообщения изменится, тест упадёт, хотя смысловая причина не изменилась.

Главное правило этого примера — использовать `errors.Is()` для проверки обёрнутой sentinel-ошибки.

### 9. Проверка примера документации тестом

В Go функции `Example` могут одновременно служить примером документации и автоматически проверяемым тестом.

```go
package main

import "fmt"

func greeting(name string) string {
	return "Привет, " + name + "!"
}

func Example_greeting() {
	fmt.Println(greeting("Али"))

	// Output: Привет, Али!
}
```

`greeting()` возвращает простую строку:

```go
func greeting(name string) string {
	return "Привет, " + name + "!"
}
```

Например, результат:

```text
greeting("Али")
```

равен:

```text
Привет, Али!
```

Внутри `Example_greeting()` результат выводится в stdout:

```go
fmt.Println(greeting("Али"))
```

Затем написан особый комментарий:

```go
// Output: Привет, Али!
```

Когда `go test` выполняет функцию-пример, он сравнивает фактический вывод stdout с этим значением `Output`.

Упрощённо процесс выглядит так:

```text
greeting("Али")
        ↓
"Привет, Али!"
        ↓
fmt.Println(...)
        ↓
stdout: Привет, Али!
        ↓
 // Output: Привет, Али!
        ↓
сравнение
```

Если фактический результат и `Output` совпадают, пример проходит.

Например, если позже функцию изменить на:

```go
return "Добрый день, " + name + "!"
```

но не обновить `// Output:`, `go test` пометит пример как проваленный.

Поэтому `Example` — не только код, показываемый читателю. Он также может автоматически проверять, что пример в документации соответствует реальному коду.

Имя `Example_greeting` в этом примере обозначает пример, привязанный к функции `greeting`. `go test` может выполнить его вместе с обычными тестами.

Главное правило — функции `Example` с `// Output:` одновременно выполняют роль документации и автоматического теста.
