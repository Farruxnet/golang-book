# Работа с файлами в Go

Файл — один из способов сохранить данные даже после завершения программы. Обычные переменные в памяти программы исчезают, когда программа завершается. А данные, записанные в файл, остаются на диске и могут быть прочитаны снова при следующем запуске.

Конфигурация, логи, JSON-документы, изображения, отчёты и многие другие данные могут храниться в виде файлов.

При работе с файлами в Go ошибки — обычное дело. Например:

* файла может не существовать;
* у программы может не быть прав на чтение или запись файла;
* на диске может закончиться свободное место;
* файл может использоваться другим процессом;
* заданный путь может быть неверным.

Поэтому почти каждая операция с файлами возвращает `error`. Если продолжать, не проверяя эти ошибки, можно получить неправильный результат или даже `panic`.

## Основные пакеты

При работе с файлами часто встречаются несколько пакетов стандартной библиотеки Go:

* `os` — для создания, открытия, чтения, записи и удаления файлов и получения метаданных;
* `io` — даёт общие интерфейсы и вспомогательные функции для чтения и записи потоков данных;
* `bufio` — для буферизованного чтения и записи, в том числе удобен для построчного чтения файла;
* `path/filepath` — для построения и разбора путей к файлам с учётом операционной системы;
* `encoding/json` — для преобразования JSON-данных в значения Go и значений Go в JSON.

В старом коде на Go можно встретить и пакет `io/ioutil`. Многие его функции позже были перенесены в пакеты `os` и `io`.

Например, в новом коде обычно используются такие функции:

* `os.ReadFile`;
* `os.WriteFile`;
* `os.CreateTemp`;
* `io.ReadAll`.

Это не значит, что старый код не работает. Вы можете встретить существующий код, написанный с `io/ioutil`. Но при написании нового кода лучше использовать современные функции `os` и `io`.

## Запись в файл и чтение из него

Чтобы записать небольшой файл одной операцией, очень удобен `os.WriteFile`.

Его основное поведение такое:

1. если файла нет, создаёт новый файл;
2. если файл существует, обрезает его старое содержимое;
3. записывает переданные данные с начала файла.

В следующем примере сначала текст записывается в файл, а затем этот же файл читается обратно:

```go
package main

import (
	"fmt"
	"log"
	"os"
)

func main() {
	path := "message.txt"
	content := []byte("Go читает файлы как последовательность байтов.\n")

	if err := os.WriteFile(path, content, 0o644); err != nil {
		log.Fatal("не удалось записать файл: ", err)
	}

	data, err := os.ReadFile(path)
	if err != nil {
		log.Fatal("не удалось прочитать файл: ", err)
	}

	fmt.Print(string(data))
}
```

Результат:

```text
Go читает файлы как последовательность байтов.
```

Разберём этот код по шагам.

Сначала задаётся путь к файлу:

```go
path := "message.txt"
```

Это относительный путь. Значит, файл обычно ищется или создаётся относительно текущего каталога, в котором работает программа.

Затем текст преобразуется в `[]byte`:

```go
content := []byte("Go читает файлы как последовательность байтов.\n")
```

`os.WriteFile` принимает данные в виде `[]byte`.

На базовом уровне в файловой системе нет понятий «текст», «JSON» или «изображение». Файл хранит последовательность байтов. Формат файла определяет, как эти байты нужно интерпретировать.

Например:

```go
[]byte("Go")
```

преобразует строковое значение в последовательность байтов в кодировке UTF-8.

Затем файл записывается:

```go
if err := os.WriteFile(path, content, 0o644); err != nil {
	log.Fatal("не удалось записать файл: ", err)
}
```

Здесь три аргумента:

```text
path
content
0o644
```

`path` — имя файла.

`content` — байты для записи.

`0o644` — режим файла, используемый при создании нового файла.

Затем файл читается обратно:

```go
data, err := os.ReadFile(path)
```

`os.ReadFile` тоже возвращает `[]byte`. Поэтому при выводе значение `[]byte` преобразуется в `string`:

```go
fmt.Print(string(data))
```

### Что означает `0o644`?

`0o644` — режим файла, записанный в восьмеричной (octal) системе счисления.

В системах семейства Unix он примерно означает такие права:

```text
владелец:  read + write
группа:    read
остальные: read
```

В символьном виде:

```text
rw-r--r--
```

Это значение можно рассматривать как три части:

```text
6 4 4
```

`6`:

```text
4 + 2 = read + write
```

`4`:

```text
read
```

Ещё одна `4` тоже:

```text
read
```

Но здесь есть важная тонкость. Реальные итоговые права нового файла зависят ещё и от настройки `umask` процесса.

Значит, даже если задано `0o644`, операционная система может убрать из него некоторые права.

А Windows интерпретирует биты прав Unix не так, как системы Unix.

> **Внимание**
>
> `os.WriteFile` заменяет содержимое существующего файла. Если старые данные нужны, сначала сохраните их или откройте файл в режиме `os.O_APPEND`.

### Когда использовать `os.ReadFile`?

`os.ReadFile` загружает всё содержимое файла в память за один раз.

Например, для конфигурационного файла на 20 KiB это очень удобно:

```go
data, err := os.ReadFile("config.json")
```

Код получается простым и понятным.

Но если файл весит несколько гигабайт, ситуация меняется. Например, если попытаться прочитать лог-файл на 4 GiB через `os.ReadFile`, программа может занять очень большой объём памяти.

Поэтому большие файлы лучше обрабатывать потоком (stream). Тогда весь файл не загружается в память сразу. Он читается небольшими частями.

Для таких задач используются средства вроде `bufio.Scanner`, `bufio.Reader`, `file.Read` или `io.Copy`.

## Дозапись в файл

Иногда нужно добавить новые данные в конец существующего файла, не теряя его содержимое.

Хороший пример — лог-файл:

```text
сервер запущен
запрос получен
вошёл новый пользователь
```

Каждая новая запись лога должна добавляться в конец файла, не заменяя старые данные.

Для этого можно использовать `os.OpenFile`:

```go
package main

import (
	"fmt"
	"os"
)

func appendLine(path, line string) error {
	file, err := os.OpenFile(path, os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0o644)
	if err != nil {
		return fmt.Errorf("открытие файла: %w", err)
	}

	if _, err := file.WriteString(line + "\n"); err != nil {
		_ = file.Close()
		return fmt.Errorf("запись в файл: %w", err)
	}

	if err := file.Close(); err != nil {
		return fmt.Errorf("закрытие файла: %w", err)
	}
	return nil
}

func main() {
	path := "app.log"
	if err := os.Remove(path); err != nil && !os.IsNotExist(err) {
		fmt.Println("удаление старого файла:", err)
		return
	}

	if err := appendLine(path, "сервер запущен"); err != nil {
		fmt.Println("ошибка:", err)
		return
	}
	if err := appendLine(path, "запрос получен"); err != nil {
		fmt.Println("ошибка:", err)
		return
	}

	data, err := os.ReadFile(path)
	if err != nil {
		fmt.Println("ошибка:", err)
		return
	}
	fmt.Print(string(data))
}
```

Результат:

```text
сервер запущен
запрос получен
```

Основная строка:

```go
file, err := os.OpenFile(
	path,
	os.O_APPEND|os.O_CREATE|os.O_WRONLY,
	0o644,
)
```

В исходном коде это записано в одну строку. Смысл тот же: несколько флагов объединяются в одно значение.

Здесь `|` — оператор побитового ИЛИ.

Флаги выполняют следующее:

* `os.O_APPEND` — добавляет записи в конец файла;
* `os.O_CREATE` — создаёт файл, если его нет;
* `os.O_WRONLY` — открывает файл только для записи.

Их объединение:

```go
os.O_APPEND | os.O_CREATE | os.O_WRONLY
```

сообщает `os.OpenFile`, что нужны сразу три поведения.

### Почему проверяется ошибка `Close`?

В пишущем коде закрытие файла тоже проверяется отдельно:

```go
if err := file.Close(); err != nil {
	return fmt.Errorf("закрытие файла: %w", err)
}
```

На первый взгляд это может показаться лишним. Ведь `WriteString` завершилась успешно.

Но при записи данные не обязаны сразу попасть на физический диск. Операционная система может временно держать их в буфере.

Некоторые ошибки могут обнаружиться во время:

* `Write`;
* `Sync`;
* `Close`.

Поэтому при важной записи полезно проверять и ошибку `Close`.

А для файлов, открытых только для чтения, часто достаточно:

```go
defer file.Close()
```

Потому что успешность результата чтения не зависит от `Close`.

### Что будет, если несколько горутин пишут в один файл?

Несколько горутин или несколько процессов могут одновременно писать в один файл.

В такой ситуации записи могут:

* прийти в неожиданном порядке;
* перемешаться друг с другом;
* нарушить границы логических записей, которых ожидала программа.

Не считайте, что использование `O_APPEND` автоматически делает любую сложную запись полностью атомарной.

Например, если одна запись лога состоит из нескольких вызовов `Write`, другой писатель может вставить между ними свои данные.

Поэтому для параллельной записи в общий файл обычно используют одно из следующего:

* одна горутина-писатель;
* `sync.Mutex`;
* специальная библиотека логирования;
* внешняя система логов.

## Построчное чтение файла

При чтении большого текстового файла не обязательно загружать его в память целиком.

Например, лог-файл можно обрабатывать по одной строке.

Для этого удобен `bufio.Scanner`:

```go
package main

import (
	"bufio"
	"fmt"
	"os"
)

func main() {
	file, err := os.Open("app.log")
	if err != nil {
		fmt.Println("открытие файла:", err)
		return
	}
	defer file.Close()

	scanner := bufio.NewScanner(file)
	scanner.Buffer(make([]byte, 64*1024), 1024*1024)

	lineNumber := 1
	for scanner.Scan() {
		fmt.Printf("%d: %s\n", lineNumber, scanner.Text())
		lineNumber++
	}

	if err := scanner.Err(); err != nil {
		fmt.Println("чтение файла:", err)
	}
}
```

Сначала открывается файл:

```go
file, err := os.Open("app.log")
```

`os.Open` открывает файл только для чтения.

После успешного открытия пишется:

```go
defer file.Close()
```

Это гарантирует закрытие файла при завершении функции.

Затем создаётся `Scanner`:

```go
scanner := bufio.NewScanner(file)
```

`bufio.NewScanner` принимает `io.Reader`. А `*os.File` реализует интерфейс `io.Reader`. Поэтому файл можно передать в `Scanner` напрямую.

Цикл:

```go
for scanner.Scan() {
	fmt.Printf("%d: %s\n", lineNumber, scanner.Text())
	lineNumber++
}
```

на каждой итерации читает следующий токен.

По умолчанию `Scanner` работает по строкам. Поэтому здесь токен — одна строка.

`scanner.Scan()` возвращает:

* `true`, если есть следующая строка;
* `false`, когда файл закончился;
* `false` и при ошибке чтения.

Текущая строка получается через:

```go
scanner.Text()
```

`Text()` не возвращает символ `\n` в конце строки.

### Зачем после цикла проверяется `scanner.Err()`?

Проблема в том, что `Scan()` может вернуть `false` в двух разных ситуациях:

1. файл нормально закончился;
2. во время чтения произошла ошибка.

Поэтому после выхода из цикла проверяется:

```go
if err := scanner.Err(); err != nil {
	fmt.Println("чтение файла:", err)
}
```

Если `scanner.Err()` равен `nil`, чтение обычно завершилось нормально.

Если есть ошибка, при чтении файла возникла проблема.

### Зачем нужен `Scanner.Buffer`?

`Scanner` ограничивает размер одного токена.

Если встретится очень длинная строка, лимита по умолчанию может не хватить.

В примере:

```go
scanner.Buffer(make([]byte, 64*1024), 1024*1024)
```

максимальный размер токена устанавливается в 1 MiB.

Здесь:

```text
64 * 1024
```

используется для начального буфера.

```text
1024 * 1024
```

устанавливает максимальный размер токена в 1 MiB.

Если одна строка в файле ещё длиннее, `Scanner` может вернуть ошибку.

При работе с очень длинными записями, большими блоками или бинарными данными, не разделёнными на строки, лучше могут подойти:

* `bufio.Reader`;
* `file.Read`;
* `io.Copy`.

## `os.File` и файловый курсор

Когда `os.Open` или `os.OpenFile` завершается успешно, возвращается `*os.File`.

Хотя `*os.File` выглядит как обычное значение структуры Go, за ним стоит открытый файловый ресурс операционной системы.

У открытого файла есть текущая позиция. Её часто называют файловым курсором или смещением (offset).

Например, представим, что в файле есть данные:

```text
abcdef
```

Если программа прочитает первые три байта:

```text
abc
```

файловый курсор переместится на следующую позицию:

```text
abc|def
```

Следующий `Read` обычно начнётся с позиции, где находится `d`.

`Read` и `Write` обычно работают с текущей позиции и после операции сдвигают курсор вперёд.

А `Seek` позволяет переместить курсор в другое место.

Например, концептуально:

```text
начало   -> offset 0
середина -> определённый offset
конец    -> размер файла
```

Это полезно для произвольного доступа (random access), то есть для перехода к любой части файла.

### Зачем закрывать файл?

Открытый файл занимает место не только в памяти Go.

Для каждого открытого файла операционная система хранит ограниченный ресурс — обычно файловый дескриптор или handle.

Если программа открывает файлы и не закрывает их, со временем этот лимит может исчерпаться.

В системах Unix в такой ситуации может появиться ошибка вроде:

```text
too many open files
```

Особенно для долго работающей backend-программы это серьёзная проблема.

**Внимание**

Открывать тысячи файлов в цикле и каждый раз писать `defer file.Close()` тоже может быть проблемой. Вызовы `defer` выполняются при завершении функции. Значит, все файлы могут оставаться открытыми, пока не закончится большой цикл.

Например, такой подход требует осторожности:

```go
for _, path := range paths {
    file, err := os.Open(path)
    if err != nil {
        continue
    }
    defer file.Close()

    // ...
}
```

Если в `paths` тысячи файлов, все они могут оставаться открытыми до завершения внешней функции.

Вместо этого работу с одним файлом можно вынести в отдельную функцию:

```go
func processFile(path string) error {
    file, err := os.Open(path)
    if err != nil {
        return err
    }
    defer file.Close()

    // ...
    return nil
}
```

В этом случае соответствующий файл закрывается по завершении каждого вызова `processFile`.

Или можно явно вызвать `Close` в конце итерации.

## Проверка существования и типа файла

Для получения метаданных о файле или каталоге используется `os.Stat`.

При успехе он возвращает `os.FileInfo`.

Пример:

```go
package main

import (
	"errors"
	"fmt"
	"os"
)

func main() {
	info, err := os.Stat("message.txt")
	switch {
	case err == nil:
		fmt.Println("имя:", info.Name())
		fmt.Println("размер:", info.Size(), "байт")
		fmt.Println("каталог:", info.IsDir())
		fmt.Println("режим:", info.Mode())
	case errors.Is(err, os.ErrNotExist):
		fmt.Println("файл не существует")
	default:
		fmt.Println("не удалось получить информацию о файле:", err)
	}
}
```

Здесь разделены три случая.

Первый случай:

```go
case err == nil:
```

`os.Stat` отработал успешно. Значит, метаданные есть.

Второй случай:

```go
case errors.Is(err, os.ErrNotExist):
```

указанного пути не существует.

Третий случай:

```go
default:
```

произошла ошибка другого типа.

Например:

* недостаточно прав;
* к части пути нет доступа;
* ошибка ввода-вывода, связанная с файловой системой.

Поэтому делать вывод «раз это не `IsNotExist`, значит файл существует» неправильно.

### Методы `os.FileInfo`

Часто используемые методы `os.FileInfo`:

* `Name()` — возвращает базовое имя файла или каталога;
* `Size()` — возвращает размер обычного файла в байтах;
* `Mode()` — возвращает тип файла и биты прав;
* `ModTime()` — возвращает время последнего изменения;
* `IsDir()` — возвращает `true`, если объект — каталог;
* `Sys()` — даёт дополнительные метаданные, зависящие от операционной системы.

Например:

```go
info.Size()
```

для обычного файла возвращает его размер в байтах.

Но значение `Size()` для каталога не нужно понимать просто как «суммарный размер файлов внутри каталога». Семантика метаданных каталога зависит от файловой системы.

### Зачем используется `errors.Is`?

Следующий код:

```go
errors.Is(err, os.ErrNotExist)
```

может проверить не только то, что ошибка — это сам `os.ErrNotExist`, но и то, что она подходит, даже если обёрнута внутри других ошибок.

Например, ошибка могла быть обёрнута через:

```go
fmt.Errorf("не удалось открыть config: %w", err)
```

Поэтому в новом коде на Go `errors.Is` очень удобен для проверки ошибок по причине.

### Безопасно ли сначала сделать `Stat`, а потом `Open`?

Следующая идея на первый взгляд кажется логичной:

```text
1. проверить, существует ли файл;
2. если существует, открыть.
```

Но между этими двумя операциями другой процесс может удалить файл, заменить его или изменить его права.

Например:

```text
Stat -> файл существует
        другой процесс удаляет файл
Open -> ошибка
```

Поэтому предварительная проверка через `Stat` не заменяет проверку ошибки, возвращённой `Open`.

Часто самый правильный подход:

1. выполнить нужную операцию;
2. обработать `error`, возвращённую именно этой операцией.

## Удаление файла

Для удаления одного файла или пустого каталога используется `os.Remove`:

```go
if err := os.Remove("message.txt"); err != nil && !errors.Is(err, os.ErrNotExist) {
	return fmt.Errorf("удаление файла: %w", err)
}
```

Этот фрагмент — не полная программа.

Для его использования нужно импортировать пакеты:

```go
"errors"
"fmt"
```

Также код должен быть написан внутри функции, которая может возвращать `error`.

Логика кода такая.

Сначала:

```go
os.Remove("message.txt")
```

пытается удалить файл.

Если ошибки нет:

```text
err == nil
```

ничего не делается.

Если файла не существует:

```go
errors.Is(err, os.ErrNotExist)
```

будет `true`.

В примере этот случай тоже принимается как успех. Потому что цель — чтобы в конце операции файла не было.

Но другие ошибки, например:

* недостаточно прав;
* ошибка файловой системы;
* неверный путь

возвращаются наверх.

### Безопасность при удалении

`os.Remove` удаляет файл. Он не гарантирует перемещение в «корзину» (trash или recycle bin).

Поэтому перед вызовом:

```go
os.Remove(path)
```

важно убедиться, что `path` относится именно к нужному файлу.

Это особенно важно, когда `path` приходит от пользователя, из HTTP-запроса или другого внешнего источника.

Например, пользователь может прислать путь вроде:

```text
../../secret.txt
```

Эта опасность будет рассмотрена ещё раз в разделе `Безопасность путей`.

## Работа с JSON-файлом

Пакет `encoding/json` используется для преобразования JSON-данных в значения Go и значений Go в JSON.

Следующая программа:

1. записывает JSON-документ в файл;
2. открывает файл;
3. читает JSON через поток;
4. помещает результат в структуру `Person`.

```go
package main

import (
	"encoding/json"
	"fmt"
	"os"
)

type Person struct {
	Name   string   `json:"name"`
	Age    int      `json:"age"`
	Skills []string `json:"skills"`
}

func main() {
	const document = `{
  "name": "Ali",
  "age": 25,
  "skills": ["Go", "PostgreSQL"]
}`

	if err := os.WriteFile("person.json", []byte(document), 0o644); err != nil {
		fmt.Println("запись JSON-файла:", err)
		return
	}

	file, err := os.Open("person.json")
	if err != nil {
		fmt.Println("открытие JSON-файла:", err)
		return
	}
	defer file.Close()

	var person Person
	decoder := json.NewDecoder(file)
	decoder.DisallowUnknownFields()
	if err := decoder.Decode(&person); err != nil {
		fmt.Println("чтение JSON-файла:", err)
		return
	}

	fmt.Println("Имя:", person.Name)
	fmt.Println("Возраст:", person.Age)
	fmt.Println("Навыки:", person.Skills)
}
```

Результат:

```text
Имя: Ali
Возраст: 25
Навыки: [Go PostgreSQL]
```

`os.WriteFile()` записывает JSON-текст в файл `person.json`. Поскольку значение `*os.File`, возвращённое `os.Open()`, реализует интерфейс `io.Reader`,
его можно передать в `json.NewDecoder()` напрямую. А `Decode(&person)` записывает прочитанные
значения в существующую переменную `person`.

Соответствие типов JSON и Go, теги структур, `Marshal`, `Unmarshal` и строгое декодирование подробно объясняются в уроке о работе с JSON в Go.

## Атомарная замена важного файла

Перезаписывать некоторые файлы напрямую обычным `os.WriteFile` может быть опасно.

Например, в файле `config.txt` есть:

```text
port=8080
```

Во время его обновления программа:

1. обрезает старый файл;
2. начинает записывать новые данные;
3. процесс останавливается до завершения записи.

В результате может остаться только часть файла.

Для важного конфигурационного файла это плохая ситуация.

Практический подход такой:

1. записать новое содержимое во временный файл;
2. синхронизировать записанные данные;
3. закрыть файл;
4. переименовать (`Rename`) готовый временный файл в основное имя.

Пример:

```go
package main

import (
	"fmt"
	"os"
	"path/filepath"
)

func writeAtomic(path string, data []byte, perm os.FileMode) error {
	dir := filepath.Dir(path)
	temp, err := os.CreateTemp(dir, ".update-*")
	if err != nil {
		return fmt.Errorf("создание временного файла: %w", err)
	}
	tempName := temp.Name()
	defer os.Remove(tempName)

	if err := temp.Chmod(perm); err != nil {
		_ = temp.Close()
		return fmt.Errorf("установка прав: %w", err)
	}
	if _, err := temp.Write(data); err != nil {
		_ = temp.Close()
		return fmt.Errorf("запись во временный файл: %w", err)
	}
	if err := temp.Sync(); err != nil {
		_ = temp.Close()
		return fmt.Errorf("сброс файла на диск: %w", err)
	}
	if err := temp.Close(); err != nil {
		return fmt.Errorf("закрытие временного файла: %w", err)
	}
	if err := os.Rename(tempName, path); err != nil {
		return fmt.Errorf("замена основного файла: %w", err)
	}
	return nil
}

func main() {
	if err := writeAtomic("config.txt", []byte("port=8080\n"), 0o600); err != nil {
		fmt.Println("ошибка:", err)
		return
	}

	data, err := os.ReadFile("config.txt")
	if err != nil {
		fmt.Println("ошибка:", err)
		return
	}
	fmt.Print(string(data))
}
```

Результат:

```text
port=8080
```

Теперь разберём функцию `writeAtomic` по шагам.

### 1. Определение каталога основного файла

```go
dir := filepath.Dir(path)
```

Например, если:

```text
path = /app/config/config.txt
```

то:

```text
dir = /app/config
```

### 2. Создание временного файла в том же каталоге

```go
temp, err := os.CreateTemp(dir, ".update-*")
```

Это создаёт временный файл именно в том каталоге, где находится основной файл.

Например, может получиться имя вроде:

```text
/app/config/.update-123456
```

Почему именно этот каталог?

Потому что потом используется `Rename`. `Rename` в пределах одной файловой системы обычно лучше обеспечивает нужные свойства атомарности.

Если временный файл создан в другой файловой системе, переименование может перестать быть простой сменой имени или вообще не сработать.

### 3. Сохранение имени временного файла

```go
tempName := temp.Name()
```

Это имя понадобится позже для `Rename`.

### 4. Очистка временного файла при ошибке

```go
defer os.Remove(tempName)
```

Если один из следующих шагов завершится ошибкой, планируется попытка удалить временный файл, чтобы он не остался на диске.

Если `Rename` пройдёт успешно, старого `tempName` больше не будет. В этом случае `os.Remove(tempName)` может вернуть ошибку, но её результат здесь намеренно не используется.

### 5. Установка прав

```go
if err := temp.Chmod(perm); err != nil {
	_ = temp.Close()
	return fmt.Errorf("установка прав: %w", err)
}
```

Временному файлу задаются нужные права.

В примере задано:

```go
0o600
```

В системах Unix это обычно означает:

```text
rw-------
```

то есть читать и писать может только владелец файла.

### 6. Запись данных во временный файл

```go
if _, err := temp.Write(data); err != nil {
	_ = temp.Close()
	return fmt.Errorf("запись во временный файл: %w", err)
}
```

Основной файл пока не меняется.

Новые данные сначала записываются во временный файл.

Поэтому если при записи произойдёт ошибка, старая основная конфигурация ещё сохранится.

### 7. `Sync`

```go
if err := temp.Sync(); err != nil {
	_ = temp.Close()
	return fmt.Errorf("сброс файла на диск: %w", err)
}
```

`Sync` просит операционную систему передать записи файла на устройство хранения.

Это нужно, чтобы уменьшить опору на предположение «Write вернулся, значит данные точно попали на физический диск».

Но точные гарантии надёжности `Sync` зависят от операционной системы, файловой системы и устройства хранения.

### 8. Закрытие временного файла

```go
if err := temp.Close(); err != nil {
	return fmt.Errorf("закрытие временного файла: %w", err)
}
```

Здесь тоже проверяется ошибка `Close`.

При записи важного файла это полезно.

### 9. Замена основного имени готовым файлом

```go
if err := os.Rename(tempName, path); err != nil {
	return fmt.Errorf("замена основного файла: %w", err)
}
```

До этого шага старый основной файл сохранялся.

Теперь полностью записанный временный файл перемещается под имя `path`.

Концептуальный поток:

```text
config.txt
    |
    | старый файл ещё используется
    |
.update-123
    |
    | новые данные записываются полностью
    | Sync
    | Close
    v
Rename
    |
    v
config.txt
```

### Всегда ли `Rename` работает одинаково?

Нет.

Семантика замены существующего файла через `Rename` может зависеть от операционной системы.

Особенно при работе с:

* Windows;
* ситуацией, когда несколько процессов держат один файл открытым;
* разными файловыми системами;
* сетевой файловой системой

поведение нужно проверять отдельно.

Кроме того, этот подход не означает «есть абсолютная гарантия, даже если внезапно отключится электричество».

Если нужна сильная гарантия долговечности (durability), на некоторых платформах могут потребоваться дополнительные меры, например синхронизация метаданных каталога.

Значит, этот подход практичен и важен, но его точные гарантии зависят от файловой системы и операционной системы.

## Безопасность путей

Если путь к файлу приходит из внешнего источника, доверять ему как обычной строке опасно.

Например, программа получает от пользователя имя файла:

```text
report.txt
```

и открывает его внутри следующего каталога:

```text
/app/files/
```

В обычном случае получается:

```text
/app/files/report.txt
```

Но пользователь может прислать следующее:

```text
../../secret.txt
```

В результате построенный путь может выйти за пределы разрешённого каталога.

Это называется **path traversal** — уязвимость выхода наружу по дереву каталогов.

### Достаточно ли `filepath.Clean`?

Например:

```go
clean := filepath.Clean(userPath)
```

нормализует путь.

Например:

```text
a/../b
```

может быть приведён примерно к виду:

```text
b
```

Но `filepath.Clean` не проверяет, безопасен ли путь.

Например:

```text
../../secret.txt
```

и после очистки может остаться путём, выходящим за пределы базового каталога.

Поэтому границу доверия нужно проверять отдельно.

Для этого можно использовать `filepath.Rel` или другую явную проверку относительно доверенного базового каталога.

Концептуальное требование:

```text
путь пользователя
      |
      v
объединение с базовым каталогом
      |
      v
нормализация
      |
      v
итоговый путь внутри базового каталога?
      |
   +--+--+
   |     |
  да    нет
   |     |
 разрешить  отклонить
```

### Символические ссылки тоже важны

Проверки только строкового вида пути в некоторых случаях тоже недостаточно.

Например, внутри разрешённого каталога:

```text
/app/files/link
```

может быть символической ссылкой, ведущей во внешний каталог:

```text
/etc/
```

Тогда снаружи путь:

```text
link/passwd
```

выглядит так, будто он внутри разрешённого каталога, но реальный файл может быть в другом месте.

Поэтому при работе с именами файлов, которые контролирует пользователь, вопросы path traversal и символических ссылок — часть дизайна безопасности.

Это особенно важно для:

* HTTP-обработчиков;
* endpoint'ов загрузки и скачивания файлов;
* программ, распаковывающих архивы;
* CLI-утилит;
* файловых серверов.

Пути каталогов и их безопасная проверка подробно рассматриваются в следующем уроке.

## Частые ошибки

### Продолжение выполнения после ошибки

Например:

```go
file, err := os.Open("data.txt")
if err != nil {
	fmt.Println(err)
}

defer file.Close()
```

Этот код опасен.

Если `os.Open` вернул ошибку, `file` обычно не является пригодным для использования `*os.File`.

Несмотря на это, код продолжается:

```go
defer file.Close()
```

Это позже может привести к `panic`.

Правильный подход:

```go
file, err := os.Open("data.txt")
if err != nil {
	fmt.Println(err)
	return
}
defer file.Close()
```

Или, если функция возвращает `error`:

```go
file, err := os.Open("data.txt")
if err != nil {
	return fmt.Errorf("открытие файла: %w", err)
}
defer file.Close()
```

Основное правило простое:

> Если следующий код зависит от успешного результата, не продолжайте выполнение после ошибки.

### Загрузка любого файла в память целиком

`os.ReadFile` очень удобен:

```go
data, err := os.ReadFile(path)
```

Но он загружает весь файл в память.

Если размер файла не контролируется, расход памяти тоже может выйти из-под контроля.

Например, если:

```text
размер файла: 5 GiB
```

загрузка его в один `[]byte` требует много памяти.

Поэтому для больших или внешних файлов можно использовать:

* `bufio.Scanner`;
* `bufio.Reader`;
* `file.Read`;
* `io.Copy`;
* явное ограничение размера.

Выбор способа зависит от формата файла.

Например, для построчного лога удобен `Scanner`. Для копирования большого бинарного потока из одного места в другое лучше может подойти `io.Copy`.

### Игнорирование числа байтов в результате записи

`Write` возвращает два значения:

```go
n, err := file.Write(data)
```

Здесь:

* `n` — сколько байтов записано;
* `err` — ошибка.

В идеальном случае:

```text
n == len(data)
err == nil
```

Но если:

```text
n < len(data)
```

записаны не все данные.

Даже если `n < len(data)` и `err == nil`, это считается короткой записью (short write).

Поэтому результат записи нельзя беспечно отбрасывать.

Например, может потребоваться проверка вроде:

```go
n, err := file.Write(data)
if err != nil {
	return err
}
if n != len(data) {
	return io.ErrShortWrite
}
```

Вспомогательные функции вроде `io.WriteString` и `io.Copy` тоже возвращают результат и ошибку. В важном коде ввода-вывода их нужно проверять.

### Чрезмерная опора на отдельную проверку существования

Часто встречается такая последовательность:

```text
1. существует ли файл?
2. если существует, использовать.
```

Но между первой и второй операцией другой процесс может изменить ситуацию.

Например:

```text
Stat -> существует
        |
        | другой процесс удаляет файл
        v
Open -> ошибка
```

Или:

```text
Stat -> существует
        |
        | права меняются
        v
Open -> permission denied
```

Это называется **TOCTOU** — состояние гонки time-of-check to time-of-use (между моментом проверки и моментом использования).

Поэтому предварительная проверка не заменяет проверку ошибки основной операции.

Например, если вам нужно открыть файл, сделайте:

```go
file, err := os.Open(path)
```

и обработайте именно ошибку, возвращённую `Open`.

## На что обращают внимание на собеседовании?

В вопросах о файлах на собеседовании часто проверяют не просто знание синтаксиса `os.Open`, а понимание семантики ввода-вывода.

Важные моменты:

* `os.ReadFile` загружает весь файл в память. Потоковое чтение позволяет ограничить расход памяти.
* `defer file.Close()` удобен при чтении. При важной записи ошибку `Close` может понадобиться проверять отдельно.
* Флаги `O_CREATE`, `O_APPEND`, `O_TRUNC`, `O_RDONLY` и `O_WRONLY` определяют, в каком режиме открывается файл.
* `O_APPEND` сохраняет существующие данные и направляет записи в конец файла.
* `O_TRUNC` обрезает содержимое существующего файла. При неправильном использовании старые данные могут потеряться.
* Случай «файл не существует» в `os.Stat` нужно отличать от ошибок прав или других ошибок ввода-вывода.
* `errors.Is(err, os.ErrNotExist)` работает и с обёрнутыми ошибками.
* Подход «сначала проверь, потом используй» не устраняет состояние гонки TOCTOU.
* `bufio.Scanner` удобен для построчного чтения, но имеет ограничение на размер токена.
* `*os.File` связан с ресурсом операционной системы. Несвоевременное закрытие файлов может привести к исчерпанию лимита файловых дескрипторов.
* При обновлении важного файла можно использовать подход атомарной замены через временный файл, `Sync`, `Close` и `Rename`.
* Атомарность и долговечность (durability) — не одно и то же. `Rename` может быть атомарным, но гарантия сохранности при отключении питания зависит от файловой системы и операционной системы.
* Для путей к файлам, пришедших снаружи, нужно учитывать риски path traversal и символических ссылок.

В следующем уроке мы научимся создавать каталог, читать его содержимое, обходить дерево каталогов и безопасно строить пути к файлам.
