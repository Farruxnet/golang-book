# Инструменты проверки кода Go

Проверка кода в Go-проекте — это не только запуск тестов. Разные инструменты проверяют разные стороны кода.

Например:

* инструменты форматирования делают стиль написания кода единообразным;
* инструменты статического анализа стараются найти подозрительные конструкции ещё до запуска кода;
* тесты проверяют, что программа работает так, как ожидается;
* race detector ищет гонки данных (data race) в конкурентном коде.

Задачи этих проверок отличаются друг от друга. Поэтому успешное завершение одной из них не означает, что остальные можно не выполнять.

На практике полезно выполнять их одну за другой в одном и том же порядке. Это помогает рано находить ошибки и перед ревью, и перед релизом кода.

## Форматирование

В Go основной инструмент для приведения кода к стандартному стилю — `gofmt`.

Форматирование одного файла:

```bash
gofmt -w main.go
```

Здесь важен флаг `-w`.

`gofmt` форматирует код, а `-w` записывает полученный результат обратно в тот же файл. То есть команда не просто показывает, какие изменения нужны, а действительно изменяет файл `main.go`.

Например, неправильные отступы, лишние пробелы или некоторые расположения, не соответствующие стандарту Go, исправляются автоматически.

Чтобы отформатировать пакеты всего модуля через команду Go:

```bash
go fmt ./...
```

`go fmt` сначала выбирает пакеты. Затем запускает `gofmt` для Go-файлов этих пакетов.

В этой команде:

```text
./...
```

используется, чтобы выбрать текущий пакет внутри текущего модуля и пакеты под ним.

Задача форматирования — стандартизировать внешний вид кода. Например, если два разработчика написали один и тот же код с разными отступами, `gofmt` приведёт оба варианта к одному виду.

Но здесь есть важное ограничение.

Форматирование не проверяет бизнес-логику.

Например, если:

```go
total := price - tax
```

на самом деле должно быть:

```go
total := price + tax
```

`gofmt` этого не обнаружит. Потому что оба варианта кода правильны синтаксически и с точки зрения формата.

Поэтому форматирование нужно рассматривать как первый этап проверки качества кода, но не как полную проверку.

## Статический анализ

`go vet` анализирует код, не запуская его.

Он ищет некоторые конструкции, которые компилятор может принять, но которые с высокой вероятностью ошибочны или подозрительны на практике.

Проверка всего модуля:

```bash
go vet ./...
```

Например, `go vet` может обнаружить такие проблемы:

* несоответствие строки формата типу аргумента в функциях вроде `fmt.Printf`;
* копирование некоторых значений синхронизации, которые нельзя копировать;
* другие подозрительные конструкции, которые умеют находить стандартные анализаторы.

Например:

```go
count := "три"
fmt.Printf("%d\n", count)
```

Этот код может скомпилироваться. Но `%d` предназначен для целого числа, а `count` — `string`.

`go vet` может заранее указать на такое несоответствие.

В этом главная польза статического анализа: найти проблему не во время работы программы, а раньше.

Но и `go vet` находит не все виды ошибок.

Например, если бизнес-правило написано неправильно:

```go
if age > 18 {
	allow()
}
```

а требование на самом деле `age >= 18`, `go vet` этого не знает. Потому что для этого нужно понимать требования к программе.

Поэтому `go vet` не заменяет тесты.

## Тесты и проверка гонок

Чтобы выполнить тесты всего модуля:

```bash
go test ./...
```

`go test` компилирует выбранные пакеты и выполняет их тесты.

Если тесты написаны, они проверяют ожидаемое поведение кода.

Например, если есть такая функция:

```go
func Add(a, b int) int {
	return a + b
}
```

тест может проверить, что для `2 + 3` она возвращает `5`.

Здесь тест отвечает не на вопрос, работает ли код, а на вопрос, даёт ли код требуемый результат.

Для конкурентного кода может понадобиться дополнительная проверка:

```bash
go test -race ./...
```

Флаг `-race` включает race detector.

Обычный тест проверяет ожидаемое поведение. А race detector отслеживает признаки гонок данных в тех путях конкурентного кода, которые выполнили тесты. Их задачи не совпадают.

Определение гонки данных, практические примеры и ограничения детектора подробно объясняются в уроке о Race detector.

## Рекомендуемая последовательность

Для небольшого Go-проекта следующие проверки могут стать хорошим начальным рабочим процессом:

```bash
go fmt ./...
go vet ./...
go test ./...
go test -race ./...
```

Смысл этого порядка такой.

Сначала:

```bash
go fmt ./...
```

приводит код к стандартному формату.

Затем:

```bash
go vet ./...
```

выполняет статический анализ.

Потом:

```bash
go test ./...
```

запускает обычные тесты.

В конце:

```bash
go test -race ./...
```

снова выполняет тесты с race detector.

Форматирование может изменить файлы. Особенно если использованы `go fmt` или `gofmt -w`, в файлах репозитория появляются реальные изменения.

Поэтому после проверок полезно посмотреть:

```bash
git diff
```

Это позволяет проверить, какие строки изменились в результате форматирования или другой работы.

Цель — коммитить только ожидаемые изменения.

Проверка гонок работает медленнее обычного теста. Причина в том, что race detector использует дополнительную инструментацию и проверки во время выполнения, чтобы отслеживать обращения к памяти.

Поэтому использовать `-race` на каждой очень быстрой локальной итерации не всегда удобно.

Но в проектах с большим количеством конкурентного кода запускать его в CI или перед релизом очень полезно.

В больших проектах эти команды обычно выполняются и внутри CI pipeline.

Например, если локально используются:

```bash
go vet ./...
go test ./...
```

а в CI выполняются совсем другие команды, проблема, которую разработчик не видел локально, может появиться только после push.

Если локальная среда и CI используют одинаковые или очень близкие проверки, проблемы обычно обнаруживаются раньше.

Это также упрощает ревью. Вместо того чтобы тратить время на форматирование или простые статические проблемы, ревьюер может больше внимания уделить архитектуре и логике кода.

## Границы инструментов

У каждого инструмента есть конкретная задача.

* форматирование делает стиль кода единообразным;
* `go vet` находит определённые подозрительные конструкции;
* тест проверяет требуемое поведение;
* race detector ищет гонки данных в выполненных путях кода.

Успешное завершение одного из этих инструментов не делает другой ненужным.

Например:

```text
go fmt завершился успешно
```

не означает, что бизнес-логика кода правильна.

Точно так же:

```text
go test завершился успешно
```

не означает, что гонок нет.

Даже если `go vet` не нашёл никаких проблем, может остаться неправильный алгоритм или бизнес-правило, не соответствующее требованиям.

Кроме того, эти инструменты не предназначены для полного анализа проблем производительности.

Для производительности нужны другие инструменты.

Например:

* бенчмарки;
* профилирование CPU;
* профилирование памяти;
* трассировка выполнения (execution trace).

Поэтому в процессе проверки кода нет «одного универсального инструмента». Каждый инструмент обнаруживает отдельный вид проблем.

## Примеры

### 1. Просмотр различий через `gofmt -d`

Этот пример показывает, как увидеть результат форматирования `gofmt`, не записывая его в файл.

```go
package main

import "fmt"

func main() {
	numbers := []int{3, 1, 4}
	fmt.Println(numbers)
}
```

Если файл `main.go` намеренно написан с неправильными отступами или расположением, можно выполнить такую команду:

```bash
gofmt -d main.go
```

Флаг `-d` используется в смысле «покажи diff».

Он не изменяет файл.

Вместо этого он выводит разницу между текущим кодом и кодом, который рекомендует `gofmt`.

Например, в выводе в формате diff видно, какую строку нужно удалить и на что её заменить.

Это особенно полезно при проверке в CI или перед ревью. Потому что можно, не трогая файл, увидеть, соответствует ли он требованию к формату.

Блок кода выше показывает стандартный вид после `gofmt`.

Главное правило: `gofmt -d` показывает разницу в формате, но не изменяет файл.

### 2. Форматирование файла через `gofmt -w`

В этом примере показано стандартное расположение литерала `map`.

```go
package main

import "fmt"

func main() {
	ports := map[string]int{
		"http":  80,
		"https": 443,
	}
	fmt.Println(ports)
}
```

Чтобы автоматически отформатировать файл:

```bash
gofmt -w main.go
```

На этот раз используется `-w`.

Значит, результат, полученный `gofmt`, записывается прямо в `main.go`.

`ports` — это `map` с ключами `string` и значениями `int`.

В нём есть значения:

```go
"http": 80
```

и:

```go
"https": 443
```

`80` обычно используется как порт HTTP, а `443` — как порт HTTPS. В этом примере они выбраны, чтобы показать результат форматирования.

`gofmt` выравнивает следующие части для удобства чтения:

```go
"http":  80,
"https": 443,
```

Это только форматирование.

`gofmt` не проверяет, действительно ли `80` или `443` — правильные порты для этих протоколов.

Даже если написать:

```go
"http": 9999
```

`gofmt` спокойно отформатирует код.

Значит, форматирование упорядочивает синтаксический вид, но не проверяет бизнес- или технический смысл значений.

### 3. Список неотформатированных файлов

В этом примере значение `struct` записано в стандартном формате.

```go
package main

import "fmt"

type Server struct {
	Host string
	Port int
}

func main() {
	server := Server{
		Host: "localhost",
		Port: 8080,
	}
	fmt.Println(server)
}
```

Чтобы увидеть Go-файлы в текущей директории, которым нужно форматирование:

```bash
gofmt -l .
```

Флаг `-l` выводит список имён файлов.

Он не изменяет файлы.

Например, если `main.go` не в стандартном виде `gofmt`, в выводе может появиться:

```text
main.go
```

Если ни одного имени файла не выведено, `gofmt` не нашёл в проверенных файлах различий, требующих форматирования.

Часть кода:

```go
type Server struct {
	Host string
	Port int
}
```

объявляет `struct` с именем `Server`.

Затем через:

```go
server := Server{
	Host: "localhost",
	Port: 8080,
}
```

создаётся его значение.

`8080` выбран как альтернативный порт HTTP, часто встречающийся в локальных средах разработки. Это значение не влияет на цель примера — форматирование.

Главное правило: `gofmt -l` показывает, какие файлы нужно отформатировать, но не изменяет их.

### 4. Переход к более простой записи через `gofmt -s`

В этом примере срез slice намеренно записан в более длинной форме.

```go
package main

import "fmt"

func main() {
	values := []int{10, 20, 30, 40}
	last := values[2:len(values)]
	fmt.Println(last)
}
```

Здесь:

```go
values[2:len(values)]
```

берёт часть slice от индекса `2` до конца.

В Go индексы начинаются с `0`:

```text
index 0 -> 10
index 1 -> 20
index 2 -> 30
index 3 -> 40
```

Значит, начать с индекса `2` — значит начать с третьего элемента.

Верхняя граница:

```go
len(values)
```

то есть `4`.

В срезе slice верхняя граница не входит в результат.

Поэтому:

```go
values[2:4]
```

даёт такие значения:

```text
[30 40]
```

Но в Go при срезе до конца верхнюю границу можно не писать.

Поэтому вместо:

```go
values[2:len(values)]
```

достаточно написать:

```go
values[2:]
```

Следующая команда:

```bash
gofmt -s -d main.go
```

может предложить это упрощение в виде diff.

Здесь `-s` включает режим «simplify» (упрощение), а `-d` показывает разницу.

Главное правило: `gofmt -s` может привести некоторые синтаксические конструкции к более простой форме, не меняя их смысла.

### 5. Проверка всего модуля через `go fmt`

В этом примере есть небольшая функция вычисления.

```go
package main

import "fmt"

func Total(prices []int) int {
	total := 0
	for _, price := range prices {
		total += price
	}
	return total
}

func main() {
	fmt.Println(Total([]int{12, 8, 5}))
}
```

Если в корне модуля выполнить:

```bash
go fmt ./...
```

соответствующие пакеты текущего модуля будут выбраны и отформатированы.

Теперь посмотрим на сам код.

Функция:

```go
func Total(prices []int) int
```

принимает `[]int` и возвращает `int`.

Сумма начинается с:

```go
total := 0
```

Причина в том, что ни одна цена ещё не добавлена в сумму.

Затем через:

```go
for _, price := range prices {
	total += price
}
```

все значения прибавляются по очереди.

Вычисление по шагам:

```text
начало: 0
0 + 12 = 12
12 + 8 = 20
20 + 5 = 25
```

Результат:

```text
25
```

Но `go fmt` этого не проверяет.

Он смотрит только на формат кода.

Даже если в коде по ошибке написано:

```go
total -= price
```

эта строка может быть правильной с точки зрения формата.

То, что результат действительно равен `25`, должен проверить тест.

Главное правило: `go fmt ./...` помогает отформатировать пакеты всего модуля, но не проверяет функциональную правильность.

### 6. Поиск ошибки строки формата через `go vet`

Этот пример показывает практическую пользу `go vet`.

```go
package main

import "fmt"

func main() {
	count := "три"
	fmt.Printf("Количество файлов: %d\n", count)
}
```

Проблема этого кода — в спецификаторе формата:

```go
%d
```

`%d` предназначен для вывода целого числа.

Но из-за:

```go
count := "три"
```

тип `count` — `string`.

Значит, формат и тип аргумента не соответствуют друг другу.

При выполнении `go run` пакет `fmt` может показать эту ситуацию особым диагностическим текстом.

Но лучше найти проблему до запуска кода.

Поэтому используется:

```bash
go vet ./...
```

`go vet` умеет проверять соответствие строки формата и аргументов для функций семейства `Printf`.

Правильный вариант:

```go
fmt.Printf("Количество файлов: %s\n", count)
```

Здесь `%s` подходит для `string`.

Или, если `count` действительно должно быть числом, можно написать:

```go
count := 3
fmt.Printf("Количество файлов: %d\n", count)
```

Этот пример показывает, что `go vet` заранее обнаруживает некоторые подозрительные конструкции, которые компилятор может принять.

### 7. Проверка компиляции пакетов через `go test`

В этом примере нет отдельного тестового файла.

```go
package main

import "fmt"

func average(total, count int) int {
	if count == 0 {
		return 0
	}
	return total / count
}

func main() {
	fmt.Println(average(30, 3))
}
```

Тем не менее при выполнении:

```bash
go test ./...
```

пакеты всё равно компилируются.

Если в пакете нет тестовых функций, Go может вывести сообщение вроде:

```text
[no test files]
```

Это не значит, что «пакет вообще не проверялся».

Пакет прошёл компиляцию как часть процесса тестирования.

Посмотрим на саму функцию:

```go
func average(total, count int) int
```

Сначала проверяется:

```go
if count == 0 {
	return 0
}
```

Это предотвращает деление на ноль.

Без этой проверки случай `count == 0` в части:

```go
total / count
```

мог бы привести к panic во время выполнения.

В примере:

```text
30 / 3 = 10
```

Поскольку выбраны числа, которые делятся нацело, дополнительной проблемы с дробной частью при целочисленном делении нет.

Например:

```text
10 / 3
```

при вычислении с `int` дало бы `3`, а не `3.333...`.

Главное правило этого примера: `go test ./...` компилирует и пакеты без тестовых файлов.

Но вывод `[no test files]` не означает, что бизнес-поведение проверено тестами.

### 8. Применение проверки гонок ко всему модулю

В этом примере slice заполняется последовательно.

```go
package main

import "fmt"

func main() {
	values := make([]int, 3)
	for index := range values {
		values[index] = (index + 1) * 10
	}
	fmt.Println(values)
}
```

Сначала выполняется:

```go
values := make([]int, 3)
```

Это создаёт `[]int` длиной `3`.

Нулевое значение `int` — `0`.

Поэтому начальное состояние можно представить так:

```text
[0 0 0]
```

Затем:

```go
for index := range values
```

проходит по индексам.

Индексы:

```text
0
1
2
```

Вычисление выполняется через:

```go
values[index] = (index + 1) * 10
```

По шагам:

```text
index = 0
(0 + 1) * 10 = 10

index = 1
(1 + 1) * 10 = 20

index = 2
(2 + 1) * 10 = 30
```

Результат:

```text
[10 20 30]
```

В самом этом коде нет горутин. Поэтому показанный поток выполняется последовательно, и конкурентного доступа к общей памяти нет.

Когда для всего модуля используется:

```bash
go test -race ./...
```

race detector отслеживает пути кода, выполненные тестами.

Важное различие здесь в том, что использование флага `-race` не делает автоматически весь код конкурентным.

Он ищет опасные обращения к памяти в уже существующем конкурентном коде.

Главное правило: race detector отслеживает только реально выполненные пути кода. Если проблемный путь не выполняется в тесте, он может не быть обнаружен.

### 9. Отдельная оценка покрытия и успешности тестов

В этом примере есть небольшая функция с двумя логическими путями.

```go
package main

import "fmt"

func discount(total int) int {
	if total < 100 {
		return 0
	}
	return 10
}

func main() {
	fmt.Println(discount(100))
}
```

Условие в функции записано как:

```go
if total < 100
```

Значит:

```text
total = 99  -> 0
total = 100 -> 10
total = 101 -> 10
```

Особенно `100` здесь — граничное значение.

Причина — оператор:

```go
<
```

то есть «меньше».

Если бы условие было:

```go
total <= 100
```

результат для `100` был бы другим.

Поэтому важно тестировать граничные значения (boundary value).

После написания тестов покрытие можно посмотреть через:

```bash
go test -cover ./...
```

Покрытие показывает, какая часть кода была выполнена во время тестов.

Например, если тесты проходят обе ветки функции, покрытие может вырасти.

Но высокое покрытие не означает автоматически хороший тест.

Например, тест может вызывать:

```go
discount(100)
```

но ожидать неверный результат.

Или все инструкции функции могут выполниться, но важный случай из бизнес-требования вообще не будет проверен (assert).

Значит, нужно отдельно смотреть на две вещи:

* выполнились ли пути кода;
* правильны ли результаты на этих путях.

Главное правило: покрытие показывает охват тестами, но само по себе не гарантирует качество тестов.

### 10. Выполнение проверок в одном порядке

Этот пример показывает небольшую программу, которая может пройти основные инструменты проверки.

```go
package main

import (
	"fmt"
	"strings"
)

func normalize(words []string) string {
	cleaned := make([]string, 0, len(words))
	for _, word := range words {
		cleaned = append(cleaned, strings.TrimSpace(word))
	}
	return strings.Join(cleaned, ", ")
}

func main() {
	words := []string{" Go ", " test ", " vet "}
	fmt.Println(normalize(words))
}
```

Проверки можно выполнять в таком порядке:

```bash
go fmt ./...
go vet ./...
go test ./...
go test -race ./...
```

Теперь посмотрим, как работает код.

Функция:

```go
func normalize(words []string) string
```

принимает slice строк и возвращает одну `string`.

Сначала через:

```go
cleaned := make([]string, 0, len(words))
```

создаётся новый slice.

Здесь длина:

```text
0
```

потому что в результат ещё не добавлено ни одного слова.

А ёмкость равна:

```go
len(words)
```

В примере в `words` три элемента:

```text
" Go "
" test "
" vet "
```

Значит, для `cleaned` можно сразу выделить место под три элемента.

Причина этого подхода проста: для каждого входного элемента ожидается по одному очищенному результату.

Затем:

```go
for _, word := range words {
	cleaned = append(cleaned, strings.TrimSpace(word))
}
```

проходит по каждому элементу.

`strings.TrimSpace` удаляет пробельные символы в начале и в конце строки.

Поэтому получаем:

```text
" Go "   -> "Go"
" test " -> "test"
" vet "  -> "vet"
```

В результате `cleaned` содержит:

```text
["Go", "test", "vet"]
```

В конце:

```go
return strings.Join(cleaned, ", ")
```

объединяет элементы через `", "`.

Результат:

```text
Go, test, vet
```

В этой программе каждая проверка выполняет свою задачу.

`go fmt ./...` проверяет формат кода и при необходимости изменяет его.

`go vet ./...` ищет статически подозрительные конструкции.

`go test ./...` компилирует пакеты и выполняет существующие тесты.

`go test -race ./...` также ищет гонки данных в путях кода, выполненных тестами.

Поэтому эти команды можно рассматривать как одну общую «проверку кода», но нельзя забывать, что каждая из них выполняет отдельную задачу.
