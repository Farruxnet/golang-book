# Работа с регулярными выражениями в Go

Регулярное выражение (regular expression), сокращённо **regex**, — это шаблон, описывающий определённую форму в тексте. Он описывает не конкретный текст, а то, какую структуру должен иметь текст.

С помощью regex можно:

* искать в тексте нужные значения;
* проверять, соответствует ли значение определённому формату;
* извлекать отдельные части текста;
* заменять совпавшие части другим текстом.

Например, можно найти дату в строке лога, проверить формат имени пользователя или заменить несколько подряд идущих пробелов одним пробелом.

Но regex — не лучший инструмент для всех задач обработки текста. Для простого поиска подстроки часто проще и надёжнее `strings.Contains()`, для проверки префикса — `strings.HasPrefix()`, для работы с URL — `net/url`, а для дат и времени — `time.Parse()`.

Поэтому regex лучше использовать, когда нужно описать **форму** в тексте.

## Первый шаблон

Найдём в следующем тексте часть, похожую на дату вида `YYYY-MM-DD`:

```text
Сегодняшняя дата: 2025-08-31
```

Для этого можно использовать такой regex:

```text
\d{4}-\d{2}-\d{2}
```

Разберём этот шаблон по частям:

* `\d` — соответствует цифре ASCII, то есть от `0` до `9`;
* `{4}` — означает, что предыдущий элемент должен повториться ровно четыре раза;
* `-` — обычный дефис;
* `\d{2}` — ровно две цифры.

Таким образом:

```text
\d{4}
```

находит четыре цифры.

Следующий:

```text
-
```

соответствует дефису.

Затем:

```text
\d{2}
```

находит две цифры.

Полный шаблон:

```text
\d{4}-\d{2}-\d{2}
```

соответствует такому виду:

```text
2025-08-31
```

Здесь есть важное ограничение. Regex проверяет только **вид** значения. Он не доказывает, что значение — настоящая дата.

Например:

```text
9999-99-99
```

тоже соответствует этому regex.

Но это не настоящая дата.

Поэтому при работе с датами обычно нужны два этапа:

1. через regex находится часть нужного вида;
2. найденное значение проверяется как настоящая дата через `time.Parse()`.

Например:

```go
time.Parse("2006-01-02", value)
```

Такой подход разделяет задачу regex и задачу семантической валидации.

## Основные символы

В синтаксисе regex некоторые символы имеют специальный смысл.

| Символ   | Значение                              | Пример     | Совпадающее значение   |
| -------- | ------------------------------------- | ---------- | ---------------------- |
| `.`      | Любой один символ, кроме новой строки | `c.t`      | `cat`, `cut`           |
| `\d`     | Цифра ASCII                           | `\d{2}`    | `12`                   |
| `\w`     | Буква ASCII, цифра или `_`            | `\w+`      | `go_123`               |
| `\s`     | Пробельный символ                     | `a\s+b`    | `a b`, `a\tb`          |
| `+`      | Один или более раз                    | `a+`       | `a`, `aaa`             |
| `*`      | Ноль или более раз                    | `ba*`      | `b`, `baa`             |
| `?`      | Ноль или один раз                     | `colou?r`  | `color`, `colour`      |
| `{n}`    | Ровно `n` раз                         | `\d{4}`    | `2025`                 |
| `{n,m}`  | От `n` до `m` раз                     | `\d{2,4}`  | `12`, `2025`           |
| `^`      | Начало текста                         | `^привет`  | `привет` в начале      |
| `$`      | Конец текста                          | `мир$`     | `мир` в конце          |
| `[abc]`  | Один символ из набора                 | `[abc]`    | `a`, `b` или `c`       |
| `[^0-9]` | Символ, не входящий в набор           | `[^0-9]`   | любой символ, кроме цифры |
| `a\|b`   | Левый или правый вариант              | `cat\|dog` | `cat` или `dog`        |
| `()`     | Группировка и захват результата       | `(ab)+`    | `ab`, `abab`           |

При использовании этих символов важно знать некоторые особенности regex в Go.

Например, классы в стиле Perl, такие как `\d`, `\w` и `\b`, основаны на правилах ASCII.

`\w` примерно охватывает следующее:

```text
A-Z
a-z
0-9
_
```

Поэтому `\w` не охватывает автоматически все буквы Unicode, например кириллицу или узбекские `o‘`, `g‘`.

Для работы с Unicode используются классы вида `\p{...}`.

Например:

```text
\p{L}
```

соответствует символам, которые по Unicode считаются буквами.

```text
\p{N}
```

соответствует цифрам Unicode.

Если нужно найти сам специальный символ, его обычно нужно экранировать через `\`.

Например:

```text
.
```

в regex означает любой один символ.

Чтобы найти саму обычную точку, пишется:

```text
\.
```

Точно так же `+` в regex — оператор повторения. Чтобы совпасть с обычным символом `+`, пишется:

```text
\+
```

## Компиляция regex в Go

В стандартной библиотеке Go для работы с regex есть пакет `regexp`.

Regex обычно используется в два этапа:

1. текстовый шаблон компилируется;
2. полученный объект `*regexp.Regexp` используется для поиска или проверки.

Пример:

```go
package main

import (
	"fmt"
	"regexp"
)

func main() {
	re := regexp.MustCompile(`\d{4}-\d{2}-\d{2}`)
	date := re.FindString("Дата заказа: 2025-08-31")

	fmt.Println(date)
}
```

Результат:

```text
2025-08-31
```

Разберём этот код по шагам.

Сначала:

```go
re := regexp.MustCompile(`\d{4}-\d{2}-\d{2}`)
```

компилирует шаблон.

В результате в переменной `re` будет значение `*regexp.Regexp`.

Следующая строка:

```go
date := re.FindString("Дата заказа: 2025-08-31")
```

ищет в заданном тексте первую часть, совпадающую с шаблоном.

В результате находится:

```text
2025-08-31
```

Шаблон записан в обратных кавычках:

```go
`\d{4}-\d{2}-\d{2}`
```

Это raw string literal в Go.

Внутри raw string символ `\` не экранируется отдельно синтаксисом строк Go. Поэтому при записи regex обратные кавычки часто удобны.

Если использовать обычную строку Go в двойных кавычках, придётся писать:

```go
"\\d{4}-\\d{2}-\\d{2}"
```

Причина в том, что в этом случае первый `\` — экранирование для строки Go, а второй — настоящий символ `\`, который доходит до regex.

`regexp.MustCompile()` вызывает panic, если шаблон неверен.

Это удобно для постоянных шаблонов, известных заранее и записанных в коде.

Например:

```go
var phonePattern = regexp.MustCompile(`^\+998[0-9]{9}$`)
```

Этот шаблон написан разработчиком и почти не меняется до запуска программы. Если в нём есть синтаксическая ошибка, полезно сразу увидеть её при разработке или тестировании.

## Разница между поиском и полной валидацией

Одна из самых частых ошибок при работе с regex — считать поиск и полную валидацию одним и тем же.

`MatchString()` может вернуть `true`, если совпадение найдено в любой части строки.

Если всё значение должно соответствовать определённому формату, нужно обозначить также начало и конец строки.

Для этого:

```text
^
```

обозначает начало строки,

а:

```text
$
```

— конец строки.

Пример проверки номера телефона:

```go
package main

import (
	"fmt"
	"regexp"
)

var phonePattern = regexp.MustCompile(`^\+998[0-9]{9}$`)

func main() {
	fmt.Println(phonePattern.MatchString("+998901234567"))
	fmt.Println(phonePattern.MatchString("Телефон: +998901234567"))
	fmt.Println(phonePattern.MatchString("+99890123456"))
}
```

Результат:

```text
true
false
false
```

Разберём шаблон:

```text
^\+998[0-9]{9}$
```

по частям.

`^`:

```text
^
```

означает, что совпадение должно начинаться ровно с начала строки.

Следующий:

```text
\+998
```

требует обычную последовательность символов `+998`.

Здесь, поскольку `+` — оператор regex, он экранирован:

```text
\+
```

Следующая часть:

```text
[0-9]{9}
```

требует ровно девять цифр ASCII после кода страны.

Последний:

```text
$
```

означает, что совпадение должно закончиться в конце строки.

Поэтому:

```text
+998901234567
```

совпадает.

Но:

```text
Телефон: +998901234567
```

не совпадает. Потому что `+998...` не начинается с начала строки.

Если бы `^` и `$` не были написаны, regex мог бы найти небольшую совпадающую часть внутри строки и вернуть `true` и во втором случае.

Здесь есть ещё одно важное различие.

Regex проверяет:

> Похож ли номер телефона на нужный синтаксический формат?

Но он не определяет:

* действительно ли этот номер выделен;
* активен ли номер;
* соответствует ли он диапазону оператора;
* владеет ли пользователь этим номером.

Это проверяется не regex, а отдельными бизнес-правилами.

## Поиск всех совпадений

Иногда из текста нужно получить не только первое совпадение, а все совпадающие части.

Для этого используется `FindAllString()`.

Пример:

```go
package main

import (
	"fmt"
	"regexp"
)

func main() {
	re := regexp.MustCompile(`[0-9]+`)
	prices := re.FindAllString("Яблоки 12000, груши 18000, итого 30000", -1)

	fmt.Println(prices)
}
```

Результат:

```text
[12000 18000 30000]
```

Здесь шаблон:

```text
[0-9]+
```

соответствует последовательности из одной или более цифр.

Второй аргумент `FindAllString()` задаёт максимальное число результатов.

Здесь передано:

```go
-1
```

`-1` означает возврат всех совпадений.

Поэтому находятся три числа:

```text
12000
18000
30000
```

Если написать:

```go
re.FindAllString(text, 2)
```

вернутся только первые два совпадения.

Например:

```text
[12000 18000]
```

Если совпадений нет совсем, метод возвращает slice `nil`.

В этом примере найденные значения ещё не `int`. Они возвращаются как `string`.

Например:

```go
"12000"
```

Если с этим значением нужно выполнять арифметику, его нужно преобразовать в числовой тип.

Обычно используется:

```go
strconv.Atoi()
```

Например:

```go
value, err := strconv.Atoi("12000")
```

Здесь нужно проверить и ошибку преобразования.

Regex находит нужные части текста. Преобразование найденных данных в нужный тип Go на следующем этапе — отдельная задача.

## Извлечение частей через группы

В regex круглые скобки:

```text
(...)
```

не только группируют элементы, но и создают **захватывающую группу (capturing group)**, то есть группу, которая отдельно попадает в результат.

Например, есть такое значение:

```text
order-42
```

Мы хотим отдельно получить из него части:

* `order`;
* `42`.

Для этого:

```go
package main

import (
	"fmt"
	"regexp"
)

func main() {
	re := regexp.MustCompile(`^([a-z]+)-([0-9]+)$`)
	parts := re.FindStringSubmatch("order-42")
	if parts == nil {
		fmt.Println("Формат не совпадает")
		return
	}

	fmt.Println("Полностью:", parts[0])
	fmt.Println("Тип:", parts[1])
	fmt.Println("ID:", parts[2])
}
```

Результат:

```text
Полностью: order-42
Тип: order
ID: 42
```

Шаблон:

```text
^([a-z]+)-([0-9]+)$
```

имеет две захватывающие группы.

Первая группа:

```text
([a-z]+)
```

соответствует одной или более строчным буквам ASCII.

Вторая группа:

```text
([0-9]+)
```

соответствует одной или более цифрам.

Между ними обычный дефис:

```text
-
```

`FindStringSubmatch()` возвращает результат в виде slice.

В этом slice:

```go
parts[0]
```

всегда обозначает полное совпадение.

В этом примере:

```text
order-42
```

Следующий элемент:

```go
parts[1]
```

— значение первой захватывающей группы:

```text
order
```

А `parts[2]` — значение второй захватывающей группы:

```text
42
```

Здесь очень важна проверка:

```go
if parts == nil {
	fmt.Println("Формат не совпадает")
	return
}
```

Если шаблон не совпал, `FindStringSubmatch()` может вернуть `nil`.

Если после этого обратиться к индексу вроде:

```go
parts[0]
```

программа вызовет panic.

Поэтому при работе с методами submatch нужно сначала проверить, что результат есть.

Иногда группировка нужна, а отдельно получать результат не нужно.

В таком случае используется незахватывающая группа (non-capturing group):

```text
(?:...)
```

Например:

```text
(?:ab)+
```

группирует часть `ab`, но не сохраняет её как отдельный захваченный результат.

В regex Go есть и именованные группы.

Синтаксис:

```text
(?P<name>...)
```

Например:

```text
(?P<type>[a-z]+)
```

Позже имена групп можно получить через:

```go
SubexpNames()
```

Это облегчает чтение индексов вроде `parts[1]`, `parts[2]`, особенно в больших шаблонах с несколькими группами.

## Замена текста

Regex нужен не только для поиска. Совпавшие части можно заменить другим текстом.

Для этого используется `ReplaceAllString()`.

Например, сведём подряд идущие пробельные символы к одному пробелу:

```go
package main

import (
	"fmt"
	"regexp"
	"strings"
)

func main() {
	re := regexp.MustCompile(`\s+`)
	cleaned := re.ReplaceAllString("  Go\tработает\n с   regex  ", " ")

	fmt.Println(strings.TrimSpace(cleaned))
}
```

Результат:

```text
Go работает с regex
```

Шаблон:

```text
\s+
```

соответствует одному или более пробельным символам.

Это не только обычный пробел. Например, могут совпасть такие символы:

* пробел;
* табуляция `\t`;
* новая строка `\n`.

В исходном тексте:

```text
  Go\tработает\n с   regex  
```

каждая группа подряд идущих пробельных символов заменяется на:

```text
" "
```

Но пробелы могут остаться в начале и в конце строки.

Поэтому используется:

```go
strings.TrimSpace(cleaned)
```

Он удаляет пробельные символы в начале и в конце строки.

В этом примере можно использовать regex, но если задача — только нормализовать пробелы в тексте, есть и другое простое решение:

```go
strings.Fields()
```

`strings.Fields()` разбивает текст на части по пробельным символам. Затем их можно соединить одним пробелом.

Например:

```go
strings.Join(strings.Fields(text), " ")
```

Если нужна замена по более сложным правилам, regex полезнее.

В тексте замены `ReplaceAllString()` можно использовать и захватывающие группы.

Например:

```text
$1
```

обозначает значение первой захватывающей группы.

Для именованной группы можно использовать:

```text
${name}
```

Здесь есть тонкость. `$` в строке замены имеет специальный смысл.

Поэтому если нужно добавить обычный знак доллара, нужно учитывать синтаксис замены `ReplaceAllString()`.

В сложных случаях удобнее может быть:

```go
ReplaceAllStringFunc()
```

Этот метод позволяет вызывать функцию Go для каждого найденного совпадения.

## Шаблон, пришедший снаружи

`MustCompile()` удобен для шаблонов, известных заранее.

Но если шаблон приходит из конфигурации, HTTP-запроса или от пользователя, ситуация другая.

Если неверный шаблон передать в:

```go
regexp.MustCompile(pattern)
```

произойдёт panic.

В серверной программе panic всего процесса из-за ошибки пользователя обычно нежелателен.

В таком случае используется `regexp.Compile()`.

Пример:

```go
package main

import (
	"fmt"
	"regexp"
)

func main() {
	pattern := `[a-z+`

	re, err := regexp.Compile(pattern)
	if err != nil {
		fmt.Println("Неверный шаблон:", err)
		return
	}

	fmt.Println(re.MatchString("go"))
}
```

Здесь шаблон:

```text
[a-z+
```

неверен.

Причина в том, что класс символов, начатый с `[`, не закрыт.

`regexp.Compile()` не вызывает panic.

Он возвращает два значения:

```go
re, err := regexp.Compile(pattern)
```

Если шаблон верен:

* `re` — regex, готовый к использованию;
* `err == nil`.

Если шаблон ошибочен:

* `err` даёт информацию об ошибке.

Текст ошибки может немного отличаться в зависимости от версии Go:

```text
Неверный шаблон: error parsing regexp: missing closing ]: `[a-z+`
```

Этот подход безопаснее для шаблонов, заданных пользователем.

Например, если пользователь отправит неверный regex в веб-API, сервер может вернуть ответ вроде:

```text
400 Bad Request
```

Но выводить клиенту внутреннюю ошибку парсера полностью не всегда хорошо.

На практике лучше дать пользователю более понятное сообщение валидации.

Например:

```text
Неверный regex-шаблон.
```

А внутреннюю техническую ошибку можно записать в лог.

## Валидация email и URL

Email можно проверять через regex, но в этой задаче нужна осторожность.

Следующий шаблон упрощённо проверяет обычные формы email:

```text
(?i)^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$
```

Разберём этот шаблон по частям.

```text
(?i)
```

включает режим без учёта регистра.

Значит, разница между заглавными и строчными буквами не учитывается.

Следующий:

```text
^[a-z0-9._%+-]+
```

проверяет допустимые символы в части до знака `@`.

Затем:

```text
@
```

должен идти обычный знак `@`.

Доменная часть проверяется через:

```text
[a-z0-9.-]+
```

В конце:

```text
\.[a-z]{2,}$
```

требует точку и суффикс минимум из двух букв.

Например:

```text
user@example.com
```

может совпасть.

Но этот шаблон не выражает всех случаев стандарта email.

Синтаксис email на практике гораздо сложнее.

Кроме того, regex не может определить:

* существует ли домен на самом деле;
* существует ли почтовый ящик;
* владеет ли пользователь этим email;
* дойдёт ли письмо на этот email.

Поэтому в таком процессе, как регистрация аккаунта, самая надёжная итоговая проверка — обычно отправка письма с подтверждением.

Для URL действует тот же принцип.

Вместо полной валидации URL очень большим regex лучше использовать:

```go
net/url.ParseRequestURI()
```

или другой подходящий для задачи парсер.

Парсер разбивает URL на части.

Например, в структурированном виде получаются такие части, как:

* scheme;
* host;
* path;
* query;
* экранирование.

Regex для URL может быть полезен только для дополнительной проверки узкого формата, которого требует проект.

Например, правило проекта вроде:

> Принимаются только URL, начинающиеся с `https://`.

можно проверить regex или дополнительной валидацией после парсера.

## Особенности движка regex в Go

Пакет Go `regexp` основан на синтаксисе RE2.

Это не только различие в синтаксисе. Важна и его модель работы.

Regex в Go спроектирован так, чтобы время сопоставления оставалось линейным относительно размера входа.

Проще говоря, в некоторых движках regex с возвратами (backtracking) неудачно построенный шаблон может привести к огромным вычислительным затратам.

Это явление часто называют **catastrophic backtracking** (катастрофическим возвратом).

Дизайн RE2 направлен на ограничение такой ситуации.

Это важно для систем, куда текст приходит от пользователей, например веб-серверов. Потому что очень тяжёлый regex может надолго занять ресурсы CPU.

Но в обмен на эту более безопасную модель работы некоторые возможности regex не поддерживаются.

В пакете Go `regexp` нет:

* обратных ссылок (backreference): `\1`, `\k<name>`;
* lookahead: `(?=...)`, `(?!...)`;
* lookbehind: `(?<=...)`;
* условных шаблонов;
* рекурсивных шаблонов.

Например, возьмём такую задачу:

> Найти два одинаковых слова, написанных рядом.

В некоторых движках regex первое слово можно захватить группой, а затем через обратную ссылку снова потребовать то же значение.

В regex Go обратных ссылок нет.

Поэтому нужные части сначала нужно извлечь через regex, а затем сравнить в коде Go.

Здесь есть важное практическое правило.

Если шаблон не меняется, его не нужно каждый раз компилировать заново.

Например, такая запись:

```go
func ValidatePhone(value string) bool {
	re := regexp.MustCompile(`^\+998[0-9]{9}$`)
	return re.MatchString(value)
}
```

компилирует regex заново при каждом вызове.

Лучше один раз подготовить постоянный шаблон на уровне пакета:

```go
var phonePattern = regexp.MustCompile(`^\+998[0-9]{9}$`)

func ValidatePhone(value string) bool {
	return phonePattern.MatchString(value)
}
```

Причина в том, что `*regexp.Regexp` после компиляции можно переиспользовать.

Он также безопасно используется несколькими горутинами конкурентно.

Это особенно полезно в серверном коде. Потому что пересоздание regex на каждый запрос увеличивает затраты CPU и аллокаций.

## Unicode и байтовые индексы

Строки Go состоят из байтов в кодировке UTF-8.

А regex работает, рассматривая текст как кодовые точки Unicode, то есть руны.

Например:

```text
.
```

обычно соответствует одной руне.

Для текста ASCII это не имеет большого значения. Потому что каждый символ ASCII в UTF-8 занимает один байт.

Но символ Unicode может состоять из нескольких байтов.

Поэтому у методов regex, возвращающих индексы, есть тонкость.

Например:

```go
FindStringIndex()
```

возвращает не индексы рун, а **байтовые смещения**.

Это соответствует правилам индексации строк в Go.

Если в тексте есть кириллица, `o‘`, `g‘` или другие многобайтовые символы Unicode, байтовое смещение и порядковый номер руны могут не совпадать.

Для работы с узбекскими, русскими и другими буквами Unicode полезны классы Unicode вроде `\p{L}`.

Пример:

```go
package main

import (
	"fmt"
	"regexp"
)

func main() {
	re := regexp.MustCompile(`^\p{L}+(?:[’']\p{L}+)*$`)

	fmt.Println(re.MatchString("g‘alaba"))
	fmt.Println(re.MatchString("o'zbek"))
	fmt.Println(re.MatchString("go123"))
}
```

Результат:

```text
true
true
false
```

Разберём шаблон:

```text
^\p{L}+(?:[’']\p{L}+)*$
```

по частям.

Первая часть:

```text
^\p{L}+
```

требует одну или более букв Unicode, начиная с начала строки.

`\p{L}` охватывает не только ASCII, а все символы, которые по Unicode считаются буквами.

Следующая часть:

```text
(?:[’']\p{L}+)*
```

необязательно разрешает апостроф, за которым снова идут буквы.

```text
[’']
```

принимает два варианта апострофа:

* типографский апостроф: `’`;
* обычный апостроф: `'`.

Поэтому:

```text
g‘alaba
```

совпадает.

```text
o'zbek
```

тоже совпадает.

Но:

```text
go123
```

не совпадает.

Причина в том, что цифры не входят в группу `\p{L}`.

Этот шаблон не нужно воспринимать как настоящую валидацию имени.

В настоящих именах могут встречаться:

* дефисы;
* пробелы;
* несколько слов;
* разные символы апострофа;
* разные системы письма.

Поэтому валидация имени определяется отдельными бизнес-правилами в зависимости от требований проекта.

## Частые ошибки

При работе с regex часто встречаются несколько ошибок.

* Забыть `^` и `$` в шаблоне валидации. Тогда `MatchString()` может вернуть `true`, даже если совпала лишь небольшая часть строки. Если проверяется всё значение, границы нужно писать явно.

* Путать экранирование в raw string и в обычной строке Go. В regex часто используется `\`. Поэтому raw string в обратных кавычках часто упрощает чтение шаблона.

* Использовать `MustCompile()` с шаблоном, пришедшим от пользователя. Неверный шаблон может вызвать panic. Для внешнего шаблона используются `regexp.Compile()` и обработка `error`.

* Заново компилировать один и тот же regex на каждый запрос. Лучше один раз скомпилировать постоянный шаблон и переиспользовать готовый `*regexp.Regexp`.

* Обращаться по индексу к результату `FindStringSubmatch()` без проверки на `nil`. Если совпадения нет, slice может быть `nil`, и обращение по индексу вызовет panic.

* Думать, что `\w` охватывает все буквы Unicode. В regex Go `\w` работает на основе ASCII. Для букв Unicode нужно использовать классы вроде `\p{L}`.

* Приравнивать совпадение с regex к достоверности данных. `2025-99-99` может быть похоже на формат даты, но это не настоящая дата. Для email, URL, телефона и других значений отдельно нужна и семантическая валидация.

* Решать простую задачу сложным regex. Иногда `strings`, `strconv`, `time`, `net/url` или другой специальный парсер делают код гораздо понятнее и надёжнее.

## На что обращают внимание на собеседовании?

На собеседовании по Go в теме regex могут спросить не только синтаксис, но и особенности пакета `regexp`.

Один из важных моментов — `MatchString()` принимает частичное совпадение.

Например:

```go
re := regexp.MustCompile(`[0-9]+`)
fmt.Println(re.MatchString("ID: 42"))
```

здесь результат может быть `true`, потому что совпала только часть строки `42`.

Поэтому если валидируется всё значение, нужно понимать важность границ:

```text
^
```

и:

```text
$
```

Важна и разница между `Compile()` и `MustCompile()`.

`MustCompile()`:

* вызывает panic, если шаблон неверен;
* удобен для постоянных шаблонов, известных заранее.

`Compile()`:

* возвращает ошибку как `error`;
* больше подходит для внешних или динамических шаблонов.

То, что regex в Go основан на RE2, — тоже важный технический момент.

Этот подход спроектирован так, чтобы время сопоставления оставалось линейным относительно размера входа, и ограничивает проблему catastrophic backtracking.

Из-за такого дизайна в regex Go нет некоторых возможностей:

* обратных ссылок;
* lookahead;
* lookbehind.

Нужно уметь различать и задачи стандартных методов:

```go
FindString()
```

находит первое совпадение.

```go
FindAllString()
```

возвращает несколько или все совпадения.

```go
FindStringSubmatch()
```

возвращает захватывающие группы вместе с полным совпадением.

```go
ReplaceAllString()
```

заменяет совпавшие части.

При работе с Unicode полезно знать разницу между `\w` и `\p{L}`.

Также нельзя забывать, что результат методов, возвращающих индексы, — не индекс руны, а байтовое смещение.

Ещё одно практическое правило:

```go
*regexp.Regexp
```

можно переиспользовать после компиляции, и он безопасен для конкурентного использования несколькими горутинами.

Поэтому многократно компилировать один и тот же шаблон внутри запроса обычно не нужно.
