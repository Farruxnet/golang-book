# Небуферизованные, буферизованные и направленные каналы

В Go все каналы выполняют одну и ту же основную задачу: одна горутина отправляет значение, а другая горутина его принимает.

Но в зависимости от того, как создан канал, порядок его работы различается.

Есть три основных важных случая:

* **небуферизованный канал** — отправитель и получатель ждут друг друга в момент обмена значением;
* **буферизованный канал** — имеет ограниченную очередь, где значения хранятся временно;
* **направленный канал** — на уровне типа определяет, может ли функция через канал только отправлять или только получать.

Эти различия — не просто вопрос синтаксиса. Они напрямую влияют на то, когда блокируются горутины, как управляется нагрузка и как устроен API.

## Небуферизованный канал

Если при создании канала не указать ёмкость, создаётся небуферизованный канал:

```go
ch := make(chan int)
```

Явное указание ёмкости `0` даёт тот же результат:

```go
other := make(chan int, 0)
```

Значит, семантика работы следующих двух каналов одинакова:

```go
ch := make(chan int)
other := make(chan int, 0)
```

У небуферизованного канала нет очереди для временного хранения значений.

Поэтому send и receive напрямую связаны друг с другом:

* отправляющая горутина ждёт, пока не будет готов соответствующий receive;
* принимающая горутина ждёт, пока не будет готов соответствующий send;
* когда обе стороны готовы, значение передаётся.

В этот момент между двумя горутинами происходит синхронизация.

Иначе говоря, в небуферизованный канал нельзя просто «бросить значение и уйти». Значение передаётся именно в тот момент, когда другая сторона готова его принять.

### Пример: сигнал о завершении работы

В следующем примере канал используется не для передачи полезных данных, а чтобы сообщить о завершении работы.

```go
package main

import "fmt"

func prepare(done chan<- struct{}) {
	fmt.Println("Данные подготовлены")
	done <- struct{}{}
}

func main() {
	done := make(chan struct{})

	go prepare(done)
	<-done

	fmt.Println("Программа продолжила работу")
}
```

Результат:

```text
Данные подготовлены
Программа продолжила работу
```

Здесь `done` — небуферизованный канал:

```go
done := make(chan struct{})
```

`prepare` работает внутри отдельной горутины:

```go
go prepare(done)
```

А `main` ждёт на следующей строке:

```go
<-done
```

Это операция receive.

Но поскольку `done` небуферизованный, `main` блокируется здесь, пока не придёт сигнал.

Функция `prepare` сначала выполняет строку:

```go
fmt.Println("Данные подготовлены")
```

После этого отправляет сигнал через:

```go
done <- struct{}{}
```

`struct{}{}` здесь не хранит никаких полезных данных. Его задача — только доставить сигнал «работа завершена».

Когда сигнал отправлен, receive в `main`:

```go
<-done
```

завершается, и программа продолжает работу:

```go
fmt.Println("Программа продолжила работу")
```

Поэтому в выводе сначала появляется:

```text
Данные подготовлены
```

а затем:

```text
Программа продолжила работу
```

Небуферизованный канал особенно полезен, когда нужно:

* передать работу другой горутине и дождаться, пока она её примет;
* сообщить о завершении выполнения;
* ждать до прихода ответа;
* создать точную точку синхронизации между двумя горутинами.

### Send без получателя

Чтобы отправить значение в небуферизованный канал, должна существовать и принимающая сторона.

Например:

```go
package main

func main() {
	ch := make(chan int)
	ch <- 10
}
```

Эта программа не завершится успешно.

`ch` небуферизованный:

```go
ch := make(chan int)
```

Затем `main` пытается выполнить отправку:

```go
ch <- 10
```

Но нигде нет:

```go
<-ch
```

или эквивалентной операции receive.

Поэтому `main` блокируется на send.

Поскольку единственная горутина в программе тоже заблокирована, Go runtime обнаруживает взаимоблокировку, и программа завершается с ошибкой.

Важное правило здесь такое:

> Send в небуферизованный канал не завершается, пока не готов соответствующий receive.

## Буферизованный канал

Если каналу задать положительную ёмкость, создаётся буферизованный канал:

```go
ch := make(chan int, 3)
```

Здесь `3` — ёмкость буфера канала.

Значит, канал может временно хранить в очереди три значения.

В буферизованном канале send и receive работают так:

* если в буфере есть свободное место, send может завершиться, не дожидаясь получателя;
* если буфер заполнен, следующий send блокируется, пока не освободится место;
* если в буфере есть значение, receive может сразу его взять;
* если буфер пуст, receive блокируется до прихода нового значения.

Поэтому буфер до определённого предела развязывает скорости работы отправителя и получателя.

Но эта развязка не бесконечна. В очереди может временно стоять столько значений, сколько позволяет ёмкость буфера.

### Самый маленький пример

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)

	ch <- 10
	ch <- 20

	fmt.Println(<-ch)
	fmt.Println(<-ch)
}
```

Результат:

```text
10
20
```

Ёмкость канала — `2`:

```go
ch := make(chan int, 2)
```

Первый send:

```go
ch <- 10
```

помещает значение в буфер.

Состояние буфера:

```text
[10]
```

Следующий send:

```go
ch <- 20
```

тоже завершается, потому что в буфере ещё есть одно свободное место.

Состояние буфера:

```text
[10, 20]
```

Теперь буфер заполнен.

Затем выполняется первый receive:

```go
fmt.Println(<-ch)
```

Канал возвращает самое раннее значение:

```text
10
```

Состояние буфера:

```text
[20]
```

Второй receive берёт значение:

```text
20
```

Значения в канале извлекаются в порядке FIFO.

**FIFO — First In, First Out**, то есть первым вошло — первым вышло.

Здесь есть тонкость.

FIFO относится к порядку значений, успешно отправленных в канал. Если несколько горутин одновременно пытаются отправить, то какая именно горутина первой завершит send, может зависеть от планировщика.

Например, если две горутины одновременно выполняют:

```go
ch <- 10
```

и:

```go
ch <- 20
```

Go не гарантирует, что «`10` всегда входит первым».

Но если `10` успешно отправлено в канал первым, receive не заберёт `20` раньше него.

Канал сохраняет порядок получения, соответствующий порядку успешных отправок.

Если буфер заполнен, новый send блокируется.

Например:

```go
// ch := make(chan int, 2)
// ch <- 10
// ch <- 20
// ch <- 30 // Буфер заполнен, получателя нет: deadlock.
```

По шагам:

```text
ch <- 10
буфер: [10]

ch <- 20
буфер: [10, 20]

ch <- 30
буфер заполнен
receive нет
send блокируется
```

Если другая горутина возьмёт одно значение, например:

```go
<-ch
```

в буфере освободится место, и третий send сможет продолжиться.

## Практический пример: ограниченная очередь

Одно из самых полезных применений буферизованного канала — создание ограниченной очереди между производителем и потребителем.

В следующем примере `produce` создаёт задачи, а `main` их принимает.

```go
package main

import "fmt"

func produce(jobs chan<- int) {
	for job := 1; job <= 5; job++ {
		jobs <- job
	}
	close(jobs)
}

func main() {
	jobs := make(chan int, 2)

	go produce(jobs)

	for job := range jobs {
		fmt.Println("Получено:", job)
	}
}
```

Результат:

```text
Получено: 1
Получено: 2
Получено: 3
Получено: 4
Получено: 5
```

Здесь:

```go
jobs := make(chan int, 2)
```

создаёт буфер на два элемента.

`produce` запускается как отдельная горутина:

```go
go produce(jobs)
```

Она создаёт пять задач в следующем цикле:

```go
for job := 1; job <= 5; job++ {
	jobs <- job
}
```

Если в буфере есть место, производитель может продолжать отправлять значения, не дожидаясь получателя.

Например, представим, что потребитель ещё не начал работу.

Первое значение:

```text
1
```

попадает в буфер:

```text
[1]
```

Второе значение:

```text
2
```

тоже помещается:

```text
[1, 2]
```

Теперь буфер заполнен.

Когда производитель доходит до:

```go
jobs <- 3
```

он временно блокируется.

Потребитель начинает брать значения из канала через:

```go
for job := range jobs
```

Как только одно значение взято, в буфере освобождается место, и производитель снова продолжает.

Так производитель и потребитель не ждут друг друга полностью, но и разрыв между ними не растёт бесконечно.

После того как `produce` отправит все значения, он закрывает канал через:

```go
close(jobs)
```

Это очень важно.

`range`:

```go
for job := range jobs
```

продолжает работать, пока канал не закрыт и пока из него не взяты все оставшиеся значения.

Когда канал закрывается, в буфере ещё могут оставаться значения.

Например:

```text
[4, 5]
```

Хотя канал закрыт, `range` заберёт эти два значения.

`range` завершается только когда:

1. канал закрыт;
2. буфер пуст.

### Противодавление (backpressure)

Буфер временно развязывает скорости производителя и потребителя.

Например, пусть производитель создаёт 100 задач в секунду, а потребитель обрабатывает 80 задач в секунду.

Сначала буфер может временно поглотить разницу.

Но если потребитель всегда медленнее производителя, очередь постепенно заполняется.

Когда ёмкость буфера исчерпана, производитель не может отправить новые значения и блокируется.

Эта ситуация называется **backpressure**, то есть противодавление.

Проще говоря:

> Более медленная часть системы оказывает давление на более быструю, говоря: «теперь подожди».

Это полезное свойство.

Иначе, если бы производитель продолжал создавать новые задачи с неограниченной скоростью, они могли бы бесконечно накапливаться в памяти.

Ограниченный буфер задаёт для очереди чёткий предел.

## Как выбрать ёмкость?

Выбирать размер буфера просто как большое случайное число — неправильный подход.

Например, запись:

```go
jobs := make(chan Job, 100000)
```

не решает проблему автоматически.

Ёмкость буфера на самом деле определяет, сколько незавершённых задач разрешено одновременно держать в очереди в системе.

Поэтому при выборе ёмкости нужно ответить на несколько вопросов.

### Сколько задач может обработать потребитель?

Если потребитель или воркеры могут эффективно работать одновременно только с 10 задачами, очень большая очередь не всегда полезна.

Тысячи задач в очереди всё равно будут ждать.

### Насколько может временно вырасти нагрузка?

Иногда скорость производителя растёт только на короткое время.

Например, обычно приходит 100 запросов в секунду, но на короткое время может быть 150.

В таком случае буфер может быть полезен, чтобы поглотить короткий всплеск.

### Сколько памяти занимает каждое значение?

Значения в буфере канала хранятся в памяти.

Если в канале маленькие `int`, проблема может быть невелика.

Но если каждое значение хранит большой `struct`, slice или ссылки на другие крупные объекты, большой буфер может заметно увеличить расход памяти.

### Устаревает ли результат от долгого ожидания в очереди?

Для некоторых задач старые данные становятся бесполезными.

Например, если метрики реального времени или события обновления пользовательского интерфейса долго стоят в очереди, к моменту обработки они могут уже устареть.

В таком случае большая очередь лишь скрывает проблему задержки.

### Должен ли отправитель блокироваться, когда система замедляется?

Иногда блокировка производителя — именно нужное поведение.

Например, если нижестоящий (downstream) сервис не успевает, вышестоящий (upstream) тоже должен снизить скорость.

Это одна из главных целей противодавления.

А слишком маленький буфер может вызвать обратную проблему.

Даже если скорости производителя и потребителя почти равны, из-за маленькой очереди они могут блокироваться чаще, чем нужно.

А слишком большой буфер:

* показывает проблему позже;
* увеличивает расход памяти;
* увеличивает задержку;
* надолго удерживает старые задачи в очереди.

Поэтому важно сначала определить нужную семантику.

Затем нужно измерять на реальной нагрузке.

Ёмкость буфера лучше проверять не предположениями о производительности, а результатами бенчмарков, профилирования и нагрузочных тестов.

## `len` и `cap`

Для канала можно использовать встроенные функции `len` и `cap`.

`cap(ch)` возвращает общую ёмкость буфера канала.

`len(ch)` возвращает, сколько значений сейчас находится в буфере.

Например:

```go
package main

import "fmt"

func main() {
	ch := make(chan string, 3)
	ch <- "один"
	ch <- "два"

	fmt.Println("Длина:", len(ch))
	fmt.Println("Ёмкость:", cap(ch))
}
```

Результат:

```text
Длина: 2
Ёмкость: 3
```

Из-за канала:

```go
ch := make(chan string, 3)
```

результат:

```go
cap(ch)
```

равен:

```text
3
```

Отправлено два значения:

```go
ch <- "один"
ch <- "два"
```

Поэтому сейчас в буфере два значения:

```text
["один", "два"]
```

Значит, результат:

```go
len(ch)
```

равен:

```text
2
```

Для небуферизованного канала:

```go
ch := make(chan int)
```

`cap(ch)` всегда `0`.

Здесь есть важная тонкость конкурентности, связанная с `len(ch)`.

Например:

```go
if len(ch) < cap(ch) {
	ch <- value
}
```

на первый взгляд может показаться безопасным.

Будто программа:

1. проверяет, что в буфере есть место;
2. затем отправляет.

Но эти две операции не атомарны.

После проверки `len(ch)` другая горутина может отправить значение в канал.

Например:

```text
1. Горутина A: len(ch) = 1, cap(ch) = 2
2. A ещё не отправила
3. Горутина B отправляет значение в канал
4. Буфер заполняется
5. Горутина A отправляет
6. A блокируется
```

Поэтому:

```go
if len(ch) < cap(ch)
```

не гарантирует, что следующий send не заблокируется.

`len(ch)` показывает лишь состояние в тот конкретный момент.

При конкурентности эта информация может сразу устареть.

По этой причине логику программы обычно не нужно привязывать к `len(ch)`.

Если нужен неблокирующий send или receive, для этого используются `select` и `default`.

Эта тема рассматривается в следующем уроке.

## Направленные типы каналов

Обычный:

```go
chan T
```

— двунаправленный канал.

Например, для:

```go
chan int
```

возможны обе операции:

```go
ch <- 10
```

и:

```go
value := <-ch
```

Но если функция должна работать с каналом только в одном направлении, это право можно ограничить через тип.

Например:

```go
func send(out chan<- int) {
	out <- 10
}

func receive(in <-chan int) int {
	return <-in
}
```

Здесь:

```go
chan<- int
```

— тип канала, разрешающий только отправку.

Символ `<-` стоит после `chan`:

```go
chan<- int
```

то есть значение отправляется в сторону канала.

В функции `receive` использовано:

```go
<-chan int
```

Это канал, разрешающий только получение.

Этот синтаксис можно запомнить так:

```go
chan<- T
```

значение идёт в канал.

```go
<-chan T
```

значение выходит из канала.

Основные типы:

* `chan<- int` — только для отправки;
* `<-chan int` — только для получения;
* `chan int` — можно и отправлять, и получать.

Двунаправленный канал можно передать в направленный параметр.

Например:

```go
ch := make(chan int, 1)
send(ch)
fmt.Println(receive(ch))
```

Тип `ch`:

```go
chan int
```

Но функция `send` принимает только:

```go
chan<- int
```

Здесь Go автоматически сужает двунаправленный канал до представления, у которого есть только право отправки.

Тот же канал затем можно передать и через:

```go
receive(ch)
```

в параметр, который только получает.

Польза в том, что функция может выполнить только нужную операцию.

Например, внутри:

```go
func send(out chan<- int) {
	out <- 10
}
```

нельзя написать такой код:

```go
value := <-out
```

Это будет ошибкой компиляции.

Точно так же внутри:

```go
func receive(in <-chan int) int
```

нельзя написать:

```go
in <- 10
```

Это позволяет обнаружить ошибку не во время выполнения, а на этапе компиляции.

Направленный канал также ясно показывает намерение API.

Например, разработчик, увидевший сигнатуру:

```go
func produce(out chan<- Job)
```

сразу понимает, что функция не читает значения из `out`.

### Закрытие канала и направление

Канал, переданный только для получения, закрыть нельзя.

Например, внутри следующей функции:

```go
func consume(in <-chan int) {
	close(in) // ошибка компиляции
}
```

`close(in)` не разрешён.

Причина в том, что `in` передан только для получения.

А закрытие канала — операция, относящаяся к ответственности отправляющей стороны.

Поэтому для `close` нужен канал с правом отправки:

```go
chan T
```

или:

```go
chan<- T
```

Обычно канал закрывает производитель, который знает, что новых значений больше отправлено не будет.

## Какой тип канала выбрать?

Следующая таблица обобщает основные случаи.

| Ситуация                                                            | Подходящий выбор          |
| ------------------------------------------------------------------- | ------------------------- |
| Отправитель и получатель должны встретиться именно в момент обмена  | Небуферизованный канал    |
| Короткий всплеск нагрузки нужно удержать в ограниченной очереди     | Буферизованный канал      |
| Функция только производит значения                                  | Параметр `chan<- T`       |
| Функция только потребляет значения                                  | Параметр `<-chan T`       |

Здесь нет общего правила «небуферизованный канал медленный, буферизованный быстрый».

Буферизованный канал может улучшить пропускную способность при некоторых нагрузках.

В другом случае он может принести лишь лишнюю очередь, задержку и расход памяти.

А точная синхронизация небуферизованного канала в некоторых алгоритмах может быть именно нужной семантикой.

Поэтому выбор нельзя делать только на основе предположений о производительности.

Сначала вопрос должен быть таким:

> Какая семантика нужна здесь между отправителем и получателем?

Затем:

> Нужна ли очередь?

> Если нужна, то какого размера?

> Когда должен блокироваться отправитель?

А разницу в производительности нужно измерять бенчмарком на конкретной нагрузке.

## Частые ошибки

### Думать, что буфер полностью устраняет взаимоблокировку

Буфер развязывает send и receive только в пределах своей ёмкости.

Например:

```go
ch := make(chan int, 2)

ch <- 1
ch <- 2
ch <- 3
```

первые две отправки могут завершиться.

Но третья отправка:

```go
ch <- 3
```

блокируется, потому что в буфере нет места.

Если получатель никогда не заработает, программа может попасть во взаимоблокировку.

Значит, буфер не устраняет проблему взаимоблокировки автоматически.

Жизненный цикл горутин, закрытие канала и поток send/receive всё равно нужно правильно организовать.

### Бесконечное увеличение буфера

Большой буфер не исправляет проблему медленного потребителя.

Он лишь откладывает момент, когда проблема станет видна.

Например, если потребитель всегда медленнее производителя:

```text
скорость производителя > скорость потребителя
```

очередь всё равно заполняется.

Разница только в том, что:

* маленький буфер заполняется быстрее;
* большой буфер заполняется позже.

За это время большой буфер использует больше памяти и увеличивает время ожидания задач в очереди.

Поэтому нужно задать чёткий предел и механизм противодавления, подходящие системе.

### Думать, что FIFO даёт глобальный порядок выполнения

Хотя канал работает по FIFO, это не значит, что все горутины выполняются в строгом глобальном порядке.

Например:

```go
go func() {
	ch <- 1
}()

go func() {
	ch <- 2
}()
```

в этом коде именно планировщик решает, какая горутина отправит первой.

При одних запусках результат может быть:

```text
1
2
```

В другой раз:

```text
2
1
```

FIFO гарантирует следующее:

> Какое значение было успешно отправлено в канал раньше, то раньше и будет получено.

Но канал не гарантирует, какая из разных горутин отправит первой.

### Синхронизация через `len(ch)`

Следующий подход — небезопасная синхронизация:

```go
if len(ch) > 0 {
	value := <-ch
	_ = value
}
```

После проверки `len(ch)` другая горутина может забрать значение из канала.

Тогда эта горутина может заблокироваться на операции:

```go
<-ch
```

Та же проблема есть и на стороне отправки.

Поэтому нельзя делать вывод по результату `len`, что следующая операция с каналом не заблокируется.

Такое решение нужно выражать как одну операцию с каналом через `select`.

### Лишние права в параметре функции

Если функция только отправляет, написать:

```go
func produce(ch chan int)
```

технически можно.

Но это разрешает внутри функции и получение.

Например:

```go
value := <-ch
```

скомпилируется.

Если функция на самом деле только производитель, правильнее сигнатура:

```go
func produce(ch chan<- int)
```

Точно так же для потребителя лучше написать:

```go
func consume(ch <-chan int)
```

Это даёт API минимально необходимые права и предотвращает случайное неправильное использование.

## На что обращают внимание на собеседовании?

В вопросах на собеседовании часто важнее понимать семантику блокировки каналов, чем синтаксис.

Нужно точно знать следующее:

* небуферизованный send блокируется, пока не готов соответствующий receive;
* небуферизованный receive блокируется, пока не готов соответствующий send;
* буферизованный send может продолжаться без получателя только пока в буфере есть место;
* когда буфер заполнен, send снова блокируется;
* когда буфер пуст, receive блокируется до прихода нового значения;
* канал сохраняет порядок FIFO;
* FIFO не гарантирует порядок планировщика для разных горутин;
* буфер — средство создания ограниченной очереди и противодавления;
* `len(ch)` показывает лишь состояние в данный момент и не даёт гарантий синхронизации;
* `chan<- T` — только для отправки;
* `<-chan T` — только для получения;
* канал только для получения нельзя закрыть через `close`;
* ёмкость канала не выбирается просто из предположения «пусть работает быстрее»;
* ёмкость выбирается на основе нужной семантики, лимита памяти, требования к задержке и реальных измерений.

В следующей теме для выбора из нескольких операций send и receive той, что готова к выполнению в данный момент, используется оператор `select`.
