# Написание и чтение документации Go

В Go документация обычно пишется прямо в исходном коде. Для этого используются обычные комментарии. `go doc`, `pkg.go.dev` и другие инструменты Go читают эти комментарии и показывают разработчику понятную документацию об API.

Поэтому написание документации не обязательно означает подготовку отдельного большого документа. Во многих случаях достаточно правильно написанного комментария рядом с типом, функцией, методом, константой или пакетом.

Но хорошая документация не просто повторяет имя другими словами.

Например, такой комментарий не очень полезен:

```go
// DefaultLimit — значение DefaultLimit.
var DefaultLimit = 20
```

Само имя уже даёт почти ту же информацию.

Более полезный комментарий объясняет назначение значения:

```go
// DefaultLimit — стандартное количество элементов, возвращаемых за один запрос.
var DefaultLimit = 20
```

Хорошая документация по возможности объясняет то, что нужно знать вызывающему коду:

* что делает API;
* какое значение возвращает;
* есть ли важные ограничения;
* в каких случаях возвращает `error`;
* что означают особые значения;
* как следует использовать API.

## Комментарии к экспортируемым именам

В Go, если имя уровня пакета начинается с заглавной буквы, оно **экспортируется** (exported), то есть его могут использовать и другие пакеты.

Например:

```go
type User struct {
	Name string
}
```

`User` начинается с заглавной буквы. Поэтому другой пакет может использовать этот тип через импорт.

Документирующий комментарий экспортируемого имени обычно начинается с самого этого имени:

```go
// User представляет пользователя системы.
type User struct {
	Name string
}

// NewUser возвращает новый User с заданным именем.
func NewUser(name string) User {
	return User{Name: name}
}

// DisplayName возвращает отображаемое имя пользователя.
func (u User) DisplayName() string {
	return u.Name
}
```

Здесь три экспортируемых имени:

* `User`;
* `NewUser`;
* `DisplayName`.

Каждый их комментарий начинается с соответствующего имени:

```text
User ...
NewUser ...
DisplayName ...
```

Такой способ делает удобным чтение документации через `go doc` или `pkg.go.dev`. Читатель сразу видит, о каком API комментарий.

Не пытайтесь просто пересказать в комментарии реализацию, которая и так видна из кода.

Например:

```go
// DisplayName возвращает значение u.Name.
func (u User) DisplayName() string {
	return u.Name
}
```

Этот комментарий почти дословно повторяет код.

Следующий вариант полезнее:

```go
// DisplayName возвращает отображаемое имя пользователя.
```

Потому что для вызывающего кода внешнее поведение метода важнее, чем то, какое именно поле возвращается внутри.

Это один из главных принципов документации API: **объяснять не реализацию, а поведение, важное для пользователя**.

## Комментарий пакета

У пакета тоже может быть своя документация.

Комментарий пакета пишется перед объявлением `package`. Обычно он начинается в форме `Package <имя>`:

```go
// Package greeting предоставляет функции приветствия на разных языках.
package greeting
```

Этот комментарий объясняет назначение всего пакета `greeting`.

Здесь речь не об отдельной функции или типе, а о том, зачем нужен пакет в целом.

Например, в пакете может быть несколько функций:

```go
func Hello(name string) string
func HelloEnglish(name string) string
func HelloUzbek(name string) string
```

Комментарий пакета вместо объяснения каждой из них по отдельности говорит об общей цели пакета:

```go
// Package greeting предоставляет функции приветствия на разных языках.
```

Для небольшого пакета комментарий может находиться в одном из обычных `.go`-файлов.

Например:

```text
greeting/
    greeting.go
```

Внутри `greeting.go` достаточно написать:

```go
// Package greeting предоставляет функции приветствия на разных языках.
package greeting
```

Если документация пакета больше, её удобно хранить в отдельном файле `doc.go`:

```text
greeting/
    doc.go
    greeting.go
    language.go
```

Файл `doc.go` обычно используется для хранения общей и более подробной документации о пакете.

Например:

```go
// Package greeting предоставляет функции приветствия на разных языках.
//
// Пакет используется для создания простых текстов приветствия.
// Поддерживаемые языки выбираются через отдельные функции.
package greeting
```

Это не особый обязательный синтаксис. То есть Go не требует, чтобы комментарий пакета был только в `doc.go`. `doc.go` — распространённый способ аккуратно хранить большую документацию.

Следует избегать нескольких противоречащих друг другу комментариев для одного пакета. Общее назначение пакета лучше объяснить в одной понятной документации.

## Чтение документации через `go doc`

Документацию Go можно смотреть и прямо из терминала.

Для этого используется команда `go doc`:

```bash
go doc fmt
go doc fmt.Println
go doc ./...
```

Первая команда:

```bash
go doc fmt
```

показывает документацию пакета `fmt`.

В ней можно увидеть описание пакета и экспортируемые элементы API.

Вторая команда:

```bash
go doc fmt.Println
```

даёт информацию именно о функции `Println`.

Этот подход полезен, чтобы быстро найти нужную функцию или тип в большом пакете.

Например, командами:

```bash
go doc strings.Contains
```

или:

```bash
go doc os.File
```

тоже можно посмотреть документацию конкретного API.

При просмотре пакетов текущего проекта можно работать с путём пакета или текущим пакетом. В многопакетных проектах с командами Go toolchain широко используется шаблон `./...`.

`go doc` особенно удобна, когда нужно быстро проверить, как работает API, не выходя из терминала.

Документацию стандартной библиотеки и публичных Go-модулей можно читать и на `pkg.go.dev`.

Там обычно показываются:

* документация пакета;
* экспортированные типы, функции, методы, константы и переменные;
* примеры документации;
* ссылки на исходный код;
* версии модуля;
* некоторые сведения о других модулях, импортирующих пакет.

Поэтому комментарий в Go-коде нужен не только тому, кто читает код. Он также часть документации API, показываемой инструментами документации Go.

## Функции-примеры

Одна из полезных возможностей документации Go — исполняемые функции `Example`.

`Example` — не просто текстовый фрагмент кода. Это настоящая Go-функция, которая пишется в файле `_test.go`.

Например:

```go
package greeting_test

import (
	"fmt"

	"example.com/demo/greeting"
)

func ExampleHello() {
	fmt.Println(greeting.Hello("Ali"))
	// Output: Hello, Ali!
}
```

Эта функция показывает, как использовать API `greeting.Hello`.

Самая важная часть:

```go
// Output: Hello, Ali!
```

Если есть комментарий `// Output:`, `go test` запускает пример и сравнивает стандартный вывод с ожидаемым результатом, записанным в комментарии.

Рассмотрим этот процесс по шагам:

1. Запускается `ExampleHello()`.
2. Вызывается `greeting.Hello("Ali")`.
3. Результат выводится в stdout через `fmt.Println`.
4. Go сравнивает полученный вывод с текстом в строке `// Output:`.
5. Если результаты не совпадают, тест завершается неудачей.

Значит, `Example` может одновременно выполнять две задачи:

* показывать пользователю, как использовать API;
* проверять тестом, что пример по-прежнему работает правильно.

Имя функции `Example` определяет, с каким API она связана.

Общий пример для самого пакета:

```go
func Example() {
	// ...
}
```

Для конкретной функции или типа:

```go
func ExampleHello() {
	// ...
}

func ExampleUser() {
	// ...
}
```

Для метода:

```go
func ExampleUser_DisplayName() {
	// ...
}
```

Здесь:

```text
ExampleUser_DisplayName
```

распознаётся как пример, относящийся к методу `User.DisplayName`.

Пример должен быть как можно компактнее и показывать типичное использование API.

Например, в примере документации нужно осторожно обращаться со случайными результатами.

Тест могут сделать нестабильным:

* текущее время;
* случайные значения;
* данные с негарантированным порядком;
* внешний сетевой запрос;
* код, работа которого зависит от внешнего сервиса.

Например, вывод текущего времени:

```go
fmt.Println(time.Now())
```

— плохой выбор для примера, проверяемого через `// Output:`. При каждом запуске результат меняется.

Точно так же рискованно напрямую обходить элементы map и проверять их точный порядок через `Output`. На порядок итерации map полагаться нельзя.

Цель примера документации — не создать сложный тест. Он должен показывать самый понятный и стабильный вариант использования API.

## Примеры

### 1. Комментарий для исполняемого пакета

Этот пример показывает, как пишется комментарий пакета для пакета `main`.

`main` — тоже пакет. Разница в том, что обычно он используется для сборки исполняемой программы.

```go
// Package main предоставляет программу, выводящую приветствие в терминал.
package main

import "fmt"

func main() {
	fmt.Println("Привет, Go!")
}
```

Чтобы запустить проект и посмотреть документацию:

```bash
go mod init example.com/package-comment
go doc .
go run .
```

Первая команда:

```bash
go mod init example.com/package-comment
```

создаёт новый Go-модуль в текущей директории.

Затем:

```bash
go doc .
```

показывает документацию текущего пакета.

Комментарий пакета:

```go
// Package main предоставляет программу, выводящую приветствие в терминал.
```

расположен непосредственно перед объявлением `package main`.

Важно, что комментарий не просто говорит:

```text
Программа выводит "Привет, Go!".
```

Он объясняет общее назначение пакета:

```text
программа, выводящая приветствие в терминал
```

С точки зрения документации это полезнее. Реализация позже может измениться, а общее назначение пакета может остаться прежним.

Последняя команда:

```bash
go run .
```

запускает программу.

Результат:

```text
Привет, Go!
```

Главное правило этого примера: комментарий пакета должен кратко и ясно объяснять, зачем пакет существует.

### 2. Документирование результата функции

В этом примере в комментарии экспортируемой функции описано не только общее назначение функции, но и результат для особого входного значения.

```go
package main

import "fmt"

// Greeting возвращает текст приветствия для заданного имени.
// Если имя пустое, возвращается "Привет, гость!".
func Greeting(name string) string {
	if name == "" {
		return "Привет, гость!"
	}
	return "Привет, " + name + "!"
}

func main() {
	fmt.Println(Greeting("Али"))
}
```

Команды:

```bash
go mod init example.com/function-doc
go doc -cmd . Greeting
go run .
```

Первая строка комментария:

```go
// Greeting возвращает текст приветствия для заданного имени.
```

объясняет общее назначение функции.

Вторая строка документирует важный пограничный случай (edge case):

```go
// Если имя пустое, возвращается "Привет, гость!".
```

Эту информацию нельзя узнать из сигнатуры функции:

```go
func Greeting(name string) string
```

Сигнатура говорит только, что функция принимает `string` и возвращает `string`.

Что происходит при `name == ""`, объясняет документация.

При вызове `Greeting("Али")` условие:

```go
if name == ""
```

равно `false`.

Поэтому выполняется:

```go
return "Привет, " + name + "!"
```

Результат:

```text
Привет, Али!
```

Если вызвать:

```go
Greeting("")
```

результат будет:

```text
Привет, гость!
```

Главное правило этого примера: в документации полезно указывать важное поведение и пограничные случаи, которые не видны из простой сигнатуры.

### 3. Описание ошибочного случая в комментарии

Если функция возвращает `error`, важно указать в документации, в каком случае вызывающему коду ждать ошибку.

```go
package main

import (
	"errors"
	"fmt"
)

// Divide делит a на b.
// Если b равно нулю, Divide возвращает ошибку.
func Divide(a, b float64) (float64, error) {
	if b == 0 {
		return 0, errors.New("делить на ноль нельзя")
	}
	return a / b, nil
}

func main() {
	result, err := Divide(10, 2)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	fmt.Println(result)
}
```

Команды:

```bash
go mod init example.com/error-doc
go doc -cmd . Divide
go run .
```

Сигнатура функции:

```go
func Divide(a, b float64) (float64, error)
```

возвращает два значения:

1. результат вычисления;
2. `error`.

Если `b` равно нулю, выполняется:

```go
if b == 0 {
	return 0, errors.New("делить на ноль нельзя")
}
```

В этом случае первое возвращаемое значение:

```text
0
```

Это нулевое значение типа `float64`.

Но в случае ошибки вызывающий код не должен принимать решения по этому `0`.

Например, такой подход может быть неправильным:

```go
result, _ := Divide(10, 0)
fmt.Println(result)
```

Потому что `0` может быть и настоящим результатом вычисления.

Правильный подход:

```go
result, err := Divide(10, 2)
if err != nil {
	fmt.Println("Ошибка:", err)
	return
}
```

Сначала проверяется `err`. Только если ошибки нет, `result` используется как настоящий результат.

Для `Divide(10, 2)`:

```text
10 / 2 = 5
```

выводится результат:

```text
5
```

Главное правило этого примера: если условия, при которых API возвращает `error`, важны для вызывающего кода, их нужно чётко написать в документации.

### 4. Документирование типа и метода

Экспортируемая `struct`, её поля и методы могут иметь отдельный смысл. Поэтому документация пишется для каждого из них там, где нужно.

```go
package main

import "fmt"

// Account хранит данные счёта пользователя.
type Account struct {
	// Name — отображаемое имя владельца счёта.
	Name string

	// Balance — текущая сумма средств на счёте.
	Balance int
}

// CanPay сообщает, достаточно ли на счёте средств для заданной суммы.
func (a Account) CanPay(amount int) bool {
	return amount >= 0 && a.Balance >= amount
}

func main() {
	account := Account{Name: "Али", Balance: 100}
	fmt.Println(account.CanPay(60))
}
```

Команды:

```bash
go mod init example.com/type-doc
go doc -cmd . Account
go doc -cmd . Account.CanPay
go run .
```

Комментарий `Account`:

```go
// Account хранит данные счёта пользователя.
```

объясняет общее назначение типа.

Комментарии полей объясняют семантику каждого значения:

```go
// Name — отображаемое имя владельца счёта.
Name string
```

и:

```go
// Balance — текущая сумма средств на счёте.
Balance int
```

`CanPay()` проверяет, хватает ли средств на счёте для оплаты определённой суммы:

```go
func (a Account) CanPay(amount int) bool {
	return amount >= 0 && a.Balance >= amount
}
```

Здесь два условия.

Первое:

```go
amount >= 0
```

используется, чтобы не принимать отрицательное значение за настоящую сумму платежа.

Второе:

```go
a.Balance >= amount
```

проверяет, что средств на счёте не меньше запрошенной суммы.

Значения в примере:

```text
Balance = 100
amount = 60
```

Первое условие:

```text
60 >= 0
true
```

Второе условие:

```text
100 >= 60
true
```

Оба условия `true`, поэтому выводится:

```text
true
```

Этот пример показывает, что документация не должна ограничиваться повторением имени типа. Если важен бизнес-смысл поля или метода, его полезно объяснить отдельно.

### 5. Комментарий к группе констант

Константы, относящиеся к одной теме, часто пишутся в группе `const`.

В таком случае общий комментарий может объяснять назначение группы, а отдельные комментарии — разницу между значениями.

```go
package main

import "fmt"

type Status int

// Статусы заказа обозначают этапы обработки.
const (
	StatusUnknown  Status = iota // StatusUnknown означает, что статус ещё не выбран.
	StatusAccepted               // StatusAccepted означает, что заказ принят.
	StatusSent                   // StatusSent означает, что заказ отправлен.
)

func main() {
	fmt.Println(StatusAccepted)
}
```

Команды:

```bash
go mod init example.com/const-doc
go doc -cmd . Status
go run .
```

Здесь использован `iota`:

```go
StatusUnknown Status = iota
```

`iota` в этой группе `const` начинается с `0`.

Значения по шагам:

```text
StatusUnknown  = 0
StatusAccepted = 1
StatusSent     = 2
```

То, что `StatusUnknown` равно `0`, — полезный выбор.

Причина в том, что `Status` на самом деле именованный тип `int`:

```go
type Status int
```

Если новой переменной `Status` не присвоить значение, её нулевое значение будет `0`:

```go
var status Status
```

В этом случае:

```text
status == StatusUnknown
```

Значит, `Status`, значение которого ещё не выбрано, случайно не будет означать реальное бизнес-состояние вроде `StatusAccepted` или `StatusSent`.

Общий комментарий:

```go
// Статусы заказа обозначают этапы обработки.
```

говорит, зачем константы собраны в одну группу.

Комментарии в конце строк показывают отдельный смысл каждого значения.

Главное правило этого примера: если имени константы недостаточно, её семантический смысл нужно показать в документации.

### 6. Комментарий к экспортируемой переменной

Экспортируемая переменная уровня пакета тоже должна иметь документацию.

```go
package main

import "fmt"

// DefaultLimit — стандартное количество элементов, возвращаемых за один запрос.
var DefaultLimit = 20

func main() {
	fmt.Println("Лимит:", DefaultLimit)
}
```

Команды:

```bash
go mod init example.com/variable-doc
go doc -cmd . DefaultLimit
go run .
```

Из имени `DefaultLimit` можно понять, что это какой-то стандартный лимит.

Но какой именно?

Комментарий отвечает на этот вопрос:

```go
// DefaultLimit — стандартное количество элементов, возвращаемых за один запрос.
```

Значит, это может быть, например, лимит, связанный с пагинацией или количеством элементов в ответе API.

Поскольку значение:

```go
var DefaultLimit = 20
```

программа выводит:

```text
Лимит: 20
```

В этом примере `20` выбрано как примерное стандартное значение.

Важно, что хорошая документация не говорит просто:

```text
DefaultLimit равен 20.
```

Это видно из самого кода.

Документация объясняет, **что означает значение**.

### 7. Ссылка на другое имя в документации

В документирующих комментариях Go можно ссылаться на другой идентификатор.

Например:

```go
package main

import "fmt"

// Config хранит настройки программы.
type Config struct {
	Port int
}

// DefaultConfig возвращает безопасные начальные значения для нового [Config].
func DefaultConfig() Config {
	return Config{Port: 8080}
}

func main() {
	fmt.Println(DefaultConfig().Port)
}
```

Команды:

```bash
go mod init example.com/doc-link
go doc -cmd . DefaultConfig
go run .
```

Важная часть:

```go
[Config]
```

Система документации Go может связать такую ссылку на идентификатор с соответствующим именем API.

В результате в представлениях, поддерживающих документацию, читатель может перейти к документации `Config`.

Это особенно полезно, когда один API напрямую связан с другим типом или функцией.

Например, предложение:

```go
// DefaultConfig возвращает безопасные начальные значения для нового [Config].
```

ясно показывает, с каким типом связана `DefaultConfig()`.

Функция возвращает:

```go
return Config{Port: 8080}
```

Поэтому результат:

```go
DefaultConfig().Port
```

равен:

```text
8080
```

Здесь `8080` — лишь стандартный порт в примере. В реальной программе стандартное значение может отличаться в зависимости от требований проекта, протокола или политики конфигурации.

Главное правило этого примера: связывание других имён API внутри документации помогает читателю быстро перемещаться между связанными понятиями.

### 8. Разбиение комментария на заголовки и списки

Если документация пакета объясняет несколько независимых идей, не обязательно писать её одним длинным абзацем.

Документирующие комментарии Go поддерживают и такие структуры, как заголовки и списки.

```go
// Package main выводит статус заказа в терминал.
//
// # Статусы
//
// Программа использует следующие значения:
//
//   - new — новый заказ;
//   - sent — отправленный заказ.
package main

import "fmt"

func main() {
	fmt.Println("new")
}
```

Команды:

```bash
go mod init example.com/structured-doc
go doc .
go run .
```

Разберём комментарий по частям.

Первая часть:

```go
// Package main выводит статус заказа в терминал.
```

говорит об общем назначении пакета.

Затем идёт пустая строка комментария:

```go
//
```

Она помогает разделять абзацы.

Заголовок:

```go
// # Статусы
```

создаёт небольшой раздел с названием `Статусы`.

Следующая часть:

```go
// Программа использует следующие значения:
```

— вводный текст к списку.

Список:

```go
//   - new — новый заказ;
//   - sent — отправленный заказ.
```

объясняет смысл двух значений.

Использовать такую структуру в каждом маленьком комментарии не нужно.

Например, создавать заголовок для такого простого комментария излишне:

```go
// User представляет пользователя системы.
```

Но если документация пакета объясняет несколько отдельных тем, заголовки, абзацы и списки сильно упрощают чтение.

При запуске программы выводится:

```text
new
```

Главное правило этого примера: длинную документацию можно разбить на логические части, не превращая её в сплошную стену текста.

### 9. Пометка устаревшего API

Иногда старый API нельзя удалить сразу.

Причина в том, что другие пакеты или программы могут всё ещё его использовать.

В такой ситуации старый API сохраняется, но в документации указывается, какой новый API использовать вместо него.

```go
package main

import "fmt"

// NewGreeting возвращает приветствие для заданного имени.
func NewGreeting(name string) string {
	return "Привет, " + name
}

// OldGreeting возвращает приветствие для заданного имени.
//
// Deprecated: используйте функцию NewGreeting.
func OldGreeting(name string) string {
	return NewGreeting(name)
}

func main() {
	fmt.Println(OldGreeting("Али"))
}
```

Команды:

```bash
go mod init example.com/deprecated-doc
go doc -cmd . OldGreeting
go run .
```

Важная часть:

```go
// Deprecated: используйте функцию NewGreeting.
```

`Deprecated:` — особая форма документации, которая используется, чтобы пометить устаревший API.

Здесь `OldGreeting()` всё ещё работает:

```go
func OldGreeting(name string) string {
	return NewGreeting(name)
}
```

Значит, старый код:

```go
OldGreeting("Али")
```

не сломается сразу.

Но разработчику, пишущему новый код, документация указывает путь:

```text
используйте функцию NewGreeting.
```

Это помогает проводить миграцию постепенно.

Важно и то, что внутри старой функции вызывается новая:

```go
return NewGreeting(name)
```

Так логика приветствия не дублируется в двух местах.

Результат:

```text
Привет, Али
```

Главное правило этого примера: если устаревший API нужно сохранить, пользователя нужно чётко направить к новому API.

### 10. Просмотр исходника вместе с документацией

Иногда одной документации недостаточно. Может понадобиться быстро увидеть, как реализован API.

В таком случае полезна `go doc -src`.

```go
package main

import "fmt"

// NormalizeCount заменяет отрицательное значение нулём.
func NormalizeCount(count int) int {
	if count < 0 {
		return 0
	}
	return count
}

func main() {
	fmt.Println(NormalizeCount(-3))
}
```

Команды:

```bash
go mod init example.com/source-doc
go doc -src -cmd . NormalizeCount
go run .
```

Обычная `go doc` помогает посмотреть документацию API.

Флаг `-src` показывает и исходный код:

```bash
go doc -src -cmd . NormalizeCount
```

Это удобно, когда нужно быстро проверить, как объявлен API и как он реализован.

Посмотрим по шагам, как работает функция:

```go
func NormalizeCount(count int) int {
	if count < 0 {
		return 0
	}
	return count
}
```

Если вызвать:

```go
NormalizeCount(-3)
```

условие:

```text
-3 < 0
```

то есть:

```text
true
```

Поэтому выполняется:

```go
return 0
```

Результат:

```text
0
```

Если вызвать:

```go
NormalizeCount(5)
```

получаем:

```text
5 < 0
false
```

и возвращается исходное значение:

```text
5
```

Здесь есть тонкость.

Условие записано в виде:

```go
count < 0
```

Значит, заменяются только отрицательные значения.

Для `0`:

```text
0 < 0
false
```

Поэтому `0` тоже возвращается без изменений. Это правильно, потому что ноль может обозначать реальное количество.

Главное правило этого примера: `go doc -src` полезна в ситуациях, когда нужно проверить реализацию вместе с документацией.
