# Модули и пакеты в Go

В Go-проекте **пакет** (package) и **модуль** (module) — связанные понятия, но они выполняют разные задачи.

Пакет делит код на логические части. Например, код, связанный с вычислениями, можно поместить в пакет `calc`, а код, связанный с HTTP, — в другой пакет.

Модуль управляет одним или несколькими пакетами как единым версионируемым целым. Модуль используется для управления зависимостями и для определения полного пути импорта пакетов.

Понимать эту разницу важно, потому что в Go-проекте именно понятия пакета и модуля отвечают на такие вопросы:

* к какой части относится код;
* как импортировать функцию из другого пакета;
* какая версия зависимости используется;
* какой код виден из внешних пакетов;
* к какому модулю относится проект.

## Что такое пакет?

**Пакет** — это набор Go-файлов, которые обычно находятся в одной директории и имеют одинаковое имя `package`.

Например:

```text
calc/
├── add.go
├── subtract.go
└── square.go
```

Если все три файла начинаются со строки:

```go
package calc
```

они относятся к одному пакету `calc`.

Пакет выполняет несколько задач:

* делит код на логические части;
* создаёт пространство имён (namespace) для идентификаторов;
* определяет, какие имена видны из других пакетов;
* работает как единица компиляции;
* позволяет повторно использовать код в других пакетах.

Основные правила:

* каждый `.go`-файл начинается со строки `package <имя>`;
* обычные `.go`-файлы в одной директории, как правило, относятся к одному пакету;
* имя импортированного пакета не должно конфликтовать с именами других пакетов в коде;
* `package main` и `func main()` вместе образуют точку входа исполняемой программы.

Здесь есть тонкость.

Тестовые файлы могут немного отличаться от обычных `.go`-файлов. Например, тесты пакета `calc` можно написать одним из двух способов:

```go
package calc
```

или:

```go
package calc_test
```

Первый вариант запускает тест внутри самого пакета. Поэтому тест видит и неэкспортируемые имена внутри пакета.

Второй вариант работает как внешний пакет. Здесь тест использует пакет `calc` только через его экспортируемый API.

## Пакет `main`

В Go для сборки исполняемой программы имя пакета должно быть `main`.

Следующая полная программа создаёт исполняемый пакет:

```go
package main

import "fmt"

func main() {
	fmt.Println("Работаем с пакетом Go!")
}
```

Её можно запустить так:

```bash
go run main.go
```

Результат:

```text
Работаем с пакетом Go!
```

Здесь работают два отдельных правила.

Первое:

```go
package main
```

сообщает Go, что этот пакет может быть исполняемой программой.

Второе:

```go
func main()
```

обозначает функцию, с которой начинается программа.

То есть одного лишь написания функции с именем `main()` недостаточно. Она должна находиться в пакете `main`.

Например:

```go
package new_name

func main() {
}
```

В этом коде есть `main()`. Но пакет не `main`. Поэтому он не принимается как точка входа исполняемой программы.

При попытке запустить его как команду может возникнуть такая ошибка:

```text
package command-line-arguments is not a main package
```

То есть особое значение функции `main()` проявляется только внутри `package main`.

Если `main()` написана в другом пакете, это не особая точка входа. Это просто обычная функция с именем `main`.

> **Информация**
>
> Библиотечному пакету `main()` не нужна. Задача библиотечного пакета — предоставлять функции, типы, константы и переменные, которые могут импортировать другие пакеты.

## Что такое модуль?

**Модуль** — это набор пакетов, определяемый файлом `go.mod`.

Проще говоря, пакет делит код на внутренние части. Модуль определяет, к какому проекту и к какой версионируемой единице эти пакеты относятся.

Создадим новый проект:

```bash
mkdir my-project
cd my-project
go mod init example.com/my-project
```

`go mod init` создаёт файл `go.mod` в текущей директории.

Результат будет примерно таким:

```text
module example.com/my-project

go 1.xx
```

Здесь:

```text
module example.com/my-project
```

задаёт **канонический путь** модуля.

Позже, при импорте пакетов внутри модуля, этот путь становится началом импорта.

Например, если в модуле есть директория `calc`:

```text
my-project/
├── go.mod
└── calc/
    └── calc.go
```

её путь импорта обычно:

```text
example.com/my-project/calc
```

Строка в `go.mod`:

```text
go 1.xx
```

выражает требование модуля к версии Go.

Эта строка не устанавливает Go на компьютер. Она важна для того, по каким правилам должны работать семантика модуля, возможности языка и toolchain.

Точное значение версии зависит от Go toolchain в среде, где был выполнен `go mod init`.

## Создание локального пакета

Теперь создадим внутри модуля отдельный локальный пакет.

Структура проекта:

```text
my-project/
├── go.mod
├── main.go
└── calc/
    └── calc.go
```

Файл `calc/calc.go`:

```go
package calc

func Add(a, b int) int {
	return a + b
}

func Square(n int) int {
	return n * n
}

func subtract(a, b int) int {
	return a - b
}
```

Поскольку файл начинается с:

```go
package calc
```

он относится к пакету `calc`.

В пакете три функции:

```go
Add
Square
subtract
```

Затем пишем `main.go`:

```go
package main

import (
	"fmt"

	"example.com/my-project/calc"
)

func main() {
	fmt.Println(calc.Square(3))
	fmt.Println(calc.Add(3, 2))
}
```

Запускаем программу в корне проекта:

```bash
go run .
```

Результат:

```text
9
5
```

Теперь посмотрим пошагово, как сформировался путь импорта.

Путь модуля в `go.mod`:

```text
example.com/my-project
```

А пакет находится в директории:

```text
calc/
```

Поэтому полный путь импорта:

```text
example.com/my-project
+
/calc
=
example.com/my-project/calc
```

При импорте Go не указывает на сам `.go`-файл.

Например, так не пишут:

```go
import "example.com/my-project/calc/calc.go"
```

Вместо этого импортируется директория, в которой находится пакет:

```go
import "example.com/my-project/calc"
```

`.` в команде `go run .` означает текущую директорию. Go собирает и запускает пакет `main` в текущей директории.

Обратите внимание и на функцию `Square()`:

```go
func Square(n int) int {
	return n * n
}
```

Здесь нет необходимости использовать `math.Pow`.

Например, если бы мы написали через `math.Pow`, обычно пришлось бы работать с `float64`:

```go
math.Pow(float64(n), 2)
```

Но мы вычисляем квадрат значения типа `int`. Поэтому:

```go
n * n
```

проще и точнее.

Кроме того, не нужно лишнее преобразование `int -> float64 -> int`.

> **Внимание**
>
> При очень больших значениях `int` выражение `n * n` может вызвать переполнение целого числа (integer overflow). В этом примере используется небольшое значение, поэтому такой проблемы нет.

## Экспортируемые имена

В Go идентификаторы, видимые за пределами пакета, называются **экспортируемыми именами** (exported names).

Главное правило очень простое:

> Если идентификатор начинается с заглавной буквы, он экспортируется.

В предыдущем примере:

```go
func Add(a, b int) int
```

и:

```go
func Square(n int) int
```

начинаются с заглавной буквы.

Поэтому другой пакет может их использовать:

```go
calc.Add(3, 2)
calc.Square(3)
```

А:

```go
func subtract(a, b int) int
```

начинается со строчной буквы.

Поэтому `subtract` виден только внутри самого пакета `calc`.

Например, следующий код в другом пакете не компилируется:

```go
// Этот код в другом пакете не компилируется:
// fmt.Println(calc.subtract(5, 2))
```

Ошибка компилятора сообщает, что `calc.subtract` не экспортирован.

Это правило относится не только к функциям. Оно действует и для:

* типов;
* полей структур;
* методов;
* переменных;
* констант;
* функций.

Например:

```go
type User struct {
	Name string
	age  int
}
```

Здесь `User` и `Name` экспортируются. `age` виден только внутри пакета.

Но написать имя с заглавной буквы — недостаточно для хорошего API.

Например:

```go
func X(a int) int
```

может быть экспортируемой функцией. Но по имени `X` непонятно, что она делает.

Поэтому для экспортируемого API важны также:

* понятное имя;
* точное назначение;
* необходимая документация;
* стабильное поведение.

Для имён пакетов есть похожее правило.

Обычно лучше выбирать имя пакета:

* короткое;
* строчными буквами;
* понятное;
* в единственном числе.

Например:

```text
http
json
user
config
```

Очень общие имена вроде `utils`, `common`, `helpers` нужно использовать осторожно.

Причина в том, что со временем такие пакеты могут превратиться в место, где скапливаются не связанные между собой функции. В результате пакет теряет чёткую ответственность.

## Как находится импорт?

Чтобы понять пути импорта в Go, полезно разделить три основных шага.

### 1. Определяется путь текущего модуля

Сначала Go смотрит на файл `go.mod`.

Например, если там написано:

```text
module example.com/my-project
```

базовый путь текущего модуля:

```text
example.com/my-project
```

### 2. Определяется директория внутри модуля

Например, для следующего пакета:

```text
my-project/
└── calc/
```

оставшаяся часть:

```text
/calc
```

Так формируется импорт:

```go
import "example.com/my-project/calc"
```

### 3. Для внешнего модуля выбирается версия

Если импорт не относится к текущему модулю, Go проверяет модули-зависимости.

Например, для:

```go
import "example.com/other-module/client"
```

`example.com/other-module` может быть внешним модулем.

В этом случае Go через граф модулей определяет, какая версия входит в сборку.

### Путь импорта и имя пакета

В большинстве случаев имя директории и имя пакета совпадают.

Например, внутри:

```text
calc/
```

пишут:

```go
package calc
```

Но это не строгое обязательное правило.

Например, даже если директория называется:

```text
calc/
```

внутри файла можно объявить другое имя пакета:

```go
package calculator
```

Путь импорта всё равно остаётся по директории:

```go
import "example.com/my-project/calc"
```

А в коде используется объявленное имя пакета:

```go
calculator.Add(...)
```

На практике код легче понимать, если имя директории и имя пакета совпадают или явно связаны по смыслу.

### Псевдоним импорта

Иногда у двух пакетов может быть одинаковое имя.

Или в коде нужно обращаться к пакету под другим, более понятным именем.

В таких случаях импорту можно дать локальный псевдоним (alias):

```go
import mathops "example.com/my-project/calc"
```

Теперь пакет используется в виде:

```go
mathops.Add(...)
```

Важный момент: псевдоним не меняет путь импорта.

Пакет по-прежнему импортируется по пути:

```text
example.com/my-project/calc
```

Только в текущем файле к нему обращаются по имени `mathops`.

Давать псевдоним каждому импорту не нужно. Лучше использовать его в основном:

* когда имена конфликтуют;
* когда обычное имя пакета в данном контексте сбивает с толку.

## Директивы `go.mod`

Основной файл модульной системы Go — `go.mod`.

В нём могут встречаться несколько директив.

### `module`

Задаёт путь текущего модуля:

```text
module example.com/my-project
```

Это значение становится началом пути импорта локальных пакетов внутри модуля.

### `go`

Задаёт требование модуля к версии Go:

```text
go 1.xx
```

Эта директива не устанавливает Go на компьютер. Она влияет на семантику языка и toolchain, используемую для модуля.

### `require`

Указывает внешнюю зависимость и её требуемую версию.

Например:

```text
require example.com/lib v1.2.3
```

Это означает, что текущий модуль зависит от модуля `example.com/lib`.

### `replace`

Заменяет источник зависимости на другой путь или версию.

Это особенно удобно при локальной разработке.

Например:

```text
replace example.com/shared => ../shared
```

Здесь вместо получения модуля `example.com/shared` из интернета Go использует локальную директорию:

```text
../shared
```

Представим такую ситуацию:

```text
projects/
├── app/
│   └── go.mod
└── shared/
    └── go.mod
```

При работе над `app` может понадобиться проверить ещё не опубликованную локальную версию модуля `shared`.

Тогда:

```text
replace example.com/shared => ../shared
```

— удобное решение.

> **Внимание**
>
> `replace`, указывающий на локальную директорию, может не работать на другом компьютере. Например, у другого разработчика может не быть директории `../shared`. Поэтому перед коммитом такого `replace` убедитесь, что команда и CI-среда смогут найти этот путь.

### `exclude`

Используется, чтобы исключить определённую версию модуля из выбора.

Например, если в определённой версии зависимости есть серьёзная проблема, её можно убрать из списка сборки с помощью `exclude`.

`go.sum`, выбор версий зависимостей, граф модулей и связанные с ними команды подробно объясняются
в уроке о внешних библиотеках и управлении зависимостями. В этом уроке мы сосредоточимся на локальных пакетах и
структуре модуля.

## Пакеты `internal`

Некоторые пакеты должны использоваться только внутри проекта.

Например, загрузка конфигурации или реализация внутреннего сервиса может быть кодом, который внешние пользователи не должны импортировать.

Для таких случаев в Go есть директория `internal`.

Например:

```text
my-project/
├── go.mod
├── internal/
│   └── config/
└── main.go
```

Здесь:

```text
internal/config
```

— не обычное имя директории. `internal` имеет особое значение для Go toolchain.

Go разрешает импортировать пакет внутри `internal` только коду в разрешённом дереве родительской директории.

Например, пакет выше:

```text
my-project/internal/config
```

обычно доступен коду внутри дерева этого проекта.

Но если внешний модуль попытается использовать его напрямую, Go отклонит импорт.

Это полезно в больших проектах.

Например, у вас может быть:

```text
public API
```

и:

```text
internal implementation
```

Если оставить внутреннюю реализацию обычным экспортируемым пакетом, другие проекты могут случайно начать от неё зависеть.

Потом изменить реализацию становится трудно.

`internal` же защищает эту границу не только документацией, но и на уровне Go toolchain.

## Частые ошибки

### Использование относительных импортов

В режиме модулей Go импортировать локальный пакет так — неправильный подход:

```go
import "./calc"
```

Вместо этого используйте путь модуля:

```go
import "example.com/my-project/calc"
```

Преимущество этого подхода в том, что импорт привязан не к случайному расположению директории на диске, а к каноническому пути модуля.

Например, даже если проект перенести в другую директорию:

```text
/home/user/projects/my-project
```

или:

```text
/work/src/my-project
```

путь импорта не меняется:

```go
import "example.com/my-project/calc"
```

### Создание цикла импорта

Go не разрешает циклические импорты.

Например, если возникает зависимость вида:

```text
a -> b
b -> a
```

сборка завершается ошибкой.

Представим:

```go
// package a
import "example.com/project/b"
```

и:

```go
// package b
import "example.com/project/a"
```

Здесь для сборки пакета `a` нужен `b`.

Но для сборки `b` снова нужен `a`.

В результате зависимость образует цикл.

В такой ситуации обычно нужно пересмотреть архитектуру.

Например, общие типы или функции можно вынести в третий небольшой пакет, в виде:

```text
a -> shared
b -> shared
```

Другое решение — перепроектировать направление зависимостей.

Например, вместо того чтобы пакет `a` зависел от `b`, а пакет `b` одновременно от `a`, два пакета может объединить код более высокого уровня.

### Запуск одного файла

Представим, что пакет `main` состоит из двух файлов:

```text
app/
├── main.go
└── helper.go
```

`main.go` может использовать функцию, объявленную в `helper.go`.

Если запустить:

```bash
go run main.go
```

Go работает именно по указанному файлу. Поэтому нужный код в другом файле может остаться за пределами сборки.

В такой ситуации обычно правильнее:

```bash
go run .
```

Эта команда собирает весь пакет в текущей директории.

### Отдельный модуль для каждой директории

Не каждому Go-пакету нужен свой `go.mod`.

Например, в структуре:

```text
shop/
├── go.mod
├── cmd/
├── user/
├── order/
└── payment/
```

не нужно создавать отдельные файлы `go.mod` для пакетов `user`, `order` и `payment`.

Все они могут быть пакетами одного модуля:

```text
shop
```

Отдельный модуль полезен только тогда, когда нужна реальная граница модуля.

Например:

* компонент должен версионироваться независимо;
* он выпускается отдельно;
* другие проекты используют его как независимую зависимость;
* его жизненный цикл зависимостей нужно отделить от основного репозитория.

В остальных случаях модуль для каждой директории без необходимости усложняет управление зависимостями.

## На что обращают внимание на собеседовании?

По теме пакетов и модулей на собеседовании полезно уметь чётко объяснить следующие различия.

* **Пакет** — единица организации кода, компиляции и пространства имён.
* **Модуль** — граница версионирования и управления зависимостями набора пакетов.
* Экспортируемые имена начинаются с заглавной буквы. Это правило действует на границе пакета.
* `go.mod` хранит путь модуля и требования к версиям зависимостей.
* `go.sum` хранит контрольные суммы (checksum) содержимого зависимостей.
* Go не разрешает циклы импорта.
* Мажорные версии `v2` и выше обычно используют суффикс вида `/v2`, `/v3` в пути модуля и импорта.
* Не нужно создавать отдельный модуль для каждого пакета.
* Директория `internal` используется, чтобы ограничить внутреннюю реализацию на уровне импорта.

В следующем уроке мы рассмотрим добавление внешней библиотеки в модуль, а затем — написание Go-документации для экспортируемого API.

## Примеры

Следующие примеры по отдельности показывают разные стороны работы с пакетами и модулями.

Каждый пример удобно рассматривать как независимый небольшой проект. Если пробуете их на практике, создавайте для каждого отдельную директорию. Иначе повторный запуск `go mod init` в одной директории может привести к ситуации вроде `go.mod already exists`.

### 1. Создание самого маленького модуля

В этом примере для одного исполняемого пакета начинается новый модуль.

`main.go`:

```go
package main

import "fmt"

func main() {
	fmt.Println("Первый модуль работает")
}
```

Создание и запуск проекта:

```bash
mkdir first-module
cd first-module
go mod init example.com/first-module
go run .
```

Разберём команды по шагам.

```bash
mkdir first-module
```

создаёт новую директорию.

```bash
cd first-module
```

переходит в эту директорию.

Затем:

```bash
go mod init example.com/first-module
```

создаёт `go.mod` в текущей директории.

В нём появляется примерно строка:

```text
module example.com/first-module
```

Здесь:

```text
example.com/first-module
```

— путь модуля.

Строка в коде:

```go
package main
```

говорит, что это исполняемый пакет.

Наконец:

```bash
go run .
```

собирает и запускает пакет `main` в текущей директории.

Результат:

```text
Первый модуль работает
```

Главное правило в этом примере:

> Модуль определяется через `go.mod`, а исполняемый пакет — через `package main` и `func main()`.

### 2. Использование имён уровня пакета

В этом примере переменная и функция объявлены в пространстве имён уровня пакета `main`.

```go
package main

import "fmt"

var greeting = "Hello"

func message(name string) string {
	return greeting + ", " + name
}

func main() {
	fmt.Println(message("Go"))
}
```

Запуск:

```bash
go mod init example.com/package-scope
go run .
```

В этом коде:

```go
var greeting = "Hello"
```

объявлена вне функций.

Поэтому `greeting` — переменная уровня пакета.

Так же:

```go
func message(name string) string
```

тоже функция, объявленная на уровне пакета.

Когда внутри `main()` вызывается:

```go
message("Go")
```

`message()` доходит до строки:

```go
return greeting + ", " + name
```

Здесь:

```text
greeting = "Hello"
name = "Go"
```

Поэтому результат:

```text
Hello, Go
```

`greeting` и `message` начинаются со строчной буквы.

То есть они видны внутри этого пакета, но не экспортируются в другие пакеты.

Важный момент: путь модуля:

```text
example.com/package-scope
```

не меняет пространство имён внутри пакета.

Модуль определяет границу зависимостей и импорта. Пакет влияет на границу видимости идентификаторов в коде.

### 3. Разделение экспортируемых и внутренних имён

В этом примере внутри одного пакета используются функции, начинающиеся с заглавной и строчной буквы.

```go
package main

import "fmt"

func PublicMessage() string {
	return "экспортируемое имя"
}

func privateMessage() string {
	return "имя только для пакета"
}

func main() {
	fmt.Println(PublicMessage())
	fmt.Println(privateMessage())
}
```

Запуск:

```bash
go mod init example.com/export-demo
go run .
```

В коде:

```go
func PublicMessage() string
```

начинается с заглавной буквы.

Поэтому `PublicMessage` — экспортируемое имя.

А:

```go
func privateMessage() string
```

начинается со строчной буквы.

Поэтому не экспортируется.

На первый взгляд может возникнуть вопрос: почему `main()` может вызвать обе функции?

Причина в том, что все три функции находятся в одном:

```go
package main
```

Внутри самого пакета правило экспорта не ограничивает внутреннее использование.

Экспорт влияет только на видимость снаружи пакета.

То есть:

```go
PublicMessage()
privateMessage()
```

обе работают внутри этого пакета.

Но если другой пакет импортирует этот пакет, он сможет использовать только:

```go
PublicMessage()
```

Результат:

```text
экспортируемое имя
имя только для пакета
```

Главное правило в этом примере:

> Заглавная буква обозначает экспорт за пределы пакета. Она не ограничивает использование внутри пакета.

### 4. Порядок `init()` и `main()`

В этом примере `init()` выполняется при подготовке пакета, а `main()` — после неё.

```go
package main

import "fmt"

var status = "не начато"

func init() {
	status = "готово"
	fmt.Println("init:", status)
}

func main() {
	fmt.Println("main:", status)
}
```

Запуск:

```bash
go mod init example.com/init-demo
go run .
```

Разберём процесс по шагам.

Сначала переменная уровня пакета получает начальное значение:

```go
var status = "не начато"
```

То есть сначала:

```text
status = "не начато"
```

Затем выполняется `init()`:

```go
func init() {
	status = "готово"
	fmt.Println("init:", status)
}
```

Здесь `status` меняется на значение:

```text
"готово"
```

После этого выводится:

```text
init: готово
```

Затем запускается `main()`:

```go
func main() {
	fmt.Println("main:", status)
}
```

`status` уже изменён функцией `init()`.

Поэтому результат:

```text
init: готово
main: готово
```

Обычно `init()` не вызывают из кода напрямую. Go сам запускает её как часть процесса инициализации пакета.

Главное правило в этом примере:

> В пакете `main` функция `main()` начинается только после завершения инициализации пакета.

### 5. Локальное имя для импорта

В этом примере пакет `fmt` импортируется с локальным именем `format`.

```go
package main

import format "fmt"

func main() {
	format.Println("Вызов через псевдоним пакета")
}
```

Запуск:

```bash
go mod init example.com/import-alias
go run .
```

Обычно, если написать:

```go
import "fmt"
```

в коде используется:

```go
fmt.Println(...)
```

В этом же примере написано:

```go
import format "fmt"
```

В этом синтаксисе:

```text
format
```

— локальный псевдоним.

```text
"fmt"
```

— реальный путь импорта.

Поэтому в коде используется:

```go
format.Println(...)
```

Важный момент: импортируемый пакет не изменился.

Это по-прежнему пакет стандартной библиотеки:

```text
fmt
```

Просто в этом файле ему дано имя:

```text
format
```

Псевдоним обычно полезен:

* когда конфликтуют пакеты с одинаковым именем;
* когда в текущем контексте другое имя понятнее.

Но в обычном случае, если оставить `fmt` как `fmt`, код читать легче.

Результат:

```text
Вызов через псевдоним пакета
```

### 6. Групповой импорт нескольких пакетов

В этом примере импортируются два стандартных пакета.

```go
package main

import (
	"errors"
	"fmt"
)

func main() {
	err := errors.New("пример ошибки")
	fmt.Println(err)
}
```

Запуск:

```bash
go mod init example.com/grouped-imports
go run .
```

Когда импортов несколько, группировать их в круглых скобках — обычный для Go способ:

```go
import (
	"errors"
	"fmt"
)
```

Пакет `errors` создаёт новое значение `error` через:

```go
errors.New("пример ошибки")
```

Это значение присваивается переменной `err` в строке:

```go
err := errors.New("пример ошибки")
```

Затем:

```go
fmt.Println(err)
```

выводит ошибку.

Результат:

```text
пример ошибки
```

`gofmt` помогает оформлять импорты стандартным образом.

Например, группы между локальными пакетами проекта и пакетами стандартной библиотеки можно поддерживать в порядке с помощью инструментов вроде `gofmt` или `goimports`.

Главное правило в этом примере:

> Группировка нескольких пакетов внутри блока `import (...)` — стандартный и читаемый способ в Go-коде.

### 7. Просмотр пути текущего модуля

В этом примере создаётся модуль, и его канонический путь проверяется командой Go.

```go
package main

import "fmt"

func main() {
	fmt.Println("Путь модуля хранится в go.mod")
}
```

Команды:

```bash
go mod init example.com/module-path
go list -m
go run .
```

Сначала:

```bash
go mod init example.com/module-path
```

создаёт `go.mod`.

В нём есть строка:

```text
module example.com/module-path
```

Затем:

```bash
go list -m
```

выводит путь текущего главного модуля.

Результат:

```text
example.com/module-path
```

Это значение не просто для информации.

Если позже создать внутри модуля новый пакет:

```text
client/
```

его путь импорта может быть:

```text
example.com/module-path/client
```

То есть путь модуля, видимый через `go list -m`, используется как начало импорта локальных пакетов.

Затем:

```bash
go run .
```

запускает программу.

Результат:

```text
Путь модуля хранится в go.mod
```

### 8. Получение информации о текущем пакете

В этом примере `go list` показывает имя пакета и путь импорта в текущей директории.

```go
package main

import "fmt"

func main() {
	fmt.Println("Текущий пакет: main")
}
```

Команды:

```bash
go mod init example.com/package-info
go list -f "{{.Name}} {{.ImportPath}}" .
go run .
```

Главная команда здесь:

```bash
go list -f "{{.Name}} {{.ImportPath}}" .
```

`go list` может выдавать различные метаданные о пакете.

Флаг `-f` задаёт формат вывода через шаблон (template).

В шаблоне:

```text
.Name
```

означает имя пакета.

Поскольку в нашем коде:

```go
package main
```

получаем:

```text
.Name = main
```

В шаблоне:

```text
.ImportPath
```

означает путь импорта пакета.

Поскольку модуль:

```text
example.com/package-info
```

а пакет находится в корне модуля, путь импорта:

```text
example.com/package-info
```

Вывод получается таким:

```text
main example.com/package-info
```

Затем:

```bash
go run .
```

запускает программу.

Результат:

```text
Текущий пакет: main
```

Главное правило в этом примере:

> Имя пакета и путь импорта — не одно и то же. `.Name` берётся из объявления пакета, а `.ImportPath` — из модуля и расположения директории.

### 9. Приведение файла модуля в порядок

В этом примере `go mod tidy` согласует файлы модуля с импортами кода.

```go
package main

import "fmt"

func main() {
	values := []int{2, 4, 6}
	fmt.Println("Значения:", values)
}
```

Команды:

```bash
go mod init example.com/tidy-demo
go mod tidy
go run .
```

В коде используется только:

```go
import "fmt"
```

`fmt` — часть стандартной библиотеки Go.

Пакеты стандартной библиотеки не требуют записи `require` в `go.mod` как внешней зависимости модуля.

Поэтому после запуска:

```bash
go mod tidy
```

внешняя зависимость не появляется.

Это не ошибка.

Наоборот, пустой список зависимостей — именно правильное состояние для этой программы.

Задача `go mod tidy` — не просто добавлять зависимости.

Она приводит файлы модуля в нужное состояние на основе импортов в коде.

Например, если в будущем начнёт использоваться внешний пакет, `tidy` может скорректировать нужные записи зависимостей.

Если зависимость больше не используется, она может удалить и лишние записи.

Результат программы:

```text
Значения: [2 4 6]
```

Главное правило в этом примере:

> `go mod tidy` используется не для создания зависимостей, а для согласования импортов кода и метаданных модуля.

### 10. Сборка исполняемого файла из модуля

В этом примере `go build` создаёт исполняемый файл из текущего пакета `main`.

```go
package main

import "fmt"

func main() {
	fmt.Println("Собранная программа")
}
```

Команды:

```bash
go mod init example.com/build-demo
go build -o build-demo .
```

Здесь:

```bash
go build
```

компилирует код.

В отличие от `go run`, главная цель — не запустить программу сразу. `go build` создаёт результат сборки.

Флаг:

```bash
-o build-demo
```

явно задаёт имя выходного файла.

То есть в Unix-подобных системах в директории появляется исполняемый файл примерно с именем:

```text
build-demo
```

В Windows поведение, связанное с именованием и расширением исполняемого файла, адаптируется к платформе.

Часть в конце команды:

```bash
.
```

означает пакет в текущей директории.

Поскольку в этой директории есть:

```go
package main
```

и:

```go
func main()
```

собирается исполняемая программа.

Если текущая директория — обычный библиотечный пакет, он не собирается как исполняемый `main`.

Например, если пакет:

```go
package calc
```

служит библиотекой, `go build` может скомпилировать его для проверки, но цель не в том, чтобы создать из него исполняемый файл, как из программы `main`.

При запуске собранной программы результат:

```text
Собранная программа
```

Главное правило в этом примере:

> `go run` временно собирает и запускает, а `go build` используется для компиляции пакета и может создать исполняемый файл из пакета `main`.
