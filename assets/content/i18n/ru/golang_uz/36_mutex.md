# Mutex

Mutex (мьютекс) — средство синхронизации, которое управляет доступом к общим данным, когда с ними работают несколько горутин.

В Go мьютекс используется через тип `sync.Mutex`.

Проще говоря, мьютекс создаёт замок вокруг данных. Когда одна горутина берёт замок, остальные горутины ждут, пока он не будет освобождён.

Например, если две горутины хотят одновременно изменить одно и то же значение `counter`, с помощью мьютекса их операции записи можно выполнить по очереди.

Если несколько горутин только читают одни и те же данные, проблемы обычно нет. Но если хотя бы одна из них пишет в это место памяти, обращения нужно согласовывать.

Иначе:

* значение может оказаться неверным;
* одна запись может затереть другую;
* может возникнуть гонка данных.

Представим банковский счёт.

На счёте `1000` сумов. Банкомат хочет снять `800` сумов. В это же время мобильное приложение пытается снять `700` сумов.

Если обе операции одновременно прочитают старый баланс, обе могут увидеть значение:

```text
Balance = 1000
```

Банкомат проверяет:

```text
1000 >= 800
```

А мобильное приложение проверяет:

```text
1000 >= 700
```

Каждая проверка по отдельности верна. Но общей суммы на счёте не хватит на оба снятия.

Поэтому проверку баланса и списание денег нужно выполнять не по отдельности, а как одну защищённую логическую операцию.

Мьютекс используется именно в таких ситуациях.

## Гонка данных и состояние гонки

**Гонка данных** (data race) возникает, когда несколько горутин обращаются к одному месту памяти без достаточной синхронизации и хотя бы одно из обращений — запись. **Состояние гонки** (race condition) — более широкая логическая проблема, когда результат программы неправильно зависит от порядка операций.

Мьютекс помогает предотвратить гонки данных, возникающие из-за конкурентного доступа к общей памяти. Для этого весь код, обращающийся к этим данным, должен следовать одному мьютексу и одному правилу блокировки.

Определение гонки данных, команда `-race` и ограничения детектора подробно объясняются в уроке о Race detector.

## Почему `counter++` небезопасен?

Следующий код выглядит очень простым:

```go
counter++
```

В исходном коде это одна строка.

Но с точки зрения конкурентного программирования её нельзя автоматически считать атомарной операцией.

Логически `counter++` состоит из трёх шагов:

1. прочитать значение `counter`;
2. увеличить значение на `1`;
3. записать новое значение в память.

Например, пусть начальное значение:

```text
counter = 10
```

Если две горутины работают одновременно, может произойти следующее:

```text
Горутина A: читает counter -> 10
Горутина B: читает counter -> 10

Горутина A: 10 + 1 -> 11
Горутина B: 10 + 1 -> 11

Горутина A: counter = 11
Горутина B: counter = 11
```

Было выполнено два увеличения. Но итоговое значение оказалось:

```text
11
```

А ожидался результат:

```text
12
```

Значит, одно из увеличений потерялось.

Следующая программа намеренно написана неправильно:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	counter := 0

	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter++ // Неправильно: общее значение не защищено.
		}()
	}

	wg.Wait()
	fmt.Println("Счётчик:", counter)
}
```

Здесь создаётся `1000` горутин.

Каждая горутина выполняет:

```go
counter++
```

Теоретически результат должен быть:

```text
0 + 1000 = 1000
```

Но `counter` — общая переменная. Все горутины пишут в одно и то же место памяти.

Поэтому иногда результат может быть:

```text
Счётчик: 1000
```

А при другом запуске, например:

```text
Счётчик: 987
```

или другое значение.

Важно, что однократное получение `1000` не доказывает, что код безопасен.

На реальный порядок выполнения конкурентного кода влияют:

* планировщик Go;
* количество ядер CPU;
* планировщик операционной системы;
* работа других горутин;
* оптимизации;
* общая нагрузка в момент запуска программы.

Поэтому код с гонкой данных иногда может казаться «правильно» работающим.

Такой код можно проверить через `go run -race main.go`. Команда и интерпретация её результата отдельно рассматриваются в уроке о Race detector, а измерение производительности — в уроке о бенчмарках.

## Как используется `Mutex`?

У `sync.Mutex` два основных метода:

* `Lock()` — взять замок;
* `Unlock()` — освободить взятый замок.

Простой вид:

```go
mu.Lock()

// Защищённый код.

mu.Unlock()
```

Если в момент вызова `Lock()` мьютекс свободен, горутина берёт замок и продолжает работу.

Если замок удерживает другая горутина, новая горутина ждёт внутри `Lock()`.

После освобождения замка одна из ожидающих горутин может продолжить работу.

Код между `Lock()` и `Unlock()` называется **критической секцией** (critical section).

Например:

```go
mu.Lock()
counter++
mu.Unlock()
```

Здесь мьютексом защищена только операция:

```go
counter++
```

В результате внутри этой критической секции одновременно может находиться только одна горутина.

### Нулевое значение `Mutex`

Для использования `sync.Mutex` отдельный конструктор не нужен.

Достаточно такого кода:

```go
var mu sync.Mutex
```

Нулевое значение `sync.Mutex` — готовый к использованию мьютекс.

Поэтому, например, писать так не нужно:

```go
mu := NewMutex()
```

В стандартной библиотеке Go такого конструктора для `sync.Mutex` даже нет.

Теперь исправим предыдущий пример счётчика с помощью мьютекса:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var (
		wg      sync.WaitGroup
		mu      sync.Mutex
		counter int
	)

	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()

			mu.Lock()
			counter++
			mu.Unlock()
		}()
	}

	wg.Wait()
	fmt.Println("Счётчик:", counter)
}
```

Результат:

```text
Счётчик: 1000
```

Теперь каждая горутина перед увеличением `counter` вызывает:

```go
mu.Lock()
```

Если другая горутина в этот момент изменяет `counter`, новая горутина ждёт.

Только после того как первая горутина выполнит:

```go
mu.Unlock()
```

другая горутина может войти в критическую секцию.

В результате увеличения не накладываются друг на друга.

В этом примере `WaitGroup` и `Mutex` используются вместе. Но они выполняют разные задачи.

`WaitGroup` через:

```go
wg.Wait()
```

заставляет функцию `main` ждать завершения всех горутин.

А `Mutex` через:

```go
mu.Lock()
counter++
mu.Unlock()
```

защищает общее значение `counter`.

Значит:

> `WaitGroup` ждёт завершения горутин. `Mutex` согласует доступ к общей памяти.

Сам по себе `WaitGroup` не защищает `counter` от гонки данных.

Точно так же `Mutex` не ждёт завершения всех горутин.

## Освобождение замка через `defer`

В простом случае мьютекс можно использовать так:

```go
mu.Lock()
counter++
mu.Unlock()
```

Но если внутри функции несколько путей `return`, `Unlock()` легко забыть.

Например:

```go
mu.Lock()

if someCondition {
	return
}

mu.Unlock()
```

В этом коде, если `someCondition` истинно, функция вернётся, не дойдя до `Unlock()`.

В результате мьютекс останется заблокированным.

Следующие вызовы:

```go
mu.Lock()
```

могут застрять в ожидании.

Поэтому во многих случаях сразу после взятия замка используют `defer`:

```go
mu.Lock()
defer mu.Unlock()
```

Благодаря `defer` `mu.Unlock()` автоматически вызывается перед возвратом из текущей функции.

Например:

```go
func update() {
	mu.Lock()
	defer mu.Unlock()

	if someCondition {
		return
	}

	// Другая работа.
}
```

Здесь, через какой бы `return` ни произошёл выход, мьютекс освобождается.

`defer` срабатывает и во время раскрутки стека (stack unwinding) при panic.

Поэтому:

```go
defer mu.Unlock()
```

помогает освободить замок и во время panic.

Но это не «лечит» panic.

Если panic не перехвачен, после выполнения отложенных функций программа всё равно может остановиться.

**Внимание**

Пишите `defer mu.Unlock()` только после успешного вызова `Lock()`.

Например:

```go
mu.Lock()
defer mu.Unlock()
```

— правильный порядок.

Вызов:

```go
mu.Unlock()
```

для незаблокированного мьютекса приводит к ошибке во время выполнения.

В очень маленьких и очень часто вызываемых критических секциях у `defer` может быть небольшая дополнительная стоимость.

В таком случае прямой `Unlock()` в виде:

```go
mu.Lock()
counter++
mu.Unlock()
```

может быть немного дешевле.

Но здесь важно практическое правило:

> Сначала обеспечьте правильную работу кода. Затем проверьте бенчмарком, есть ли проблема с производительностью.

Отказ от `defer` только на основе предположения может увеличить количество ошибок, когда `Unlock()` забывают.

## Безопасное управление банковским счётом

Теперь посмотрим на мьютекс в более реалистичном примере.

Хранить общие данные и защищающий их мьютекс внутри одного типа считается хорошей практикой.

Например, банковский счёт:

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

var (
	errInvalidAmount     = errors.New("сумма должна быть положительной")
	errInsufficientFunds = errors.New("на счёте недостаточно средств")
)

type Account struct {
	mu      sync.Mutex
	balance int
}

func NewAccount(initialBalance int) (*Account, error) {
	if initialBalance < 0 {
		return nil, errors.New("начальный баланс не может быть отрицательным")
	}

	return &Account{balance: initialBalance}, nil
}

func (a *Account) Withdraw(amount int) error {
	if amount <= 0 {
		return errInvalidAmount
	}

	a.mu.Lock()
	defer a.mu.Unlock()

	if a.balance < amount {
		return errInsufficientFunds
	}

	a.balance -= amount
	return nil
}

func (a *Account) Balance() int {
	a.mu.Lock()
	defer a.mu.Unlock()

	return a.balance
}

func main() {
	account, err := NewAccount(1000)
	if err != nil {
		fmt.Println("Счёт не создан:", err)
		return
	}

	requests := []struct {
		name   string
		amount int
	}{
		{name: "Банкомат", amount: 800},
		{name: "Мобильное приложение", amount: 700},
	}

	var wg sync.WaitGroup
	results := make([]error, len(requests))

	for i, request := range requests {
		wg.Add(1)
		go func(index int, amount int) {
			defer wg.Done()
			results[index] = account.Withdraw(amount)
		}(i, request.amount)
	}

	wg.Wait()

	for i, request := range requests {
		if results[i] != nil {
			fmt.Printf("%s: %v\n", request.name, results[i])
			continue
		}
		fmt.Printf("%s: снято %d сум\n", request.name, request.amount)
	}

	fmt.Println("Итоговый баланс:", account.Balance())
}
```

Возможный вывод:

```text
Банкомат: снято 800 сум
Мобильное приложение: на счёте недостаточно средств
Итоговый баланс: 200
```

Разберём этот пример по шагам.

### Мьютекс внутри `Account`

```go
type Account struct {
	mu      sync.Mutex
	balance int
}
```

`balance` — общее состояние, которое могут использовать несколько горутин.

А `mu` защищает это состояние.

Хранение мьютекса рядом с защищаемым полем облегчает понимание того, какой замок для каких данных используется.

### Проверка начального баланса

```go
func NewAccount(initialBalance int) (*Account, error) {
	if initialBalance < 0 {
		return nil, errors.New("начальный баланс не может быть отрицательным")
	}

	return &Account{balance: initialBalance}, nil
}
```

Здесь не разрешается создать счёт с отрицательным балансом.

Эта проверка выполняется до того, как объект начнут использовать конкурентно. Поэтому мьютекс здесь не нужен.

### Простая проверка внутри `Withdraw`

```go
if amount <= 0 {
	return errInvalidAmount
}
```

`amount` — локальное значение, пришедшее в функцию как аргумент.

Эта проверка не обращается к общему полю `balance` у `Account`.

Поэтому её можно выполнить до мьютекса.

Польза в том, что при неверном `amount` брать мьютекс вообще не нужно.

Это сокращает критическую секцию.

### Защита баланса

Затем замок берётся через:

```go
a.mu.Lock()
defer a.mu.Unlock()
```

Следующий за этим код:

```go
if a.balance < amount {
	return errInsufficientFunds
}

a.balance -= amount
```

выполняется внутри одной критической секции.

Это очень важно.

Проверка баланса:

```go
a.balance < amount
```

и уменьшение баланса:

```go
a.balance -= amount
```

— связанные операции.

Их нужно рассматривать как одну логическую операцию.

Например, такая запись может быть неправильной:

```go
if a.balance < amount {
	return errInsufficientFunds
}

a.mu.Lock()
a.balance -= amount
a.mu.Unlock()
```

Причина в том, что между проверкой и записью другая горутина может изменить баланс.

Например:

```text
Начальный баланс = 1000

Горутина A проверяет:
1000 >= 800 -> да

Горутина B проверяет:
1000 >= 700 -> да
```

Затем обе горутины могут попытаться снять деньги.

Поэтому мьютекс должен защищать не только строку:

```go
a.balance -= amount
```

а весь инвариант.

Главный инвариант этого примера:

> Баланс счёта не должен становиться отрицательным в результате снятия денег.

Поэтому проверка и изменение баланса выполняются под одним замком.

### Какой запрос выполнится первым?

Созданы две горутины:

```go
account.Withdraw(800)
```

и:

```go
account.Withdraw(700)
```

Но какая горутина первой возьмёт мьютекс, не гарантируется.

Если первым будет банкомат:

```text
1000 - 800 = 200
```

Затем мобильное приложение пытается снять `700`:

```text
200 < 700
```

поэтому операция отклоняется.

Результат:

```text
Банкомат: снято 800 сум
Мобильное приложение: на счёте недостаточно средств
Итоговый баланс: 200
```

Если первым сработает мобильное приложение:

```text
1000 - 700 = 300
```

Затем для банкомата:

```text
300 < 800
```

При таком выполнении итоговый баланс:

```text
300
```

Значит, какая операция будет успешной, зависит от порядка планировщика.

Но в обоих случаях важный инвариант сохраняется:

* успешно завершается только одно снятие;
* баланс не становится отрицательным.

Мьютекс используется именно для гарантии этого.

### `Balance` тоже использует мьютекс

```go
func (a *Account) Balance() int {
	a.mu.Lock()
	defer a.mu.Unlock()

	return a.balance
}
```

На первый взгляд `Balance` только читает. Поэтому может возникнуть вопрос:

> Зачем блокировать и чтение?

Причина в том, что другая горутина в этот же момент может записывать это значение через:

```go
a.balance -= amount
```

Незащищённое чтение одновременно с записью — тоже гонка данных.

Поэтому общее правило:

> Если данные защищены мьютексом, все связанные с ними чтения и записи должны следовать одному правилу синхронизации.

### О slice `results`

В коде создан:

```go
results := make([]error, len(requests))
```

Затем каждая горутина пишет только в свой индекс через:

```go
results[index] = account.Withdraw(amount)
```

Например:

```text
Горутина 0 -> results[0]
Горутина 1 -> results[1]
```

Хотя заголовок slice общий, его длина или ёмкость здесь не меняются.

Каждая горутина пишет в свой уже существующий отдельный элемент.

А `main` читает результаты только после:

```go
wg.Wait()
```

Поэтому в этой конкретной структуре для `results` отдельный мьютекс не нужен.

## Хранение мьютекса вместе с данными

Мьютекс обычно хранится в одной структуре с данными, которые он защищает.

Например:

```go
type Cache struct {
	mu    sync.Mutex
	items map[string]string
}
```

Из такой структуры читающий код сразу может понять:

```text
mu -> защищает поле items
```

Например, методы могут быть написаны так:

```go
func (c *Cache) Set(key, value string) {
	c.mu.Lock()
	defer c.mu.Unlock()

	c.items[key] = value
}
```

Этот подход ясно показывает владельца замка.

### Почему используется pointer receiver?

Методы структуры, хранящей мьютекс, обычно пишутся с pointer receiver:

```go
func (c *Cache) Set(...)
```

Причина не только в изменении `items`.

Есть ещё одна важная причина:

> `sync.Mutex` нельзя копировать.

Если использовать value receiver:

```go
func (c Cache) Set(...)
```

в качестве получателя может быть создана копия `Cache`.

Вместе с ней копируется и мьютекс:

```go
c.mu
```

Это очень опасно.

Например, кажется, что две горутины работают с одними и теми же общими данными. Но они могут блокировать разные копии мьютекса.

В таком случае замок не согласует реальный общий доступ.

Поэтому о `sync.Mutex` есть важное правило:

> Мьютекс нельзя копировать после первого использования.

Это касается не только получателя.

Структура с мьютексом может вызвать проблемы и при:

* передаче в функцию по значению;
* использовании через value receiver;
* копировании через присваивание;
* переносе по значению внутрь другой структуры.

Например:

```go
original := Cache{}
copy := original
```

если мьютекс уже использовался, такое копирование может привести к неправильному дизайну.

`go vet` умеет обнаруживать некоторые случаи копирования мьютекса:

```bash
go vet ./...
```

Поэтому `go vet` — одна из полезных проверок при написании конкурентного кода.

## Гарантия памяти у мьютекса

Мьютекс — это не только механизм, который говорит:

> Пусть одна горутина войдёт, а другая подождёт.

Он также синхронизирует видимость памяти с точки зрения модели памяти Go.

Например, одна горутина работает так:

```go
mu.Lock()
value = 42
mu.Unlock()
```

Если позже другая горутина возьмёт тот же мьютекс:

```go
mu.Lock()
fmt.Println(value)
mu.Unlock()
```

благодаря правильной синхронизации записи, сделанные предыдущей горутиной до освобождения замка, будут видны следующей горутине.

Проще говоря:

> Если одна горутина обновила данные под мьютексом, а затем сделала `Unlock()`, другая горутина, позже успешно выполнившая `Lock()` на том же мьютексе, может увидеть эти обновления.

Главные условия здесь:

* используется один и тот же мьютекс;
* замок берётся правильно;
* при обращении к данным соблюдается этот порядок синхронизации.

Если одна горутина пишет с `mu`, а другая читает без мьютекса, она этой гарантией не пользуется.

## Критическая секция должна быть короткой

Пока мьютекс удерживается, другие горутины не могут его взять.

Например, при:

```go
mu.Lock()

// Долгая работа.

mu.Unlock()
```

другие горутины ждут окончания этой работы.

Поэтому критическая секция должна по возможности содержать только код, необходимый для проверки и изменения общего состояния.

Будьте осторожны, выполняя внутри замка медленные или потенциально блокирующие операции:

* сетевой запрос;
* обращение к базе данных;
* чтение файла;
* запись файла;
* долгое вычисление;
* блокирующая отправка в канал;
* вызов внешнего callback;
* вызов метода с неизвестным временем работы.

Например, код вроде:

```go
mu.Lock()

resp, err := http.Get(url)

mu.Unlock()
```

имеет опасное свойство производительности.

HTTP-запрос может длиться:

* несколько миллисекунд;
* несколько секунд;
* до тайм-аута.

Всё это время другие горутины не могут взять `mu`.

В результате растёт конкуренция (contention) — соперничество и ожидание одного замка.

Во многих случаях лучший подход:

1. взять мьютекс;
2. прочитать или скопировать нужные общие данные;
3. освободить мьютекс;
4. выполнить медленную операцию снаружи.

Например, концептуально:

```go
mu.Lock()
localValue := sharedValue
mu.Unlock()

doSlowOperation(localValue)
```

Но этот приём не всегда правильный.

Если в процессе:

```text
проверка -> долгая операция -> обновление
```

общее состояние не должно меняться посередине, простое раннее освобождение мьютекса может сломать бизнес-логику.

В таком случае может понадобиться переделать алгоритм.

Поэтому главная цель такая:

> Держать мьютекс как можно меньше, но не ценой нарушения инварианта данных.

## Взаимоблокировка и повторная блокировка

**Взаимоблокировка** (deadlock) — ситуация, когда горутины ждут друг от друга замок или сигнал, который никогда не придёт.

В такой ситуации некоторые горутины программы больше не могут продвигаться.

Две из распространённых причин взаимоблокировок с мьютексами:

* повторная блокировка одного мьютекса;
* взятие нескольких мьютексов в разном порядке.

### Повторная блокировка одного мьютекса

`sync.Mutex` в Go — не **реентерабельный** (reentrant) мьютекс.

Реентерабельный замок — механизм, позволяющий одному и тому же владельцу выполнения снова взять уже взятый им замок.

`sync.Mutex` так не работает.

Если горутина выполнит:

```go
mu.Lock()
```

и, не сделав `Unlock()`, снова:

```go
mu.Lock()
```

второй `Lock()` будет ждать свободного замка.

Но освободить замок должна та же самая горутина.

В результате горутина ждёт саму себя.

Например:

```go
// Неправильный пример: update берёт замок mu и вызывает метод value.
// value тоже пытается взять тот же замок mu.
func (s *Store) update() {
	s.mu.Lock()
	defer s.mu.Unlock()

	_ = s.value()
}
```

Представим, что `value()` тоже написан так:

```go
func (s *Store) value() int {
	s.mu.Lock()
	defer s.mu.Unlock()

	return s.someValue
}
```

Порядок выполнения:

```text
update()
    |
    +-- s.mu.Lock() -> замок взят
    |
    +-- s.value()
            |
            +-- s.mu.Lock() -> тот же замок запрашивается снова
```

Но мьютекс ещё удерживается `update()`.

А `update()` ждёт завершения `value()`.

А `value()` ждёт освобождения мьютекса.

В результате — взаимоблокировка.

В таком случае часто выделяют внутренний вспомогательный метод, не требующий замка.

Например, концептуальный подход:

```go
func (s *Store) valueLocked() int {
	return s.someValue
}
```

Этот метод сам не берёт мьютекс.

Его контракт:

> Вызывающий код уже должен был взять нужный мьютекс.

А внешний метод может работать так:

```go
func (s *Store) value() int {
	s.mu.Lock()
	defer s.mu.Unlock()

	return s.valueLocked()
}
```

Тогда место взятия замка управляется явно.

### Взятие замков в разном порядке

Если одна операция должна взять несколько мьютексов, может возникнуть ещё один вид взаимоблокировки.

Например, есть два мьютекса:

```text
muA
muB
```

Первая горутина берёт их в порядке:

```text
muA.Lock()
muB.Lock()
```

А вторая горутина — в порядке:

```text
muB.Lock()
muA.Lock()
```

Плохое выполнение может выглядеть так:

```text
Горутина 1:
взяла muA

Горутина 2:
взяла muB

Горутина 1:
ждёт muB

Горутина 2:
ждёт muA
```

Теперь:

* горутина 1 ждёт `muB`;
* горутина 2 ждёт `muA`.

Но ни одна не может освободить свой замок, потому что ждёт перехода к следующему шагу.

Это классическая взаимоблокировка.

Поэтому, если используется несколько замков, во всём коде их нужно брать в одном и том же глобальном порядке.

Например, правило может быть таким:

```text
Всегда сначала muA, затем muB.
```

Также полезно по возможности уменьшать одновременное удержание многих мьютексов в одной операции.

`defer`:

```go
defer mu.Unlock()
```

защищает от забытого замка.

Но `defer` не исправляет автоматически неправильный порядок блокировки.

## `RWMutex`: разделение чтения и записи

Некоторые данные читаются очень часто, а изменяются редко.

Если использовать обычный `sync.Mutex`, даже две горутины, которые только читают, будут ждать друг друга.

Например:

```text
Reader A -> Lock
Reader B -> ждёт
```

На самом деле, если обе горутины только читают, их одновременная работа может быть безопасной.

Для таких случаев в Go есть `sync.RWMutex`.

`RWMutex` даёт два вида замков.

Для писателя:

```go
Lock()
Unlock()
```

Для читателя:

```go
RLock()
RUnlock()
```

Несколько читателей могут одновременно удерживать `RLock()`.

А писатель требует эксклюзивного доступа.

Например:

```go
package main

import (
	"fmt"
	"sync"
)

type Scores struct {
	mu     sync.RWMutex
	values map[string]int
}

func NewScores() *Scores {
	return &Scores{values: make(map[string]int)}
}

func (s *Scores) Set(name string, score int) {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.values[name] = score
}

func (s *Scores) Get(name string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()

	score, ok := s.values[name]
	return score, ok
}

func main() {
	scores := NewScores()
	scores.Set("Ali", 95)

	score, ok := scores.Get("Ali")
	if !ok {
		fmt.Println("Результат не найден")
		return
	}

	fmt.Println("Ali:", score)
}
```

Результат:

```text
Ali: 95
```

### Почему `Set` использует `Lock`?

Метод `Set` пишет в `map` через:

```go
s.values[name] = score
```

Поэтому он берёт эксклюзивный замок:

```go
s.mu.Lock()
defer s.mu.Unlock()
```

Пока работает писатель, ни другой читатель, ни другой писатель не могут войти в защищённую часть.

### Почему `Get` использует `RLock`?

`Get` только читает через:

```go
score, ok := s.values[name]
```

Поэтому использует:

```go
s.mu.RLock()
defer s.mu.RUnlock()
```

Если другого писателя нет, несколько вызовов `Get` могут читать одновременно.

Это может быть полезно в системах с большим количеством конкурентных чтений.

### Обычный `map` не является автоматически безопасным для конкурентного использования

Обычный в Go:

```go
map[string]int
```

не является автоматически безопасным для конкурентной записи.

Также проблемы может вызвать чтение этого map без мьютекса, пока другая горутина в него пишет.

`RWMutex` согласует эти обращения.

### `RWMutex` не всегда быстрее

`RWMutex` даёт больше возможностей. Но из этого не следует:

> `RWMutex` всегда быстрее `Mutex`.

У `RWMutex` есть свои накладные расходы на управление.

Если:

* критическая секция очень короткая;
* горутин мало;
* запись происходит часто;
* польза от параллельного чтения мала,

обычный `Mutex` может дать лучший или как минимум такой же результат.

Поэтому `RWMutex` обычно рассматривают в случаях, когда:

* конкурентных чтений много;
* записей мало.

Практический выбор нужно проверять бенчмарком.

### Повышения с `RLock` до `Lock` нет

У `RWMutex` есть ещё одна тонкость.

Например, может возникнуть такая мысль:

1. сначала прочитать с `RLock()`;
2. если выяснится, что нужно изменение;
3. превратить этот замок в `Lock()`.

Тип `sync.RWMutex` в Go не поддерживает такой механизм повышения (upgrade).

То есть, удерживая `RLock`, нельзя напрямую поднять его до `Lock`.

Если сделать:

```go
RUnlock()
Lock()
```

между этими двумя операциями другая горутина может изменить общее состояние.

Поэтому, если решение о записи зависит от текущего состояния данных, обычно:

1. берётся эксклюзивный `Lock()`;
2. условие проверяется повторно;
3. при необходимости выполняется изменение.

Важное правило:

> Когда тип замка меняется, нельзя считать, что результат предыдущей проверки всё ещё верен.

## Mutex, канал или `atomic`?

В конкурентном программировании на Go есть несколько средств синхронизации.

Например:

* `sync.Mutex`;
* `sync.RWMutex`;
* каналы;
* `sync/atomic`.

Их задачи могут казаться похожими, но модели использования различаются.

### `sync.Mutex`

Если несколько горутин читают или изменяют небольшое общее состояние одного объекта, `sync.Mutex` часто оказывается самым понятным выбором.

Например:

```go
type Account struct {
	mu      sync.Mutex
	balance int
}
```

Проблема здесь:

> Все горутины обращаются к одному и тому же значению `balance`.

Поэтому защищать эти данные замком естественно.

### `sync.RWMutex`

Если:

* чтений очень много;
* записей мало;
* конкурентное чтение даёт реальную пользу,

`sync.RWMutex` может быть полезен.

Но этот выбор лучше делать на основе измерений, а не предположений.

### Канал

Канал больше подходит для передачи работы или владения данными между горутинами.

Например:

```text
worker -> result channel -> collector
```

В этой модели одна горутина производит данные, а другая их принимает.

Но использование канала не делает объект автоматически безопасным для конкурентного доступа.

Например, через канал отправили указатель:

```go
ch <- account
```

Если потом несколько горутин изменяют объект через этот указатель `account`, снова появляется общая память.

В таком случае может понадобиться отдельная синхронизация.

Значит:

> Передача указателя через канал не защищает автоматически объект, на который он указывает.

### `sync/atomic`

`sync/atomic` полезен для атомарных операций над простыми отдельными значениями.

Например:

* счётчик;
* флаг;
* простое статистическое значение.

Но `atomic` не защищает автоматически инвариант, охватывающий несколько связанных полей.

Возьмём пример банковского счёта.

Нам нужно:

1. проверить, что баланса достаточно;
2. уменьшить баланс.

Эти две операции связаны.

Одного атомарного `Load`, а затем одного атомарного `Store` недостаточно, чтобы автоматически решить всю логическую проблему.

Для таких инвариантов мьютекс часто даёт гораздо более понятный и менее подверженный ошибкам дизайн.

Главный вопрос при выборе средства синхронизации:

> Как текут данные и какой инвариант нужно защитить?

Выбирать только по вопросу «какое средство быстрее?» может быть неправильно.

## Частые ошибки

При работе с мьютексами новички и даже опытные разработчики часто сталкиваются с некоторыми ошибками.

### Блокировать только запись, но не чтение

Например:

```go
func (s *Store) Set(v int) {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.value = v
}

func (s *Store) Get() int {
	return s.value
}
```

`Set` заблокирован.

Но `Get` читает без защиты.

Если `Set` и `Get` выполняются одновременно, конкурентное чтение при записи может вызвать гонку данных.

Поэтому правило доступа к одним и тем же общим данным должно быть последовательным.

### Разные мьютексы для одних данных

Например, если одна горутина делает:

```go
muA.Lock()
shared++
muA.Unlock()
```

а другая:

```go
muB.Lock()
shared++
muB.Unlock()
```

то два мьютекса независимы друг от друга.

Даже если `muA` заблокирован, `muB` может быть свободен.

Значит, обе горутины могут одновременно обратиться к `shared`.

Для одних данных нужно использовать один механизм синхронизации.

### Забытый `Unlock()`

Например:

```go
mu.Lock()

if err != nil {
	return
}

mu.Unlock()
```

Если `err != nil`, мьютекс не освобождается.

В результате следующие `Lock()` могут ждать долго или вечно.

Во многих случаях:

```go
mu.Lock()
defer mu.Unlock()
```

безопаснее.

### `Unlock()` для незаблокированного мьютекса

`Unlock()` нужно вызывать только для мьютекса, который до этого был успешно заблокирован.

Вызов:

```go
mu.Unlock()
```

для незаблокированного мьютекса заканчивается ошибкой во время выполнения.

### Копирование структуры с мьютексом

`sync.Mutex` нельзя копировать после первого использования.

Копирование структуры с мьютексом по значению может создать отдельную копию замка.

А это приводит к «защите» одних и тех же общих данных разными замками.

Поэтому для таких структур обычно правильно использовать pointer receiver.

### Медленный ввод-вывод внутри замка

Например:

```go
mu.Lock()
readFromDatabase()
mu.Unlock()
```

Если запрос к базе данных работает медленно, другие горутины долго ждут мьютекса.

Это увеличивает конкуренцию за замок.

Нужно стараться держать под мьютексом только необходимый код, связанный с общим состоянием.

### Повторное взятие мьютекса в той же горутине

`sync.Mutex` не реентерабельный.

Поэтому ситуация вроде:

```go
mu.Lock()
mu.Lock()
```

может привести к ожиданию самого себя.

Часто это происходит, когда метод, взявший замок, вызывает другой метод, который снова берёт этот же мьютекс.

### Считать, что `RWMutex` всегда быстрее

`RWMutex` разрешает параллельное чтение.

Но его механизм управления сложнее обычного `Mutex`.

Поэтому реальная польза зависит от нагрузки.

Выбор нужно проверять бенчмарком.

### Думать, что race detector находит все проблемы

`-race` — полезный инструмент, но он не заменяет правильный конкурентный дизайн. Как работает детектор и чего он не может обнаружить, подробно объясняется в уроке о Race detector.

## На что обращают внимание на собеседовании?

На собеседовании по теме мьютексов вопрос может не ограничиться таким:

> Что делают `Lock()` и `Unlock()`?

Важно понимать следующие тонкости.

### Нулевое значение `Mutex` готово к использованию

Достаточно:

```go
var mu sync.Mutex
```

Отдельный конструктор не нужен.

### `Mutex` нельзя копировать после первого использования

Это особенно важно для структур, хранящих мьютекс.

Поэтому такие структуры часто используют через указатель.

### Критическая секция должна быть как можно короче

Чем дольше удерживается замок, тем дольше ждут другие горутины.

Но сокращение критической секции не должно нарушать инвариант данных.

### `sync.Mutex` не реентерабельный

Если горутина снова вызовет `Lock()` для уже взятого ею мьютекса без `Unlock()`, она может ждать саму себя.

### `sync.Mutex` не отслеживает горутину-владельца

Представлять мьютекс как «принадлежащий такой-то горутине» — неполная модель.

`sync.Mutex` в Go не предоставляет модели владения через идентификатор горутины, как реентерабельные замки.

Дизайн кода должен опираться на чёткие правила о том, кто и где берёт замок.

### `WaitGroup` и `Mutex` выполняют разные задачи

`WaitGroup` решает проблему:

```text
Все ли горутины завершились?
```

`Mutex` решает проблему:

```text
Кто в данный момент может обращаться к общей памяти?
```

Их нельзя использовать вместо друг друга.

### `RWMutex` разрешает многих читателей

С `RLock()` несколько читателей могут работать одновременно.

А писатель берёт эксклюзивный замок через:

```go
Lock()
```

Но `RWMutex` приносит пользу, только если нагрузка ему подходит.

### Правильная синхронизация не решает автоматически все состояния гонки

Мьютекс может устранить гонку данных.

Но если бизнес-логика неправильная, состояние гонки может остаться.

Например, если программа неправильно полагается на то, какое из двух правильно синхронизированных событий придёт первым, гонки данных может и не быть.

Но результат всё равно будет зависеть от порядка выполнения.

Поэтому в конкурентном программировании нужно отдельно проверять две вещи:

1. технически ли безопасен доступ к памяти;
2. остаётся ли бизнес-логика правильной, если порядок выполнения изменится.
