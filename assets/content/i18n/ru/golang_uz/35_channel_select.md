# Оператор `select`

`select` выбирает из нескольких операций с каналами одну, готовую к выполнению в данный момент.

Обычная операция с каналом ждёт только одну отправку или одно получение. А `select` позволяет одновременно следить за несколькими каналами.

Например, backend-сервис может одновременно ждать два события:

* приход результата от внешнего API;
* отмену запроса пользователем.

Какое событие будет готово первым, код того случая `select` и выполнит.

Поэтому `select` обычно используют:

* при ожидании результатов от нескольких горутин;
* для установки тайм-аута, то есть ограничения по времени;
* для отслеживания сигнала отмены через `context`;
* для выбора готового канала из нескольких.

## Основной синтаксис

Внешне `select` похож на `switch`. Но его `case` ждут не обычных условий, а операций с каналами:

```go
select {
case msg := <-messages:
	fmt.Println("Получено:", msg)
case results <- value:
	fmt.Println("Результат отправлен")
default:
	fmt.Println("Пока ни один канал не готов")
}
```

Здесь три варианта.

Первый `case`:

```go
case msg := <-messages:
```

пытается получить значение из канала `messages`.

Второй `case`:

```go
case results <- value:
```

пытается отправить значение `value` в канал `results`.

А `default` срабатывает, если ни одна операция с каналом сейчас не готова к выполнению.

При выполнении `select` действуют следующие правила:

* если готов только один `case`, выполняется именно он;
* если одновременно готовы несколько `case`, Go выбирает один из них псевдослучайно;
* если ни один `case` не готов и `default` нет, текущая горутина блокируется;
* если ни один `case` не готов и `default` есть, сразу выполняется `default`.

Здесь есть важное правило: порядок `case` в коде не даёт им приоритета.

Например:

```go
select {
case value := <-first:
	fmt.Println(value)
case value := <-second:
	fmt.Println(value)
}
```

если к получению готовы и `first`, и `second`, `first` не выбирается автоматически только потому, что написан выше.

`select` не идёт сверху вниз, выбирая первый готовый `case`. Если готовы несколько операций, выбирается одна из них.

## Первый работающий пример

В следующем примере две горутины отправляют результаты в разное время:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fast := make(chan string)
	slow := make(chan string)

	go func() {
		time.Sleep(100 * time.Millisecond)
		fast <- "быстрый результат"
	}()

	go func() {
		time.Sleep(200 * time.Millisecond)
		slow <- "медленный результат"
	}()

	select {
	case value := <-fast:
		fmt.Println(value)
	case value := <-slow:
		fmt.Println(value)
	}
}
```

Обычный результат:

```text
быстрый результат
```

Разберём процесс по шагам.

Сначала создаются два небуферизованных канала:

```go
fast := make(chan string)
slow := make(chan string)
```

Затем запускается первая горутина:

```go
go func() {
	time.Sleep(100 * time.Millisecond)
	fast <- "быстрый результат"
}()
```

Она ждёт примерно 100 миллисекунд и хочет отправить значение в канал `fast`.

Вторая горутина:

```go
go func() {
	time.Sleep(200 * time.Millisecond)
	slow <- "медленный результат"
}()
```

отправляет значение в канал `slow` примерно через 200 миллисекунд.

А горутина `main` доходит до следующего `select`:

```go
select {
case value := <-fast:
	fmt.Println(value)
case value := <-slow:
	fmt.Println(value)
}
```

Если в этот момент ещё ни одно значение не пришло, `select` блокируется. Он ждёт, пока любой из двух каналов станет готов к получению.

Примерно через 100 миллисекунд в канале `fast` появляется операция отправки. Поэтому:

```go
case value := <-fast:
```

становится готов к выполнению, и `select` выбирает этот `case`.

Оба канала небуферизованные. В небуферизованном канале отправитель и получатель должны встретиться. Отправитель не может просто бросить значение в канал и продолжить. Он ждёт, пока получатель будет готов.

В этом примере время сна намеренно разное. Поэтому обычно первым выбирается `fast`.

Но нужно помнить: если обе операции с каналами станут готовы одновременно, нельзя предсказать по порядку в коде, какой `case` будет выбран.

Есть ещё один важный момент. Здесь `select` выполняется только один раз.

После получения значения из `fast` `select` завершается, и функция `main` заканчивается. Go не ждёт завершения других горутин, когда заканчивается `main`.

Поэтому программа не получает второй результат из канала `slow`.

## Получение нескольких результатов

Если нужны оба результата, одного выполнения `select` недостаточно.

Его можно повторить нужное количество раз:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	first := make(chan string)
	second := make(chan string)

	go func() {
		time.Sleep(100 * time.Millisecond)
		first <- "первый канал"
	}()

	go func() {
		time.Sleep(200 * time.Millisecond)
		second <- "второй канал"
	}()

	for i := 0; i < 2; i++ {
		select {
		case value := <-first:
			fmt.Println(value)
		case value := <-second:
			fmt.Println(value)
		}
	}
}
```

Результат:

```text
первый канал
второй канал
```

Главное отличие здесь — в цикле:

```go
for i := 0; i < 2; i++ {
```

`select` выполняется дважды.

На первой итерации `first` становится готов примерно через 100 миллисекунд, и берётся значение:

```text
первый канал
```

После этого цикл выполняется второй раз. `select` снова ждёт, пока один из каналов станет готов.

На этот раз из оставшегося канала `second` берётся значение:

```text
второй канал
```

Значит, `select` сам не собирает все готовые результаты сразу. При каждом выполнении выбирается не более одного `case`.

Если количество результатов известно заранее, можно считать их, как в этом примере.

Но если количество результатов заранее неизвестно, обычно нужно отслеживать закрытие канала. В такой ситуации помогает форма `value, ok := <-ch`. Это рассмотрим позже в разделе о закрытых каналах.

## Что такое блокировка?

При работе с каналами важно чётко понимать понятие `блокировки`.

Если горутина ждёт появления условий, необходимых для выполнения операции, она считается заблокированной.

В небуферизованном канале отправка и получение должны соответствовать друг другу.

Чтобы выполнилась отправка:

```go
ch <- value
```

должен существовать получатель.

Чтобы выполнилось получение:

```go
value := <-ch
```

должен существовать отправитель.

Иначе горутина, выполняющая операцию, ждёт.

В следующем коде горутина `main` хочет отправить значение в небуферизованный канал:

```go
package main

func main() {
	ch := make(chan int)
	ch <- 10 // Получателя нет, поэтому runtime обнаруживает deadlock.
}
```

Это намеренно неправильный пример.

Процесс такой:

1. Создаётся небуферизованный канал `ch`.
2. Горутина `main` доходит до отправки значения `10`.
3. Но ни одна другая горутина не принимает значения из `ch`.
4. Поэтому `main` блокируется прямо на этой строке.
5. Другой горутины, способной работать, тоже нет.
6. Go runtime определяет, что программа не может продолжиться.

В результате программа обычно завершается такой ошибкой:

```text
fatal error: all goroutines are asleep - deadlock!
```

Проблему можно решить несколькими способами.

Например, можно запустить принимающую горутину:

```go
go func() {
	<-ch
}()
```

Или, если это подходит задаче, дать каналу буфер.

Но добавление буфера — не универсальное решение любой взаимоблокировки. Правильное решение зависит от того, откуда приходят данные, кто их принимает и как синхронизируются горутины.

## Неблокирующая операция с каналом

Иногда, если канал не готов, ждать не нужно. Программа должна продолжить другую работу.

В таком случае можно использовать `default` внутри `select`:

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)

	select {
	case value := <-ch:
		fmt.Println("Получено:", value)
	default:
		fmt.Println("В канале нет значения")
	}
}
```

Результат:

```text
В канале нет значения
```

Здесь канал буферизованный:

```go
ch := make(chan int, 1)
```

но в него не записано ни одного значения.

Поэтому:

```go
case value := <-ch:
```

сейчас не готов к выполнению.

Если бы не было `default`, `select` заблокировался бы в ожидании значения.

Но здесь есть:

```go
default:
	fmt.Println("В канале нет значения")
```

Поэтому `select` не ждёт, и сразу выполняется `default`.

Такой подход называется `неблокирующей` (non-blocking) операцией с каналом. То есть, даже если канал не готов, программа не застревает в ожидании в этом месте.

Этот приём может быть полезен, например, для телеметрии, статистики или сигнала, который можно отбросить.

Но с важными данными нужно быть осторожным.

Например, код вида:

```go
select {
case jobs <- job:
	// отправлено
default:
	// не отправлено
}
```

позволяет производителю продолжить без ожидания. Если канал `jobs` не готов, `job` отбрасывается.

Если это важная бизнес-задача, такое поведение может привести к потере данных.

`default` влияет и на противодавление (backpressure).

Противодавление — когда потребитель не успевает за скоростью производителя, и производитель естественно замедляется или ждёт.

Если через `default` сделать отправку всегда неблокирующей, можно обойти этот естественный механизм ожидания.

**Внимание**

Если в цикле `for` есть только `select` и `default`, блокирующей операции может вообще не быть. В результате цикл очень быстро крутится снова и снова. Такая ситуация называется **busy loop** (активное ожидание) и может впустую тратить время CPU.

Например:

```go
for {
    select {
    default:
    }
}
```

Этот цикл ничего не ждёт. Он крутится так быстро, как только может.

## Ограничение по времени

Бесконечно ждать ответа от внешнего сервиса или долгого вычисления часто — плохое решение.

Например, если внешний API перестанет отвечать, весь обработчик запроса может долго ждать.

Добавив в `select` канал таймера, можно задать операции ограничение по времени:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	result := make(chan string, 1)

	go func() {
		time.Sleep(200 * time.Millisecond)
		result <- "готово"
	}()

	timer := time.NewTimer(100 * time.Millisecond)
	defer timer.Stop()

	select {
	case value := <-result:
		fmt.Println(value)
	case <-timer.C:
		fmt.Println("время вышло")
	}
}
```

Результат:

```text
время вышло
```

Разберём этот код по шагам.

Сначала создаётся канал для результата:

```go
result := make(chan string, 1)
```

Его ёмкость — `1`. Значит, в буфер может поместиться одно значение.

Затем запускается горутина:

```go
go func() {
	time.Sleep(200 * time.Millisecond)
	result <- "готово"
}()
```

Эта горутина отправляет результат через 200 миллисекунд.

Но тайм-аут установлен на 100 миллисекунд:

```go
timer := time.NewTimer(100 * time.Millisecond)
```

`timer.C` — канал, который отправляет значение, когда время истекает.

А `select` ждёт два события:

```go
select {
case value := <-result:
	fmt.Println(value)
case <-timer.C:
	fmt.Println("время вышло")
}
```

Примерно через 100 миллисекунд первым готов таймер.

Поэтому выбирается:

```go
case <-timer.C:
```

и выводится:

```text
время вышло
```

В этом примере нужно особо обратить внимание на то, что канал `result` буферизованный.

Если бы он был небуферизованным:

```go
result := make(chan string)
```

после выхода `main` из `select` по тайм-ауту рабочая горутина могла бы дойти до строки:

```go
result <- "готово"
```

Но тогда уже не осталось бы горутины, принимающей значения из `result`. Из-за небуферизованного канала отправитель мог бы здесь застрять.

Буфер ёмкостью `1` позволяет воркеру положить значение и закончить работу.

Это показывает очень важное свойство тайм-аута:

> тайм-аут прекращает ожидание, но не отменяет автоматически работающую горутину.

Если нужно остановить и само вычисление, обычно используют `context` или отдельный сигнал отмены.

Для одного простого ожидания можно использовать и `time.After`:

```go
select {
case value := <-result:
	fmt.Println(value)
case <-time.After(100 * time.Millisecond):
	fmt.Println("время вышло")
}
```

Это коротко и удобно читается.

Но в долгоработающем цикле создание нового `time.After` на каждой итерации создаёт новые объекты таймеров.

Если нужно точнее управлять жизненным циклом таймера, лучше использовать `time.NewTimer` и при необходимости делать ему `Reset`.

А если нужен периодический сигнал, используется `time.NewTicker`.

## Отмена через `context`

В реальном backend-коде просто ждать тайм-аута недостаточно.

Часто нужно отменить и саму выполняемую операцию.

В Go такой сигнал обычно передаётся через `context.Context`.

Метод `Context`:

```go
ctx.Done()
```

возвращает канал, который закрывается при отмене или по истечении крайнего срока.

Когда канал закрыт, получение из него сразу готово. Поэтому ждать `ctx.Done()` внутри `select` очень удобно.

Создание `Context`, тайм-ауты, крайние сроки и правила `cancel()` подробно объясняются в уроке об основах `context`.

В следующем примере воркер периодически выполняет шаги, но останавливает работу, если `context` отменён:

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func work(ctx context.Context) error {
	ticker := time.NewTicker(20 * time.Millisecond)
	defer ticker.Stop()

	for step := 1; step <= 10; step++ {
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-ticker.C:
			fmt.Println("шаг:", step)
		}
	}

	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	if err := work(ctx); err != nil {
		fmt.Println("работа остановлена:", err)
	}
}
```

В этом коде:

```go
ticker := time.NewTicker(20 * time.Millisecond)
```

даёт сигнал примерно каждые 20 миллисекунд.

Цикл воркера:

```go
for step := 1; step <= 10; step++ {
```

пытается выполнить не более 10 шагов.

На каждой итерации `select` ждёт два события:

```go
case <-ctx.Done():
```

или:

```go
case <-ticker.C:
```

Если первым готов тикер, выполняется:

```go
fmt.Println("шаг:", step)
```

А в `main` для контекста задан тайм-аут в 50 миллисекунд:

```go
ctx, cancel := context.WithTimeout(
	context.Background(),
	50*time.Millisecond,
)
```

Примерно через 50 миллисекунд крайний срок истекает, и `ctx.Done()` закрывается.

После этого может выполниться:

```go
case <-ctx.Done():
	return ctx.Err()
```

`ctx.Err()` в этом случае возвращает ошибку:

```text
context deadline exceeded
```

Поэтому последняя строка будет такой:

```text
работа остановлена: context deadline exceeded
```

Сколько строк:

```text
шаг: ...
```

выведется до неё, может зависеть от планировщика и того, когда реально срабатывают таймеры. Поэтому не стоит полагаться на точное количество шагов.

Этот шаблон очень часто встречается в реальных программах.

Например:

* когда HTTP-запрос отменён клиентом;
* когда запрос к базе данных превысил крайний срок;
* когда несколько горутин нужно остановить одним общим сигналом;
* при управлении воркерами во время остановки сервера.

Главное правило здесь: воркер не должен просто принять `context` и забыть о нём. Он должен следить за `ctx.Done()` в нужных местах или передавать контекст в API, умеющие с ним работать.

## Закрытые и `nil`-каналы

При работе с `select` очень важна разница между закрытым и `nil`-каналом.

Они ведут себя почти противоположно:

* получение из закрытого канала не блокируется;
* получение из `nil`-канала блокируется.

Сначала рассмотрим закрытый канал.

После закрытия канала сначала читаются значения, оставшиеся в его буфере. Когда буфер закончился, повторное получение возвращает нулевое значение типа элементов канала.

Чтобы проверить, действительно ли канал закрыт, используется получение с двумя значениями:

```go
value, ok := <-ch
if !ok {
	// Канал закрыт.
}
```

Здесь:

* `value` — полученное значение;
* `ok` — показывает, дало ли получение настоящее значение.

Если:

```go
ok == false
```

то канал закрыт и в его буфере не осталось значений.

Эта проверка особенно важна для типов с нулевым значением, таких как `int`, `bool`, указатели и другие.

Например, для канала `int` значение после закрытия:

```go
0
```

Но `0` может быть и настоящими бизнес-данными. Если не проверять `ok`, можно принять нулевое значение из закрытого канала за настоящие данные.

Теперь посмотрим на проблему в `select`.

Поскольку получение из закрытого канала не блокируется, его `case` всегда готов.

Если читать несколько каналов в цикле, закрытый канал может снова и снова попадать в выбор `select`.

Чтобы это прекратить, переменной канала можно присвоить `nil`.

И отправка в `nil`-канал, и получение из него в обычном случае блокируются навсегда. А внутри `select` `case` такого канала никогда не выбирается.

Следующий пример показывает этот приём:

```go
package main

import "fmt"

func main() {
	left := make(chan int, 1)
	right := make(chan int, 1)

	left <- 10
	right <- 20

	close(left)
	close(right)

	for left != nil || right != nil {
		select {
		case value, ok := <-left:
			if !ok {
				left = nil
				continue
			}
			fmt.Println("left:", value)

		case value, ok := <-right:
			if !ok {
				right = nil
				continue
			}
			fmt.Println("right:", value)
		}
	}
}
```

Порядок строк вывода может меняться:

```text
left: 10
right: 20
```

Сначала в каждый из двух буферизованных каналов записывается по одному значению:

```go
left <- 10
right <- 20
```

Затем оба закрываются:

```go
close(left)
close(right)
```

Закрытие канала не уничтожает уже находящиеся в нём значения буфера.

Поэтому из `left` всё ещё можно взять `10`, а из `right` — `20`.

Цикл продолжается так:

```go
for left != nil || right != nil {
```

Пока активен хотя бы один канал, цикл работает.

Когда значения канала закончились и его закрытое состояние обнаружено:

```go
if !ok {
	left = nil
	continue
}
```

переменной присваивается `nil`.

После этого:

```go
case value, ok := <-left:
```

практически отключается, потому что `left` теперь `nil`.

Тот же процесс происходит для `right`.

Когда оба станут:

```go
left == nil
right == nil
```

условие цикла станет ложным, и цикл завершится.

Если не переводить закрытый канал в `nil`, его `case` получения останется готовым навсегда. В результате `select` сможет выбирать его снова и снова, возвращая нулевое значение.

Это очень полезный шаблон для динамического управления несколькими каналами через `select`.

## Пустой `select`

В Go следующий код тоже является правильным синтаксисом:

```go
select {}
```

В этом `select`:

* нет `case`;
* нет `default`.

Значит, нет и ни одной операции, которая могла бы стать готовой к выполнению.

В результате текущая горутина блокируется навсегда.

Например:

```go
func main() {
	select {}
}
```

Горутина `main` остаётся здесь, не завершаясь.

Иногда можно встретить такой код, чтобы запустить фоновые горутины и искусственно держать `main` открытой.

Но в практической программе это часто не лучший способ управления.

Причина в том, что `select {}` ничего не знает о состоянии фоновых горутин.

Например:

* воркер мог завершиться с ошибкой;
* все горутины могли уже прекратить работу;
* серверу может понадобиться остановиться.

Но `main` всё равно будет ждать вечно.

Поэтому управлять жизненным циклом горутин обычно понятнее с помощью:

* `sync.WaitGroup`;
* каналов;
* `context`.

Эти средства помогают не только ждать, но и управлять тем, когда и почему работа заканчивается.

## Частые ошибки

Хотя синтаксис `select` выглядит простым, его поведение легко понять неправильно.

Следующие ошибки встречаются особенно часто.

### Думать, что `select` выполняет все готовые `case`

Это неверно.

При одном выполнении `select` выбирает не более одного `case`.

Например, даже если одновременно готовы три канала:

```go
select {
case <-a:
case <-b:
case <-c:
}
```

выполнится только один.

Если нужно получить все результаты, `select` обычно используют внутри цикла.

### Считать, что верхний `case` имеет приоритет

Это тоже неверно.

В следующем коде:

```go
select {
case <-first:
case <-second:
}
```

`first` не имеет приоритета только потому, что написан выше.

Если обе операции готовы, Go выбирает одну из готовых операций.

Порядок в коде не работает как приоритет.

Если нужен точный приоритет, его нужно выразить отдельной логикой управления.

### Не проверять значение `ok` у закрытого канала

Следующее получение:

```go
value := <-ch
```

само по себе не показывает, что канал закрыт.

Если канал закрыт и буфер пуст, в `value` приходит нулевое значение типа элементов.

Поэтому там, где важно закрытие, нужно использовать форму:

```go
value, ok := <-ch
```

Иначе нулевое значение может быть принято за настоящие данные.

### Использование `default` везде

`default` убирает блокировку.

В некоторых ситуациях это очень полезно. Но автоматически добавлять его в каждый `select` — плохая идея.

Например:

```go
select {
case jobs <- job:
default:
}
```

позволяет производителю не ждать потребителя.

Это может привести к потере естественного противодавления или к отбрасыванию данных.

Поэтому, добавляя `default`, нужно задать вопрос:

> Если канал сейчас не готов, действительно ли правильно отбросить эту операцию или продолжить без ожидания?

### Забыть об отправляющей горутине после тайм-аута

Тайм-аут может лишь прекратить ожидание `select`.

Например:

```go
select {
case result := <-results:
	fmt.Println(result)
case <-timer.C:
	fmt.Println("timeout")
}
```

после выбора тайм-аута горутина, производящая результат, не останавливается автоматически.

Позже она может дойти до строки:

```go
results <- value
```

Если канал небуферизованный и другого получателя не осталось, воркер может застрять.

Поэтому в коде с тайм-аутом нужно думать и о жизненном цикле воркера.

Часто для этого используют:

* буферизованный канал результатов;
* `context.Context`;
* отдельный канал отмены.

### Закрытие канала на принимающей стороне

Важно и то, кто закрывает канал.

Обычно канал закрывает сторона, которая точно знает, что больше значений в него отправлено не будет. Чаще всего это производитель, то есть отправляющая сторона.

Например:

```go
for _, job := range jobs {
	results <- process(job)
}

close(results)
```

Здесь производитель знает, что отправил все результаты. Поэтому он знает и то, когда можно закрыть `results`.

А потребитель обычно может не знать, будет ли другой производитель ещё что-то отправлять.

Если в закрытый канал снова отправить значение, произойдёт panic.

Поэтому важно чётко определить, кто владеет закрытием канала.

## Важные моменты для собеседования

В разговоре или на собеседовании о `select` полезно уметь чётко сформулировать следующие правила.

* При каждом выполнении `select` выбирает не более одного готового `case`.

* В `select` без `default`, если ни одна операция не готова, текущая горутина блокируется.

* Если есть `default`, а другие `case` не готовы, сразу выполняется `default`. Поэтому такой `select` не блокируется.

* Если одновременно готовы несколько `case`, тот, что написан в коде выше, автоматически приоритета не получает.

* Получение из закрытого канала не блокируется. Когда буфер закончился, получаются нулевое значение и `ok == false`.

* А `nil`-канал никогда не бывает готов к отправке или получению. Поэтому присваивание каналу `nil` внутри `select` можно использовать как способ временно отключить его `case`.

* В `select {}` нет ни `case`, ни `default`. Поэтому он блокирует текущую горутину навсегда.

* Тайм-аут лишь прекращает ожидание результата. Он не отменяет автоматически горутину, выполняющую работу.

* Если после тайм-аута нужно остановить и самого воркера, нужен `context` или отдельный механизм отмены.
